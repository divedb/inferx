# M1 implementation specification: core contracts and deterministic scheduler simulator

- Status: proposed implementation contract
- Roadmap milestone: M1 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed M0 contract in [`docs/milestones/m0.md`](m0.md)
- Immediate successors: M2 CUDA/tensor runtime and M3 artifacts/tokenization

This document turns M1 into an executable engineering plan. It fixes the ownership, state-machine,
configuration, scheduler, resource-accounting, simulation, replay, and test contracts that M2 through
M8 build upon. It does not implement inference or anticipate physical KV layout.

## 1. Outcome

At the end of M1, InferX has a CPU-only, deterministic control-plane reference that can:

1. parse and validate an immutable engine/simulator configuration with source provenance;
2. accept hardware-neutral token requests into a bounded registry/queue;
3. execute every request lifecycle transition through one closed transition table;
4. produce resource-valid FCFS `StepPlan` objects without mutating scheduler inputs;
5. submit those plans to a deterministic fake executor and consume versioned completions;
6. simulate submit, completion, cancellation, deadline, preemption, and injected-failure events;
7. serialize an exact replay trace and reproduce it byte-for-byte; and
8. prove through generated stress tests that all requests and resources reach a valid terminal state.

The primary executable is `inferx-sim`. A representative successful run is:

```text
workload events
  -> request validation/registry
  -> request FSM
  -> scheduling snapshot
  -> FCFS ordering and capacity transaction
  -> immutable StepPlan
  -> fake execution ticket/completion
  -> counter/FSM update and response event
  -> invariant check and canonical replay record
```

M1 is the behavioral oracle for later asynchronous/CUDA implementations. It must be simple and
strict enough to identify lifecycle bugs, not optimized to resemble GPU timing.

## 2. Scope boundaries

### 2.1 In scope

- Abseil status conventions and propagation helpers.
- Strong IDs, token/count/range values, checked arithmetic, and monotonic/manual clocks.
- A bounded reference channel with explicit close/backpressure semantics.
- Strict JSON configuration via simdjson, documented environment/CLI overlays, canonical effective
  configuration, semantic validation, and field provenance.
- Hardware-neutral request/response values and request validation for token input.
- Request registry, closed FSM, transition decisions, epochs, counters, terminal reasons, and
  resource-release rules.
- Scheduler views, capacity/admission mechanism, deterministic FCFS policy, batch planner, plan
  validation, and reusable plan/snapshot storage.
- Deterministic discrete-event fake executor, workload reader, replay writer/reader, invariant
  checker, CLI, tests, stress generator, and scheduler/simulator benchmarks.

### 2.2 Explicitly out of scope

- CUDA, tensor data, physical buffers, streams, kernels, or real execution backends.
- Physical KV pages, block allocation, prefix caching, or block generations beyond the ID types.
- Real tokenizer behavior. The simulator consumes token IDs; a test-only fake input processor may
  exercise tokenization FSM edges but is not installed.
- Real model configuration/artifacts, weights, logits, or semantic model execution.
- Continuous batching policy claims, chunked prefill, priority scheduling, production preemption,
  sampling algorithms, networking, or telemetry exporters.
- A lock-free queue. Correct bounded semantics and TSan cleanliness come before a specialized queue.
- Stable wire/API/ABI compatibility. Replay schema v1 is versioned, but M1 remains pre-release.
- Cryptographic hashing. M1 persists the canonical effective configuration in replay; it must not use
  process-unstable `std::hash`/`absl::Hash` as a durable fingerprint.

`inferx::simulator` unless an ADR justifies an SDK use; install `inferx-sim` only as a developer tool

Extend M0's independent consumer to include one header from each exported module and link without
source-tree paths. Preserve zero project warnings and header self-containment for all new headers.

### 6.1 C++ implementation rules

All M1 code is C++23 in namespace `inferx` (with feature namespaces such as `inferx::scheduler`) and
follows the repository `.clang-format`/`.clang-tidy`, Google C++ naming/header rules, and applicable
C++ Core Guidelines. In particular:

- ownership is `std::unique_ptr` or a named move-only RAII lease; raw pointers/references/spans are
  observers whose owner and validity interval are stated at the declaration;
- owning types are noncopyable unless value-copy semantics are deliberate, cheap, and tested;
- factories that validate or allocate return `absl::StatusOr<T>`; fallible constructors are not used;
- public results that must be checked are `[[nodiscard]]`; enums are scoped; narrowing is explicit and
  checked; naked `new`/`delete`, C allocation, owning raw arrays, and integer invalid sentinels are
  forbidden;
- headers include what they use, have conventional `INFERX_<PATH>_H_` guards, and expose no `internal`
  symbols or transitive dependency implementation types;
- blocking/thread-safe classes document their concurrency contract and use Abseil thread-safety
  annotations where supported; coordinator-owned classes assert/document single-thread ownership;
- destructors are `noexcept`, do not perform fallible shutdown, and assert only programmer-lifetime
  violations in debug builds; callers perform explicit `Close`/`Shutdown`/`Acknowledge`; and
- comments explain invariants/lifetime/race choices, not syntax. New exceptions to these rules require
  a focused ADR and analysis-test coverage.

## 7. Base contracts

### 7.1 Status conventions

Use `absl::Status` and `absl::StatusOr<T>` directly. Do not create aliases named `Status`, `Result`,
or a second error enum that callers must translate. `status.h` contains factories and inspection
helpers, not a wrapper class.

Required conventions:

| Condition | Canonical code |
|---|---|
| Invalid user/config field, range, or transition input | `kInvalidArgument` |
| Operation on closed/terminal state or stale epoch | `kFailedPrecondition` |
| Duplicate request ID/already registered | `kAlreadyExists` |
| Unknown request/reservation/ticket | `kNotFound` |
| Queue/capacity exhausted | `kResourceExhausted` |
| Deadline event | `kDeadlineExceeded` |
| Explicit cancellation | `kCancelled` |
| Unsupported M1 feature such as real text tokenization | `kUnimplemented` |
| Parsed/user-derived checked arithmetic overflow | `kOutOfRange` |
| Overflow or contradiction of an already-validated internal invariant | `kInternal` |
| Injected fake executor failure | Configured stable code, default `kInternal` |

Messages begin with the responsible component and stable field/resource name, for example
`config.max_active_sequences: must be <= max_queued_requests`. Tests assert status code and a stable
reason/field, not the entire prose message.

Define this stable replay/metrics classification with explicit numeric values:

```cpp
enum class ErrorReason : uint16_t {
  kNone = 0,
  kInvalidConfig = 1,
  kInvalidWorkload = 2,
  kInvalidRequest = 3,
  kDuplicateRequest = 4,
  kQueueFull = 5,
  kCapacityExhausted = 6,
  kImpossibleContext = 7,
  kInvalidTransition = 8,
  kStaleCompletion = 9,
  kUnknownResource = 10,
  kExecutorRejected = 11,
  kExecutorFailure = 12,
  kDeadlineExpired = 13,
  kExplicitCancellation = 14,
  kShutdown = 15,
  kReplayMismatch = 16,
  kInvariantViolation = 17,
  kIoFailure = 18,
  kEventLimit = 19,
  kDeadlock = 20,
};
```

It accompanies a status but never replaces the canonical code. `WithErrorReason` stores the lowercase
enum name in the Abseil status payload key `type.inferx.dev/error-reason`; `GetErrorReason` validates
that payload and returns `kNone` only for OK status. Unknown/malformed payloads are rejected while
reading replay rather than mapped silently. Renumbering or reusing a value requires a replay-schema
major change.

`status_macros.h` provides exactly `INFERX_RETURN_IF_ERROR(expr)` and
`INFERX_ASSIGN_OR_RETURN(lhs, expr)`. For the assign macro, `lhs` is an already-declared assignable
lvalue; declarations/structured bindings are deliberately unsupported. The implementation helpers
must:

- evaluate expressions exactly once;
- preserve move-only values and status payloads;
- work inside normal statement scopes;
- use collision-resistant internal names; and
- have compile/failure tests.

No exception crosses an InferX API. Catch simdjson/standard exceptions, if the selected APIs can
throw, at the adapter boundary and translate them with field context.

### 7.2 Strong IDs

Use a single constrained `StrongId<Tag, Rep>` implementation with named aliases. It has explicit
construction, `value()`, equality/three-way comparison, stream/Abseil formatting support, and
`AbslHashValue`. It has no implicit integer conversion and no cross-tag conversion.

Do not use a universal invalid numeric sentinel: zero is valid for ranks, devices, and token IDs.
Strong IDs are not default-constructible; absence is `std::optional<Id>`. Coordinator-owned ID
generators explicitly define their initial value and return `OutOfRange` before wraparound.

M1 defines the following ID types; adding another requires a named tag, representation, and boundary
tests rather than a raw integer alias:

| Type | Representation | Notes |
|---|---|---|
| `RequestId`, `SequenceId`, `StepId`, `ExecutionTicketId`, `ReservationId` | `uint64_t` | Simulator generators start at 1; request IDs may be supplied by workload |
| `RequestEpoch`, `BlockGeneration`, `PlanBufferGeneration` | `uint32_t` | Increment with checked overflow; epoch changes on logical restart/preemption |
| `ModelId`, `ReplicaId`, `WorkerId`, `Rank`, `DeviceId`, `BlockId`, `PlanBufferSlot`, `TenantScope` | `uint32_t` | IDs only; M1 does not implement devices/blocks; scope zero is the explicitly constructed process-default scope |
| `TokenId` | `int32_t` | No negative-token assumption in generic core validation unless model capability says so |

Serialization uses the underlying decimal integer and a schema field that identifies its role. Never
serialize IDs through floating-point JSON values. Parsing rejects negative/out-of-range values and
does not truncate.

### 7.3 Counts, ranges, and checked arithmetic

Avoid passing ambiguous `size_t` values through scheduler interfaces. Define unit-bearing values for
`TokenCount`, `TokenOffset`, `SequenceCount`, `QueueCapacity`, `KvTokenCount`, and `ByteCount` where confusion is
plausible. `TokenCount`, `TokenOffset`, `SequenceCount`, and `QueueCapacity` use `uint32_t` storage;
aggregate `KvTokenCount` and `ByteCount` use `uint64_t`. Their factories accept parsed `uint64_t` values, check the destination
range, and construct explicitly. They are not arithmetic types: calculations unwrap, use checked
helpers, then reconstruct the intended unit.

```cpp
struct TokenRange {
  TokenOffset begin;
  TokenOffset end;  // Exclusive.

  absl::Status Validate() const;
  absl::StatusOr<TokenCount> size() const;
};
```

`checked_math.h` implements constrained integral `CheckedAdd`, `CheckedSub`, `CheckedMul`,
`CheckedCeilDiv`, and `CheckedNarrow`. It handles signedness deliberately, never relies on overflow,
and returns contextual `StatusOr`. Use it for config limits, token ranges, resource cost, durations,
and ID generation. `CheckedByteSize(element_count, element_width)` returns `ByteCount` through
`CheckedMul`; M2 shape/tensor code must reuse it rather than introducing unchecked byte products.

### 7.4 Clocks and deadlines

All engine time uses nanosecond-resolution aliases based on `std::chrono::steady_clock`. Wall time is
absent from lifecycle and replay decisions.

`MonotonicTime` is `std::chrono::time_point<std::chrono::steady_clock, Nanoseconds>` and `Deadline`
is the same type used when an operation must complete before an instant. These aliases live in
`clock.h`; public interfaces do not mix them with wall-clock time points.

```cpp
class Clock {
 public:
  virtual ~Clock() = default;
  virtual MonotonicTime Now() const noexcept = 0;
};

class SteadyClock final : public Clock { /* production adapter */ };
class ManualClock final : public Clock { /* simulator/test-only controlled advance */ };
```

`ManualClock` can only move forward and rejects duration overflow. A deadline expires when
`Now() >= deadline`. The simulator's same-timestamp ordering in section 14 makes the resulting race
semantics deterministic.

### 7.5 Bounded channel

M1's reference `BoundedChannel<T>` is a fixed-capacity ring allocated at construction and guarded by
one `std::mutex` plus separate `std::condition_variable` instances for not-empty/not-full. A blocking
operation installs a stack-scoped `std::stop_callback` that notifies the relevant condition variable;
the wait predicate rechecks closed/stopped/data/capacity state under the mutex. It is safe for multiple
producers and consumers, though initial engine use is MPSC/SPSC. It never grows and makes no lock-free
performance claim.

```cpp
enum class ChannelResult {
  kSuccess,
  kFull,
  kEmpty,
  kClosed,
  kTimeout,
  kStopped,
};

template <typename T>
class BoundedChannel {
 public:
  explicit BoundedChannel(QueueCapacity capacity);
  ChannelResult TryPush(T&& value);
  ChannelResult Push(T&& value, Deadline deadline, std::stop_token stop);
  ChannelResult TryPop(T* output);
  ChannelResult Pop(T* output, Deadline deadline, std::stop_token stop);
  void Close();
  size_t size() const;
  size_t capacity() const;
};
```

`value` is moved from only after the operation has secured a queue slot; it remains untouched on
`kFull`, `kClosed`, `kTimeout`, or `kStopped`, so callers can retry move-only work. `output` is
non-owning and written only on success. Close is idempotent, wakes all waiters, rejects future pushes,
and permits queued values to drain; pop returns `kClosed` only after the queue is empty.
Timeout/stopped operations do not consume or enqueue a value. Destruction requires all users to have
stopped; an owning component closes and joins before destruction. Tests cover move-only values and
their failed-push state, spurious wakeups, close races, full/empty transitions, and TSan
multi-producer stress.

Race precedence is part of the contract. A push observes `closed`, then `stop_requested`, then free
capacity, then timeout. A pop observes `stop_requested`, then queued data (including data left after
close), then drained `closed`, then timeout. Consequently a stop never transfers a value, close never
accepts a new value, and an expired deadline is only reported if no higher-priority result is already
observable while holding the lock. Notify occurs after publishing the ring-state change; predicates,
not notification counts, determine progress.

The scheduler simulator does not use blocking channel waits or threads. This channel establishes the
future engine boundary and is tested independently.

## 8. Configuration pipeline

### 8.1 Stages and precedence

Configuration has four source layers and three representations:

```text
compiled defaults < JSON file < documented INFERX_* environment < CLI flags
        -> ParsedConfig(value + source per field)
        -> Validate(ModelCapabilities/BuildCapabilities)
        -> immutable EngineConfig + CanonicalConfig
```

Later sources override only fields they explicitly contain. An invalid value is an error even if a
later source would replace it; this catches broken deployment inputs instead of silently masking them.
Unknown JSON keys and CLI flags are errors. M1 reads only documented environment variables and does
not enumerate/reject unrelated process environment entries.

`ConfigSource` records `kDefault`, `kFile`, `kEnvironment`, or `kCommandLine` plus a redacted source
location/flag name. It never stores secret values. `inferx-sim explain-config` prints effective values
and sources in stable field order.

### 8.2 M1 configuration schema

Use descriptive unit-suffixed names in JSON and CLI. Initial fields are:

| Field | Type/range | Default | M1 rule |
|---|---|---:|---|
| `max_queued_requests` | 1..1,000,000 | 4,096 | Bounds all live admitted requests, not only the FCFS waiting list |
| `max_active_sequences` | 1..`max_queued_requests` | 256 | Simulated active resource limit |
| `max_sequences_per_step` | 1..min(`max_active_sequences`, 16,384) | 32 | Batch cardinality and replay-line budget |
| `max_scheduled_tokens_per_step` | 1..2^31-1 | 4,096 | Prefill + decode token budget |
| `max_prompt_tokens` | 1..2^31-1 | 4,096 | Must be <= step token budget in M1 because chunking is M8 |
| `max_output_tokens` | 1..2^31-1 | 256 | Per-request cap |
| `max_model_tokens` | 2..2^31-1 | 4,352 | Engine context cap; must not exceed model capabilities |
| `simulated_kv_token_capacity` | positive 64-bit | 1,114,112 | Full-reservation reference capacity; default is `256 * 4,352` |
| `plan_buffer_slots` | 1..64 | 1 | Must cover configured in-flight fake steps |
| `submission_channel_capacity` | positive | 4,096 | Reference channel configuration, not simulator event count |
| `response_channel_capacity` | positive | 4,096 | Same |
| `fake_base_latency_ns` | positive bounded duration | 1,000 | Fake executor cost |
| `fake_prefill_latency_per_token_ns` | nonnegative duration | 100 | Checked multiply by tokens |
| `fake_decode_latency_per_sequence_ns` | nonnegative duration | 100 | Checked multiply by sequences |
| `max_simulation_events` | 1..100,000,000 | 10,000,000 | Deadlock/runaway and retained-response safety bound |

M1 reserves `prompt_tokens + max_output_tokens` simulated KV token slots at admission. This
conservative policy is intentionally simple; M8 owns incremental reservation/preemption experiments.
A request whose full reservation can never fit is rejected before queueing.

Priority exists in request values for forward compatibility, but M1 accepts only the default priority
and rejects non-default values as `Unimplemented`. M8 adds priority/aging semantics.

For every schema field `name`, the environment spelling is `INFERX_<UPPERCASE_NAME>` and the Abseil
flag spelling is `--name`; for example, `simulated_kv_token_capacity` maps to
`INFERX_SIMULATED_KV_TOKEN_CAPACITY` and `--simulated_kv_token_capacity`. Boolean negation aliases,
abbreviations, and multiple spellings are not accepted. The committed `configuration.md` contains a
generated table from the schema metadata so defaults and mappings cannot drift.

### 8.3 Immutability and canonical representation

`EngineConfig` has private construction through validation and read-only accessors. No mutable
singleton or environment read occurs after creation. Simulator components retain a reference whose
lifetime is owned by `EngineSimulator`.

Serialize the effective configuration as canonical UTF-8 JSON with:

- schema version first;
- fixed lexicographic field order;
- decimal integers only, with no floating-point durations/counts;
- no insignificant whitespace;
- enum names from a closed lowercase set; and
- exact escaping rules covered by fuzz tests.

M1 embeds the exact canonical bytes in the replay header and compares them byte-for-byte. It does not
invent a persistent short hash. A later approved BLAKE3 dependency may add a display fingerprint
without changing canonical identity.

### 8.4 Validation interface

```cpp
struct BuildCapabilities {
  bool simulator = true;
  bool cuda = false;  // M1 validation never requires CUDA.
};

struct ModelCapabilities {
  TokenCount max_context_tokens;
  bool accepts_text = false;
};

absl::StatusOr<EngineConfig> ValidateConfig(
    const ParsedConfig& parsed,
    const BuildCapabilities& build,
    const ModelCapabilities& model);
```

Validation reports all independent field errors in stable order when practical, but never continues
after an overflow or parser safety limit. Cap JSON file bytes, nesting, string lengths, and number of
object fields before constructing large values.

Schema-v1 safety constants live in `config/parser_limits.h` and are shared by file readers/tests:

| Limit | Value |
|---|---:|
| Configuration file | 1 MiB |
| Workload file | 1 GiB |
| Replay input | 16 GiB |
| One JSONL record | 16 MiB |
| JSON nesting depth | 32 |
| Members in one object | 128 |
| One non-diagnostic string | 64 KiB |

Check file/line byte limits before padding/copying into simdjson storage. A plan serializer computes
its exact record length and returns `ResourceExhausted` before writing past the line limit; config
validation also enforces the 16,384 sequence cap. Diagnostic/status messages are truncated to 4 KiB
at a valid UTF-8 boundary with an explicit `truncated` marker. Tests exercise exactly limit-1, limit,
and limit+1. These are defensive schema constants, not hidden CLI overrides.

## 9. Request and response values

### 9.1 Immutable request

`Priority` is a non-interchangeable `int32_t` value with an explicit constructor; zero is the M1
default and the only accepted value. `TenantScope` is the strong `uint32_t` ID from section 7; M1
accepts only the explicitly constructed process-default scope zero because tenant isolation is not
implemented yet. Keeping both fields typed now prevents later scheduler and admission APIs from
passing ambiguous integers.

```cpp
using PromptInput = std::variant<std::string, std::vector<TokenId>>;
```

## 10. Request context and ownership

### 10.1 Request context

`RequestContext` is mutable engine state, never part of the public request API. It owns:

- the immutable `GenerateRequest`;
- `SequenceId`, `RequestEpoch`, arrival time, and monotonically assigned arrival ordinal;
- current `RequestState` and optional pending cancellation reason;
- prompt token vector and committed synthetic output tokens;
- `num_computed_tokens`, `num_scheduled_tokens`, and `num_committed_output_tokens`;
- optional `ReservationId`, in-flight `StepId`, and `ExecutionTicketId`;
- lifecycle timestamps and terminal status/reason; and
- a boolean/sequence marker proving the terminal response was emitted exactly once.

Only `RequestController` mutates a context. Scheduler, replay writer, invariant checker, and fake
executor consume value views or const references. Plans and completions contain IDs/epochs, never a
`RequestContext*`, iterator, span into a request-owned vector, or owning smart pointer.

Admission reserves the prompt vector at its exact validated size and the output vector at
`max_output_tokens` before inserting the context. It also prepares fixed-capacity transition-history
storage when that diagnostic is enabled. Allocation failure rejects admission without consuming an
ID/arrival ordinal or resource; controller commits never grow these containers.

Counter semantics for the simulator are fixed:

- prefill schedules all prompt tokens and, on success, marks them computed and commits the first
  synthetic output token;
- each decode schedules one token and, on success, increments computed work and commits one output;
- `num_scheduled_tokens` is outstanding work, not a cumulative metric, and returns to zero on every
  completion/failure path;
- a token is committed only after a matching successful completion and finish guard; and
- max output/context checks use checked arithmetic before scheduling.

### 10.2 Registry

`RequestRegistry` owns `std::unique_ptr<RequestContext>` values in an
`absl::flat_hash_map<RequestId, std::unique_ptr<RequestContext>>` for lookup. No observable order
comes from hash iteration. A separate
`absl::btree_map<ArrivalKey, RequestId>`—where `ArrivalKey` compares arrival time, arrival ordinal,
then request ID—owns deterministic live order. Admission may allocate; insertion is transactional
across both containers and rolls back the first insertion if the second fails. Terminal erase removes
both entries.

Required operations are `Insert`, `Find`, `Contains`, `EraseTerminal`, and deterministic
`AppendSchedulingViews`. Insert assigns internal sequence/arrival values only after duplicate and
capacity checks succeed. Erase is legal only after terminal response emission, no in-flight ticket,
and reservation release.

## 11. Request finite-state machine

### 11.1 States

M1 refines the roadmap diagram with an explicit `Cancelling` state needed to prevent release while
fake/real execution is still in flight:

```text
Received -> Tokenizing -> Queued -> Reserving -> PrefillReady -> Prefilling
    |            |          ^          |              |             |
    +------------+----------+          +--------------+-------------+
                             (input ready/deferred)        completion

PrefillReady -> Prefilling -> DecodeReady <-> Decoding -> Finishing -> Finished
       ^                           |             |
       |                           v             v
    Preempted <----------------- ready       Cancelling -> Cancelled

Any non-terminal, non-in-flight state --fatal event--> Failed
Any in-flight state --execution failure completion--> Failed
```

The exact enum is:

```cpp
enum class RequestState {
  kReceived,
  kTokenizing,
  kQueued,
  kReserving,
  kPrefillReady,
  kPrefilling,
  kDecodeReady,
  kDecoding,
  kPreempted,
  kCancelling,
  kFinishing,
  kFinished,
  kCancelled,
  kFailed,
};
```

`Finished`, `Cancelled`, and `Failed` are terminal and absorbing. Terminal observation is not a state
transition. A transition request from a terminal state returns `FailedPrecondition` and makes no
change.

`ToString(RequestState)` emits the exact lowercase snake-case names (`prefill_ready`, `cancelling`,
and so on). Replay parsing accepts only those names; unknown spelling/case is invalid. The same rule
applies to `RequestEventKind`, `WorkKind`, `FinishReason`, `ChannelResult`, and `IdleReason` through
their own total switch functions. Tests fail if a new enum value lacks a string case.

### 11.2 Events and core transitions

`request_event.h` defines a closed `RequestEventKind` plus a `std::variant` of typed payload structs.
The kinds are exactly the event names in the table below. Data-bearing payloads are:

- input/tokenization success owns the validated token vector; tokenization failure owns a status and
  reason;
- reservation granted owns `ReservationId` and `ResourceCost`; deferred owns the capacity snapshot
  used for the decision;
- submit owns step/ticket/epoch/work kind and scheduled logical range;
- completion/drain owns the corresponding `ExecutionCompletion` value;
- cancel/deadline/fatal events own a `TerminalOutcome`; and
- terminal emitted owns the prepared response-reservation sequence number.

Marker events use empty structs, not `std::monostate` or magic payload values. Event kind is derived by
one visitor and checked against the variant alternative in debug/tests; callers cannot construct a
kind/payload mismatch.

| Current | Event | Guard | Next |
|---|---|---|---|
| `Received` | `StartTokenization` | text input/test processor | `Tokenizing` |
| `Received` | `InputReady` | validated token input | `Queued` |
| `Tokenizing` | `TokenizationSucceeded` | nonempty valid tokens | `Queued` |
| `Tokenizing` | `TokenizationFailed` | terminal status supplied | `Failed` |
| `Queued` | `BeginReservation` | scheduler selected request | `Reserving` |
| `Reserving` | `ReservationGranted` | reservation exists | `PrefillReady` or `DecodeReady` based on counters |
| `Reserving` | `ReservationDeferred` | no resource change retained | `Queued` |
| `PrefillReady` | `SubmitPrefill` | no in-flight work; matching plan item | `Prefilling` |
| `Prefilling` | `PrefillCompleted` | matching step/ticket/epoch; success | `DecodeReady` or `Finishing` |
| `DecodeReady` | `SubmitDecode` | output remains; matching plan item | `Decoding` |
| `Decoding` | `DecodeCompleted` | matching step/ticket/epoch; success | `DecodeReady` or `Finishing` |
| `PrefillReady`/`DecodeReady` | `Preempt` | no in-flight work | `Preempted` |
| `Preempted` | `Requeue` | epoch increment succeeds | `Queued` |
| Any nonterminal non-in-flight except `Finishing` | `CancelRequested`/`DeadlineExpired` | none | `Cancelled` |
| `Prefilling`/`Decoding` | `CancelRequested`/`DeadlineExpired` | matching work remains owned | `Cancelling` |
| `Cancelling` | `InFlightDrained` | matching completion; no commit | `Cancelled` |
| `Prefilling`/`Decoding` | `ExecutionFailed` | matching failure completion | `Failed` |
| Any nonterminal non-in-flight | `FatalError` | terminal status supplied | `Failed` |
| `Finishing` | `TerminalEmitted` | exactly one terminal response built | `Finished` |

Cancellation stores its reason/status in the transition decision. `Cancelled` may correspond to
explicit cancellation, deadline, or shutdown and maps to the appropriate `FinishReason`/status.
`Finishing` means the successful outcome and terminal response have already been selected; a late
cancel/deadline event is rejected as `FailedPrecondition` and cannot replace that outcome. The
same-timestamp ordering in section 14 ensures a cancellation that is actually simultaneous with an
execution completion is handled before the request enters `Finishing`.

Entering `Cancelled` or `Failed` builds and marks the terminal response in the same lifecycle commit
that releases the reservation. Successful completion first enters `Finishing`; its
`TerminalEmitted` commit builds/marks the response, releases the reservation, and enters `Finished`.
If response storage cannot be secured, the coordinator must not start the transition; the simulator
counts submissions while reading the bounded workload and reserves response-record capacity before
admission. Thus no terminal state is ever visible without exactly one durable terminal record, and
terminal states remain absorbing.

M1 prefill is one full prompt. The `PrefillCompleted -> PrefillReady` chunk loop is reserved for M8
and must be addable as a new guarded event without changing ownership rules.

### 11.3 Pure decision plus one mutator

```cpp
struct TransitionDecision {
  RequestState next;
  TransitionEffects effects;
  std::optional<TerminalOutcome> terminal;
};

absl::StatusOr<TransitionDecision> DecideTransition(
    const RequestView& request,
    const RequestEvent& event);

class PreparedTransition {
 public:
  PreparedTransition(PreparedTransition&&) noexcept;
  PreparedTransition& operator=(PreparedTransition&&) noexcept;
  PreparedTransition(const PreparedTransition&) = delete;
  PreparedTransition& operator=(const PreparedTransition&) = delete;
  // Opaque outside the lifecycle implementation.
};

class RequestController {
 public:
  absl::StatusOr<PreparedTransition> Prepare(
      const RequestContext& request, const RequestEvent& event) const;
  void Commit(RequestContext& request, PreparedTransition transition) noexcept;
};
```

`DecideTransition` is pure and reads a constexpr/declarative transition table plus explicit guards.
`Prepare` validates IDs/counters, materializes any status/terminal record, and performs every
operation that can allocate or fail. `Commit` only moves prepared values and updates fixed-capacity
fields/counters; it is `noexcept`. `RequestController` is the only `RequestContext` mutator.

`LifecycleCoordinator` is the orchestration boundary between the controller, resource accountant,
and production-neutral `ResponseSink`/`LifecycleObserver` interfaces declared in
`inferx::engine/event_sink.h`. It is coordinator-thread-owned and exposes
intent-specific operations such as `Admit`, `GrantReservation`, `MarkSubmitted`, `Complete`,
`Cancel`, `Preempt`, and `EmitTerminal`; callers do not apply raw FSM events themselves. Each method
follows this transaction order:

```text
locate context and call RequestController::Prepare
-> prepare a ResponseReservation if the decision emits a delta/terminal response
-> secure or release the external resource named by TransitionEffects
-> RequestController::Commit (no failure)
-> ResponseSink::Commit the prepared reservation (no failure)
-> LifecycleObserver::Observe the transition/resource values
-> run cross-component invariants and observe their result
```

`ResponseSink::Prepare` may allocate/fail but does not publish; its move-only reservation rolls back
on destruction. `ResponseSink::Commit` is `noexcept`, publishes exactly one prepared value, and is
called in the same no-fail phase that sets the context's response marker. `LifecycleObserver` is
read-only and may return a status because trace I/O can fail after a valid state commit. Both
interfaces accept only engine-owned values and expose no simdjson/file/network types.

The simulator implements the response sink with pre-sized storage and the observer by forwarding to
`ReplaySink`; a later production engine can use bounded response/telemetry queues. This keeps
`inferx::engine` independent of `inferx::simulator`. An observer failure after commit stops the current
run but does not roll back valid lifecycle/resource state; the committed response slot and in-context
terminal marker remain the source of truth for cleanup and diagnostics. The simulator then enters
cleanup mode: it disables further observer writes, cancels/drains all ownership, runs invariants in
memory, and returns the original observer status (annotated if cleanup also finds an invariant
failure). It never continues normal scheduling with a partial trace.

The implementation stores one expanded `constexpr std::array<TransitionRule, N>` indexed into a
dense `[RequestState][RequestEventKind]` lookup table at compile time. Wildcard rows in this document
are expanded to concrete state/event entries; duplicate cells are a compile error and absent cells
produce `FailedPrecondition/kInvalidTransition`. Conditional destinations use named pure resolver
functions, never hidden mutation. `tools/docs/render_request_fsm.py` renders the checked-in
`docs/request-lifecycle.md` table from JSON emitted by a small `inferx_fsm_schema` build tool over the
compiled rule array, and CI fails on a diff. The prose table here describes intent; the generated
table and executable lookup share the one metadata source.

If preparation or an external action fails, the context is unchanged and any newly acquired RAII
transaction/lease rolls back. A failure while releasing an ownership record is an invariant failure;
the simulator stops without pretending the request became terminal. The no-fail commit rule avoids a
state in which a backend accepted work or capacity was released but the request still reports the
old state.

Resource acquisition happens before `ReservationGranted`; backend acceptance happens before
`SubmitPrefill`/`SubmitDecode`; completion validation happens before a completed/failed event. Thus an
effect that can fail is not hidden after an irreversible state mutation. Invalid transitions are
side-effect free.

M1 preemption is legal only in a ready state. `Preempt` releases the committed reservation and enters
`Preempted`; `Requeue` increments the epoch and returns the request to `Queued`, where admission must
obtain a new conservative full reservation. Overflow or release failure leaves the original state
and ownership unchanged. Later milestones may retain physical KV during preemption, but must record
that as a new policy rather than silently changing this M1 oracle.

### 11.4 Epoch and stale completion rules

Every plan item, execution ticket, and completion contains request ID, sequence ID, and request epoch.
On preemption/requeue, increment the epoch with overflow checking. A completion is accepted only when:

- request and sequence exist;
- request state is the corresponding in-flight or cancelling state;
- request epoch, step ID, ticket ID, and scheduled token count match; and
- no terminal response was emitted.

A mismatch is `FailedPrecondition` with `kStaleCompletion`; it never commits tokens, releases a newer
reservation, or changes a newer state. The simulator treats a stale completion as an injected failure
case and proves accounting remains intact.

## 12. Scheduler and resource model

### 12.1 Request scheduling view

`RequestSchedulingView` is a value snapshot containing only scheduling facts:

```cpp
struct RequestSchedulingView {
  RequestId request;
  SequenceId sequence;
  RequestEpoch epoch;
  RequestState state;
  uint64_t arrival_ordinal;
  MonotonicTime arrival_time;
  TokenCount prompt_tokens;
  TokenCount computed_tokens;
  TokenCount committed_output_tokens;
  TokenCount max_output_tokens;
  std::optional<MonotonicTime> deadline;
  std::optional<ReservationId> reservation;
};
```

It owns no token vector and cannot mutate a request. `SchedulingSnapshot` contains current time,
proposed next step ID, immutable spans over a preallocated view buffer, effective scheduler limits,
and a `ResourceSnapshot`.

```cpp
struct SchedulingLimits {
  SequenceCount max_sequences_per_step;
  TokenCount max_scheduled_tokens_per_step;
};

struct SchedulingSnapshot {
  MonotonicTime now;
  StepId proposed_step;
  std::span<const RequestSchedulingView> requests;
  SchedulingLimits limits;
  ResourceSnapshot resources;
};
```

The span is valid until the coordinator next rebuilds its snapshot buffer. Policy/planner calls are
synchronous and cannot retain it. Debug builds increment a snapshot generation and assert it has not
changed during a call.

### 12.2 Capacity and reservation mechanism

M1 models three bounded resources:

- active sequence slots, reserved for a request from admission through terminal release;
- simulated KV token slots, conservatively `prompt + max_output`; and
- plan-buffer slots, leased for an accepted in-flight step.

Per-request `ResourceCost::kv_tokens` is a `TokenCount`; `ResourceSnapshot` promotes committed and
capacity totals to `KvTokenCount` before aggregation. No aggregate capacity is narrowed back to the
per-request type.

```cpp
struct ResourceCost {
  SequenceCount sequences;
  TokenCount kv_tokens;
};

struct ResourceSnapshot {
  SequenceCount sequence_capacity;
  SequenceCount sequences_used;
  KvTokenCount kv_token_capacity;
  KvTokenCount kv_tokens_used;
};

class ResourceAccountant {
 public:
  ResourceSnapshot Snapshot() const;
  absl::StatusOr<ReservationTxn> BeginReservation(
      RequestId request, ResourceCost cost);
  absl::Status Release(ReservationId id);
  absl::Status Validate() const;
};
```

`ReservationTxn` is move-only, holds tentative deltas, commits to a unique `ReservationId`, and rolls
back idempotently if destroyed before commit. The accountant is coordinator-thread-owned; no atomics
or mutexes are used. Double release, unknown ID, cost mismatch, overflow, and over-capacity are errors.

`BeginReservation` does all fallible capacity/map preparation and returns a transaction with a
provisional ID. `ReservationTxn::Commit()` is `noexcept`, promotes the prepared ownership record, and
returns that ID exactly once; calling it twice is a debug contract violation. The accountant's ID
generator advances only on commit. `Release` first validates the complete ownership record, then
performs a no-fail erase/counter decrement so a failed release is side-effect free.

Only one `ReservationTxn` may be live per coordinator-owned accountant. Internally `BeginReservation`
prepares/inserts a tentative record without charging committed counters; rollback erases it and commit
marks it committed plus applies already-checked counters. Snapshots exclude the tentative record.
This constraint is sufficient because admission commits/rolls back each candidate before evaluating
the next and avoids provisional-ID ambiguity.

The sum of committed reservation costs must exactly equal the registry's live reservation views and
never exceed capacity. Request rejection/defer leaves all totals unchanged.

### 12.3 Policy versus mechanism

`FcfsPolicy` receives eligible views and writes request indices into caller-owned scratch storage. It
does not reserve resources, change states, or allocate. FCFS order is:

```text
arrival_time ascending
-> arrival_ordinal ascending
-> RequestId ascending as defensive final tie-break
```

Arrival ordinal is unique, so the final tie-break should not normally decide. M1 ignores priority and
does not privilege decode over prefill; those policy changes belong to later measured milestones.

```cpp
class FcfsPolicy {
 public:
  absl::StatusOr<size_t> Select(
      const SchedulingSnapshot& snapshot,
      std::span<size_t> output_indices) const;
};
```

The registry already supplies live views in `ArrivalKey` order, so `Select` validates order and
filters without sorting. Insufficient output scratch is `ResourceExhausted` and writes no observable
selection count.

`AdmissionController` checks whether queued requests can receive full M1 reservations. Requests that
can never fit fail immediately; temporarily unavailable capacity leaves them queued. `BatchPlanner`
then selects ready work under `max_sequences_per_step` and `max_scheduled_tokens_per_step`.

```cpp
enum class AdmissionKind { kReservable, kTemporarilyBlocked, kNeverFits };

struct AdmissionDecision {
  AdmissionKind kind;
  ResourceCost cost;
  absl::Status rejection;  // OK unless kind == kNeverFits.
};

class AdmissionController {
 public:
  AdmissionDecision Evaluate(
      const RequestSchedulingView& request,
      const ResourceSnapshot& resources) const;
};

class BatchPlanner {
 public:
  absl::Status Build(
      const SchedulingSnapshot& snapshot,
      std::span<const size_t> selected_indices,
      StepPlanLease& output) const;
};
```

Admission and planning are strict FCFS in M1. A `kNeverFits` request fails and the scan continues; a
`kTemporarilyBlocked` request causes head-of-line blocking and stops admission for that tick. During
planning, if the earliest ready request would exceed the remaining token/sequence budget, planning
stops instead of bypassing it. These intentionally conservative rules are golden-tested and may only
change with the M8 policy experiments.

Because M1 has no chunked prefill, a prompt larger than the per-step token budget is rejected by
configuration/request validation rather than remaining forever unschedulable.

### 12.4 Step plan

```cpp
enum class WorkKind { kPrefill, kDecode };

struct KvReadPlan {
  SequenceId sequence;
  TokenRange logical_tokens;
};

struct KvWritePlan {
  ReservationId reservation;
  TokenRange logical_tokens;
};

struct ScheduledSequence {
  RequestId request;
  SequenceId sequence;
  RequestEpoch epoch;
  WorkKind kind;
  TokenRange input_tokens;
  KvReadPlan kv_read;
  KvWritePlan kv_write;
};

struct StepPlan {
  uint32_t schema_version = 1;
  StepId id;
  ModelId model;
  MonotonicTime planned_at;
  std::span<const ScheduledSequence> sequences;
  StepResourceUse resources;
  PlanBufferSlot buffer_slot;
  PlanBufferGeneration buffer_generation;
};
```

`StepResourceUse` contains checked `SequenceCount num_sequences` and `TokenCount num_tokens` values.
`PlanBufferGeneration` is a strong `uint32_t` value incremented whenever a slot is reacquired; wrap
fails planning instead of making an old reference appear current.

M1 KV plans describe logical token ranges and reservation identity only. M6 extends their physical
representation behind the same ownership/lifetime contract. No raw address or request-owned span is
stored.

The apparent `span` in `StepPlan` points into a leased `StepPlanBuffer`, not stack/scheduler scratch or
request memory. `StepPlanPool::Create` allocates `plan_buffer_slots` buffers, each sized to
`max_sequences_per_step`. Its move-only `StepPlanLease` contains a non-owning pool pointer, slot, and
generation; exposes only `const StepPlan& plan() const`; and returns the exact generation to the pool
on destruction. A lease cannot outlive its pool, so owners declare the pool before the executor and
drain the executor before pool destruction. The lease remains owned by the fake/real execution
ticket until all item completions for that step have been applied and acknowledged. Debug validation
rejects a stale slot/generation, and production code never reconstructs a lease from integer IDs.

```cpp
class StepPlanPool {
 public:
  static absl::StatusOr<std::unique_ptr<StepPlanPool>> Create(
      uint32_t slots, SequenceCount max_sequences_per_step);
  absl::StatusOr<StepPlanLease> Acquire(
      StepId step, ModelId model, MonotonicTime planned_at);
  absl::Status Validate() const;
  size_t available() const;
};

class StepPlanLease {
 public:
  StepPlanLease(StepPlanLease&&) noexcept;
  StepPlanLease& operator=(StepPlanLease&&) noexcept;
  ~StepPlanLease() noexcept;
  const StepPlan& plan() const;

 private:
  friend class BatchPlanner;
  StepPlanBuffer& mutable_buffer();
};
```

Only `BatchPlanner` can obtain the mutable buffer. `Acquire` resets sizes/metadata without changing
capacity, increments the slot generation with checked arithmetic, and fails `ResourceExhausted` when
all slots are leased. A moved-from lease is empty and safely destructible; all other access on it is a
debug contract violation.

A prefill item covers the entire prompt range and costs prompt tokens. A decode item covers exactly
one input position and costs one scheduled token. One request appears at most once per step. M1 uses
one model per plan and rejects mixed-model snapshots.

Logical positions are fixed so M2/M6 can attach physical storage without changing replay. For prompt
length `P` and `O` already-committed output tokens:

| Work | `input_tokens` | `kv_read.logical_tokens` | `kv_write.logical_tokens` | Produced output position |
|---|---|---|---|---|
| Prefill (`O == 0`) | `[0, P)` | `[0, 0)` | `[0, P)` | `0` |
| Decode (`O >= 1`) | `[P + O - 1, P + O)` | `[0, P + O - 1)` | `[P + O - 1, P + O)` | `O` |

Every expression is checked before plan construction. The generated output token is not itself KV
state until it is consumed by a later decode item. Empty KV reads are represented by equal begin/end,
never an absent or invalid range.

### 12.5 Planning sequence

The coordinator/simulator planning transaction is:

```text
build and validate an immutable admission snapshot
-> FCFS policy writes queued indices to scratch
-> for each queued candidate, prepare ReservationGranted with a tentative reservation ID
-> commit its ReservationTxn, then no-fail commit the prepared request transition
-> apply ReservationDeferred without an accountant mutation when capacity is temporary
-> rebuild and validate an immutable execution snapshot after all admission mutations
-> FCFS policy writes ready indices to scratch
-> acquire a StepPlanBuffer slot
-> BatchPlanner writes ready work within budgets
-> StepPlanValidator validates totals/epochs/states/ranges
-> prepare SubmitPrefill/SubmitDecode for every item
-> fake backend accepts the leased plan and returns a ticket
-> no-fail commit all prepared submission transitions with that ticket ID
-> executor retains the plan-buffer lease under the ticket until completion drain
```

If plan validation or backend submission fails, release the plan slot, roll back only uncommitted
reservations, and transition affected requests according to the error scope. A request reservation
committed before plan construction remains owned by that queued/ready request unless the error makes
the request terminal.

### 12.6 Allocation discipline

Construct scheduler snapshot, eligible-index, plan-item, completion, and invariant scratch arrays at
configured maximum capacity. Planning calls `clear()` but do not shrink. Use a bounded pool of plan
buffers. Do not return a newly allocated vector from `Plan()`.

Request admission/registry insertion may allocate; M1's performance gate applies to steady-state
planning after all containers and buffers are warmed at 1,024 active requests. Benchmarks install an
allocation counter around only the planning section.

## 13. Fake execution backend

### 13.1 Interface

```cpp
class FakeExecutor {
 public:
  absl::StatusOr<ExecutionTicket> Submit(StepPlanLease plan);
  absl::StatusOr<size_t> CompleteReady(
      MonotonicTime now, std::span<ExecutionCompletion> output);
  absl::Status Acknowledge(ExecutionTicketId ticket);
  std::optional<MonotonicTime> NextCompletionTime() const;
};
```

This is the implementation interface, not pseudocode. The hardware-neutral, copyable
`ExecutionTicket` in `inferx::engine` contains ticket ID, step ID, and item count. The fake executor's
private pending record adds submission ordinal and completion time and stores the move-only lease; it
never stores request pointers. `CompleteReady` writes complete tickets in
`(completion_time, submission_ordinal)` order; all items from one ticket are written atomically.
If `output` cannot hold the next ticket, it returns `ResourceExhausted` without removing or partially
writing that ticket. The simulator allocates capacity for `max_sequences_per_step`. A written ticket
moves from pending to delivered but remains owned by the executor and is not returned again.

The lifecycle coordinator applies every contiguous completion item for a delivered ticket, then calls
`Acknowledge`. Acknowledgement is the only operation that destroys the ticket's lease and releases the
plan-buffer slot; unknown, pending, or duplicate acknowledgement fails without mutation. No planning
occurs between delivery, lifecycle application, acknowledgement, and the invariant check. This keeps
the plan/ticket owner visible while request contexts still name the ticket and gives later asynchronous
backends the same explicit completion-drain boundary.

### 13.2 Latency model

For M1 schema v1:

```text
duration = fake_base_latency
         + prefill_token_count * fake_prefill_latency_per_token
         + decode_sequence_count * fake_decode_latency_per_sequence
```

All operations use checked duration arithmetic and require a strictly positive total to prevent a
zero-time infinite scheduling loop. Completion time is `submit_time + duration`. This model is for
deterministic ordering, not GPU prediction.

### 13.3 Completion values

`ExecutionCompletion` is a hardware-neutral engine value, not a simulator type:

```cpp
struct ExecutionCompletion {
  ExecutionTicketId ticket;
  StepId step;
  uint32_t item_ordinal;
  uint32_t item_count;
  RequestId request;
  SequenceId sequence;
  RequestEpoch epoch;
  WorkKind kind;
  TokenRange scheduled_tokens;
  absl::Status status;
  ErrorReason error_reason;
  std::optional<TokenId> output_token;
};
```

Each completion echoes the accepted plan identity/range and contains a stable success or failure
result. Successful M1 prefill/decode has exactly one output token; failure has none. Later backends may
extend a versioned result value for logits/hidden states but cannot drop the identity fields.
Successful fake token generation is a pure documented function of request ID, output position, and a
fixed fake vocabulary size; it does not use batch order or global RNG. This lets serial/batched
simulation results compare exactly.

Schema v1 uses a vocabulary size of 32,000 and the unsigned wraparound operations below (SplitMix64's
mixing step); the final value is representable as nonnegative `TokenId`:

```cpp
uint64_t FakeTokenBits(RequestId request, TokenOffset position) {
  uint64_t z = request.value() + 0x9e3779b97f4a7c15ULL;
  z += static_cast<uint64_t>(position.value()) * 0x9e3779b97f4a7c15ULL;
  z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9ULL;
  z = (z ^ (z >> 27)) * 0x94d049bb133111ebULL;
  return z ^ (z >> 31);
}

TokenId FakeToken(RequestId request, TokenOffset position) {
  return TokenId(static_cast<int32_t>(FakeTokenBits(request, position) % 32000ULL));
}
```

The deliberately specified modulo mapping is a correctness oracle, not a claim of statistically
unbiased sampling. `position` is zero-based in generated output, and golden tests include request ID
and position boundary cases.

Failure injection is configured by workload events targeting a `StepId`, `RequestId`, or next
submission ordinal. An injected failure has stable status code/reason and occurs at normal completion
time so cancellation/failure races remain testable. Injection rules are consumed exactly once unless
explicitly marked persistent.

A step/submission target fails every item in that ticket; a request target fails only matching items
and leaves batch peers successful. Multiple rules are applied in workload ordinal order, but the
first matching rule supplies the status for an item and consumes all matching one-shot rules with a
trace record. Rules can never turn a previously failed item back into success.

## 14. Deterministic event simulator

### 14.1 Ownership

`EngineSimulator` declares members in this dependency order; C++ destroys them in reverse, so every
non-owning reference remains valid during its owner's teardown:

1. immutable config and manual clock;
2. request registry/controller and deterministic request-order structures;
3. resource accountant and plan-buffer pool;
4. scheduler policy/planner/validator and scratch;
5. fake executor/tickets;
6. pending workload-event heap;
7. response and replay record buffers;
8. simulator response sink/lifecycle observer and lifecycle coordinator, which hold non-owning references to
   items 1 through 7; and
9. invariant checker, which holds non-owning references to the state it validates.

All simulator mutation happens on the calling thread. There are no detached threads, real sleeps,
wall-clock reads, static mutable generators, or callbacks after destruction.

The public simulator boundary is deliberately small:

```cpp
struct SimulationResult {
  absl::Status status;
  SimulationSummary summary;
};

class EngineSimulator {
 public:
  static absl::StatusOr<std::unique_ptr<EngineSimulator>> Create(
      EngineConfig config, ModelCapabilities model, ReplaySink& replay);
  absl::Status LoadWorkload(std::span<const WorkloadEvent> events);
  absl::StatusOr<SimulationResult> Run();
  absl::Status StepOneTimestamp();  // Test/debug hook; no real-time wait.
};
```

`Create` validates cross-component capacities and completes all bounded scratch allocation.
`LoadWorkload` is legal exactly once before `Run`, copies/canonicalizes into simulator-owned storage,
and rejects a second load or a running simulator. It uses checked arithmetic to require
`sum(max_output_tokens) + submit_count <= max_simulation_events`, then reserves that many maximum
response slots; allocation failure leaves the simulator unloaded. `Run` is single-use and drives to footer; the test
hook advances one complete timestamp group, including acknowledgements and invariants. Methods check
the creating thread in debug builds and are documented as not thread-safe. `ReplaySink` is non-owning
and must outlive the simulator; the CLI uses a file sink and tests use a bounded in-memory sink.

### 14.2 External events

Workload schema v1 supports:

- `submit` with token IDs, request/model IDs, output limit, optional deadline/finish-after value;
- `cancel` with request ID;
- `inject_executor_failure` with a deterministic target and status/reason;
- `preempt` and `requeue` for a ready/preempted request, used to test epoch semantics; and
- `shutdown` with `cancel` or `drain` policy.

Each input line is one JSON object. `schema_version`, `event_type`, and `at_ns` are required and appear
first in canonicalized workload records. Event-specific fields are:

| Event | Required fields after `at_ns` | Optional fields/default |
|---|---|---|
| `submit` | `request_id`, `model_id`, `token_ids`, `max_output_tokens` | `deadline_ns=null`, `finish_after_tokens=null`, `priority=0`, `tenant_scope=0` |
| `cancel` | `request_id` | none |
| `inject_executor_failure` | `target_kind`, `target_id`, `status_code`, `error_reason` | `persistent=false`; target kind is `step`, `request`, or `submission` |
| `preempt` | `request_id` | none; request must be ready |
| `requeue` | `request_id` | none; request must be preempted |
| `shutdown` | `mode` | none; mode is `cancel` or `drain` |

`deadline_ns` is an absolute simulator-monotonic instant, not a duration from submission. Null option
fields are accepted on input; the canonical workload record emits them explicitly. Token IDs are
decimal JSON integers. The error injection status must be non-OK and paired with a known stable
`ErrorReason`. A `drain` shutdown rejects future submissions but continues scheduling admitted work;
a `cancel` shutdown cancels queued/ready work and drains in-flight ownership without committing later
tokens.

Events have nonnegative `at_ns` and a file ordinal. The reader validates file size, event count,
sortedness/overflow, duplicate submit IDs, token/count bounds, and references according to event
semantics. It may accept unsorted input only if it sorts by the total order and emits a diagnostic;
the recommended strict mode rejects unsorted workloads.

Structural parsing may refer to a request declared by a later submit, but executing cancel/preempt/
requeue before that request exists returns `NotFound` and records a deterministic workload failure.
Duplicate submit IDs are rejected before simulation. Step/submission failure targets may refer to a
future generated ID/ordinal; an unconsumed one-shot rule at the footer is an error unless the fixture
marks that failure as expected.

### 14.3 Total event order

For equal timestamps, process in this order:

1. shutdown, explicit cancellation, and deadline expiration;
2. fake execution failures/completions;
3. request submissions and test-only preemption/requeue events;
4. one scheduler planning tick after all events at that timestamp are drained.

Class 1 is further ordered as: the single shutdown event, explicit cancels by workload file ordinal,
then expired deadlines by `ArrivalKey`. Class 2 is executor submission ordinal then completion item
ordinal. Class 3 is workload file ordinal. A second shutdown event is invalid workload input. Since a
deadline expires at `now >= deadline`, cancellation/deadline wins over a same-time completion: the
matching completion drains ownership but commits no token. Shutdown therefore wins over explicit
cancel, and explicit cancel wins over an exactly simultaneous deadline for finish-reason selection.
This rule is deliberately strict and golden-tested.

If planning submits work completing at a later time, advance directly to the minimum of next external
event, deadline, and completion. A strictly positive fake latency prevents an immediate loop. Stop
with `Internal/kInvariantViolation` if unfinished requests exist but there is no future event and no
schedulable work.

### 14.4 Main loop

```text
parse config/workload -> validate -> initialize bounded storage
while pending event, in-flight work, or live request exists:
  choose next deterministic time and advance ManualClock
  drain shutdown/cancel/deadline events
  drain and validate completions/failures
  apply submissions/test events
  build snapshot, reserve capacity, and plan at most one M1 step
  submit plan or record idle reason
  run invariants
  enforce max_simulation_events
finalize/verify terminal responses and zero resources
write replay footer
```

An idle iteration records a closed `IdleReason` (`kNoRequests`, `kWaitingForEvent`,
`kWaitingForCompletion`, `kCapacityBlocked`, or `kNoPlanBuffer`) rather than free-form text.

## 15. Replay and workload formats

### 15.1 Canonical JSON Lines

Use UTF-8 JSON Lines so a partial trace remains inspectable. Every line is one object with
`schema_version`, `record_type`, and `ordinal` first, followed by a fixed field order. Record types are:

```text
header
workload_event
request_transition
resource_change
step_plan
execution_completion
response_event
idle
footer
```

After the three common fields, schema-v1 records contain these payload fields in the listed order:

| Record | Ordered payload |
|---|---|
| `header` | `inferx_version`, `config`, `fake_model`, `workload_event_count` |
| `workload_event` | `at_ns`, `event_type`, then the canonical event fields from section 14.2 |
| `request_transition` | `at_ns`, `request_id`, `sequence_id`, `epoch`, `from`, `event`, `to`, `status_code`, `error_reason` |
| `resource_change` | `at_ns`, `action`, `reservation_id`, `request_id`, `sequence_delta`, `kv_token_delta`, `used_sequences`, `used_kv_tokens` |
| `step_plan` | `at_ns`, `step_id`, `model_id`, `buffer_slot`, `buffer_generation`, `num_sequences`, `num_tokens`, `sequences` |
| `execution_completion` | `at_ns`, `ticket_id`, `step_id`, `request_id`, `sequence_id`, `epoch`, `kind`, `token_begin`, `token_end`, `status_code`, `error_reason`, `output_token` |
| `response_event` | `at_ns`, `request_id`, `event_kind`, `output_position`, `token_id`, `finish_reason`, `status_code`, `error_reason`, `prompt_tokens`, `output_tokens` |
| `idle` | `at_ns`, `idle_reason`, `next_event_ns` |
| `footer` | `final_status_code`, `error_reason`, `events`, `steps`, `requests`, `finished`, `cancelled`, `failed`, `used_sequences`, `used_kv_tokens`, `live_tickets`, `leased_plan_slots`, `invariants_ok` |

Fields that do not apply to a variant are emitted as JSON `null`, not omitted, so record shape is
stable. `step_plan.sequences` uses plan order and emits, for each item, request/sequence/epoch/kind,
input begin/end, reservation ID, and logical KV read/write begin/end. The committed
`docs/replay-schema.md` supplies equivalent JSON examples and is tested against the same serializer
metadata; it must not define a second hand-maintained field list.

The header contains InferX version, replay schema, canonical effective config, fake-model capability,
and workload-event count. It is followed by the exact canonical `workload_event` records before the
first derived transition/plan. The footer contains final status, event/step/request counts, terminal
counts by reason, resource totals, and invariant result.

Timestamps/durations and all IDs/counts are decimal integers. Status records contain the numeric
Abseil code and stable `ErrorReason`; free-form status messages are diagnostics and are deliberately
excluded from canonical replay. Arrays follow scheduler/plan order. Object keys are always emitted in
the schema order. New optional fields require a schema-compatible reader rule; semantic changes
increment the replay schema.

### 15.2 Writer/parser boundary

Use simdjson for input parsing. Implement only a small schema-specific canonical writer with one
well-tested JSON string escaper; do not add another general JSON DOM library. Replay decisions must not
depend on object key order in user input.

Cap line length, total trace bytes, record count, array length, and string size. Reject invalid UTF-8,
duplicate object keys, numbers outside exact integer ranges, NaN/Inf, and unknown record
types/required fields. The adapter detects duplicates while visiting every object member; it does not
rely on a parser's first-key/last-key lookup behavior.

### 15.3 Replay modes

`inferx-sim` provides:

```text
inferx-sim validate-config --config <file>
inferx-sim explain-config --config <file> [overlays]
inferx-sim run --config <file> --workload <file> --trace <file>
inferx-sim replay --trace <file> --output <new-file>
inferx-sim check-trace --trace <file>
```

`replay` reconstructs inputs, reruns the simulator, writes a new trace, and compares bytes. On mismatch
it reports the first record/byte and a semantic field diff without overwriting the original. It never
accepts build paths, pointer values, wall time, unordered iteration, or random seeds not stored in the
trace.

Golden traces are small, reviewed files under `tests/correctness/replay/data/`. Large generated traces
are CI artifacts under `out/`, not committed.

## 16. Invariant checker

The invariant checker is callable after every event/transition/plan/completion in simulator/debug
tests and once per planning iteration in release simulator builds.

### 16.1 Per-request invariants

- Prompt/output/scheduled/computed counts are in range and checked sums fit model context.
- `num_scheduled_tokens > 0` iff the request has matching in-flight step/ticket work.
- In-flight states have exactly one ticket; ready/queued/terminal states have none.
- A committed reservation exists in ready/in-flight/cancelling/finishing states. `Queued`,
  `Reserving` before commit, `Preempted`, and terminal states have none under the M1 policy.
- Epoch/step/ticket in context match plan/executor ownership.
- Output token vector size equals committed output count.
- `Cancelling` has a reason and commits no later completion token.
- Terminal state has a status/reason and exactly one terminal response marker.

### 16.2 Registry/queue invariants

- Request and sequence IDs are unique.
- Each live request appears in exactly the queues implied by its state and nowhere else.
- FCFS order structures contain IDs only once and never use hash iteration order.
- Registry size, queued count, active count, and terminal count match resource/simulator summaries.
- Erased requests are terminal, acknowledged, resource-free, and ticket-free.

### 16.3 Resource invariants

- Each reservation belongs to exactly one live request and vice versa where required.
- Sum of reservation costs equals accountant counters and never exceeds capacity.
- Tentative transactions and leased plan-buffer slots have exactly one owner.
- A plan slot is not reused until its ticket completion returns the lease.
- Final capacity equals initial capacity with zero reservation/ticket/plan leases.

### 16.4 Plan/completion invariants

- Plan schema/model/step/slot are valid and step IDs increase.
- Plan items are unique by request, match ready states/epochs/reservations, and have legal token ranges.
- Per-item and aggregate token/sequence costs match and remain within budgets.
- Completion items match exactly one accepted plan item and cannot be applied twice.
- Failure/cancellation paths clear scheduled counts without committing output.

Invariant failure returns `Internal/kInvariantViolation`, writes a bounded diagnostic snapshot and the
last N replay records, and stops simulation. It must not attempt to “repair” state and continue.

## 17. Testing requirements

All M1 tests are CPU-only and inherit M0 format, analysis, sanitizer, install, and header gates.
Every test carries the general `m1` label plus one category label:

| Suite | Required CTest label |
|---|---|
| Unit | `core-unit` |
| Integration | `core-integration` |
| Correctness/replay | `core-correctness` |
| Failure | `core-failure` |
| Bounded-channel TSan | `core-channel` |
| Presubmit stress | `core-stress` |

Benchmarks are executable targets, not CTest pass/fail tests. CI first queries `ctest --show-only=json-v1`
and fails if any required label selects zero tests.

### 17.1 Unit tests

**Base**

- Cross-type strong ID construction is impossible; zero/maximum round trips correctly; generator
  overflow fails.
- Every checked arithmetic signed/unsigned boundary and range-validation branch.
- Manual clock monotonicity/overflow and exact deadline boundary.
- Bounded channel capacity 1/N, move-only values, FIFO, full/empty, close/drain, stop/timeout, and
  multi-producer/consumer TSan runs.
- Status macro single evaluation, move-only values, payload/status preservation, and nested scopes.

**Configuration**

- Each default, source precedence, provenance, unknown field, parser limit, integer boundary, duration
  overflow, cross-field constraint, and capabilities mismatch.
- Canonical effective output is byte-identical across semantically equivalent input key order and
  source combinations.
- Text/environment/CLI values that fail parsing never partially mutate a valid config.

**FSM/registry**

- Every legal row in the transition table and representative illegal state/event pairs.
- Cancellation/deadline from every nonterminal state, including in-flight drain.
- Terminal absorption, one terminal response, duplicate ID, capacity, epoch increment/overflow, stale
  step/ticket/epoch, and erase preconditions.
- Counter updates for prefill first token, decode, simulated EOS, length, failure, and no-commit cancel.

**Scheduler/resources**

- FCFS tie-breaking, temporarily blocked/can-never-fit admission, exact/full budgets, multi-model
  rejection, full prompt and one-token decode plan construction.
- Reservation commit/rollback/destruction, double/unknown release, cost overflow, and plan-slot
  generation/lease behavior.
- Every `StepPlanValidator` failure branch and proof that invalid plans are not submitted.

### 17.2 Integration tests

At minimum include deterministic scenarios for:

1. one request: submit -> prefill -> N decodes -> length terminal;
2. multiple same-time requests with constrained step/capacity budgets and FCFS order;
3. cancel queued, ready, prefilling, and decoding requests;
4. deadline before admission, during prefill, and at the exact completion timestamp;
5. temporary capacity block followed by terminal release/admission;
6. preempt/requeue with epoch increment and stale old completion injection;
7. injected executor failure affecting one/all planned requests according to fixture;
8. shutdown with queued, ready, and in-flight requests; and
9. run -> trace -> replay -> byte equality through the CLI.

Every scenario asserts terminal responses, token sequence, plan order, exact final counters, no live
ticket/lease, and invariant success.

### 17.3 Correctness tests

- Check in reviewed golden workload/config/trace triples for the core scenarios.
- Run identical inputs with different unordered-map insertion histories and prove identical traces.
- Run config files with reordered keys and equivalent overlays and prove canonical config/trace
  equality.
- Compare batched fake outputs with a serial per-request fake-execution reference; outputs must be
  token-identical because generation is request/position based.
- Replaying the same trace twice produces byte-identical files and final summaries.

Golden updates require a human-readable semantic diff and reviewer confirmation; a test must not
blindly rewrite expected traces.

### 17.4 Stress and property tests

Use a deterministic custom generator based on `std::mt19937_64` with the seed printed/stored. Do not
add RapidCheck before its planned qualification unless an ADR changes that dependency decision.

Generate valid and intentionally invalid sequences of submit/cancel/deadline/preempt/failure/shutdown
events with varied capacities and limits. A reference model tracks only abstract state/counters and is
compared after each operation.

- Presubmit: at least 50,000 operations across fixed seeds under ASan/UBSan.
- Nightly/release: at least 1,000,000 operations, plus TSan bounded-channel stress.
- On failure: minimize by deleting event ranges/fields while preserving failure, then write the
  minimized workload/seed/replay under `out/failures/` as a CI artifact.

Assertions include no deadlock, no invariant violation for valid inputs, correct error without state
change for invalid inputs, bounded event count/memory, exactly one terminal per admitted request, and
final resource equality.

### 17.5 Failure tests

Inject and verify:

- queue full, duplicate request, invalid/empty/oversized prompt, impossible reservation/context;
- invalid config JSON/UTF-8/unknown/duplicate fields, oversized file, arithmetic/duration overflow;
- invalid FSM transition and transition from terminal state;
- plan buffer exhaustion, rejected plan, fake submit failure, execution completion failure;
- missing/duplicate/stale/wrong-request/wrong-epoch completion;
- cancellation/deadline race at each event priority;
- max event bound and deadlock/no-future-event detection;
- truncated/oversized/unknown-version replay records and canonical mismatch; and
- shutdown from every request state.

Each failure fixture asserts status code/reason, no unrelated request corruption, no leaked resource,
and deterministic trace suffix.

### 17.6 Performance benchmarks

`scheduler_benchmark` measures planning with 1, 32, 256, and 1,024 active/eligible requests for:

- all prefill-ready;
- all decode-ready;
- mixed ready/queued/capacity-blocked; and
- exact token/sequence budget saturation.

Warm registry/snapshot/scratch/plan pools before measurement. Report p50/p90/p99, requests inspected,
items planned, tokens planned, CPU cycles when available, and allocations in the measured region. At
1,024 active requests, p99 planning must be <= 1 ms on M0's recorded reference CPU and measured-region
heap allocations must be zero.

`simulator_benchmark` reports events/second, peak resident memory, trace-on/off overhead, and workload
size scaling. It establishes a baseline; no absolute simulator throughput gate is required in M1.
All benchmark JSON records the M0 machine/toolchain/dependency manifest and M1 config/workload.

## 18. CLI and diagnostics

`inferx-sim` uses Abseil flags and logging qualified in M0. Commands never use positional ambiguity;
all input/output paths are explicit. It refuses to overwrite an existing trace unless
`--overwrite` is supplied, and validates output parents without accepting the repository root, `/`,
or a home directory as a recursive cleanup target.

Default output is a concise final summary. `--verbose` adds transitions/plans but never raw pointer,
wall time, environment dump, or unbounded token output. Diagnostics include request/step/epoch IDs,
status code/reason, resource snapshot, and last bounded trace records.

Exit codes are stable and documented:

| Code | Meaning |
|---:|---|
| 0 | Valid config/run/replay/check completed successfully |
| 2 | CLI or configuration/workload validation error |
| 3 | Simulation completed with injected/request failure when failure was not expected |
| 4 | Invariant or replay mismatch |
| 5 | Output I/O failure |

Signals and threaded graceful shutdown remain outside the simulator; M7/M9 own production process
handling.

## 19. Risks and experiments that gate M1

These questions are resolved by measurement or qualification during M1; they are not permission to
leave ownership/schema behavior unspecified:

| Risk/question | Required experiment/evidence | Decision rule and fallback |
|---|---|---|
| `flat_hash_map` + B-tree registry costs threaten planning latency | Benchmark 1/32/256/1024 live requests with deterministic iteration and allocation counters | Keep if section 17.6 gate passes; otherwise ADR 0010 selects a preallocated indexed-slot/order structure without changing views or FCFS semantics |
| A dependency/toolchain makes a `RequestContext` commit potentially throwing | Compile-time nothrow assertions for every moved commit field plus injected preparation-allocation failures | Keep `Commit noexcept` only when proved; otherwise store fixed status/reason values in context and keep allocated diagnostics solely in prepared records |
| Blocking channel stop/timeout implementation allocates or races on a supported standard library | Allocation instrumentation for uncontended/blocked paths and GCC/Clang TSan close-stop races | Prefer the standard-library implementation; if it misses the gate, ADR 0013 may add fixed waiter bookkeeping, not an unbounded queue or silent semantic change |
| simdjson duplicate-key, UTF-8, integer, or nesting behavior differs by backend/architecture | Run the checked malformed/limit corpus while forcing each supported simdjson implementation where possible | Adapter explicitly detects/rejects duplicates and normalizes errors; unsupported parser implementations are disabled by the build capability report |
| Canonical replay accidentally captures compiler/library-specific text/order | Cross-GCC/Clang golden replay, randomized insertion histories, locale/time-zone matrix | Remove unstable fields and serialize only stable code/reason; do not weaken byte-equality to semantic-only equality |
| Conservative full KV reservation makes representative workloads appear deadlocked | Compare admission/resource traces with analytically computed capacity fixtures | M1 keeps the conservative oracle if accounting is correct; utilization changes require an M8 policy ADR and must not rewrite M1 goldens silently |
| More than one plan slot exposes completion/acknowledgement lifetime bugs | Stress 1/2/8/64 slots with same-time completions, injected failures, cancellation, and slot-generation wrap boundary | Merge only with explicit delivered-ticket acknowledgement and zero leaked slots; otherwise cap M1 to one slot and record the limitation in ADR 0010 |
| The 1 ms p99 threshold is dominated by an unsuitable reference CPU or benchmark noise | Pin/record CPU governor, affinity, warm-up, compiler, and at least 30 benchmark repetitions | Optimize data structures first; revise the numeric gate only through an accepted ADR containing raw results and a replacement regression threshold |

The most important semantic limitation is intentional: this simulator validates lifecycle and
accounting, not GPU throughput, real continuous-batching quality, or model output. Performance claims
outside scheduler planning wait for the CUDA milestones.

## 22. Definition of done

### Core/configuration

- [ ] Exported M1 headers/targets build with GCC/Clang C++23 and pass M0 install/consumer gates.
- [ ] Abseil statuses are the only cross-module error type; exceptions do not cross adapters.
- [ ] IDs/units are non-interchangeable, checked arithmetic covers every parsed/resource sum, and no
      invalid sentinel is overloaded with a valid numeric ID.
- [ ] Bounded channel close/full/empty/timeout/stop semantics are documented and TSan-clean.
- [ ] JSON/env/CLI precedence, strict unknown-field handling, provenance, validation, and canonical
      effective configuration pass all fixtures.

### Lifecycle/scheduler

- [ ] The implementation uses one declarative request transition table and one mutating controller.
- [ ] Every valid/invalid transition and cancellation/deadline from every nonterminal state is tested.
- [ ] Request/sequence/epoch/step/ticket checks reject stale completions without side effects.
- [ ] Scheduler consumes immutable value snapshots, emits plans backed by owned pool leases, and never
      stores request pointers/views past their owner lifetime.
- [ ] FCFS order and resource transaction behavior are deterministic and all plan/capacity invariants
      pass generated tests.

### Simulator/replay

- [ ] Simulator uses manual monotonic time, no sleeps/threads/wall clock, and the documented total
      event order.
- [ ] Core submit/prefill/decode/cancel/deadline/preempt/failure/shutdown scenarios have reviewed
      golden traces.
- [ ] Same input/config produces byte-identical replay across repeated GCC/Clang runs on the supported
      platform; no pointer/build path/unordered iteration enters output.
- [ ] Every admitted request emits exactly one terminal response and final reservations/tickets/plan
      slots are zero after every success/failure fixture.
- [ ] Invalid/truncated/oversized/unknown replay and workload inputs fail safely and deterministically.

### Verification/performance

- [ ] Unit, integration, correctness, stress, failure, and performance suites are independently
      selectable and retained in CI evidence.
- [ ] >=50,000 generated operations pass presubmit sanitizer tests; >=1,000,000 pass nightly/release.
- [ ] TSan reports no bounded-channel race.
- [ ] Planning 1,024 active requests has <=1 ms p99 and zero measured-region heap allocations on M0's
      reference CPU, or an accepted ADR changes data structures/gate with evidence.
- [ ] Format, clang-tidy, IWYU, header self-containment, ASan, UBSan, install/consumer, dependency
      manifest/license/SBOM, and build-metric gates remain green.
- [ ] ADRs 0008 through 0013 and configuration/lifecycle/scheduler/simulator docs match code.

## 23. Handoff to M2 and M3

The M1 handoff is a green immutable commit plus:

- accepted ADRs and installed module/API documentation;
- canonical config schema and golden config corpus;
- request FSM transition table and coverage report;
- StepPlan/replay schema v1 documentation and golden traces;
- minimized stress seeds/workloads, if any bugs were found;
- M1 scheduler/simulator benchmark JSON tied to the M0 machine manifest; and
- explicit known limitations.

M2 adds tensor/device memory and a real asynchronous execution backend. It must preserve request
epoch/ticket/plan-buffer ownership and completion validation, but it may replace the private M0 CUDA
smoke and implement physical completion fences. M2 must not put CUDA types in M1 public control-plane
headers.

M3 adds real artifact/model capabilities and tokenization. It replaces the test-only input processor,
extends validated configuration through versioned fields, and preserves source provenance/canonical
configuration. Neither successor may bypass the FSM/controller or mutate scheduler snapshots.
