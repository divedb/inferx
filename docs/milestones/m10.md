# M10 implementation specification: observability, failure containment, and developer preview

- Status: proposed implementation contract
- Roadmap milestone: M10 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M9](m9.md), including M1-M8 transitively
- Immediate consumer: M11 cross-request prefix caching
- Later consumers: M12 performance work, M13 quantization/model expansion, M14 worker/tensor
  parallelism, M15 data/pipeline parallelism, and M17 speculative decoding

This document turns M10 into an executable engineering plan. It defines bounded metrics, distributed
trace propagation, structured redacted logging, health aggregation, progress watchdogs, failure
classification and containment, diagnostic snapshots, deterministic fault injection, reproducible
request/scheduler trace capture, signal and shutdown behavior, a production container, dependency/
license/SBOM controls, a compatibility report, a benchmark workload/SLO, soak and release evidence,
an operational runbook, and the developer-preview handoff.

M10 makes the M9 serving process operable and diagnosable. It must not alter model math, sampling,
scheduler decisions, output ordering, HTTP wire behavior, or fence-safe ownership merely because
telemetry is enabled or an exporter is unavailable.

## 1. Outcome

At the end of M10, an operator can:

1. reconstruct received, admitted, active, and terminal request accounting exactly from bounded
   metrics while observing queue, scheduler, KV, GPU, sampling, and HTTP behavior with fixed units and
   label domains;
2. correlate one sampled request from HTTP parsing through tokenization, admission, scheduling,
   prefill/decode, sampling, response serialization, and terminal cleanup using propagated trace IDs;
3. consume one versioned structured-log schema whose field classification and redaction rules prevent
   prompts, outputs, credentials, raw bodies, and unsafe diagnostics from leaking by default;
4. query immutable liveness/readiness/health snapshots that reflect the authoritative model,
   coordinator, worker, allocator, network, and shutdown states without probing the GPU synchronously;
5. detect stalled network loops, coordinator turns, tokenizer jobs, device-worker tickets, GPU fence
   progress, diagnostic/exporter work, and shutdown phases using monotonic, work-aware watchdogs;
6. contain request-scoped, component-degraded, worker-poisoning, and process-fatal failures according
   to one explicit matrix, with bounded drain or bounded process termination when safe cleanup cannot
   complete;
7. capture privacy-safe diagnostic snapshots and deterministic structural replay traces without
   stopping inference, plus explicitly enabled protected token-level replay capsules for test data;
8. inject reproducible failures at allocator, CUDA/kernel, worker, queue, tokenizer, sampler,
   response, exporter, watchdog, and shutdown boundaries in owned test processes;
9. build and verify a non-root, minimal, reproducible OCI image with pinned inputs, SBOM, license and
   vulnerability results, model/runtime compatibility metadata, and no embedded model or secret; and
10. publish a developer-preview report containing compatibility, conformance, benchmark/SLO,
    telemetry-overhead, fault-matrix, two-hour and 24-hour soak, resource-growth, and known-limit data.

```text
request/network/tokenizer/coordinator/device owners
       | exact counters + bounded telemetry records + heartbeats
       v
immutable owner snapshots / fixed-cardinality shards
       |                         |                         |
       v                         v                         v
health aggregator        telemetry aggregator       diagnostic recorder
       |                 metrics / spans / logs      recent-event ring
       |                         |                         |
       +---------- immutable published snapshots --------+
                                 |
             +-------------------+-------------------+
             v                   v                   v
        health routes      bounded exporters     protected snapshot files

watchdog reads progress snapshots only
  -> soft stall: degraded + readiness false + diagnostic trigger
  -> hard stall: stop admission + cancel/drain + poison classification
  -> unsafe/unresponsive past deadline: bounded process termination
```

M10 is complete only if telemetry-on and telemetry-off executions are token/outcome identical, no
exporter/log/diagnostic failure can stall inference, every injected failure reaches its documented
terminal containment state, and the 24-hour release soak satisfies the roadmap resource and loss
criteria.

## 2. Scope boundaries

### 2.1 In scope

- Fixed-schema counters, gauges, histograms, bounded exemplars, and a scrape/export snapshot.
- W3C trace-context intake, deterministic head sampling, bounded span/event recording, and optional
  OTLP export through a failure-isolated worker.
- Structured JSON logs to stderr and optional bounded exporter, with typed field classification,
  redaction, rate limiting, and request/trace correlation.
- Critical/noncritical component health, immutable aggregation, readiness policy, and state history.
- Work-aware watchdogs for network loops, coordinator, tokenizer workers, device/GPU, telemetry,
  diagnostics, and shutdown.
- Request/component/worker/process failure classification, circuit breaking, drain, poison, and exit.
- Bounded privacy-safe diagnostic snapshots and structural scheduler/request trace capture.
- Explicit opt-in sensitive replay capsules for non-production fixtures under protected storage.
- Compile-time/test-only fault injection and subprocess orchestration.
- Async-signal-safe signal intake and deterministic graceful/cancel/forced shutdown escalation.
- Reproducible release-mode OCI image, dependency/license/vulnerability/SBOM evidence, compatibility
  matrix, benchmark workload/SLO, soak, preview report, and operator runbook.

### 2.2 Explicitly out of scope

- A hosted monitoring stack, alert manager, dashboard service, log storage, trace backend, or service
  mesh. M10 exports/serves data and ships example queries/dashboards only.
- Remote administration, arbitrary debug RPCs, heap dumps, live token/logit inspection, or a public
  fault-injection endpoint.
- Automatic in-process recovery of a hung thread, poisoned CUDA context, corrupted allocator, or
  invariant failure. M14 process isolation may later enable supervised worker replacement.
- Cross-process request routing, multi-GPU health quorum, rolling model reload, prefix-cache behavior,
  or speculative/graph-specific telemetry.
- Uploading diagnostics, traces, logs, cores, prompts, outputs, token IDs, environment variables, or
  configuration files to a remote service without explicit separate deployment policy.
- Treating ordinary invalid input, cancellation, client disconnect, deadline, or bounded overload as
  a worker-health failure.
- Blocking the coordinator/device/network loops on formatting, symbolization, filesystem I/O, DNS,
  exporter I/O, scrape, compression, or diagnostic capture.
- Catching `SIGSEGV`/`SIGBUS` to continue execution, detaching stuck threads, resetting CUDA under
  uncertain ownership, or running destructors over possibly in-flight GPU memory after fatal timeout.

## 6. Telemetry architecture and noninterference

M10 separates authoritative accounting from best-effort telemetry:

- **authoritative owner counters/snapshots** live with coordinator, KV manager, device worker,
  tokenizer pool, and server session manager; exact lifecycle/reconciliation uses these values and
  cannot be dropped;
- **metric shards** contain fixed-cardinality counters/histograms updated by their owning threads and
  copied through generation-checked snapshots;
- **trace/log records** use a bounded preallocated MPSC queue into one telemetry aggregator; producers
  perform nonblocking `try` publication only;
- **exporters** read immutable aggregator batches on dedicated bounded workers; and
- **diagnostics** receive explicit bounded triggers and copy published snapshots/recent-event rings,
  never mutable registries.

If trace/log publication has no capacity, the producer increments an exact per-owner dropped-record
counter and continues inference. Formatting, encoding, batching, compression, DNS, connection,
retry, and file operations occur only off request-owner threads. One reserved minimal diagnostic lane
may report the first telemetry failure, but it is also bounded and cannot recurse into logging.

Instrumentation is observational:

- it cannot choose a kernel, sampler token, scheduler victim, request order, timeout, or finish reason;
- monotonic timing reads used only for telemetry are excluded from decision inputs;
- exporter health cannot make model readiness false unless it exhausts an independently proved
  safety-critical local resource—which is treated as an implementation invariant, not normal outage;
- turning a sink on/off cannot change memory available to model/KV pools after startup capacity is
  resolved; and
- telemetry failures never roll back already committed request or response state.

## 7. Metric schema and exact accounting

Metric definitions are generated from one reviewed schema containing stable name, kind, unit,
description, fixed label keys/domains, histogram buckets, owner, and lifecycle version. Duplicate
names, suffix/unit mismatches, unbounded labels, and bucket drift fail build/schema tests.

### 7.1 Naming and units

- Monotonic event counters end in `_total`.
- Byte quantities end in `_bytes`; durations use seconds and end in `_seconds`.
- Gauges name the current resource without `_total`.
- Ratios are computed by the backend/dashboard rather than exported as ambiguous gauges when source
  counters exist.
- Histograms use cumulative fixed buckets plus sum/count; bucket sets are immutable within a schema
  version.
- Integer token/request/page/sequence counts are never converted to floating point before snapshot
  serialization if exact integer export is available.

Metric labels are closed enums or startup-bounded identifiers: component, phase, work kind, terminal
reason, stable error class, endpoint, stream mode, model slot, worker slot, page-size bucket, and
sampling/filter class. Request/trace/span/user/principal/token IDs, prompt/output text, raw model IDs,
paths, addresses, error messages, policy digests, and dynamic status strings are forbidden labels.

### 7.2 Required request reconciliation

Authoritative monotonic counters include:

- HTTP received and transport/auth/validation/rate rejected before engine submission;
- engine submission attempted, admission accepted/rejected/withdrawn;
- tokenization success/failure/cancel;
- queued/ready/in-flight and terminal completed/cancelled/deadline/failed/shutdown totals;
- SSE/non-stream success, post-header error, disconnect, and slow-client cancellation; and
- output tokens committed, response events committed, and response events/bytes written.

The following identities must hold for each snapshot interval after in-flight work is accounted for:

- engine accepted equals active plus all terminal outcomes;
- admitted terminal total equals completed plus cancelled plus deadline plus failed plus shutdown;
- output-token total equals the sum of committed per-request completion tokens;
- each accepted execution ticket is in-flight, completed awaiting acknowledgement, or acknowledged;
  and
- M6/M7/M8/M9 current resource gauges reconcile to their owner pool capacity/leases.

The integration oracle reads owner snapshots, not exported rounded text, and proves the equations at
turn boundaries and final quiescence. Metrics scrape tests prove serialized values equal the same
snapshot.

The exported terminal outcomes in that equation are mutually exclusive normalizations: explicit or
client cancellation, deadline expiry, controlled shutdown, request/system failure, or successful
completion. If the underlying FSM represents deadline/shutdown as cancellation subreasons, metric
normalization assigns the request to exactly one terminal label rather than incrementing both.

### 7.3 Required performance/resource metrics

At minimum expose bounded series for:

- request duration, TTFT, TPOT/inter-token, queue/tokenizer/admission/scheduler/GPU/sampling/
  serialization/write duration;
- prompt/completion/scheduled/recompute/cached token distributions and SLO-goodput counters;
- batch sequence/token/chunk/phase composition, plan fill, scheduler turn cost, preemption, deadline,
  rollback, and idle reasons;
- KV quota/pages/free/low-water/fragmentation/pins/tables and workspace/activation/event pools;
- connection/session/parser/body/outbound/mailbox/channel current/peak and rejection reasons;
- CPU sampling/filter/logprob cost, trace/log queue fill/drop, exporter batch/retry/drop, diagnostic
  triggers/success/failure/truncation; and
- worker progress age, watchdog soft/hard/fatal transitions, component state, poison, drain, and exit
  intent.

### 7.4 Snapshot and scrape behavior

Each owner publishes an immutable generation-tagged metric fragment at a bounded cadence or explicit
quiescent checkpoint. The aggregator combines only compatible schema/generation fragments and marks
staleness; it never waits for a slow owner. Counters remain monotonic across a fragment refresh.

The baseline metrics route is `GET /metrics` on a separate loopback telemetry listener; sharing the
public M9 listener requires explicit authentication/network-policy configuration. It serves a
prebuilt immutable Prometheus text exposition buffer. Scrape serialization never locks an owner,
queries CUDA, drains queues, or allocates proportional to requests. Concurrent scrapes share/copy a
bounded snapshot and obey connection/response limits. A scrape timeout affects only that client.

## 8. Trace context, sampling, and span model

### 8.1 Context intake and propagation

Generation routes accept the W3C `traceparent` header and a bounded `tracestate` only for tracing;
neither changes M9 protocol JSON, authentication, scheduling, or response IDs. Parsing validates
version, fixed hex lengths, nonzero IDs, flags, total bytes, and member count. Invalid context is
recorded as a bounded category and starts a new local trace rather than rejecting an otherwise valid
generation request. Baggage is not accepted in M10.

One immutable trace context follows the strong request ID through HTTP session, M3 tokenization, M8
scheduler/tickets, M9 sampling, response pump, and terminal cleanup. Worker messages carry IDs and
sampling flags by value, never pointers or exporter objects. Internal async work uses explicit links
when a strict parent/child interval would be misleading.

### 8.2 Deterministic head sampling

The decision occurs once after authentication and request-ID assignment, before tokenization. It is
the deterministic comparison of a keyed hash over trace ID plus configured salt against a fixed-point
probability threshold. Parent sampled flags are honored only within configured local rate/capacity
limits; overflow drops recording rather than inference. Errors may produce a bounded unsampled-event
counter but do not retroactively allocate an unbounded trace.

Sampling configuration includes probability, maximum sampled traces per second, maximum spans/events
per trace, attribute bytes, queue records/bytes, batch size, flush interval, exporter deadline, retry
count/backoff, and shutdown flush budget. All are validated with checked worst-case storage.

### 8.3 Span graph

The baseline span/event vocabulary is fixed:

- server request span: headers accepted through final write/close;
- parse/auth/rate/protocol-validation spans;
- engine submission/admission and tokenizer job spans;
- queue-ready wait and scheduler decision events;
- execution-step spans with prefill/recompute/decode/mixed attributes and ticket links;
- GPU enqueue-to-fence, CPU sampling, output commit, incremental decode/stop, and serialization spans;
- network write spans aggregated by response rather than one span per byte; and
- cancellation/deadline/preemption/poison/shutdown events with stable enums.

Per-token detail is represented as bounded events on execution/request spans or sampled aggregate
spans, not an unlimited span per token. When a per-trace cap is reached, one truncation event/counter
is retained and later trace detail is dropped.

Attributes use the same allowlisted field classification as logs. Durations use monotonic clocks;
wall-clock timestamps derive from a periodically calibrated mapping and carry a clock-discontinuity
flag rather than producing negative durations.

### 8.4 Export isolation

The aggregator forms immutable bounded batches for a sink interface. The baseline optional remote
sink is OTLP with connection, DNS, serialization, compression, retry, and backoff confined to the
export worker. Queue full, timeout, server error, malformed response, DNS/TLS failure, or shutdown
budget expiry increments sink counters and drops the affected telemetry batch according to policy.

Retries are capped, jitter is deterministic per process, and stale batches expire; remote recovery
cannot flood memory or starve new batches. The exporter has no callback into request owners. Local
metrics/health remain available when remote tracing is down.

## 9. Structured logging and privacy

### 9.1 Event schema

Every log line is one valid UTF-8 JSON object with schema version, UTC timestamp, monotonic event
ordinal, severity, stable event name, component, process/worker slot, message code, public bounded
fields, optional request correlation hash, and sampled trace/span IDs. Human text is a bounded
allowlisted template selected by event code, not raw exception/status text.

Severity is closed: debug, info, warning, error, critical. Event names and field keys come from a
generated registry. Unknown/dynamic keys cannot be logged through the production API. Numeric values
are locale-independent; nonfinite values use a stable category rather than invalid JSON.

### 9.2 Field classification

Every possible field is classified at declaration:

| Class | Examples | Default handling |
|---|---|---|
| public | schema version, enum reason, count, duration, public model slot | emit within bounds |
| operational | request/trace identity, source bucket, policy/system digest | keyed correlation hash or sampled bounded value |
| sensitive | prompt/output text, token IDs, seeds, raw model/user ID, filesystem path | never emit to ordinary logs/metrics/traces |
| secret | authorization, auth digest/key, environment secret, encryption material | never enter telemetry values |

Raw HTTP bodies/headers, chat messages, prompts, generated text, token/logit arrays, stop strings,
credentials, complete environment/config, memory addresses, stack memory, and exception `what()`
strings are forbidden. Stable sanitized error codes and safe source locations replace them.

Operational correlation uses HMAC-SHA-256 with a per-process random key held in locked/zeroized secret
storage where supported. Hashes are stable only for one process lifetime by default and are truncated
to the reviewed collision/security length. The key is never exported or included in snapshots.

### 9.3 Rate limiting and sinks

JSON stderr is the baseline container-friendly sink. M10 does not rotate files inside the container.
An optional remote/log sink consumes the same bounded aggregator path as tracing and cannot block
stderr or inference.

Each high-volume event has a fixed token-bucket rate/burst and a suppressed-count summary. One
reserved bounded lane accepts the first error/critical state transition per component generation.
Recursive logging from sink/redaction failure is prohibited; it increments a minimal atomic counter
and disables the faulty sink. Log storms cannot allocate, format, or queue beyond configured limits.

Debug logging that could increase cost remains privacy-safe and is disabled by default. Sensitive
replay capture is a separate facility and never enabled by log level.

## 10. Health model and readiness aggregation

### 10.1 Component state

Components publish generation-tagged status values from a closed state set:

```text
Starting -> Healthy <-> Degraded -> Unhealthy or Poisoned
     \          \          \             \
      +-----------> Draining --------------> Stopped
```

Every transition contains monotonic time, stable reason, progress ordinal, optional deadline, and
component generation. Illegal regression, stale update, or skipped required poison state is an
invariant failure. Human messages are not state.

Registered components include configuration/model package, tokenizer pool, coordinator/scheduler,
KV/resource manager, device worker/CUDA context, network acceptor/event loops, telemetry aggregator,
each exporter, diagnostic writer, and shutdown controller. Each registration declares criticality,
minimum healthy capacity, allowed degraded-readiness behavior, heartbeat contract, and owner.

### 10.2 Aggregation

One health aggregator consumes bounded status/heartbeat snapshots and publishes an immutable overall
snapshot. It never polls CUDA, joins threads, locks request state, scrapes metrics, or performs I/O.

- **live** means the process and health/network control path are responding; it does not imply model
  readiness;
- **ready** requires M9 admission open and every critical component at its permitted Healthy/Degraded
  capacity;
- **degraded** records reduced but policy-permitted service, such as some tokenizer capacity lost;
- **unready** stops new generation admission but permits health/metrics/diagnostic drain; and
- **poisoned** permanently rejects new work for that component generation and requires shutdown or a
  future process-isolated replacement.

Telemetry/exporter/diagnostic sink failure is noncritical and leaves inference ready while exposing
degraded health. Ordinary request validation, cancellation, deadline, client disconnect, rate limit,
and resource backpressure do not change component health. M2 device poison, allocator invariant,
coordinator failure, or model corruption makes the single-replica M10 server unready immediately.

M9 `/health/live` and `/health/ready` serialize the published aggregate only. An optional protected
detail endpoint may expose bounded component enums/generations, never internal addresses, paths,
requests, tokens, or secrets.

## 11. Progress heartbeat and watchdog design

### 11.1 Heartbeat contract

Every watched owner publishes a cache-line-safe progress snapshot containing component/generation,
monotonic timestamp, progress ordinal, current work class/identity hash, work start, expected soft/
hard deadline, and state. A heartbeat advances only when the documented unit makes progress; a timer
thread repeatedly writing the same work is not proof of progress.

Work-aware deadlines are resolved from configured absolute caps and prepared-operation bounds. GPU
steps use shape/backend-specific measured upper bounds plus an explicit safety factor; tokenization,
network, exporter, and shutdown stages use their own caps. Arithmetic and clock regression are
checked. Thresholds are immutable in one watchdog policy generation and appear in diagnostics.

### 11.2 Watched components

- Each network event-loop thread posts/executes a bounded probe ordinal.
- The coordinator advances after a turn or deliberate wait-state transition and reports its next
  expected wake deadline.
- Tokenizer workers advance on job accept/progress/return and identify a bounded job class.
- The device worker advances on submission accept, launch stages, fence polls, sampler completion,
  completion publish, and acknowledgement.
- GPU progress is the matching event/fence state observed only by the device owner; the watchdog does
  not call CUDA.
- Telemetry/exporter/diagnostic workers advance per batch/write attempt and expose retry sleep.
- The shutdown controller advances at every close/drain/join phase.

### 11.3 Escalation stages

At **soft timeout**:

1. atomically mark the component suspect/degraded;
2. make readiness false if the component is critical;
3. stop new work directed to that component;
4. enqueue one bounded privacy-safe diagnostic trigger; and
5. notify the owning control path to report or drain at its next safe point.

At **hard timeout** without progress:

1. for a critical component or loss of its declared minimum capacity, stop all new server admission;
2. classify outstanding work for request cancellation/failure or uncertain drain;
3. poison an uncertain device/allocator/worker generation;
4. begin bounded server/engine cancel shutdown; and
5. publish stable exit intent.

For a noncritical exporter/log/diagnostic component, hard timeout disables new work for that sink,
keeps inference readiness unchanged, and retains only its already bounded ownership. If the stuck
thread later prevents process shutdown, the shutdown fatal deadline may force process exit; its
runtime outage alone does not stop admission. A partially degraded tokenizer pool follows its
declared minimum-capacity rule rather than treating every single-worker loss identically.

At **fatal timeout** when the owner cannot drain/join safely, the watchdog records a minimal prebuilt
fatal record to a pre-opened safe descriptor where possible, then terminates the process with the
documented forced-watchdog exit code using a path that does not run destructors over uncertain GPU or
thread-owned resources. This is containment, not recovery; an external supervisor restarts the
container/process.

No watchdog kills/restarts a C++ thread, invokes CUDA from the watchdog, frees uncertain buffers,
extends deadlines forever because logs are flowing, or marks readiness true without a new healthy
component generation.

### 11.4 False-positive controls

- Startup calibration/warmup operations declare separate bounded deadlines.
- Debugger/sanitizer/test profiles explicitly scale thresholds and record the scale.
- Long kernels are rejected by capability/capacity validation if no defensible upper bound exists.
- Soft/hard/fatal thresholds have ordered minimum separation and checked maximums.
- Suspend/resume or monotonic clock discontinuity enters a documented unready revalidation path.
- Tests use a manual clock and progress source; production never changes real deadlines from wall
  clock or exporter time.

## 12. Failure classification and containment matrix

Every error is classified before it changes health:

| Class | Examples | Scope and required action |
|---|---|---|
| client/request | invalid JSON/parameter, auth/rate rejection, cancel, deadline, disconnect | one protocol/request terminal; component remains healthy |
| bounded pressure | queue/mailbox/KV/session/telemetry capacity | reject/defer per policy; health unchanged unless invariant says capacity leaked |
| request execution | tokenizer input error, NaN logits, response rendering failure | fail one request after safe drain; peers continue |
| safe batch failure | post-fence per-item/result failure with known ownership | fail affected items/batch; release through acknowledgement; worker may continue if contract allows |
| component degraded | one tokenizer instance/exporter/sink unavailable with sufficient remaining capacity | quarantine/disable component part; update degraded health; continue within policy |
| worker/replica poison | uncertain CUDA launch/fence/context, stale ownership corruption | fail/drain affected work, reject new work, permanently poison generation, controlled process shutdown |
| process fatal | coordinator/allocator invariant, memory corruption signal, stuck critical thread, impossible accounting | stop admission, bounded diagnostics/drain if safe, nonzero exit or forced termination |

### 12.1 Poison rules

Poison is monotonic for a worker/context generation. A poisoned device worker:

- cannot accept another plan, even if a later CUDA call appears successful;
- makes readiness false before affected client terminal delivery where ordering permits;
- retains all uncertain model/KV/workspace/event memory until the owner proves fences or process exit;
- drains already materialized completions only when M2 identity/fence rules say they are trustworthy;
- maps requests to stable sanitized M9 errors when the socket remains writable; and
- exits the single-worker M10 process after bounded cleanup rather than attempting in-process CUDA
  reset/reload.

Ordinary request failures never poison. An exporter, log sink, metrics scrape, or diagnostic write
cannot poison the model worker.

### 12.2 Circuit breaking and recovery

Bounded transient failures may open a component circuit after a fixed count/window from the health
policy snapshot. The circuit stops new work for a cooldown and permits only a bounded explicit probe.
Its counters/state are deterministic and observable.

In M10, automatic recovery is limited to stateless/noncritical exporters and fresh network sessions.
A tokenizer instance may be removed only after its job/thread returns and ownership is safe; no hung
thread is detached. Coordinator, KV allocator, CUDA context, and device-worker poison require process
restart. Later M14 process isolation may change that boundary.

## 13. Diagnostic snapshots

### 13.1 Safe snapshot contents

The default snapshot is privacy-safe and contains:

- schema/snapshot ID, trigger/time, build/container/system/model public fingerprints;
- redacted resolved configuration and policy generations/digests;
- immutable component health and watchdog progress/deadline snapshots;
- authoritative request lifecycle totals by state/reason, never individual prompt/output;
- queue/channel/pool/KV/workspace/session/response/sampling/telemetry current/peak/capacity;
- current/last bounded plan/ticket identities hashed for correlation, logical lengths/ranges, and
  stable error/invariant codes;
- recent fixed-ring state transitions, scheduler decisions, fault activations, and telemetry drops;
- runtime/driver/device properties already declared safe by M2, with no raw memory contents; and
- truncation, stale component, capture-duration, and write-status markers.

It excludes raw request/response bodies, messages, prompt/output/token IDs, logits, seeds, stop
strings, auth/principal values, environment, secrets, arbitrary paths, pointer values, stack/heap/core
contents, and full exception messages.

### 13.2 Consistency and capture path

A trigger receives a preallocated slot and global ordinal. The coordinator and each owner publish a
snapshot at their next safe boundary; no observer stops the world. The diagnostic worker waits only
to a configured capture deadline, then writes a complete or explicitly partial manifest using the
latest compatible component generations.

Serialization and filesystem I/O occur on one bounded diagnostic worker. Trigger queue full coalesces
the same reason and increments an exact counter. Capture failure, slow disk, full disk, permission
error, or retention cleanup failure degrades diagnostics only and never blocks inference/shutdown
beyond the separately reserved fatal record path.

Files are created through a prevalidated directory descriptor with no symlink following, restrictive
permissions, random/counter name, size limit, temporary incomplete marker, flush, and atomic rename.
Retention is bounded by file count, total bytes, and age; deletion is confined to files created under
the validated diagnostic directory and is recorded. Container deployment mounts that directory
explicitly or uses ephemeral storage.

### 13.3 Triggers

Triggers include manual signal, first transition to critical Degraded/Unhealthy/Poisoned, watchdog
soft/hard stage, invariant failure, device poison, unexpected shutdown escalation, release-test fault,
and an explicitly authorized local tool request. Repeated identical triggers within a cooldown
coalesce. No unauthenticated public HTTP route triggers diagnostics.

## 14. Reproducible trace capture and replay privacy

M10 defines two distinct formats:

### 14.1 Structural replay trace

Enabled by default within a bounded rolling window, it records coordinator-observed event order,
request/epoch/ticket hashes, arrival/deadline/priority/sampling parameter classes, prompt/output
lengths, resource snapshots, policy generations, plan logical ranges, victim/rollback decisions,
completion categories, fault sites, and terminal reasons. It contains no token IDs or text.

This trace must reproduce lifecycle, admission, scheduler, resource, cancellation, preemption, and
failure decisions in the deterministic CPU execution path. It does not claim to reproduce model logits/tokens.

### 14.2 Sensitive exact replay capsule

Exact request/model-output replay requires token IDs, effective seed, exact normalized sampling
parameters, stop-token/string data, and relevant fixtures. These values are sensitive because token
IDs can reveal text. Capsule capture is therefore:

- excluded from the production image unless explicitly built;
- off by default even in capable builds;
- accepted only from local protected configuration before startup, never a request header/API;
- restricted to an allowlisted request/test workload and bounded request/count/byte/time window;
- written only to a validated mode-0700 directory as mode-0600 files;
- labeled sensitive with model/license provenance and deletion deadline; and
- prohibited from ordinary CI artifacts unless the inputs are committed non-sensitive fixtures.

If optional at-rest encryption is implemented, its key comes from a secret provider, never config/
logs/snapshot, and encryption failure aborts capture rather than writing plaintext. M10 does not claim
that filesystem permissions alone make production prompt capture acceptable.

### 14.3 Format and replay

Both formats have schema version, endianness, checksummed length-delimited records, build/model/
tokenizer/system/policy fingerprints, monotonic event ordinal, capture completeness, and a final
digest. Unknown required fields/schema versions fail closed. Truncated files yield a bounded partial-
capture diagnosis and are never treated as complete evidence.

Offline replay performs no network access and compares canonical decisions/invariants/digests. Exact
capsule replay refuses fingerprint mismatch unless an explicit comparison mode reports—not hides—the
difference. Replay output follows the same redaction mode as input.

## 15. Deterministic fault-injection framework

### 15.1 Availability and control

Fault injection is compiled only with `INFERX_ENABLE_FAULT_INJECTION`, excluded and scan-verified from
the production container, and controlled only by a local test configuration or test harness before
threads/listeners start. No HTTP header, request JSON, environment inherited from untrusted clients,
metrics route, or signal can enable or alter a fault plan.

A fault plan contains schema/version, seed, ordered rules, global activation budget, and expected
containment. Each rule names a registry site, scope, trigger, action, and maximum duration/status. A
canonical digest appears in test logs/snapshots/replay.

### 15.2 Site registry

Stable named sites cover:

- host fixed-pool reserve/commit/release and device allocation/load-time allocation;
- M6 quota/page/table/append/reclaim prepare/commit/rollback;
- plan/workspace/metadata/event/sampling/response reservation;
- before/after CUDA launch, event record/query, D2H completion, and context error observation;
- tokenizer job enqueue/run/result, worker command/completion/acknowledgement queues;
- coordinator proposal/accept/commit, cancellation/deadline, and terminal publication;
- sampler/stop/logprob rendering, JSON/SSE serialization, socket write completion;
- telemetry queue, exporter connect/write/response, diagnostic trigger/write/rename;
- heartbeat/watchdog stage, signal intake, shutdown close/drain/join; and
- trace/replay read/write validation.

Each site declares owner thread, before/after ownership state, legal actions, expected recovery, and
whether it requires a subprocess/GPU-exclusive lane. Registry/schema drift fails tests.

### 15.3 Triggers and actions

Deterministic triggers include Nth global/site hit, request/step/ticket hashed match, lifecycle state,
resource threshold, manual-clock time, and seeded probability with fixed RNG. Actions are bounded
typed failures such as return status, reject reservation, delay under test clock, close channel,
simulate timeout, produce stale/duplicate identity, force safe completion error, fail write, or invoke
an owned test kernel/context poison.

The framework never performs arbitrary memory writes, unlocks foreign mutexes, kills a thread, frees
uncertain GPU resources, or drops an ownership-bearing message unless the site provides a tested
recovery record. Memory-corruption and truly hung process behavior use a disposable subprocess and
external timeout.

Every activation emits a nonrecursive reserved audit record before/after as ownership permits. Tests
assert the named expected containment, terminal counts, health transition, diagnostic trigger, exit
code, and resource baseline. A rule that never fires fails the test unless explicitly optional.

## 16. Signal handling and exit contract

### 16.1 Signal intake

The Linux developer-preview process blocks managed signals in worker threads and receives them through
`signalfd` or an equivalent async-signal-safe self-pipe integrated with the control event loop. The
signal path performs no allocation, logging, locking, CUDA, engine mutation, or filesystem I/O; it
publishes only a bounded control value/ordinal.

- First `SIGTERM`: stop admission/readiness and begin graceful drain.
- First `SIGINT`: stop admission and begin cancel shutdown for interactive use.
- `SIGUSR1`: request one privacy-safe diagnostic snapshot, subject to cooldown/capacity.
- `SIGHUP`: record unsupported-reload and request a safe snapshot; it does not reload config/model.
- `SIGPIPE`: ignored; socket errors follow M9 write handling.
- Fatal synchronous signals retain the platform/default crash behavior; M10 does not attempt to
  continue from memory corruption. Core dumps are disabled by default because they may contain
  secrets/tokens, with any opt-in documented as sensitive operations policy.

A second termination signal escalates drain to cancellation and closes client sockets after reserved
errors where possible. A third signal or expiration of the configured hard shutdown deadline uses the
forced-shutdown path and exit code. Signal ordinals and chosen escalation are deterministic.

### 16.2 Ordered shutdown

Shutdown extends M9's order:

1. publish exit intent, readiness false, and stop admission;
2. stop accept, new diagnostic/replay captures, policy updates, and exporter retries;
3. drain or cancel HTTP sessions and engine handles under the selected deadline;
4. drain tokenizer jobs and accepted device tickets under M2/M7 fence ownership;
5. close response/session resources and join network/tokenizer/device owners safely;
6. publish final authoritative metric/health snapshot and request one bounded telemetry flush;
7. write final safe diagnostic/report marker if already reserved and time remains;
8. close exporter/diagnostic queues, join their workers, then stop watchdog/health control;
9. verify all pools/leases/counters and select final exit category; and
10. return normally only when no uncertain ownership remains.

Telemetry flush has a short independent deadline and cannot extend engine safety deadlines. If a
critical owner is unresponsive or GPU ownership remains uncertain past fatal timeout, forced exit
does not invoke ordinary destructors for that state.

### 16.3 Stable exit categories

| Exit code | Meaning |
|---:|---|
| 0 | clean requested drain/cancel and verified resource reconciliation |
| 2 | configuration/CLI validation failure before listener |
| 3 | model/tokenizer/artifact/dependency initialization failure |
| 4 | bind/auth/security initialization failure |
| 10 | controlled runtime fatal after safe drain |
| 11 | device/worker poison requiring process restart |
| 12 | watchdog or shutdown forced termination with unsafe/unresponsive ownership |
| 13 | invariant/accounting corruption requiring restart |

Platform launch failure may use a documented shell/OCI code before InferX starts. Client errors,
ordinary request failures, rate limits, and exporter outages do not change process exit status.

## 19. Reproducible production container

### 19.1 Image construction

The release image uses a multi-stage build with digest-pinned builder/runtime bases, pinned package
and language dependencies, release compiler flags, deterministic archive order, normalized file
owners/modes/timestamps via `SOURCE_DATE_EPOCH`, and a recorded toolchain/build manifest. Two clean
builds on the declared builder platform must reproduce the application-layer digest; unavoidable
vendor/base differences are isolated and reported rather than ignored.

The runtime image contains only required InferX binaries, selected shared libraries, license notices,
CA roots when remote TLS export is enabled, and minimal runtime metadata. It excludes source, compiler,
package manager caches, shell/debug tools unless a separate debug image, tests, fault injection,
models, auth tokens, replay capsules, and build secrets. Debug symbols are a separate protected
artifact keyed by build ID.

### 19.2 Runtime security contract

- Run as a fixed non-root UID/GID with no supplemental privileges by default.
- Drop Linux capabilities, enable no-new-privileges, use a read-only root filesystem, and provide only
  explicit writable tmp/diagnostic mounts.
- Mount model artifacts read-only and validate them through M3; never bake model weights into the
  server image.
- Obtain GPU device/driver libraries from the documented host runtime and validate compatibility at
  startup.
- Inject auth/export secrets through orchestrator secret files/providers, not image layers, CLI, or
  environment dumps.
- Bind loopback by default; remote service deployment documents proxy/TLS/network policy.
- Set bounded CPU/memory/pid/file-descriptor/locked-memory limits compatible with the startup capacity
  proof; failure is explicit.

OCI labels contain source revision, build time epoch, version, license, SBOM/provenance references,
base digest, and compatibility-profile identifiers. The image entrypoint is the server binary, not a
shell wrapper that masks signals or exit codes.

## 23. Soak and developer-preview release evidence

### 23.1 Two-hour presubmit-equivalent soak

Run the workload at multiple deterministic load phases—for example low, target, near-saturation, and
bursts—with production telemetry, exporter disruptions, controlled client churn, and periodic safe
snapshots. It must complete on the owned GPU lane for changes affecting request/worker/resource paths.

### 23.2 Twenty-four-hour release soak

Run the exact candidate image/model/config with the final production telemetry sampling/export policy.
Include steady target load, scheduled near-saturation periods, long/short mixes, cancellations/
deadlines, slow/disconnected clients, exporter outages/recovery, snapshot triggers, and a bounded set
of non-destructive fault scenarios. Destructive poison/watchdog cases run in separate candidate-image
subprocesses and restart under the test supervisor.

The required result is:

- zero unexpected request loss: every admitted request reconciles to exactly one terminal audit;
- zero invariant violation, deadlock, watchdog false positive, crash, or unexplained restart;
- zero token/outcome mismatch against sampled deterministic fixture requests;
- no memory growth beyond 1% of fixed-pool committed/high-water expectations after warmup, with RSS,
  allocator, driver, pool, cache, telemetry queue, and file growth reported separately;
- no leaked connection/session/request/ticket/page/pin/response/trace/log/diagnostic lease at final
  quiescence; and
- all SLO and telemetry-overhead gates met with complete evidence.

Memory growth is evaluated after a declared warmup: every fixed-pool current-use gauge must return to
its equivalent-load baseline at quiescent checkpoints, and the last-hour versus first-post-warmup-hour
RSS/committed-memory trend may grow by no more than 1% of total configured fixed-pool bytes. Driver/
runtime retained memory, mapped model bytes, diagnostic files, and exporter buffers are reported as
separate components with absolute deltas; none may be hidden by a falling pool gauge or process
restart.

## 24. Telemetry performance methodology and gates

Compare instrumentation compiled/enabled with production settings against the same binary/config with
export/recording disabled through the supported switch. Use identical workload schedule, request
seeds, model/system fingerprint, warmup, successful request set, hardware, and trial order randomized/
paired. Telemetry configuration/digest is recorded separately and must not alter M9's behavior
fingerprint.

Measure:

- output and SLO goodput, TTFT/TPOT/end-to-end p50/p95/p99/max;
- coordinator/device/network CPU time, event-loop delay, context switches, allocations, cache misses;
- RSS/locked/pinned/device memory and fixed telemetry pool reservation/high water;
- metric update/snapshot/scrape, span/log publication, aggregation, export, redaction, and diagnostic
  costs independently;
- trace/log drop and exporter retry behavior under healthy and unavailable sinks; and
- token IDs, output text/usage, terminal reasons, scheduler plans, and lifecycle digests.

Production telemetry settings must add no more than 2% throughput loss and no more than 2% p99 latency
overhead. Telemetry on/off must produce identical tokens, usage, terminal outcomes, and deterministic
scheduler decisions for identical inputs. Exporter outage cannot stall inference or exceed queue/
memory bounds. Results outside noise/confidence are reported honestly; sampling or labels cannot be
quietly reduced after measurement without updating the declared production policy.

### 25.6 Stress, fuzz, sanitizers, and release tests

## 26. Failure-injection acceptance matrix

At minimum retain evidence for:

| Injected boundary | Expected containment |
|---|---|
| request/response/trace/log pool exhaustion before commit | rollback/reject only affected operation; exact counters |
| KV/page/workspace plan prepare rejection | M8 reverse rollback; no health degradation |
| tokenizer instance error | one request failure; quarantine instance only after safe return |
| completion queue/result corruption | reject stale/malformed identity; poison if ownership uncertain |
| CUDA prelaunch failure with no submitted work | fail batch safely; worker policy decides recoverability |
| CUDA async/context fault after launch | fail/retain uncertain batch resources, poison worker, unready, exit 11 |
| coordinator invariant/account mismatch | stop admission, safe snapshot if possible, exit 13 |
| client/socket/serializer failure | one session cancel/abandon; engine/network peers healthy |
| metrics scrape/trace/log exporter outage | bounded drop/degraded telemetry; inference ready |
| diagnostic disk full/permission/rename failure | diagnostic degraded/drop; inference ready |
| network/coordinator/tokenizer/device hard stall | soft unready/capture, hard cancel/poison, fatal exit 12 |
| termination during each prepare/commit/in-flight/write state | one terminal where writable, safe drain or bounded forced exit |

The matrix records actual health timeline, readiness, requests affected, diagnostic ID, resource
snapshot, process exit, supervisor restart, and replay seed—not only whether the process survived.

## 29. Risks and experiments

| Risk | Required evidence | Decision/fallback |
|---|---|---|
| metric updates contend on hot paths | per-owner shard/cache profile and on/off benchmark | shard/preallocate/snapshot; never weaken exact lifecycle counters |
| labels or logs leak sensitive/high-cardinality data | generated schema checks and adversarial marker corpus | allowlisted typed fields; fail build/release on leakage |
| trace exporter outage grows memory/stalls owners | queue/retry/flap stress | bounded drop/expiry and noncritical degraded state |
| tracing spans explode with output length | max-output sampled stress | bounded events/trace and one truncation marker |
| watchdog fires on valid long GPU work | shape upper-bound calibration and soak | capability-specific thresholds/safety factor; reject unbounded work |
| watchdog cannot safely drain hung CUDA | subprocess real-fault test | retain uncertain memory and forced exit; supervisor restart |
| snapshot capture is inconsistent | generation/stale/partial replay tests | owner safe-point snapshots and explicit completeness markers |
| diagnostics fill disk or follow unsafe path | full-disk/symlink/retention tests | validated directory descriptor and bounded degradation |
| replay usefulness conflicts with privacy | structural-vs-exact reproduction matrix | safe structural default; protected fixture-only exact capsules |
| fault injection escapes test environment | release binary/image symbol/config scan | compile out, no remote control, fail release if present |
| signal escalation duplicates cleanup | signal at every lifecycle state under TSan | one shutdown controller/ordinal and generation-safe callbacks |
| reproducible image differs due vendor/base inputs | two-build diff/provenance analysis | pin/isolate/report exact nonreproducible layer; no false claim |
| telemetry 2% gate misses due sampling/log rate | component microprofiles and paired runs | optimize implementation; declared production policy cannot change post hoc |
| 24-hour RSS grows despite fixed pools | pool/driver/RSS decomposition | fix leak or document verified bounded driver behavior; do not average away growth |

## 31. Definition of done

### Metrics, traces, logs, and privacy

- [ ] Metric schema names/units/labels/buckets/cardinality are generated, fixed, documented, and
      exactly reconcile every admitted/active/terminal/resource lifecycle.
- [ ] One sampled request correlates across every required stage with bounded W3C context/span/event
      behavior; exporter failure only drops telemetry within limits.
- [ ] Structured JSON logs are valid, rate-limited, correlated, and pass the adversarial redaction
      corpus with no prompt/output/token/credential/raw-body/secret leakage.
- [ ] Telemetry snapshots/scrapes/exporters never lock mutable engine state, query CUDA, block request
      owners, or change tokens/outcomes/scheduler decisions.

### Health, containment, diagnostics, and shutdown

- [ ] Component aggregation and readiness match every normal/degraded/unhealthy/poison/drain state;
      ordinary request errors do not degrade readiness.
- [ ] Every watched owner has meaningful monotonic progress and calibrated soft/hard/fatal behavior;
      injected stalls reach documented unready/drain/poison/exit without unsafe recovery.
- [ ] Poisoned workers cannot accept work, uncertain resources remain owned until safe drain/process
      exit, and all fault scenarios have bounded terminal containment.
- [ ] Safe snapshots and structural replay are bounded, consistent/explicitly partial, filesystem-
      safe, and privacy-clean; sensitive capsule capability remains protected/off by default.
- [ ] Signals and repeated escalation produce one ordered shutdown, stable exit code, no duplicate
      terminal action, no detached thread, and exact final resource reconciliation when safe.

### Release and evidence

- [ ] Production image is reproducible under declared inputs, minimal, non-root, read-only capable,
      capability-dropped, signal-correct, fault-injection-free, and contains no model or secret.
- [ ] Dependency lock, SBOM, license, vulnerability, provenance, compatibility, and conformance reports
      are complete and tied to the candidate image/model/source digests.
- [ ] Versioned workload/SLO and load-generator inputs contain exact numeric targets before candidate
      evaluation; capacity curves and exclusions are honest/reproducible.
- [ ] Production telemetry overhead is <=2% for throughput and p99 latency, and exporter outage cannot
      stall inference or exceed memory bounds.
- [ ] Two-hour and 24-hour soaks have zero unexpected loss, invariant violation, crash, false watchdog,
      token mismatch, or unexplained restart, and memory growth is <=1% of fixed pools after warmup.
- [ ] Developer-preview bundle, operational runbook, known limitations/exceptions, ADRs 0064-0072,
      schemas, tests, minimized seeds, and evidence all match the implementation.

## 32. Handoff to M11

M10 hands M11 an observable and failure-contained single-worker serving baseline: exact metrics,
bounded tracing/logging, health/watchdog state, deterministic scheduler/resource replay, safe
diagnostics, fault injection, container/supply-chain evidence, a declared workload/SLO, and a release
runbook.

M11 may add cross-request prefix caching, cache namespaces, page sharing/pins/eviction, cache-aware
scheduling, reset/debug operations, and cache telemetry. It must extend the fixed metric/log/trace/
health schemas without dynamic prefix/request labels, keep telemetry on/off token-identical, include
cache state in safe structural snapshots without token/prompt leakage, register every cache fault site,
make cache corruption/namespace violation affect readiness according to the containment matrix, and
preserve M10's container, soak, privacy, watchdog, and preview-evidence gates.
