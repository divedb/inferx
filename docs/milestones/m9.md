# M9 implementation specification: baseline sampling and OpenAI-compatible HTTP serving

- Status: proposed implementation contract
- Roadmap milestone: M9 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M8](m8.md), including M1-M7 transitively
- Immediate consumer: M10 observability, failure containment, and developer preview
- Later consumers: M11 prefix caching, M12 CUDA graphs/GPU sampling, M13 quantization/model expansion,
  and M14 worker processes

This document turns M9 into an executable engineering plan. It defines deterministic CPU sampling,
penalties and filters, stop handling, requested log probabilities, a versioned OpenAI-compatible API
subset, bounded Boost.Asio/Beast HTTP/1.1 and SSE serving, simdjson request parsing, authentication and
admission hooks, error mapping, health/readiness, shutdown, configuration, an open-loop load generator,
tests, evidence, and the handoff to M10.

M9 adds a protocol adapter and a complete baseline token-selection policy. It does not replace the
M7/M8 engine, make deadlines hard real-time, add tool calling or multimodal input, or move mutable
request/KV state into network or sampling threads.

## 1. Outcome

At the end of M9, a supported InferX process can:

1. select the next token on CPU using a deterministic, versioned algorithm covering temperature,
   top-k, top-p, optional min-p, repetition/frequency/presence penalties, logit bias, and per-request
   seeds;
2. preserve M5 greedy behavior exactly when stochastic sampling is disabled;
3. enforce model EOS, minimum/maximum output tokens, explicit stop-token IDs, and stop strings that
   can cross tokenizer, UTF-8, and streamed response boundaries without retracting bytes;
4. return requested sampled-token and top-token log probabilities from the exact distribution used
   for selection;
5. expose versioned `/v1/completions`, `/v1/chat/completions`, and model-discovery behavior over a
   documented OpenAI-compatible subset;
6. stream well-formed SSE chunks ending in `[DONE]` on success and produce an equivalent bounded
   non-streaming response;
7. map validation, authentication, admission, timeout, cancellation, model, tokenizer, scheduler,
   and execution outcomes to stable HTTP/protocol errors without leaking internal diagnostics;
8. keep every parser buffer, connection, request, response, timer, sampling snapshot, and outbound
   byte queue within configured per-object and global limits;
9. cancel or abandon engine work when a client disconnects or exceeds write/backpressure policy,
   without blocking the coordinator or GPU; and
10. measure protocol overhead and open-loop behavior against the embedded M8 API with reproducible
    conformance and performance evidence.

```text
TCP accept -> bounded HTTP connection/session -> strict route/header/body validation
                                            -> simdjson parse into owned protocol request
                                            -> protocol validation/normalization
                                            -> M8 AsyncEngine submission
                                                        |
                                                        v
                                  immutable sampling snapshot in accepted step
                                                        |
                                    logits -> deterministic CPU sampling result
                                                        |
                                                        v
                                  M7 ordered response events / terminal outcome
                                                        |
                          +-----------------------------+----------------------------+
                          |                                                          |
                          v                                                          v
             bounded SSE serializer/pump                                bounded final accumulator
                          |                                                          |
                          +----------------------- HTTP write ------------------------+
                                                   |
                               success `[DONE]`, error close, or disconnect cancellation
```

M9 is complete only if fixed-seed outputs are independent of batch composition and preemption,
protocol behavior matches the checked-in compatibility suite, and slow/malformed/disconnected clients
cannot produce unbounded memory, coordinator stalls, duplicate terminals, or leaked engine resources.

## 2. Scope boundaries

### 2.1 In scope

- CPU reference and production baseline sampling from FP32 logits copied under M5/M7 fence rules.
- One immutable sampling configuration and RNG stream per request.
- Temperature, top-k, top-p, min-p when the InferX extension is enabled, repetition penalty,
  frequency penalty, presence penalty, bounded logit bias, and seed.
- Model EOS, minimum/maximum generated tokens, explicit stop-token IDs for the embedded extension,
  stop strings, usage accounting, and requested logprobs.
- HTTP/1.1 keep-alive with one active request per connection, JSON requests, JSON responses, and SSE.
- `/v1/completions`, `/v1/chat/completions`, `/v1/models`, `/v1/models/{model}`, liveness, and
  readiness routes with an explicit compatibility version.
- Bounded parser/serializer/session/timer/admission resources and network-specific slow-client policy.
- Optional static bearer authentication plus replaceable authentication/admission hooks.
- Global connection/request/rate/concurrency limits and stable overload responses.
- Plaintext loopback-default serving; secure reverse-proxy deployment is documented.
- CLI/config documentation and a separate HTTP load generator with open-loop arrivals.

### 2.2 Explicitly out of scope

- TLS termination, HTTP/2, HTTP/3, WebSocket, gRPC, request/response compression, browser CORS, or a
  reverse proxy. These may be provided externally and are not implied by OpenAI compatibility.
- Multiple choices (`n > 1`), `best_of`, beam search, prompt batching, suffix insertion, prompt echo,
  tool/function calling, structured output, JSON schema, audio/image/file content, embeddings, or
  moderation.
- Multi-tenant fairness, distributed rate limits, quota billing, account lookup, dynamic keys, OAuth,
  or an administrative API.
- GPU sampling, graph-captured sampling, speculative decoding, grammar-constrained decoding, or
  custom sampler plugins.
- Re-tokenizing generated text to compute penalties, reconstructing token IDs from streamed bytes,
  or changing committed tokens after client-visible output.
- A network thread directly mutating request FSM, scheduler, KV, sampling state, or response mailbox.
- Unbounded HTTP pipelining, an unbounded task per connection, one blocking thread per socket, or
  waiting for a slow client on the coordinator/device worker.
- Production-grade metrics/tracing/log aggregation, watchdogs, signals, containers, and operational
  runbooks beyond the minimum health and bounded diagnostics required here; M10 owns them.

## 6. Sampling parameter contract

The internal immutable `SamplingParams` value is normalized before engine admission. It contains:

| Field | Default / accepted range | Meaning |
|---|---|---|
| `temperature` | 1.0; finite `[0, 2]` | zero selects deterministic greedy after bias/penalties |
| `top_k` | 0; `0..min(vocab, configured max)` | zero disables; otherwise keep stable best K |
| `top_p` | 1.0; finite `(0, 1]` | retain smallest stable prefix reaching cumulative mass |
| `min_p` | 0.0; finite `[0, 1]` | zero disables; threshold relative to maximum remaining probability |
| `repetition_penalty` | 1.0; finite `[0.01, 100]` | sign-aware multiplicative penalty for seen tokens |
| `frequency_penalty` | 0.0; finite `[-2, 2]` | subtract value multiplied by prior occurrence count |
| `presence_penalty` | 0.0; finite `[-2, 2]` | subtract value once when token has appeared |
| `logit_bias` | empty; bounded token map with values in `[-100, 100]` | additive before penalties; duplicate token key invalid |
| `seed` | generated at admission if absent | exact unsigned 64-bit normalized seed |
| `min_output_tokens` | 0; `0..max_output_tokens` | masks normalized model EOS until minimum is reached |
| `max_output_tokens` | server default; `1..configured maximum` | hard generated-token cap |
| `stop_token_ids` | empty; bounded unique in-vocabulary list | user stop after minimum policy described below |
| `stop_strings` | empty; bounded ordered unique UTF-8 strings | client-visible byte exclusion and termination |
| `return_logprobs` | false | include selected-token probability metadata |
| `top_logprobs` | 0; `0..configured maximum` | number of alternatives; requires logprobs enabled |

All floating fields reject NaN and infinity. Numeric JSON values that cannot be represented exactly
under the documented conversion rule are rejected rather than wrapped. Token IDs are validated
against the loaded model vocabulary before an active engine slot or KV quota is committed.

`top_k` and `min_p` are implemented by the engine baseline but exposed over HTTP only when the named
InferX extension profile is enabled. The standard profile rejects them as unsupported fields.
Embedded callers may use them through the typed API.

The normalized sampling version, values, effective seed, stop-list digest, requested logprob bound,
model/tokenizer fingerprint, and penalty-history generation become part of the request's immutable
sampling identity and replay trace.

## 7. Penalty history and immutable sampling snapshots

Penalties operate on token IDs, never decoded strings. The initial policy counts the full prompt plus
all committed generated tokens. Special tokens are counted exactly like other IDs unless an accepted
future sampling version says otherwise.

Each request owns a bounded penalty state containing canonical token-ID/count pairs:

- token IDs are unique and ordered ascending in durable snapshots;
- counts use checked integers and equal the occurrences in immutable prompt plus committed output;
- prompt counts are constructed once after tokenization and before engine admission;
- one sampled token is added only in the same no-fail transaction that commits that output token;
- cancellation/failure or a drained, uncommitted completion does not alter counts; and
- M8 recomputation/preemption does not add counts because it rebuilds KV for already known tokens.

The coordinator is the only mutator. For an accepted execution ticket it freezes and pins a
generational read-only sampling snapshot containing parameters and the affected token/count pairs.
The CPU sampler resolves only this strong handle; it never dereferences `RequestContext` or changes
history. The coordinator cannot update/reuse the slot until completion acknowledgement releases the
pin.

Storage is capacity-proved at startup from active-request, context, vocabulary, logit-bias, and
selected-sequence limits. Sparse state is bounded by `min(history length, vocabulary size)`. Snapshot
arenas, logits rows, candidate scratch, logprob results, and completion records are preallocated for
the maximum admitted batch. No per-token heap allocation is permitted on the sampling hot path.

## 8. Exact sampling algorithm

ADR 0056 defines the normative algorithm and a separate small reference implementation used only by
fixtures. The production CPU path must produce the same selected token and logprob values within the
declared tolerance.

### 8.1 Input validation

For each sequence, the sampler receives exactly one contiguous FP32 logits row of vocabulary length.
It verifies the row length and snapshot/ticket generations. Any NaN is a request-scoped `DataLoss`
failure with no token commit. If one or more selectable adjusted logits are positive infinity, those
tokens receive equal probability and every finite/negative-infinity token receives zero before
filters. Without positive infinity, negative infinity receives zero normally. An all-negative-
infinity/no-selectable row fails rather than inventing a fallback token. Fixtures cover each case.

### 8.2 Transform order

Transforms occur in this fixed order:

1. copy/convert the FP32 row into the preallocated working representation;
2. apply bounded additive `logit_bias` by token ID;
3. apply repetition penalty to every token with nonzero history count: divide a positive logit by
   the penalty and multiply a negative logit by it;
4. subtract `frequency_penalty * count` for every seen token;
5. subtract `presence_penalty` once for every seen token;
6. mask normalized model EOS IDs while committed output count is below `min_output_tokens`;
7. if temperature is zero, choose the greatest adjusted logit with lowest token ID on an exact tie;
8. otherwise divide adjusted logits by temperature and compute stable softmax using maximum
   subtraction and deterministic FP64 accumulation in token-ID order;
9. apply top-k with probability descending and token ID ascending tie order;
10. renormalize, apply top-p by retaining the smallest stable prefix whose cumulative probability is
    at least `top_p`, always retaining at least one token;
11. renormalize, apply min-p by retaining probabilities at least `min_p * maximum_probability`,
    always retaining the maximum token;
12. renormalize the final distribution in token-ID order; and
13. select the first token whose cumulative probability is strictly greater than the request RNG
    variate, scanning token IDs ascending and forcing the final survivor only for rounding residue.

Filtering sets excluded probabilities to zero. Every renormalization validates a finite positive
sum. Filter ties, the exact comparison at cumulative boundaries, and floating-point rounding are
locked by fixtures. Changing the order or accumulator requires a new sampling version.

For `temperature == 0`, bias and penalties still apply, but temperature division and top-k/top-p/
min-p filtering are bypassed. This preserves M5's lowest-ID greedy tie behavior when bias is empty
and all penalties have their defaults.

### 8.3 Counter-based RNG

The baseline uses Philox4x32-10 with a key derived from the normalized 64-bit seed and sampling
version. The counter contains the zero-based committed output position and a fixed substream tag.
The uniform variate is formed from a specified 53-bit integer mapping into `[0,1)`; no standard-library
distribution is used.

Consequences:

- the same model fingerprint, prompt tokens, normalized parameters, seed, and sampling version produce
  the same token sequence regardless of batch peers, chunking, preemption, or thread scheduling;
- a cancelled/uncommitted attempt does not consume RNG state;
- replay can evaluate output position directly without replaying a mutable global RNG; and
- absent seeds are generated once from the configured secure system source at coordinator admission,
  stored in request state, and recorded in protected trace metadata.

Failure to obtain an automatic seed rejects admission. The seed is not treated as a secret, but it is
not added to ordinary high-cardinality metrics.

### 8.4 CPU execution ownership

The initial production sampler runs on the M7 device-worker host phase after the final logits D2H
fence and before the atomic completion batch is published. This retains the existing one-step
ownership graph and avoids sending full vocabulary rows through another queue.

The sampler may read only pinned immutable sampling snapshots and ticket-owned logits/scratch. It
returns selected token ID, selected logprob when requested, stable top alternatives, sampling version,
seed position, and status in the completion item. It does not mutate penalty history, output, FSM, KV,
mailbox, or tokenizer state. Those commit only on the coordinator after complete identity validation.

CPU sampling cost is part of TPOT. Moving it to a bounded pool or GPU is a later ADR and must preserve
the exact ownership and reference semantics; M9 does not silently select a different path under load.

## 9. Logprob semantics

Requested logprobs describe the final normalized distribution used to choose the token after bias,
penalties, temperature, and enabled filters. Filtered tokens have probability zero and logprob
negative infinity. In greedy mode, the selected token has logprob zero and all others negative
infinity under this API profile.

The result contains:

- sampled token ID and its natural-log probability;
- up to `top_logprobs` alternatives ordered by probability descending, token ID ascending;
- the sampled token even when it would not otherwise fit the alternative count;
- a flag distinguishing ordinary finite, zero-probability, and positive-infinity normalization cases;
  and
- exact output position and sampling-version identity.

The configured maximum alternatives is small and capacity-proved. A response may therefore contain
at most `top_logprobs + 1` token entries per generated token. Duplicate sampled/alternative IDs are
removed deterministically.

Protocol rendering uses M3's qualified tokenizer operation to obtain owned token text/byte values.
Rendering is prepared with bounded storage before the output token commit. Invalid UTF-8 token pieces
use the endpoint's documented replacement/token-bytes representation; raw arbitrary bytes never make
the JSON invalid. A rendering failure aborts that token commit and fails the request after safe ticket
drain.

When logprob serving is enabled, model readiness builds an immutable render table for every vocabulary
ID using one qualified tokenizer instance. Each entry contains bounded valid display text and the
original bounded byte sequence when available. Total entries/bytes are checked against model and
server limits and included in the tokenizer/system fingerprint. Failure to build the complete table
disables readiness for a configuration that advertises logprobs; the coordinator never blocks on a
tokenizer worker to render alternatives after a GPU completion.

Logprob numeric serialization uses locale-independent shortest round-trip formatting for finite
values. Negative-infinity alternatives are omitted under the rules below; JSON never contains bare
NaN or infinity.

For the legacy completions shape, logprobs are parallel per-sampled-token arrays: rendered token,
finite selected-token logprob, a bounded object of rendered alternative token to finite logprob, and
a visible-text offset measured in Unicode scalar values. If different
token IDs render to the same object key, keep the higher-probability entry, break an exact tie by lower
token ID, and return fewer than the requested maximum rather than inventing a key. `text_offset` is
the count of visible Unicode scalar values published before that sampled token was processed; several
tokens may share an offset when incremental decoding buffers bytes. Metadata still contains a
committed sampled token whose bytes were partly/fully suppressed by a stop match, and suppressed bytes
do not advance later offsets.

For chat, each committed sampled token uses the profile's content-logprob entry: rendered token,
finite logprob, nullable array of original token bytes, and an ordered array of top alternatives with
the same fields. Invalid/non-text token bytes are represented through the bytes array and a valid
replacement token string; they are never inserted raw into JSON. Negative-infinity alternatives are
omitted from both protocol shapes, so greedy mode normally returns only the selected token even when
a larger alternative count was requested. “Top” is a maximum, not a promise of exactly that count.

## 10. Termination and stop semantics

### 10.1 Generated-token accounting

`completion_tokens` is the number of sampled tokens committed by the engine, including a committed
EOS/stop token and a token whose decoded bytes cause a stop-string match. Suppressing stop bytes does
not roll back the token or KV/output accounting. `prompt_tokens` is the exact post-template encoded
prompt length. `total_tokens` is their checked sum.

Minimum output tokens mask only normalized model EOS IDs until the minimum is reached. Explicit user
stop-token IDs and stop strings remain active from the first output token; this distinction is part of
the compatibility profile. Maximum output tokens always apply.

### 10.2 Stop-token and finish precedence

After a sampled token and its decoded bytes are prepared, terminal conditions are classified in this
order for internal audit:

1. normalized model EOS, if no longer masked;
2. explicit user stop-token ID;
3. stop-string match;
4. maximum output length; and
5. continue.

The byte stop matcher still runs before publication even when an earlier token condition applies, so
no forbidden stop-string bytes leak. If more than one condition is true, the first internal reason is
retained. Model EOS, stop token, and stop string all map to public `finish_reason="stop"`; maximum
length maps to `"length"`. Cancellation, deadline, and failures use protocol errors, not a fabricated
normal finish reason.

### 10.3 Streaming stop-string matcher

Stop strings are nonempty valid UTF-8 byte strings, kept in request order, deduplicated by exact bytes,
and bounded by count, per-string bytes, and aggregate bytes. Matching is exact and case-sensitive; no
Unicode normalization is performed.

One request-confined matcher consumes only stable bytes returned by M3's incremental decoder. It keeps
a bounded pending suffix and guarantees:

- bytes are published only when they cannot become part of any future stop match;
- a match spanning tokens, decoder pushes, or UTF-8 code points is recognized;
- the earliest byte position wins; matches beginning at the same position choose the lowest original
  stop-list index;
- bytes before the match are emitted, the matched bytes and all later bytes from that prepared token
  are suppressed, and no previously emitted byte is retracted;
- without a match, it retains the longest suffix that is a prefix of at least one stop string, plus
  any incomplete UTF-8 boundary needed for a valid JSON string; and
- memory and per-byte work remain bounded by the configured aggregate stop bytes through a prepared
  automaton, not repeated unbounded rescanning.

On normal EOS/length, M3 decoder `Finish()` bytes pass through the same matcher. If they complete a
stop match, stop classification applies before terminal serialization. Otherwise all unmatched valid
pending bytes are emitted before the terminal response. On cancellation/error, previously committed
bytes remain valid but pending unpublished suffix need not be exposed; the terminal error is
authoritative.

## 11. Compatibility profile and endpoint inventory

M9 ships a named, versioned compatibility profile, recorded in server startup output, every golden
fixture manifest, and the `system_fingerprint` response field. “OpenAI-compatible” means the exact
documented subset below; it does not mean silently ignoring every field accepted by any OpenAI API
revision.

| Method and route | Authentication | Behavior |
|---|---|---|
| `POST /v1/completions` | required when configured | one text or token-ID prompt, one choice |
| `POST /v1/chat/completions` | required when configured | ordered text-only messages through M3 template |
| `GET /v1/models` | required when configured | one loaded ready model descriptor or bounded list |
| `GET /v1/models/{model}` | required when configured | exact configured model ID lookup |
| `GET /health/live` | configurable, default unauthenticated | process/event-loop liveness only |
| `GET /health/ready` | configurable, default unauthenticated | engine/model admission readiness |

Unknown routes return a stable 404; known routes with a wrong method return 405 plus `Allow`.
Trailing-slash and percent-decoding behavior is fixed by the route ADR. Query parameters are rejected
unless explicitly documented for the health endpoint. The API never falls back from chat to raw text
or invents a missing chat template.

## 12. Common request validation

Every generation request requires:

- exact `model` string matching a loaded public model ID;
- one valid prompt representation for the selected endpoint;
- normalized sampling/output/stop/logprob parameters within server limits; and
- successful authentication, global admission policy, body parsing, tokenizer processing, M8
  feasibility/admission, and M7 response-capacity reservation.

Common supported fields are `model`, `stream`, `temperature`, `top_p`, `stop`, `seed`,
`frequency_penalty`, `presence_penalty`, `logit_bias`, and `user` under the limits below. `user` is an
opaque valid UTF-8 string used only as a bounded, redacted/hashable audit value; it never changes
scheduling or model input.

Common rules:

- missing optional fields use profile defaults; JSON null is accepted only where listed explicitly;
- duplicate object member names are rejected at every semantic object level;
- unknown fields are rejected with `param` naming the field, except a documented inert compatibility
  field explicitly listed by the profile;
- booleans are not accepted as numbers and integral fields reject fractional or out-of-range values;
- strings require valid UTF-8, bounded byte length, and no embedded NUL where passed to platform APIs;
- `stop` is one string or an array of up to the configured count; null/missing means none;
- `n` may be missing or exactly 1; any other value is explicitly unsupported;
- `stream` defaults false; `stream_options.include_usage` is supported only with streaming; and
- conflicting legacy/current aliases are rejected instead of choosing by member order.

The standard HTTP seed is a nonnegative JSON integer no greater than `INT64_MAX`, normalized into the
internal 64-bit key. The embedded typed API may provide the full unsigned domain. An omitted seed uses
the generated value described in section 8; negative, fractional, or imprecise JSON seeds are invalid.

The server rejects unsupported `best_of`, `suffix`, `echo`, `tools`, `tool_choice`, `functions`,
`function_call`, `response_format`, multimodal content, `store`, and other unimplemented semantic
fields with a stable `unsupported_parameter` error. An allowlist is versioned with the profile.

## 13. `/v1/completions` contract

### 13.1 Request

`prompt` is required and is either one UTF-8 string or one nonempty array of integer token IDs.
Arrays representing multiple prompts and nested prompt batches are unsupported. Token IDs are copied
and vocabulary-validated through M3.

`max_tokens` selects maximum output and defaults to the configured server value. A profile may accept
`max_completion_tokens` as an alias only if exactly one is present. `min_tokens`, `top_k`, `min_p`,
`repetition_penalty`, and `stop_token_ids` are accepted only in the explicitly enabled InferX
extension profile.

`logprobs` is absent/null/false for none or an integer alternative count within the configured bound.
The profile does not support prompt logprobs or echo in M9. `n` must equal one.

### 13.2 Non-streaming response

The success object contains stable ID, object type, injectable wall-clock creation seconds, public
model ID, system fingerprint, one choice at index zero, generated text, public finish reason, optional
logprobs, and exact usage. Response IDs derive from a collision-resistant server request identity,
not user input or pointer values.

The full generated text is the concatenation of published decoder/stop-matcher bytes. Stop text is
excluded. The server accumulates it in a reservation made before engine admission; it never grows an
unbounded string as tokens arrive.

### 13.3 Streaming response

Every data event has completion-chunk object type, the same ID/model/fingerprint/creation values,
one choice at index zero, an ordered text delta, optional per-token logprobs, and null finish reason.
Empty text with nonempty logprobs is legal. The final JSON chunk contains an empty delta and the finish
reason. When `include_usage` is requested, the profile emits the documented final usage chunk before
`[DONE]`; otherwise usage is omitted from chunks. Exactly one `data: [DONE]` follows a successful
terminal chunk.

## 14. `/v1/chat/completions` contract

### 14.1 Request and prompt construction

`messages` is a required nonempty ordered array. The initial profile accepts only `system`, `user`,
and `assistant` roles with string `content`, matching M3's closed role set. Names, content-part arrays,
images/audio/files, tool calls, function calls, refusals, and developer-specific fields are
unsupported unless M3 and this profile explicitly add them together.

The exact loaded artifact chat template is required. Protocol parsing creates an owned `ChatPrompt`;
M3 renders the template once, validates UTF-8/special tokens, and tokenizes once. Missing/unsupported
template is a request/model capability error, never a guessed formatting fallback.

`max_completion_tokens` is the preferred maximum. The compatibility profile may accept legacy
`max_tokens`; supplying both is invalid. `logprobs` is boolean and `top_logprobs` is a bounded integer
requiring `logprobs=true`. The InferX extension parameters follow section 13.

### 14.2 Non-streaming response

The success object contains stable ID, chat-completion object type, creation time, model and system
fingerprint, one choice at index zero, an assistant message with accumulated content, optional
logprobs, public finish reason, and exact usage. No tool/refusal fields are synthesized.

### 14.3 Streaming response

The first successful choice delta establishes `role="assistant"` and may also contain the first
content bytes. Later deltas contain only ordered content/logprob fields needed by the profile. A final
choice delta contains no content and has the public finish reason. Optional usage and `[DONE]` follow
the same rule as completions. Role, content, finish, and usage order is golden-tested for empty decoder
pushes, multi-byte boundaries, EOS, length, and stop-string termination.

## 15. Model discovery and system fingerprint

`/v1/models` returns only models that are configured for public discovery. Each entry has the public
model ID, object type, stable creation metadata from model load/config, and configured owner label.
`/v1/models/{model}` uses exact decoded path-segment equality and never interprets filesystem paths.

Generation requests may target only a loaded model whose engine instance is admitting requests.
Unknown ID is `model_not_found`; known but loading/unready is `model_not_ready`. M9's initial process
may serve one model, but the response format and registry lookup do not hard-code that assumption.

`system_fingerprint` is a bounded opaque digest over model package, tokenizer/template, operator/
numeric policy, sampling version, compatibility profile, and relevant scheduler/backend generation.
It contains no path or secret. It changes when behavior capable of changing tokens or response
semantics changes and remains stable across requests for one published server configuration.

## 16. HTTP parsing and protocol normalization

Boost.Beast performs incremental HTTP framing with header/body limits installed before bytes are
accepted. simdjson parses one complete owned/padded body only after framing completes. On-demand views
never outlive that buffer; every value crossing an asynchronous boundary is copied into bounded owned
protocol values.

The parser enforces:

- HTTP/1.1, origin-form target, configured target/header/count/body limits, and one Host header;
- `Content-Type: application/json` with documented optional UTF-8 charset for generation routes;
- no content encoding and no ambiguous simultaneous framing headers;
- complete JSON with one root object, valid UTF-8, no trailing non-whitespace, and duplicate-key
  rejection;
- checked numeric conversions and operation/allocation budgets for nested arrays/maps;
- a fixed maximum message count/content bytes, stop bytes, bias entries, and token-ID prompt length;
- route-specific allowlists and semantic cross-field validation; and
- sanitized bounded errors that do not echo whole request bodies, authorization values, or prompts.

Both Content-Length and valid chunked request framing may be supported by Beast under the same decoded
body limit. A slow header/body timer closes incomplete requests. The server does not begin engine
admission until the final body is validated and normalized.

## 17. Server topology and ownership

The baseline uses one configured Asio `io_context`, a fixed network thread count, one acceptor, and a
fixed session pool. Asynchronous handlers are serialized per session through an executor/strand. There
is no blocking read/write and no thread created per connection.

One session owns:

- socket and generation-checked session slot;
- fixed parser/header/body buffers within configured maxima;
- header/body/idle/write timers;
- at most one normalized protocol request and one engine handle;
- one bounded serialized-output queue and one write in progress;
- response ID/profile/model values; and
- explicit state for read, submitting, streaming/accumulating, terminal write, keep-alive reset, and
  close.

HTTP keep-alive is supported for sequential requests. Only one request is active per connection;
the session does not parse/submit the next request until the prior response is fully written and its
engine handle released. Pipelined bytes remain bounded by the parser buffer and are processed in
order or rejected according to ADR 0060; they never create concurrent hidden requests.

All cross-thread messages are values or strong generation handles. Network code calls only public
`AsyncEngine` submit/cancel/handle operations. Engine events are consumed by a bounded response pump;
the coordinator never calls an Asio handler or writes a socket.

## 18. Response pump, serialization, and backpressure

Each admitted HTTP request reserves worst-case protocol record and byte capacity derived from maximum
output tokens, tokenizer maximum bytes, requested top logprobs, JSON escaping expansion, fixed
envelope overhead, and terminal/error/`[DONE]` records. Impossible reservations reject before engine
admission.

The response pump obtains already-finalized M7/M9 events in order; stop matching, incremental decode,
logprob rendering, usage, and token commit have already been prepared by the coordinator. The pump
does not reinterpret tokens or finish reasons. It serializes into fixed-capacity owned chunks using
locale-independent formatting, escapes every JSON control character, validates all strings, and never
emits a partial JSON or SSE record.

One session has exactly one asynchronous write chain. A serialized chunk remains owned until Beast's
completion handler consumes it. Events are not reordered or coalesced in a way that changes protocol
boundaries defined by the compatibility profile.

### 18.1 Slow clients

The outbound queue has byte/record high-water limits and a write-progress deadline. If it cannot
accept the next reserved record or a write makes no progress before the deadline:

1. mark the session response as failed once;
2. post idempotent cancellation through the engine handle;
3. detach/abandon external delivery and arrange bounded internal handle drain;
4. cancel socket operations and close the connection; and
5. release network/protocol reservations only after callbacks and handle generations are safe.

The engine may finish or safely drain already accepted GPU work, but no network thread waits for it.
M7's mailbox capacity prevents coordinator blockage during the race. Slow clients consume bounded
capacity and eventually lose their connection; accepted response data is never dropped while the
connection is still advertised as successful.

### 18.2 Non-streaming accumulation

Non-streaming output uses a pre-reserved accumulator sized by the same admission proof. Engine deltas
and logprobs append through checked no-fail operations. Only after a normal terminal does the server
serialize/write one success response. An engine error before that produces an error response instead;
partial model text is not returned as a successful completion.

## 19. SSE framing and terminal behavior

Successful streaming uses status 200 and `Content-Type: text/event-stream; charset=utf-8`, disables
cache, and writes each protocol chunk as exactly one `data:` record terminated by a blank line. The
JSON itself contains no unescaped newlines. Optional heartbeat comments are disabled in the initial
profile because they alter golden wire output.

SSE headers commit only after `AsyncEngine` accepts the request and all protocol/output reservations
are owned. Parse, authentication, rate, immediate engine-admission, and queue-capacity failures can
therefore use ordinary HTTP errors. Tokenizer/template, later deadline, scheduler, sampler, and
execution failures after that point use the post-header rule below.

Before response headers commit, any failure maps to an ordinary JSON HTTP error. After SSE headers:

- normal engine termination writes the final finish chunk, optional usage chunk, then exactly one
  `[DONE]` record;
- request cancellation/deadline/internal failure writes one versioned SSE error object if the socket
  and reserved output capacity are still writable, then closes without `[DONE]`;
- serialization failure or socket write failure closes immediately and posts cancellation; and
- peer EOF/reset/timeout never fabricates a terminal wire event and never writes after close.

`[DONE]` therefore means successful protocol completion, not merely connection shutdown. One atomic
session terminal flag prevents duplicate final chunk, error event, `[DONE]`, cancellation, or close
callbacks.

## 20. Authentication, admission, and limits

### 20.1 Binding and authentication

The default bind address is loopback. Binding a non-loopback address requires either configured
bearer authentication or an explicit `allow_insecure_non_loopback` acknowledgement. TLS is expected
at a trusted reverse proxy for remote deployments.

The baseline authentication hook supports a fixed set of bearer-token digests loaded from a
permission-checked file or secret environment source before the listener opens. Plain tokens are
never printed, stored in request objects after validation, or accepted as ordinary CLI arguments.
Comparison is constant-time over normalized bounded digests. Missing/malformed credentials and valid-
format unknown credentials share the configured sanitized 401 response.

Health-route authentication is separately configurable. The hook returns a bounded principal ID for
rate accounting; the raw credential never becomes a metric label.

### 20.2 Limit layers

Limits are applied in this order:

1. global open connections and per-source connection hook;
2. header bytes/count/line and header deadline;
3. body bytes and body deadline;
4. authentication and global/principal request-rate bucket;
5. parsed field/message/prompt/stop/bias/logprob/output limits;
6. active HTTP request and streaming connection limits;
7. protocol response-byte reservation;
8. M7/M8 engine admission, deadline feasibility, KV, and response reservation; and
9. write queue and progress deadline.

Every successful acquisition has one generation-tagged lease released on all parse, rejection,
disconnect, completion, and shutdown paths. Rate buckets use the monotonic clock, checked fixed-point
arithmetic, bounded cardinality, deterministic refill, and a documented idle-entry eviction policy.
Rate rejection returns 429 and a bounded `Retry-After` when calculable.

### 20.3 Request deadline

The server assigns a monotonic engine deadline from configured total request timeout, clamped to the
server maximum. An authenticated InferX deadline header may request a shorter duration when extensions
are enabled; it cannot lengthen the server deadline. Time spent parsing, authenticating, waiting for
admission, tokenizing, scheduling, sampling, serializing, and writing is included according to the
documented timer split.

Expiry before engine admission rejects directly. Expiry after admission posts M7/M8 deadline/
cancellation and observes normal drain ownership. A client socket deadline does not authorize freeing
in-flight engine resources.

## 21. Stable error mapping

All pre-stream errors use a versioned JSON envelope with bounded sanitized `message`, stable `type`,
optional `param`, stable `code`, and an `X-Request-ID` response header. Internal status messages,
paths, stack traces, prompt content, tokens, and credentials are never copied verbatim.

| Condition | HTTP status | Stable protocol type/code |
|---|---:|---|
| malformed target/header/JSON/type/range/conflict | 400 | `invalid_request_error` / specific validation code |
| unsupported parameter or model capability | 400 | `invalid_request_error` / `unsupported_parameter` |
| missing/invalid bearer credential | 401 | `authentication_error` / `invalid_api_key` |
| forbidden principal/hook decision | 403 | `permission_error` / `forbidden` |
| unknown route or model | 404 | `invalid_request_error` / `not_found` or `model_not_found` |
| wrong method | 405 | `invalid_request_error` / `method_not_allowed` |
| parsed/engine request deadline before response | 408 | `request_timeout` / `deadline_exceeded` |
| header/body exceeds configured transport limit | 413 | `invalid_request_error` / `payload_too_large` |
| unsupported media/content encoding | 415 | `invalid_request_error` / `unsupported_media_type` |
| rate/concurrency/queue/response capacity exhausted | 429 | `rate_limit_error` / `rate_limited` or `server_overloaded` |
| known model/engine temporarily not ready | 503 | `server_error` / `model_not_ready` |
| controlled shutdown before admission | 503 | `server_error` / `server_stopping` |
| tokenizer/model/execution/internal invariant failure | 500 | `server_error` / sanitized stable category |

Errors after SSE start follow section 19. Client disconnect/write failure is recorded internally and
causes cancellation but has no HTTP status because the peer cannot reliably receive one. Error
mapping is table-driven and golden-tested; handlers do not improvise status codes.

## 22. Health and readiness

Liveness returns success only when the process and network event loop can service the probe. It does
not claim that a model or GPU is healthy. The bounded response contains no internal topology.

Readiness is derived from the authoritative engine state and returns success only when:

- configuration and model/tokenizer validation completed;
- device worker/context/model are healthy;
- coordinator and required queues/pools are running;
- server admission is open; and
- shutdown/drain/poison has not made new work unacceptable.

Capacity saturation by itself does not make readiness false; generation requests receive 429 with
backpressure. A poisoned/unavailable engine or draining server makes readiness 503. Readiness never
runs a GPU request, blocks on the coordinator, or caches true beyond a generation-checked state
snapshot.

The model-discovery endpoint is not a readiness probe: it may identify a configured model while its
generation endpoint returns `model_not_ready`, as explicitly represented in internal state.

## 23. Shutdown and connection draining

M9 layers network shutdown around M7's engine shutdown without weakening it:

1. atomically stop admission and make readiness false;
2. cancel/close the acceptor and prevent session-pool acquisition;
3. let already admitted sessions drain until the server drain deadline;
4. on deadline, mark remaining sessions failed, post idempotent request cancellation, stop writes,
   and close sockets;
5. drain or abandon every engine handle and release protocol/session leases;
6. invoke M7 shutdown in configured drain or cancel mode and retain its fence-safe semantics;
7. wait for all socket/timer callbacks to observe closed generations;
8. stop/join network executors only after sessions are gone; and
9. verify connection/request/rate/parser/body/output/timer/handle and all engine resources at baseline.

A second shutdown request is idempotent; cancel may escalate drain. No session, callback, engine
handle, or thread is detached. Exceeding the network deadline closes clients but does not free
uncertain GPU resources. M10 later adds production signal handling and watchdog diagnostics.

## 25. Open-loop load generator

`inferx-loadgen` is a standalone bounded HTTP client, not an in-process engine benchmark. It supports:

- completions or chat endpoint and streaming or non-streaming response validation;
- fixed-rate, Poisson, or timestamped trace arrivals driven by a monotonic clock;
- request templates with bounded prompt/output/priority/deadline distributions and deterministic seed;
- configurable maximum outstanding requests/connections and explicit overload action: record/drop
  locally or wait, never silently alter arrival timestamps;
- keep-alive reuse, optional bearer credential source, server/model/profile verification;
- full response/SSE parsing, per-request ID/order/terminal/usage validation, and error classification;
- warmup and measured intervals, reproducible seeds, raw bounded samples, and histogram export; and
- SIG/control cancellation only through its own documented client lifecycle, without server internals.

Open-loop latency is measured from scheduled arrival, so client-side queueing is included and
coordinated omission is visible. Reports distinguish offered, sent, locally dropped, admitted,
completed, protocol-failed, timed-out, and disconnected counts. Throughput is never reported without
offered rate and error/drop rate.

The generator records server/profile/system fingerprint, workload digest, client/server clocks,
hardware/software metadata, connection mode, payload sizes, and exact command/config digest. It does
not log authorization tokens or prompt/response bodies unless a non-sensitive fixture explicitly
enables them.

## 27. Failure behavior

| Failure | Required result |
|---|---|
| invalid sampling combination/range | 400 before engine admission; no sampling/KV/resource leak |
| RNG seed source unavailable for omitted seed | admission error; never fall back to shared weak state |
| NaN/no surviving logits | request-scoped engine error; no token/penalty/output commit |
| sampling snapshot/ticket generation mismatch | invariant failure; reject result and safely drain ticket |
| logprob token rendering failure | no new token commit; terminal error after safe acknowledgement |
| stop matcher capacity/UTF-8 violation | validation or request failure; never emit invalid/retractable bytes |
| oversized/truncated/chunk-framing JSON | bounded 400/413 and close or safe keep-alive per parser state |
| duplicate/unknown/unsupported field | stable 400 with bounded `param`; no silent ignore |
| auth/rate/concurrency rejection | 401/403/429 before tokenization/engine admission |
| tokenizer/template/model failure | stable mapped error; no protocol-specific fallback prompt |
| engine command/response capacity full | bounded 429 overload; caller request ownership resolved exactly |
| impossible/deadline expiry | mapped timeout behavior; accepted work cancels/drains through M8 |
| disconnect during parse/admission/generation | release parser/session; withdraw or cancel/abandon exactly once |
| socket write failure after success headers | close, cancel/abandon, no duplicate write or `[DONE]` |
| slow outbound client | deadline/high-water cancellation and bounded close; coordinator keeps progressing |
| malformed/stale engine event | no serialization; invariant failure and safe handle cleanup |
| model/device poison | readiness false, affected request error if writable, stop new admission |
| shutdown race at any session state | generation-checked callbacks, at most one close/cancel/terminal |

Temporary overload is not labeled internal failure. Client-caused parse/auth errors do not poison the
engine. Error responses remain bounded even when allocation pressure caused the original failure.

### 28.5 Independent correctness oracle

A small pinned reference tool implements ADR 0056 independently of the production sampler and reads
committed FP32 logits fixtures. For hand-constructed and model-produced rows it records normalized
parameters, penalty counts, transformed/filter survivor sets, RNG word/uniform, selected token, and
logprobs.

At least 100 prompts across sampling configurations run for up to the configured fixture output limit.
Production must match every selected token exactly for fixed seeds and match declared logprob
tolerances. The corpus covers ties, boundary probabilities, repeated history, multiple EOS IDs,
stop/length outcomes, batch reshaping, M8 chunking, and preemption.

### 28.6 Stress, failure, fuzz, and sanitizers

- At least 1,000 concurrent keep-alive/SSE clients within configured capacity, with mixed prompt sizes,
  samplers, deadlines, and response speeds.
- Slow/non-reading clients at every outbound threshold while ordinary clients maintain progress.
- Repeated connect/disconnect/reconnect, malformed/truncated/oversized bodies, auth/rate storms, and
  server drain/cancel loops.
- Fault injection at session/parser/body/auth/rate/receipt/tokenizer/engine/sampler/renderer/
  serializer/write/timer/shutdown boundaries.
- libFuzzer/AFL-style targets for HTTP-independent JSON semantic parser, stop matcher, protocol
  serializer values, and SSE response parser with allocation/operation budgets.
- ASan/UBSan over all CPU tests, TSan over network/engine/handle/snapshot/shutdown stress, and existing
  GPU/Compute Sanitizer correctness lanes for sampled execution integration.

At test end, accepted plus rejected categories reconcile, each admitted engine request has one
terminal audit outcome, and connection/session/parser/body/timer/output/auth/rate/handle/sampling plus
all M8 resource counters equal baseline. Required tests fail rather than silently skip.

## 29. Performance methodology and gates

Performance evidence uses the same model, prompt/output/sampling seeds, engine policy, hardware,
software, warmup, concurrency/arrival trace, and success set for paired embedded and HTTP runs.
The batch-one protocol comparison uses a warm persistent loopback connection; connection setup is
reported separately rather than hidden or charged inconsistently to only one side.

Measure separately:

- simdjson parse and semantic validation time by body size/message count;
- serialization and escaping time/bytes by stream/logprob configuration;
- CPU sampling time by vocabulary, distinct penalty tokens, filters, survivor count, and top logprobs;
- submit/tokenization/queue/GPU/sampling/response-pump/socket components of TTFT/TPOT;
- event-loop CPU, context switches, allocations, connection reuse, and outbound high water;
- achieved/output/SLO goodput, offered load, local drops, HTTP errors, p50/p95/p99/max latency; and
- embedded versus non-stream HTTP versus SSE overhead at batch one and saturation.

The required gates are:

- local non-streaming batch-one HTTP adds no more than 5% median end-to-end latency versus the
  equivalent embedded API request;
- HTTP saturation throughput is no more than 3% below the paired embedded reference saturation
  point;
- no steady-state per-token heap allocation occurs in sampler, stop matcher, engine-to-protocol pump,
  or serializer; and
- 1,000-client stress stays within configured memory/session/output limits with no coordinator
  progress regression attributable to slow clients.

Sampling microbenchmarks are reported rather than hidden inside the HTTP aggregate. If a gate misses,
the evidence identifies parser, serialization, network, sampling, tokenizer, or engine contribution;
the compatibility/correctness contract is not weakened to improve a number.

## 32. Risks and experiments

| Risk | Required evidence | Decision/fallback |
|---|---|---|
| CPU vocabulary sampling dominates TPOT | vocab/filter/logprob profile and GPU idle timeline | optimize bounded CPU path; M12 may add GPU sampling without changing reference |
| platform math changes boundary selections | known-answer logits around every comparison boundary | deterministic accumulator/order and pinned tolerance/version |
| sparse penalty snapshot is too large/costly | history/distinct-token capacity and copy/pin benchmark | tune fixed arena/layout; never scan decoded text or allocate per step |
| stop buffering harms streaming latency | prefix-heavy stop-set TTFT/TPOT and byte-hold histogram | bound stop count/bytes and document unavoidable suffix delay |
| logprobs explode response memory | worst-case JSON escape/candidate reservation proof | small configured cap; reject requests that cannot reserve |
| strict profile surprises clients | published accepted/rejected field matrix and conformance suite | version/add fields deliberately; never silently ignore semantics |
| one active request/connection limits clients | keep-alive/open-loop connection sweep | document and scale connections; no unbounded pipelining |
| network pump consumes response pools under slow readers | high-water/write-timeout stress | cancel/abandon bounded clients while engine continues |
| SSE failure after headers is ambiguous | golden disconnect/error matrix | error event when writable, close without `[DONE]` otherwise |
| plaintext is deployed remotely by accident | startup bind/auth validation | loopback default; require explicit insecure acknowledgement |
| rate-key cardinality grows without bound | adversarial principal/source churn | bounded table with deterministic idle eviction/global fallback |
| HTTP overhead gates confound workload changes | paired trace/system fingerprint comparison | fail comparison on mismatched inputs/success sets |

## 34. Definition of done

### Sampling and stops

- [ ] Normalized sampling parameters, transform/filter order, numeric behavior, and Philox mapping are
      versioned and covered by independent known-answer fixtures.
- [ ] Temperature-zero defaults are exactly token-identical to M5 greedy selection.
- [ ] Fixed-seed output is independent of batching, chunking, preemption, cancellation retry, and
      thread timing.
- [ ] Penalty state changes only with committed output and remains generation/pin safe.
- [ ] EOS/min/max, stop tokens/strings, usage, finish precedence, and logprobs match all boundary
      fixtures without invalid UTF-8, byte retraction, or duplicate output.

### Protocol and bounded serving

- [ ] Every documented endpoint/parameter/default/response/error passes the versioned compatibility
      suite; every unsupported semantic field is rejected explicitly.
- [ ] JSON/SSE serialization is valid, ordered, capacity-reserved, and ends with `[DONE]` exactly on
      successful streams.
- [ ] Parser, session, connection, auth/rate, timer, response, and engine resource limits are enforced
      before acquisition can exceed capacity.
- [ ] No slow/disconnected client blocks coordinator/GPU progress or causes unbounded memory.
- [ ] Disconnect, write failure, deadline, shutdown, and stale callbacks post at most one cancellation/
      close/terminal action and safely drain engine ownership.
- [ ] Health/readiness and error mapping reflect authoritative engine state and expose no sensitive
      diagnostics.

### Correctness, stress, and evidence

- [ ] Embedded, non-stream HTTP, and SSE fixed-seed tokens/text/logprobs/usage agree for the same
      request and system fingerprint.
- [ ] At least 1,000 concurrent keep-alive/SSE clients, slow-reader storms, malformed-input fuzzing,
      rate saturation, reconnect loops, and shutdown soak pass with all counters at baseline.
- [ ] ASan/UBSan/TSan and required GPU integration/sanitizer lanes pass without hidden skips.
- [ ] Open-loop load generator reports offered/sent/drop/error/success counts without coordinated
      omission and produces reproducible workload manifests.
- [ ] Median local batch-one HTTP overhead is <=5% and saturation throughput loss is <=3% versus the
      paired embedded API reference.
- [ ] ADRs 0056-0063, sampling/API/config/loadgen docs, schemas, golden fixtures, compatibility report,
      and performance evidence match the implementation.

## 35. Handoff to M10

M9 hands M10 a bounded serving process with deterministic CPU sampling, exact stop/logprob/usage
semantics, a strict versioned compatibility profile, stable errors, network lifecycle/resource
accounting, health/readiness, a load generator, and protocol/engine correlation identities.

M10 may add production metrics/exporters, structured/redacted logging, distributed tracing, watchdogs,
diagnostic snapshots, fault orchestration, signals, containers, and an operational runbook. It may not
change sampling or wire behavior when telemetry is enabled, turn health into a blocking probe, leak
prompts/tokens/credentials through diagnostics, bypass bounded response/network queues, or free engine
resources before M7-M9 cancellation/fence/acknowledgement ownership is complete.
