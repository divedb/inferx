# M6 implementation specification: production paged KV cache

- Status: proposed implementation contract
- Roadmap milestone: M6 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M5](m5.md), including M1-M4 transitively
- Immediate consumer: M7 asynchronous engine and continuous batching
- Later consumers: M8 preemption/chunked prefill, M11 prefix caching, M14 parallel workers, and M18
  disaggregated KV transfer

This document turns M6 into an executable engineering plan. It defines fixed paged-KV geometry,
physical storage, a generation-safe allocator, sequence block tables, quota-backed append
transactions, in-flight pins, device block-table mirrors, paged attention, capacity/fragmentation
accounting, deterministic replay, failure containment, tests, evidence, and the exact handoff to M7.

M6 changes physical KV storage only. It does not change Llama semantics, token positions, scheduling
policy, output selection, or request lifecycle.

## 1. Outcome

At the end of M6, a supported InferX build can:

1. reserve a fixed device-memory budget once and expose it as a finite set of equal-geometry physical
   KV blocks without serving-time `cudaMalloc`/`cudaFree`;
2. allocate/reclaim blocks deterministically using strong block IDs, generations, explicit states,
   owner references, in-flight pins, and fence-aware reuse;
3. maintain one fixed-capacity logical-to-physical `SequenceBlockTable` per active sequence;
4. reserve an append across an existing partial tail and any required new blocks transactionally,
   then commit visibility only after the matching GPU completion succeeds;
5. charge conservative per-request block quota at admission so an admitted request cannot later fail
   merely because its promised KV capacity was overcommitted;
6. publish exact capacity, physical-use, quota-use, tail-fragmentation, and low-water snapshots;
7. construct bounded, versioned pinned/device block-table metadata for prefill/decode without raw
   device pointers in M1 plans;
8. execute MHA/GQA over paged K/V for page sizes 8, 16, and 32 within the accepted M6/M4 envelope;
9. run M5 generation with `paged` or forced `contiguous` KV and produce identical logits within M5
   thresholds and identical greedy tokens/decoded bytes;
10. survive exhaustion, rollback, cancellation, stale handles/epochs, failed writes, repeated reuse,
    and shutdown without exposing unwritten/old data or reusing memory before its fence; and
11. reproduce at least one million allocator/table/transaction operations from a deterministic
    value-only event log while checking all invariants after each operation.

The control/data flow is:

```text
M1 logical KV read/write ranges + request reservation
  -> M6 quota admission and SequenceBlockTable
  -> BeginAppend(range)
       pin existing reads/tail + reserve new physical blocks
       build value-only PagedKvPlan with block handles/table epoch
  -> M5 eager backend submission
       validate handles -> build/upload device mirror
       per layer: write rotated K/V page slots -> paged causal attention
  -> final M2 CompletionFence
  -> prepare matching KV completion
  -> success: commit table/valid-token visibility
     cancel/failure: abort after safe drain; poison on uncertain CUDA fault
  -> acknowledge ticket -> release pins/metadata/workspace
```

M6 is complete only when paged and contiguous paths share the same end-to-end corpus with no greedy
token divergence, and allocator invariants hold under pressure and faults. A page table that is
correct only while physical IDs happen to be sequential is not complete.

### Implementation status (2026-08-31)

This file is a documentation specification only. No M6 source implementation is authorized by this
change. M6 cannot begin until M5's real execution ticket, contiguous KV oracle, numeric fixtures, and
CUDA model instance exist. Any M6 prototype must consume those interfaces rather than creating a
parallel model loop or request state machine.

## 2. Scope boundaries

### 2.1 In scope

- One CUDA device and one loaded dense Llama model instance per physical pool.
- Fixed uniform model geometry: local layers, KV heads, head dimension, dtype, and selected tokens per
  block.
- Separate K and V arenas with a stable layer/block/token/head/dimension layout.
- A fixed physical-block count derived from an explicit KV device budget after model/runtime reserve.
- Coordinator-owned CPU allocator metadata with deterministic lowest-free-ID allocation.
- Strong pool/block/generation/table/epoch/reservation/transaction IDs.
- Fixed-capacity sequence-table slots preallocated for the configured maximum active sequences.
- Conservative quota reservation at admission and lazy physical block assignment on append.
- Existing-tail writes plus multi-block new append, commit/abort, release, and fence-aware reclaim.
- Value-only physical plans and bounded device mirrors for batch metadata up to the M4 capability,
  even though M5 end-to-end execution remains batch one.
- Paged MHA/GQA prefill/decode adapters and an owned correctness fallback if the qualified optimized
  backend does not cover the selected geometry.
- Forced contiguous/paged selection for differential diagnosis.
- Debug invariant dump, deterministic operation log/replayer, model-check/property tests, stress,
  Compute Sanitizer, and performance/fragmentation evidence.
- A low-water signal for later admission policy; M6 defines the mechanism, not queue policy.

### 2.2 Explicitly out of scope

- Continuous batching, request channels, coordinator/worker loops, fairness, or admission queue policy.
  M7 consumes M6 snapshots and plans.
- Prompt chunking, preemption policy, recomputation, swap, or priority. M8 owns them.
- Cross-request prefix lookup/sharing, prefix hashing, eviction policy, partial-page copy-on-write, or
  tenant sharing. M11 adds those over M6 leases; M6 table ownership is exclusive.
- Beam-search branching or multiple sequences per request.
- Host/off-device KV, compression, quantized KV, tiering, peer transfer, remote KV, or disaggregated
  prefill/decode.
- Tensor/pipeline/expert parallel rank mapping; M14+ incorporates rank/layout into pool identity.
- Dynamic page-size changes after model readiness, pool growth/shrink, defragmentation by moving live
  pages, or per-request page geometry.
- Changing M5 weight/activation plans, RoPE convention, greedy selection, tokenizer, or output schema.
- Treating stale generation, uncertain asynchronous CUDA fault, or invariant failure as recoverable
  by blindly clearing allocator metadata.

## 3. Inherited contracts and prerequisites

M6 preserves:

- M1 logical `KvReadPlan`/`KvWritePlan`, request epochs, reservation ownership, step/ticket identity,
  stale completion rejection, coordinator-only request mutation, and no raw pointer in plans;
- M2 checked tensors/bytes, fixed device allocations, memory categories, healthy/poisoned context,
  nonblocking streams, metadata ring, workspace, events/fences, and acknowledgement before reuse;
- M3 model/layout identity and normalized Llama KV geometry;
- M4 attention math, GQA head mapping, rotated-K convention, backend registry/capability/warm-up,
  no post-launch fallback, and numeric policy; and
- M5 exact prefill/decode positions, eager ticket resource bundle, transactional commit-after-final-
  fence, contiguous KV reference, model memory report, and greedy/token corpus.

Before M6 merges:

1. M5 must pass its 100-prompt correctness and 1,000-request resource gates on the supported GPU;
2. M4 must extend its attention contract/registry with the exact M6 paged layout/page sizes and retain
   contiguous forced execution;
3. the accepted attention backend must qualify its paged native API, or InferX must provide the owned
   paged fallback defined in section 13;
4. M2 metadata/event/workspace pools must be sized for M6's worst accepted batch/table mirror;
5. M1 resource snapshots must be version-extended rather than reinterpreting KV tokens as physical
   block IDs; and
6. ADRs 0037-0042 below must be accepted with evidence before dependent code merges.

M6 work may parallelize CPU allocator/table/replay with CUDA paged-attention work only after the page
layout and value-plan schema are fixed. Neither branch may invent a temporary physical layout.

## 5. Initial M6 capability

| Property | Schema-v1 rule |
|---|---|
| model/device | one ready M5 dense Llama instance on one CUDA device |
| page sizes | exactly 8, 16, or 32 tokens; one immutable choice per pool |
| dtype | model activation/KV FP32, FP16, or BF16; uniform across pool |
| layout | separate K/V, NHD: `[layer][physical_block][token][kv_head][head_dim]` |
| heads/dimension | M3-valid and within M4 paged-attention capability |
| context | configured M5 context; table capacity `ceil(context/page_tokens)` |
| active sequences | fixed configured maximum; CPU tables preallocated |
| table ownership | exclusive to one sequence in M6; no cross-request sharing |
| writable tail | exclusive; no partial-page sharing/copy-on-write |
| in-flight writes | at most one append transaction per sequence |
| execution | M5 batch-one end to end; paged-attention harness validates batch up to M4 maximum |
| allocation | one fixed K arena and one fixed V arena; no serving-time device allocation |
| reclaim | only owner refs zero, pins zero, no pending write/fence, valid generation |

Supporting more page sizes/layouts is a schema/capability addition, not a loose integer range.

## 7. KV geometry and physical device layout

### 7.1 Checked geometry

Inputs are local layer count L, page tokens P, KV heads Hkv, head dimension D, dtype bytes S,
block alignment A, device KV budget B, and maximum context C. Validate positive values, P in
`{8,16,32}`, power-of-two A (schema-v1 A=256), supported dtype/head geometry, and M4 capability.

```text
payload_bytes_per_layer_kind = P * Hkv * D * S
physical_block_stride = AlignUp(payload_bytes_per_layer_kind, A)
physical_bytes_per_logical_block = 2 * L * physical_block_stride
max_blocks_per_sequence = CeilDiv(C, P)
block_capacity = Floor(B / physical_bytes_per_logical_block)
pool_allocated_bytes = block_capacity * physical_bytes_per_logical_block
unusable_budget_tail = B - pool_allocated_bytes
```

All operations are checked for `uint64_t`, `ByteCount`, host `size_t`, CUDA allocation sizes, and
metadata index narrowing. Require at least one block and enough capacity for the configured minimum
admissible sequence. Geometry is immutable and included in instance/compatibility identity.

Logical payload bytes exclude alignment padding; physical charged bytes include it. Reports show
both. `unusable_budget_tail` is layout/budget padding, not per-sequence fragmentation.

### 7.2 NHD address mapping

K and V are separate fixed device arenas. For kind base, layer `l`, physical block `b`, token slot
`t`, KV head `h`, and dimension `d`, the byte offset is conceptually:

```text
((l * block_capacity + b) * physical_block_stride)
+ (((t * Hkv + h) * D + d) * S)
```

This is NHD within each page. Valid indices are range-checked on host; CUDA kernels perform defensive
bounds checks appropriate to their launch contract. Generic code never receives the computed raw
address. `CudaKvPool` resolves a validated physical index into per-layer tensor views internally.

Each arena is one explicit M2 device allocation at model load. K/V base and every block start meet A.
Padding is inaccessible to logical views and canary-checked in tests.

### 7.3 Position mapping

For logical token position `p`:

```text
logical_block = p / P
token_in_block = p % P
```

`SequenceBlockTable[logical_block]` yields a generational physical handle. Sequence length, not page
contents, determines visible tokens in the partial final page. Empty/unwritten/reclaimed slots are
never inferred from bytes.

## 8. Physical block allocator

### 8.1 Strong handles and metadata

```text
PhysicalBlockHandle = (BlockPoolId, PhysicalBlockId, BlockGeneration)
```

IDs are strong fixed-width values. Generation is 64-bit, incremented with checked arithmetic whenever
a free slot is allocated. If increment would wrap, retire that physical slot permanently and reduce
capacity; never emit a live-looking reused handle. Pool ID/generation changes on model reload.

Per-block host metadata contains state, current generation, table owner count, in-flight pin count,
pending ticket/fence identity, and debug last-transition ordinal. It contains no device pointer.

### 8.2 States and transitions

States are:

```text
Free
  -> Reserved             allocation into an unsubmitted append transaction
Reserved
  -> Free                 rollback before any possible write
  -> Writing              backend accepted ticket / writes may occur
Ready
  -> Writing              append into exclusive partial tail
Writing
  -> Ready                matching successful completion commits visibility
  -> ReclaimPending       cancellation/failure/release after work, await pins/fence
Ready
  -> ReclaimPending       table owner released while a pin remains
  -> Free                 last owner released and no pin/fence
ReclaimPending
  -> Free                 final pin/fence released safely
Any non-Free
  -> Retired              generation/invariant/device safety failure; never reused
```

New blocks become table-owned only at successful commit. An existing tail retains its table owner
while Writing. M6 has at most one table owner; M11 may add immutable shared full-page owners through a
versioned extension. Pin counts may exceed one only for explicitly prepared multi-consumer test/
future bundles; schema-v1 execution normally pins once per ticket.

### 8.3 Deterministic free selection

The allocator stores all free IDs in a fixed-capacity min-heap and always allocates the lowest
available ID. Heap backing is preallocated. Reserve `n` blocks transactionally:

1. validate quota/capacity and output scratch;
2. peek/pop n IDs into a fixed transaction buffer;
3. increment generations and transition all to Reserved; and
4. publish the transaction only after every transition is prepared.

Failure leaves heap/metadata unchanged. Rollback reinserts all IDs and is idempotent. Allocation,
free, pin, and transition perform no heap allocation. Determinism depends only on prior value events,
not address/container hash order.

### 8.4 Owners, pins, and reuse

- Table owner: makes committed contents logically reachable by one sequence.
- Reservation owner: transaction owns a new Reserved block before table commit.
- Execution pin: prevents reclaim while a plan/ticket/kernel may reference the block.
- Quota charge: admission capacity promise; it is not a block reference or physical assignment.

A block enters Free only when owner count and pin count are zero, no transaction/ticket/fence names
it, and state/generation are valid. Returning an ID to the heap earlier is an invariant failure.
Double release/unpin, unknown/stale handle, negative counter, or state mismatch is side-effect-free
`FailedPrecondition` and poisons the manager in production because continued reuse is unsafe.

## 9. Sequence table pool and invariants

### 9.1 Fixed table slots

`SequenceTablePool` preallocates `max_active_sequences` table objects and, for each, an array of
`max_blocks_per_sequence` entries. Acquire selects the lowest free table slot, increments its table
generation, assigns sequence/request epoch/quota, clears sizes without reallocating, and starts with
committed length zero/epoch one.

One table contains:

- table slot/generation and `SequenceId`/`RequestEpoch`;
- `BlockTableEpoch` (64-bit checked monotonic);
- committed token length;
- committed physical handle count;
- optional pending append transaction/ticket;
- fixed entry storage and capacity; and
- linked quota reservation ID/charged block count.

Release is legal only after pending work drains. It drops table owners for committed handles, returns
or defers blocks according to pins/fences, releases unused quota, clears identity, increments/retains
generation policy, and returns the table slot.

### 9.2 Core table invariants

For active table, page size P, committed length N:

- `entry_count == CeilDiv(N,P)` when no new-block reservation is pending;
- N=0 implies no committed entries;
- every entry index below entry_count contains one unique live handle in the same pool;
- no handle appears twice in one table or in another M6 table;
- all full earlier pages have P committed tokens;
- final page has `N % P` valid tokens, or P when evenly divisible;
- committed entries have one table owner;
- table epoch equals the latest committed/tentative mapping schema seen by its pending plan;
- allocated blocks plus free plus retired equals fixed capacity; and
- table physical use never exceeds its quota charge.

Pending append adds transaction-owned tentative entries, but committed length and public committed
entry count remain unchanged. Invariant dumps distinguish committed and pending mappings.

### 9.3 Table epoch

Increment epoch whenever a tentative physical mapping is installed for submission, committed, rolled
back, or the table is reset/released. A `PagedKvPlan`, device mirror, execution ticket, and completion
echo the exact table generation/epoch they use.

Only one operation may be in flight for a sequence in M6, so a completion with an old epoch is an
internal stale-plan violation, never a benign reorder. It cannot commit or release a newer mapping.
The manager is marked unhealthy and the affected replica drains.

## 10. Quota reservation, capacity, and low water

### 10.1 Conservative admission quota

For request prompt count Q and maximum output count O, preserve M1's conservative KV-token promise:

```text
promised_tokens = Q + O
promised_blocks = CeilDiv(promised_tokens, P)
```

Even though the final emitted token may never enter KV, M6 does not silently weaken M1 admission.
`KvQuotaAccountant::BeginReservation` charges promised blocks and one sequence table before request
reservation commits. It allocates no device page. Early EOS/cancel/terminal release returns unused
quota.

Quota records link M1 `ReservationId`, request/sequence/epoch, promised tokens/blocks, currently
physically assigned blocks, and table handle. A transaction cannot allocate beyond its quota. Healthy
lazy allocation under a committed quota must not fail for physical exhaustion; such a failure is an
invariant/accounting error.

### 10.2 Snapshot

`KvCapacitySnapshot` contains checked values:

- total/retired/usable physical blocks;
- free, Reserved, Writing, Ready, and ReclaimPending counts;
- total/used/available quota blocks;
- active/free sequence tables;
- committed and pending logical tokens;
- table-tail unused token slots;
- physical payload, alignment padding, budget tail, current/peak charged bytes; and
- low-water threshold/state.

Admission availability is:

```text
available_quota_blocks = usable_blocks - committed_quota_blocks
```

and must not exceed the physical/free-plus-reclaimable invariant. Snapshot construction is
allocation-free, deterministic, and coordinator-owned. M1's logical token snapshot remains available
for replay; M6 adds versioned physical facts rather than changing token units in place.

### 10.3 Low-water signal

Default resolved low-water blocks are:

```text
max(max_active_sequences, CeilDiv(usable_blocks, 20))
```

(5% or one potential tail per sequence, whichever is larger), capped below usable capacity. An
explicit configured value may override within `[1, usable_blocks-1]`.

`low_water=true` when available quota blocks are at or below the threshold. This is a mechanism
signal only. M7 may stop admission; M8 may preempt; M6 does not bypass FCFS, evict, or allocate extra
memory. State changes emit bounded value events.

### 10.4 Fragmentation definition

Internal token fragmentation is only unused slots in each committed partial tail:

```text
tail_waste(sequence) =
  0                         if committed_tokens == 0 or divisible by P
  P - (committed_tokens % P) otherwise
```

Therefore total internal fragmentation is strictly less than one page per active nonempty sequence.
Unused promised quota is admission reservation, not physical fragmentation, because pages are lazy.
Alignment padding and unusable budget tail are reported separately. No metric combines these into a
misleading percentage.

## 11. Append reservation and completion transaction

### 11.1 Begin append

`BeginAppend` accepts table handle/epoch, M1 logical write range `[begin,end)`, logical read range,
work kind, request/sequence epoch, and quota. Validate:

- matching active identities and no pending append;
- `begin == committed_tokens`, `end >= begin`, and end within promised/context capacity;
- M1 prefill/decode range rules from M5;
- read range exactly the expected committed prefix;
- required final table entries/blocks with checked `CeilDiv`;
- enough unassigned quota and physical free blocks; and
- caller-provided fixed scratch capacity.

Determine whether the current Ready partial tail is extended, then reserve the exact number of new
blocks. The transaction records per logical page:

- live/tentative physical handle;
- token subrange within page;
- prior committed valid-token count;
- new valid-token count on success; and
- whether block is existing tail or newly reserved.

No committed length/table owner changes. Failure rolls back all new reservations and pins.

### 11.2 Prepare physical plan and submit

Pin every committed read block, existing writable tail, and new reserved block. Install tentative
entries, increment table epoch, and create immutable `PagedKvPlan` containing:

- schema/pool/layout/page geometry IDs;
- request/sequence/request epoch/table generation/table epoch;
- committed length before and target length;
- sorted logical page -> generational physical handles;
- append spans and work kind; and
- expected M1 ticket/step association placeholder.

The CUDA backend validates/resolves this plan and accepts the M1 plan. After it returns a ticket
(including a draining-failure ticket if launches began), `CommitToWriting(ticket)` is no-fail:
Reserved/Ready append blocks transition to Writing and the transaction associates the ticket. Then
M1 submission commits. If backend rejects before launch, rollback tentative mappings/pins/pages and
increment epoch again.

### 11.3 Successful completion

On a matching successful final fence/completion:

1. validate all request/sequence/table/epoch/step/ticket/range identities;
2. prepare table capacity/owner/state mutations and M1 lifecycle/response reservation;
3. make new blocks table-owned and all append blocks Ready;
4. advance committed length and committed entry count;
5. clear pending transaction while retaining ticket pins until acknowledgement;
6. perform M1 no-fail completion/token response commit in the same coordinator turn; and
7. on ticket acknowledgement, release execution pins and metadata/resource leases.

Steps 2-6 form one prepared/no-fail commit boundary. Observers cannot see M1 computed tokens with old
KV length or new KV length without the corresponding lifecycle result.

### 11.4 Abort, cancellation, and failure

- Before launch: remove tentative entries, unpin, return new Reserved blocks, retain existing tail.
- Safe completed failure/cancellation: do not advance committed length; ignore newly written slots;
  remove/free new blocks after fence/pins; restore existing tail Ready at prior valid length. A
  terminal sequence then releases all committed pages normally.
- Uncertain asynchronous CUDA fault: poison device/model/KV manager; no affected block returns Free;
  retain arenas/metadata through M2 shutdown.
- Stale completion: no mutation or unpin of newer ownership; mark invariant failure and drain.

Abort is idempotent only for the same live transaction identity. A duplicate completion/abort returns
`FailedPrecondition` without counter changes.

### 11.5 Multi-page prefill

A full prompt may span many pages. Reserve all needed new blocks in one transaction before backend
submission so partial physical exhaustion cannot occur halfway. Each layer writes the same logical
spans into its corresponding physical pages. Visibility commits for all pages/layers together after
the one final model fence.

Large M8 chunked prefills later reuse this transaction with smaller logical ranges; M6 itself keeps
M5 full-prompt behavior.

## 12. Device block-table mirror

### 12.1 Value schema

The host `PagedKvBatchMetadata` schema supports B sequences within M4 capability:

- schema/layout/pool ID and tokens per block;
- `sequence_ids[B]`, sequence generations, request epochs, table generations/epochs;
- `block_indptr[B+1]` beginning zero and nondecreasing;
- flattened physical block indices and optional debug generations;
- `kv_lengths_before[B]`, `kv_lengths_after[B]`;
- query/new-token indptr/positions from M4; and
- append block/slot mapping for every new token.

Arrays have fixed configured maximum capacity and exact used counts. No raw host/device pointer is
serialized. Physical indices are not accepted from scheduler/request input; they are derived from
validated handles by the resolver.

### 12.2 Resolver validation

Before writing metadata:

1. validate plan schema/pool/layout/geometry and exact model instance;
2. validate each table/epoch/request/ticket identity;
3. validate handle pool/id/generation/state and required execution pin;
4. reject duplicate/unreachable handles except deliberate cross-sequence sharing, which M6 forbids;
5. validate indptr/count/position/page-slot arithmetic;
6. prove every visible logical token maps to a committed or current-append slot; and
7. prove output fits the acquired M2 metadata-ring slot.

Only then emit compact physical indices. Failure makes no device upload/launch.

### 12.3 Upload and lifetime

Use M2's paired pinned/device metadata ring:

```text
acquire generation-checked slot
-> fill/validate complete host schema
-> async H2D on transfer stream
-> record upload event; compute stream waits
-> launch append/attention consumers
-> retain slot/upload event in execution ticket
-> final model fence completes
-> acknowledgement releases metadata slot/event
```

No overwrite/reuse occurs while pending. Metadata upload is bounded and performs no serving heap or
device allocation. If transfer stream is disabled, use the compute stream explicitly.

## 13. Paged KV append and attention

### 13.1 M4 contract extension

Add `KvLayoutId::kPagedNhdSeparate` plus page geometry/table metadata to M4's attention key and
capability. Mathematical attention, dtype/accumulation, causal mask, GQA mapping, RoPE, alias, error,
workspace, warm-up, and no-fallback rules remain unchanged.

The model semantic order per layer is:

```text
project Q/K/V
-> apply RoPE to Q/K
-> write rotated K and V into current page slots
-> paged causal attention reads prior committed pages plus current append
-> output projection
```

The same compute stream orders write before read. Cached K is never re-rotated.

### 13.2 Backend requirements

Every registered paged backend declares exact:

- page sizes/layout/dtypes/SM;
- batch/query/context/head/GQA ranges;
- required metadata/workspace/alignment;
- whether prefill/decode use separate capability IDs;
- stream/thread/persistent-state ownership; and
- graph compatibility reserved false in M6.

If the M4-qualified FlashInfer/native backend covers paged NHD, integrate only its qualified subset.
Otherwise or for uncovered required keys, an owned simple paged fallback must cover the complete M5
envelope for P=8/16/32. It may be slow but cannot gather the whole cache into a hidden contiguous
buffer, allocate by sequence length, synchronize the host, or read beyond visible slots.

There is no runtime fallback after append/attention launch. Forced `contiguous`, forced `paged`, and
specific backend modes are preparation-time choices.

### 13.3 Warm-up

For each configured page size/backend/dtype/model geometry, warm:

- one token in first page;
- P-1, P, and P+1 visible tokens;
- multiple nonsequential physical IDs;
- partial final page;
- decode append creating a new page;
- MHA and GQA fixtures;
- minimum/maximum admitted context/batch keys; and
- reused pages filled with old poison outside valid slots.

Compare paged output/KV writes with M5 contiguous/CPU reference, check canaries, then reset/reclaim
the warm-up sequence only after final fence. Model readiness requires both selected paged and forced
contiguous diagnostic backends prepared for the committed tiny envelope.

### 13.4 Logical KV comparison

Tests reconstruct a canonical contiguous logical K/V tensor by walking the host table and copying
only valid slots. Compare it to M5 contiguous KV at every committed step. Physical block order and
unused bytes have no semantic meaning. This detects correct logits accidentally hiding a page-write
or table bug.

## 14. Ownership and thread boundary

| Object | Mutable owner | Lifetime rule |
|---|---|---|
| quota accountant/allocator/tables | coordinator thread | no atomics/mutex; all transitions in lifecycle transaction |
| fixed K/V device arenas | CUDA model instance/device worker | created at load, released after every sequence/ticket drains |
| physical handles/value plans | coordinator-owned values | may cross worker boundary; never grant mutation/pointer access |
| logical execution pins | coordinator ticket registry | acquired before submit; released after completion acknowledgement |
| device mirror/workspace | worker execution ticket | retained through final M2 fence/acknowledgement |
| paged backend state | device worker/context | constructed at warm-up; immutable/per-stream as M4 requires |
| replay/debug state | CPU diagnostic owner | never mutates live manager except through public value operations |

The coordinator transfers a value-only `PagedKvPlan`; the worker resolves it against immutable pool
geometry and builds device metadata. The worker never decrements owner/pin/quota counts. Completion
returns echoed identities; the coordinator prepares/commits mutations. This remains valid when M7
places a bounded channel between them and when M14 later moves the worker to another process.

## 15. Error taxonomy and containment

M6 adds stable reasons for invalid geometry, pool/table/quota exhaustion, stale pool/block/table
generation, invalid block state/transition, quota mismatch, duplicate handle, table epoch mismatch,
append range mismatch, metadata overflow, paged-backend unsupported, and KV invariant failure.

| Failure | Status/action |
|---|---|
| bad config/geometry/range | `InvalidArgument`; fail before allocation/mutation |
| valid unsupported page/layout/backend/SM | `Unimplemented`; fail warm-up/readiness |
| request promised blocks exceed entire pool | `ResourceExhausted`/never fits; reject admission |
| quota temporarily unavailable/low water | value snapshot; admission defers, not an execution error |
| free pages unavailable despite committed quota | `Internal`; invariant failure/manager unhealthy |
| stale handle/table/epoch/ticket | `FailedPrecondition`; no current-state mutation, drain replica |
| double free/unpin/release or illegal state edge | `Internal`; preserve evidence, stop allocation/reuse |
| metadata/workspace slot insufficient | `ResourceExhausted`; fail preparation before launch |
| synchronous paged launch failure after prior work | M5 draining failed ticket; no KV commit |
| asynchronous CUDA fault/device loss | `Unavailable`; poison context/pool, never recycle affected pages |
| debug invariant mismatch | `Internal`; snapshot/event log retained, no in-place repair |

Diagnostics contain pool/table/block/generation/epoch/state/counts, logical ranges, backend/layout,
and required/available capacities. They do not contain KV values, raw addresses, tokens/prompts, or
unbounded table dumps. A bounded dump is referenced by artifact path/digest when explicitly enabled.

## 16. Release, cancellation, and shutdown

### 16.1 Sequence release

Terminal/cancelled/failed requests release through the coordinator:

1. if append pending/in flight, enter release-pending and drain/abort under section 11;
2. validate table generation/epoch and absence of unacknowledged ticket ownership;
3. remove table owners from all committed blocks;
4. immediately free blocks with zero pins/fences; transition others ReclaimPending;
5. release quota and table slot; and
6. validate allocator/table/quota snapshot.

No block is freed merely because the request state became terminal; the covering execution fence and
ticket acknowledgement are required first.

### 16.2 Pool/model shutdown

```text
stop admission/reservations
-> drain or cancel every sequence by deadline
-> acknowledge all tickets and metadata mirrors
-> require no active table/quota/pending transaction/pin
-> validate all nonretired blocks Free and heap exact
-> release fixed K/V arenas
-> continue M5 model/M4/M2 shutdown
```

If deadline expires or context is poisoned with uncertain work, retain K/V arenas and metadata for
safe context teardown and return error. Never reset counters/free the allocation to make diagnostics
look clean. Explicit close is idempotent; destructors do not synchronize.

## 17. Debug invariant dump and deterministic replay

### 17.1 Event schema

Every logical mutation may emit bounded schema-v1 events:

```text
pool_created
quota_reserved / quota_released
table_acquired / table_released
append_begun / append_submitted
write_completed / write_aborted
block_transition / block_pin / block_unpin
snapshot / invariant_failure
```

Events contain operation ordinal, strong IDs/generations/epochs, logical ranges, old/new states and
counts, status/reason, and geometry identity. They contain no pointers, CUDA handles, KV/token values,
wall-clock time in deterministic mode, or unordered fields.

### 17.2 Replay

`inferx-kv-replay` parses bounded JSONL through the repository's strict parser, constructs a CPU fake
pool/fence domain with the recorded geometry, applies operations in ordinal order, and validates
after each. It can generate a normalized output trace/snapshot digest and minimize a failing suffix
without changing event semantics.

Replay allocation always chooses the lowest free ID, so identical input produces byte-identical
normalized output. CUDA execution events are represented by explicit submit/complete/fail values;
the CPU replayer does not load CUDA.

### 17.3 Invariant dump

On explicit debug request or first failure, emit stable sorted JSON containing:

- geometry/capacity/accounting totals;
- free heap IDs and retired set, bounded or externalized with digest;
- each active quota/table identity, committed length, epoch, committed/tentative mappings;
- each non-Free block's state/generation/owner/pin/pending ticket; and
- cross-check results plus first failing invariant.

Dump creation must not mutate or attempt repair. If bounded inline limits are exceeded, write an
atomic local diagnostic artifact and keep a summary/digest. Production logging never emits a block
per line without a bound.

## 18. Testing and evidence requirements

### 18.1 Unit/model-check tests (`m6-unit`, CPU presubmit)

- Geometry formulas for P=8/16/32, all dtypes, zero/overflow/budget/alignment boundaries.
- Exact address-offset examples without dereferencing device memory.
- Every legal state edge and every illegal edge from every block state.
- Generation increment, stale handles, near-wrap retirement, pool reload identity.
- Lowest-ID allocation, transactional multi-reserve rollback, heap invariants.
- Owner/pin combinations, reclaim pending, double free/release/unpin.
- Table acquire/release, empty/partial/full/multipage mappings and epoch increments.
- Quota admission/release, never-fits/temporary shortage, lazy physical guarantee, low-water edges.
- Append using existing tail, exact page boundary, multiple new pages, rollback and completion.
- M1 prefill/decode range and request/sequence/table/ticket stale matrices.
- Exhaustive small-state model checking for pools <=4 blocks, tables <=2, short event sequences.
- Replay parser/goldens/determinism/minimization and invariant-dump schema.

### 18.2 CUDA integration (`m6-gpu`, required GPU)

- Allocate fixed K/V pool once, verify M2 category/accounting/alignment and explicit close.
- Append/reconstruct K/V at first/last slot, across every page boundary, and nonsequential IDs.
- Build/upload mirrors for B=1,2,4,8 within M4 capability with generation/epoch failure cases.
- Paged prefill/decode MHA/GQA for FP32/FP16/BF16 and P=8/16/32.
- Reuse a page containing poison/old request values and prove only newly committed range is visible.
- Multi-stream disjoint tables/resources if backend declares it; no shared metadata/workspace race.
- M5 token/text CLI forced `paged` and forced `contiguous`, load/generate/release/unload.

### 18.3 Correctness (`m6-correctness`)

For every M5 deterministic model/prompt corpus applicable to the dtype/backend:

- compare paged versus contiguous named attention outputs, per-layer logical K/V, final norm, logits,
  greedy tokens, finish reason, and decoded bytes;
- require M5 numeric thresholds and zero token/byte divergence;
- cover lengths `0,1,P-1,P,P+1,2P-1,2P,2P+1,max-1,max` where legal;
- cover partial tails, append exactly filling tail, append spanning several pages, and decode creating
  a new page;
- cover MHA/GQA/head dimensions/model variants and all page sizes;
- permute physical block IDs independently of logical order; and
- compare optimized paged backend and owned paged fallback separately to contiguous/CPU reference.

At least 100 prompts and up to 32 output tokens retain M5's exact-token gate for the selected default
page size; nightly runs the complete page-size matrix.

### 18.4 Randomized stress (`m6-stress`)

- At least 1,000,000 deterministic randomized allocate/quota/table/append/submit/complete/fail/cancel/
  release operations with full invariant validation after every operation in a debug run.
- Seeds bias boundary pages, pool exhaustion, partial tails, stale generations/epochs, rollback, and
  frequent lowest-ID reuse.
- GPU saturation repeatedly fills to low water/exhaustion, decodes through boundaries, cancels, and
  reuses pages under Compute Sanitizer.
- Many active CPU tables/quota records exercise M7-scale capacity without CUDA batching.
- Multi-hour nightly load/pool/request/unload soak records current/peak/fragmentation and trace digest.

On failure retain/minimize seed and replay log. At completion, all quota/tables/pins/transactions are
zero, all nonretired blocks Free, and heap/capacity/accounting reconcile exactly.

### 18.5 Failure tests (`m6-failure`)

- Pool/table/quota/metadata/workspace exhaustion and request never-fits.
- Invalid geometry/budget/page/backend/layout/head/dtype.
- Stale pool/block/table/request epoch/table epoch/ticket and duplicate handle.
- Double release/free/unpin/complete/abort and illegal state transition.
- Backend rejection before launch, synchronous failure after some layer writes, delayed async fault,
  cancellation at every append stage, and final-fence failure.
- Shutdown with Reserved, Writing, Ready pinned, ReclaimPending, and poisoned blocks.
- Corrupted replay/dump input, excessive arrays/depth, duplicate keys, and arithmetic overflow.

Each asserts status/reason/scope, side effects, retained/free ownership, first-poison preservation, and
bounded diagnostic output.

### 18.6 Sanitizers (`m6-sanitizers`)

- ASan/UBSan for allocator/table/quota/replay/model-check; TSan for any channel/test wrapper while
  core manager remains coordinator-owned.
- Compute Sanitizer memcheck on append/paged attention/reuse/full end-to-end.
- racecheck on paged reductions and multi-stream disjoint execution.
- initcheck on partial pages, old poisoned slots, padding, tail kernels, and metadata reuse.
- synccheck on all paged attention/fallback kernels containing barriers.

Required GPU tests cannot skip. InferX-owned sanitizer findings have no suppression path.

### 18.7 Performance and capacity (`m6-performance`)

Record:

- allocator/table/quota/append prepare/commit/abort p50/p90/p99 and steady allocations;
- metadata build bytes/time and H2D time by batch/table length/page size;
- paged vs contiguous attention latency for target prefill/decode contexts, MHA/GQA, dtype, page size;
- end-to-end M5 prefill/TPOT difference under each page size/backend;
- physical usable tokens, alignment/budget padding, quota use, tail waste, and peak blocks;
- page reuse/reclaim latency and low-water transition cost; and
- pool startup/close time.

No serving operation may allocate host/device memory after warm-up. Changes may not regress their
target benchmark median by >3% without reviewed evidence. Page-size ADR selects the default from
correctness, usable capacity, metadata, attention, and end-to-end evidence—not one favorable kernel.

## 22. Risks and required experiments

| Risk/question | Required evidence | Decision/fallback |
|---|---|---|
| chosen page size trades capacity for poor attention latency | full 8/16/32 capacity/kernel/end-to-end matrix | default 16 unless combined evidence selects another supported value |
| one logical block across all layers is too large/coarse | fragmentation/capacity across target Llama configs | retain uniform cross-layer ID for M6; ADR needed for layer-group pools |
| backend requires different page layout | native adapter/layout benchmark and no-copy proof | add explicit layout/version or reject backend; no hidden repack |
| quota promises capacity but lazy allocation fails | invariant/property pressure tests | stop manager/replica; never reject an already promised healthy request as normal shortage |
| existing tail is corrupted on failed append | slot-range fault/cancel tests and logical reconstruction | old length remains visible only after safe fence; poison on uncertain fault |
| stale completion unpins/reclaims reused page | generation/epoch/ticket exhaustive and near-wrap tests | reject side-effect-free and drain; never best-effort match by ID |
| metadata mirror outlives table mutation | one in-flight/sequence, pin ownership, delayed completion tests | retain mirror+pins through final acknowledgement |
| attention accidentally assumes physical order | forced random/nonsequential mapping correctness | fix page-table use; sequential-ID-only result cannot register |
| old request data leaks through partial page reuse | poison old slots plus initcheck/logit/token corpus | strict valid length/append writes; optional zeroing is defense, not correctness |
| min-heap allocator is too costly at large pool | allocator p99/CPU profile and alternative fixed hierarchy | optimize preallocated deterministic structure without changing handle semantics |
| full invariant checks are expensive in release | benchmark sampled/transition-local checks | full debug/nightly; mandatory cheap transition guards remain release-on |
| poisoned CUDA context prevents page cleanup proof | subprocess fault/shutdown evidence | retain entire pool to process/context teardown, report leak, never recycle |

## 24. Definition of done

### Geometry, allocator, and tables

- [ ] Page geometry/layout/default are accepted from complete 8/16/32 evidence and fingerprinted.
- [ ] Fixed K/V allocations and checked capacity formulas match device/accounting reports exactly.
- [ ] Strong pool/block/table generations reject every stale/near-wrap case without side effects.
- [ ] State/owner/pin/free-heap transitions are deterministic, bounded, and allocation-free serving.
- [ ] Sequence-table invariants hold for empty/partial/full/multipage and all release paths.

### Quota and transactions

- [ ] Conservative quota prevents physical overcommit for every admitted request.
- [ ] Low-water snapshots and fragmentation categories use exact documented units/formulas.
- [ ] Existing-tail/new-page appends reserve atomically and commit visibility only after success.
- [ ] Cancellation/failure/rollback/release never exposes partial data or frees before fence/pin release.
- [ ] Stale epoch/ticket/generation cannot commit, abort, unpin, or reclaim newer state.

### Device metadata and attention

- [ ] Device mirror is value-derived, bounded, generation/epoch-validated, and ticket-owned to fence.
- [ ] Paged append/attention supports required FP32/FP16/BF16 MHA/GQA and page-size matrix.
- [ ] Nonsequential/reused physical mappings produce the same logical KV/logits as contiguous.
- [ ] Forced paged and contiguous modes remain available for correctness diagnosis.
- [ ] No serving-step CUDA/host allocation, hidden gather/repack, default stream, or host/device sync.

### Verification and evidence

- [ ] Paged/contiguous meet M5 numeric thresholds and have zero token/decoded-byte divergence.
- [ ] At least 1,000,000 randomized operations pass invariants after every debug operation.
- [ ] GPU pressure/reuse and all Compute Sanitizer tools pass with no required skip.
- [ ] Internal fragmentation is less than one page per active sequence plus documented layout padding.
- [ ] Shutdown/unload returns every safe block/table/quota/pin/category to baseline; uncertain faults
      retain the pool rather than unsafe reuse.
- [ ] Allocator/metadata/attention/capacity/performance reports and minimized failure logs are retained.
- [ ] ADRs 0037-0042 and paged-KV/layout/replay docs match implemented behavior.

## 25. Handoff to M7

M6 hands M7:

- a fixed-capacity paged K/V device pool and immutable geometry identity;
- coordinator-owned quota, allocator, sequence tables, append transactions, capacity/low-water
  snapshots, and exact invariants;
- value-only paged plans with request/sequence/table generations/epochs suitable for a bounded worker
  channel;
- worker-owned device mirror/upload and paged append/attention resource bundles retained by tickets;
- paged/contiguous forced backends and exact end-to-end correctness fixtures;
- deterministic allocator/table operation replay and bounded invariant diagnostics; and
- capacity, fragmentation, failure, sanitizer, and performance baselines.

M7 adds multiple live requests, a coordinator/worker loop, bounded channels, and continuous batching.
It may combine several already-prepared M6 sequence plans into one device metadata batch, but it may
not mutate tables from the worker, admit beyond quota, reuse pages before acknowledgement, discard
table epochs, or change page geometry while ready. Batched M7 output must match serial M5/M6 execution
before throughput claims are accepted. M8 may later release/reacquire quota through preemption, and
M11 may add shared immutable full-page owners; both extend rather than bypass M6 generations, pins,
transactions, and replay.
