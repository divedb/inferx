# M3 implementation specification: safe model artifacts and tokenizer fidelity

- Status: proposed implementation contract
- Roadmap milestone: M3 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M0](m0.md) and [M1](m1.md) contracts
- May execute in parallel with: [M2](m2.md), subject to the boundary in section 6
- Immediate consumers: M4 reference operators, M5 model execution, M6 model/cache identity, and M9
  request serving

This document turns M3 into an executable engineering plan. It fixes the local artifact trust
boundary, file and mapping lifetimes, safetensors validation, initial Llama configuration and weight
schema, durable model identity, tokenizer dependency gate, tokenizer concurrency model, prompt
processing, diagnostics, tests, evidence, and merge order. M3 validates and describes model data; it
does not allocate model weights on a GPU or execute a transformer.

## 1. Outcome

At the end of M3, a CPU-only InferX build can:

1. open an explicitly selected local model directory through a rooted, traversal-resistant file API;
2. parse and validate `config.json`, an optional InferX integrity manifest, one safetensors file or a
   Hugging Face shard index, and all referenced shard headers within fixed resource limits;
3. construct an immutable dense `LlamaForCausalLM` `ModelSpec` and a complete weight plan in which
   every required parameter and every external tensor is accounted for exactly once;
4. calculate and print a stable, versioned `ModelFingerprint` over semantic configuration,
   tokenizer artifacts, weights, and compatibility/layout inputs;
5. encode, one-shot decode, and incrementally decode supported `tokenizer.json` checkpoints with
   byte/token agreement against pinned Hugging Face references;
6. render supported checkpoint chat templates without guessing a template, then turn raw text,
   chat messages, or already-tokenized input into M1's validated token request;
7. run tokenization through a bounded pool whose ownership matches the selected library's actual
   non-thread-safe handle contract; and
8. inspect the result through `inferx-model-inspect` without CUDA, Python, network access, pickle, or
executing code from the checkpoint.

### Implementation status (2026-08-31)

The artifact/model slice is implemented and CPU-tested: exact dependency pins, rooted file access,
file identities, bounded reads and mappings, strict manifest/index/safetensors readers, Llama config
normalization, complete weight coverage, BLAKE3 primitives, fingerprint record construction, and the
artifact inspection CLI. The CLI deliberately reports `tokenizer_qualified=false` and
`model_fingerprint=unavailable`; it returns an `InspectedModelArtifacts`, not the milestone's
`ValidatedModelPackage`.

M3.0 audited and rejected the current tokenizer pin unchanged. ADR 0024 remains Proposed until an
exact local-only, error-returning, streaming-decode-capable replacement revision passes the required
differential, subprocess-fuzz, and TSan gates. M1 source interfaces are also not present in this
worktree, so input processing does not invent replacement request/ID/channel types. Consequently the
complete milestone remains open even though its independent artifact/model implementation is usable.

The principal startup flow is:

```text
explicit local model root
  -> ModelLocator / RootDirectory
  -> bounded JSON and artifact discovery
  -> config + optional integrity manifest
  -> safetensors index and shard-header validation
  -> LlamaModelFactory -> immutable ModelSpec
  -> WeightPlanner -> complete WeightPlan
  -> tokenizer metadata/backend qualification
  -> versioned content digests -> ModelFingerprint
  -> ValidatedModelPackage
  -> inspector or M4/M5 consumer
```

The request-side flow is separate:

```text
PromptInput(raw text | chat messages | token IDs)
  -> bounded TokenizationJob
  -> PromptProcessor (template only for chat)
  -> TokenizerPool worker
  -> existing M1 GenerateRequest with owned TokenId vector
  -> M1 InputReady / TokenizationSucceeded lifecycle event
```

M3 is complete only when the declared tokenizer decision is closed and the 10,000-case differential
corpus passes exactly. A loader that accepts the tiny fixture while ignoring unexplained tensors or
unsupported tokenizer constructs is not complete.

## 2. Scope boundaries

### 2.1 In scope

- Linux local-directory model discovery and safe relative artifact opening.
- Regular-file identity, bounded `pread`, streaming hashing, page-aligned read-only `mmap`, and RAII
  unmapping/descriptor closure.
- Strict schema-specific JSON readers using M1's parser limits and simdjson adapter conventions.
- Optional `inferx.manifest.json` schema v1 with file size and BLAKE3 digest declarations.
- Hugging Face `config.json`, `model.safetensors`, and `model.safetensors.index.json` for one dense,
  unquantized Llama causal language model.
- Complete safetensors metadata validation, including sub-byte dtype accounting even though M3's
  Llama capability rejects sub-byte and quantized source weights.
- Architecture registry, immutable model/parameter specifications, external tensor catalog, weight
  coverage validation, tied embedding/output alias handling, and future-facing transform/shard
  descriptors.
- Stable file, tokenizer, semantic configuration, compatibility, and package fingerprints.
- A native tokenizer facade, dependency adapter, metadata cross-checks, bounded tokenizer instance
  pool, incremental decoder, prompt variants, and chat-template processing.
- Deterministic fixture generation and Hugging Face differential fixture generation as test tooling.
- Inspection CLI, structured diagnostics, fuzz targets, stress tools, and retained benchmark/evidence
  manifests.

### 2.2 Explicitly out of scope

- Hub/model downloads, HTTP, authentication tokens, cache management, remote code, or resolving a
  model name. `ModelLocator` accepts a local path only.
- PyTorch pickle, `torch.load`, GGUF, ONNX, TensorFlow checkpoints, arbitrary shared libraries, or
  checkpoint-provided executable code.
- GPU allocations, pinned staging, H2D transfer, dtype conversion, tensor transpose/packing,
  quantization, operator execution, CUDA, cuBLASLt, NCCL, or warm-up. Those begin in M4/M5.
- Tensor/pipeline/expert parallel slicing. M3 represents a neutral future `ShardSpec`; M14/M15 create
  the actual parallel plan. A single M3 package describes the unsharded logical parameter set.
- RoPE scaling variants, sliding-window attention, biases, mixture of experts, multimodal inputs,
  adapters, speculative models, or arbitrary Transformers architectures in the first capability.
- Runtime tokenizer vocabulary mutation. Added tokens serialized in the checkpoint are required;
  adding new tokens at runtime would require resizing model parameters and is rejected.
- Inventing a default chat template or a partial Jinja interpreter. A missing or unsupported template
  is an actionable error.
- A public plugin ABI or stable installed ABI. M3 targets remain first-party experimental static
  interfaces under ADR 0004.
- A general-purpose JSON DOM, cryptography library, tensor framework, model downloader, or file-cache
  service.

## 3. Repository fit and inherited contracts

At the time this specification was written, the worktree contains M0's CMake/preset scaffold,
`inferx_apply_project_options`, `src/base`, `include/inferx/base`, `apps/inferx_info`, optional CUDA
smoke, central test registration, dependency manifest/bootstrap scripts, and M0 documentation. M1
and M2 have detailed specifications but their source trees are not yet present. An M3 implementation
must therefore merge after M1, or develop behind a branch that supplies the exact M1 interfaces; it
must not duplicate temporary status, parser, ID, token, bounded-channel, clock, or configuration
types in M3.

M3 inherits these rules unchanged:

- C++23 host code, Google C++ Style, C++ Core Guidelines, target-scoped warnings, format/tidy/IWYU,
  public-header self-containment, sanitizer, install-consumer, and offline-build gates;
- Abseil `Status`/`StatusOr`, structured error payloads, checked arithmetic, strong `ModelId` and
  `TokenId`, monotonic deadlines, `std::stop_token`, and no exception crossing an InferX boundary;
- M1 parser limits, strict JSON field access helpers, immutable/canonical configuration, bounded
  channels, `GenerateRequest`, request epochs, and lifecycle events;
- no process-stable use of `std::hash` or `absl::Hash` for durable identity; and
- source dependencies must be pinned gitlinks with manifest/qualification records, never fetched by
  CMake and never locally patched inside a submodule.

M3 must leave all M1 simulator replays byte-identical. Adding a real `InputProcessor` replaces only
the test-only fake text processor; token-ID submissions keep the same `InputReady` path.

M3 and M2 are intentionally parallelizable. M3 core represents external artifact metadata as
`ArtifactDType`, `ArtifactShape`, `ArtifactByteRange`, and `TensorSource`; none includes M2 headers.
After both milestones merge, a small M4 adapter converts a mapped byte lease and validated metadata
to M2 `BufferView`/`TensorView`. M3 must not define a competing runtime tensor type or make artifact
parsing depend on CUDA.

### 5.1 Dependency responsibilities

| Dependency | M3 use | Required boundary/disposition |
|---|---|---|

| BLAKE3 official C implementation 1.8.7, commit `f3149ec5bb5449af877ba20377a11008ff499fa2` | streaming artifact digests and versioned model fingerprints | private `inferx::base` hash adapter; portable C baseline first, SIMD optional after equivalence tests |
| GoogleTest/GoogleMock | all functional suites | test only |
| Google Benchmark | tokenizer, parser, hashing, and mapping benchmarks | benchmark only |
| Clang libFuzzer runtime | in-process parser/tokenizer fuzzers | fuzz preset only; no production link |

Add BLAKE3 as a source submodule and `fingerprinting` feature through ADR 0003's process. Build only
the official C implementation, disable TBB/multithreaded and assembly paths initially, and wrap
`blake3_hasher_*` behind `Hasher`/`Digest256`. Test official vectors before use. M6 and M11 reuse this
same target and domain-separation rules; they must not add another hash implementation.

Do not add `syoyo/safetensors-cpp` in the baseline. Its own current documentation leaves strict shape
and UTF-8-key validation incomplete and requires callers to invoke offset validation separately.
InferX already needs schema-specific index/config validation through simdjson, and the safetensors
wire format is deliberately small. Implement the narrow reader in section 10 and compare it against
the official Rust implementation. This is not permission to build a general serialization library.

### 5.2 Tokenizer pin audit and mandatory integration changes

The current direct tokenizer gitlink is
`f109b7aef148dd4866a3dae7a8e5a6d221f95c75`. A source audit establishes useful facts that the M3
implementation must not rediscover by trial and error:

- it wraps a vendored Rust `tokenizers` engine and handles local `tokenizer.json`, tokenizer config,
  special-token resolution, added tokens, batch operations, and chat templates;
- its `PretrainedTokenizer` is explicitly non-thread-safe and thread-affine; every mutating call must
  have one owner, while returned decode/token strings alias backend-owned scratch before being copied;
- its C++ surface does not expose incremental decode, although the vendored Rust `tokenizers` 0.21.x
  engine contains the upstream `DecodeStream`/`step_decode_stream` implementation;
- its build currently unconditionally adds private copies of Abseil, nlohmann/json, minja,
  tokenizers-cpp/SentencePiece, curl, and system OpenSSL, and uses force-set cache values/symlink
  mutation unsuitable for embedding unchanged in InferX; and
- its own compatibility report covers fewer cases and checkpoints than M3's required corpus.

Therefore the current pin remains **candidate, not approved unchanged**. M3.0 must advance it to an
upstream revision, or an ADR-approved owned fork, that provides all of the following without a local
submodule patch:

1. parent-provided Abseil and GoogleTest targets with no duplicate target or revision;
2. a local-only build mode that removes Hub resolver, curl, proxy/token, cache, and OpenSSL from the
   production target while retaining local tokenizer/config/template loading;
3. tests/CLI disabled when embedded, contained cache options, and no configure/build network;
4. an error-returning tokenizer construction path—no Rust `unwrap()`/panic/abort reachable from
   malformed checkpoint bytes;
5. a C ABI for upstream streaming decode state (`step_decode_stream` semantics), returning owned
   bytes and a status rather than a pointer with hidden invalidation;
6. no third-party type in InferX public headers, no exception crossing the adapter, and a clean
   C++23 GCC 13/Clang 18 build; and
7. complete license/SBOM records for the recursive closure, including Rust crates, SentencePiece,
   minja/nlohmann if chat rendering retains them, and any generated C bridge.

If those changes cannot be obtained at a reviewable pin, ADR 0024 rejects the dependency and selects
a replacement that exposes the same `inferx::tokenization` interface and passes the same corpus. It
is forbidden to compensate with a home-grown BPE, SentencePiece, Unicode normalizer, byte fallback,
or Jinja approximation. M3 cannot progress past M3.0 while the decision or closure is unknown.

### 5.3 Supported tokenizer capability in M3

The M3 product capability is deliberately narrower than every feature the dependency may expose:

- local `tokenizer.json` is required; a legacy `tokenizer.model`-only checkpoint is unsupported;
- serialized normalizer, pre-tokenizer, model, post-processor, decoder, and added-token constructs
  accepted by the qualified engine are supported only when present in the committed conformance
  matrix;
- runtime token additions, stochastic tokenization, text pairs, training, remote loading, and
  `trust_remote_code` are unsupported;
- encoding accepts valid UTF-8 only and returns `InvalidArgument` for invalid input bytes;
- decoding accepts model-range nonnegative IDs only; an out-of-range ID is `InvalidArgument`, not a
  silent empty token;
- streaming decode uses the upstream engine's streaming algorithm, never repeated one-token decode
  or a guessed Unicode suffix window; and
- streaming whitespace cleanup is disabled because cleanup can rewrite already-emitted bytes. The
  serving/default decode option is `clean_up_tokenization_spaces=false`.

`docs/tokenizer-capabilities.md` names every accepted component/type and tested version. Encountering
an unlisted construct returns `Unimplemented` with its tokenizer JSON path before a request is
admitted.

## 7. Ownership, lifetime, concurrency, and shutdown

### 7.1 Artifact objects

| Object | Owner | Lifetime/access rule |
|---|---|---|
| `RootDirectory` | `ArtifactSession` | move-only directory fd; created once from the explicit root and closed last |
| `ArtifactFile` | parsing/hash operation or `ArtifactSession` catalog | move-only fd plus immutable identity (`dev`, `ino`, size, mode, timestamps); only `pread`, hash, and map |
| `MappedRegion` | `MappedTensorLease` | move-only `mmap` owner; destructor only `munmap`; never stores a naked path |
| `ShardMappingPool` slot | `ValidatedModelPackage` | fixed slots/byte budget; slot reusable only after lease release and generation match |
| `SafeTensorsMetadata` | `ValidatedModelPackage` | immutable names/dtypes/shapes/offsets; owns strings/vectors, no views into parser padding |
| `ModelSpec`/`WeightPlan` | `ValidatedModelPackage` | immutable values; safe for concurrent reads; no tensor byte pointer |
| `Tokenizer` facade | model/input layer | immutable logical facade over a bounded pool; dependency handles remain private |
| `TokenizerInstance` | one pool worker/lease | unique, thread-affine, never called concurrently or moved after first use |
| `IncrementalDecoder` | one output sequence | request-confined stream state; no shared mutable state and no emitted-byte rewrite |
| `TokenizationJob` | queue then one worker | owns input bytes, options, IDs/epoch, byte-budget reservation until completion is queued |

`ValidatedModelPackage` is move-only during construction and published as
`std::shared_ptr<const ValidatedModelPackage>` only after every check and tokenizer pool construction
succeeds. Publication does not expose mutable caches. Partial construction remains on the loading
thread and unwinds in reverse order through RAII.

### 7.2 Synchronization

Artifact discovery, header parsing, weight planning, and fingerprinting are synchronous startup work
in M3. They use no internal thread pool. This gives one deterministic failure order and avoids racing
untrusted parsers. Hashing may use large sequential reads but the official BLAKE3 portable streaming
API stays single-threaded in M3.

`TokenizerPool` creates exactly `worker_count` independent dependency handles before readiness. Each
worker owns one handle and consumes an M1 `BoundedChannel<TokenizationJob>`. The submission path first
reserves queued-byte capacity, then enqueues; failure rolls back the reservation. Workers never call
the engine coordinator. They place value-only `TokenizationCompletion{request_id, epoch, result}`
objects on a completion channel; the coordinator validates epoch and performs the lifecycle
transition.

Incremental decoding is request-confined state but may borrow any decoder-capable pool instance for
one `Push` call because upstream stream state is externalized by the qualified ABI. A call has a
deadline/stop token and never keeps an instance between tokens. Calls for one decoder are serialized
by its owner; concurrent calls on the same decoder return `FailedPrecondition` in debug/test builds.

Shutdown order is fixed:

1. close job admission and reject new submissions;
2. request stop on workers;
3. drain or cancel queued jobs according to the engine shutdown deadline, emitting one completion for
   every accepted job and releasing its byte reservation;
4. close/drain the completion channel and join workers;
5. destroy tokenizer instances and incremental decoders;
6. release mapping leases/package consumers, then mapping pool and root directory.

No destructor waits indefinitely, invokes a user callback, logs secrets/prompt bytes, or hides a
failed accepted job.

## 8. Rooted local filesystem contract

### 8.1 `ModelLocator` and safe relative paths

```cpp
class ModelLocator {
 public:
  static absl::StatusOr<ArtifactSession> OpenLocal(
      const std::filesystem::path& root, const ArtifactLimits& limits);
};

class ArtifactSession {
 public:
  absl::StatusOr<ArtifactFile> OpenRegular(SafeRelativePath path) const;
  absl::StatusOr<bool> ExistsRegular(SafeRelativePath path) const;
  const std::filesystem::path& diagnostic_root() const;
};
```

The caller's root may itself be a symlink because it is selected explicitly. Resolve it once, open a
directory fd with `O_DIRECTORY|O_CLOEXEC`, record its canonical path only for diagnostics, and anchor
all later operations to that fd. A manifest/index path must be valid UTF-8, relative, nonempty, contain
no NUL, `.` or `..` component, backslash alias, empty component, or absolute/root-name prefix. It is
stored as normalized slash-separated UTF-8, not as an unchecked `std::filesystem::path`.

On Linux, open descendants with `openat2` and
`RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS`, plus
`O_RDONLY|O_CLOEXEC|O_NOFOLLOW`. If the kernel returns `ENOSYS`/unsupported flags, walk every
component with `openat`, `O_NOFOLLOW`, and directory/regular `fstat` checks. Do not fall back to
`weakly_canonical` plus `open`, which has a time-of-check/time-of-use gap. Reject directories where a
file is expected and reject device nodes, FIFOs, sockets, procfs magic links, and other non-regular
files.

The session never recursively scans the model root. It opens only fixed well-known files and exact
relative shard names from a validated index/manifest. Unreferenced files do not affect identity and
are not an error; unreferenced tensors inside a selected shard are an error during coverage.

### 8.2 File identity and concurrent mutation

`ArtifactFile` records `st_dev`, `st_ino`, mode, size, nanosecond mtime/ctime where available, and a
monotonic internal file ID after open. All size arithmetic comes from the opened fd. Header reads use
`pread` loops that handle `EINTR`, short read, EOF, and checked `off_t` conversion. Hashing and mapping
use the same opened file identity.

Before and after parsing/hashing, repeat `fstat`; a changed identity/size/timestamp returns `Aborted`
(`kArtifactChanged`) and publishes no package. Reopening a shard for a later mapping must match the
cataloged identity. Path replacement is therefore detected and the original open fd cannot be
redirected.

Linux cannot make a writable regular file immutable merely by mapping it read-only; truncation of an
active mapping can still fault the process. M3's deployment contract requires model directories to
be staged completely and atomically renamed into place, then remain immutable for the lifetime of a
loaded package. Bytes are untrusted parser input, but concurrent malicious mutation of the underlying
inode is outside the in-process recovery guarantee. ADR 0020 records this explicitly and M3 tests
benign races. A later experiment may require fs-verity or copying into a content-addressed immutable
store; signal-handler recovery from `SIGBUS` is forbidden.

### 8.3 Mapping windows

```cpp
struct ArtifactByteRange {
  uint64_t offset;
  uint64_t size;
};

class MappedTensorLease {
 public:
  std::span<const std::byte> bytes() const;
  ArtifactByteRange requested_range() const;
  FileIdentity file_identity() const;
};
```

Map only the requested tensor window, rounded down/up to the host page size with checked arithmetic.
The public byte span excludes page-prefix/suffix bytes and is immutable. A zero-byte tensor returns an
empty lease without calling `mmap`. Regions larger than `map_window_bytes` are consumed through a
sequential `MappedTensorReader` whose windows never cross the validated tensor range.

`ShardMappingPool` preallocates slot metadata, tracks active region count and rounded bytes, and tags
slots with non-wrapping generations. Acquisition is transactional: budget and slot are reserved
before `mmap`; any error rolls both back. A live lease prevents slot reuse. Exhaustion returns
`ResourceExhausted` with active/count/byte context; startup code may process sequentially, but it may
not silently exceed a limit. Stress tests prove final counts return exactly to zero.

## 9. Artifact discovery, manifest, and JSON parsing

### 9.1 Deterministic discovery

The selected root must contain `config.json` and `tokenizer.json`. Weight selection is exclusive:

1. if `model.safetensors.index.json` exists, it is the selected source and every weight tensor must be
   present in its `weight_map`;
2. otherwise `model.safetensors` must exist and is the selected source;
3. if neither exists, return `NotFound`;
4. if both an index and standalone file exist, the index wins only when
   `inferx.manifest.json` explicitly declares it as `weights_entry`; otherwise return
   `FailedPrecondition` for ambiguity; and
5. `.bin`, `.pt`, `.pth`, and pickle files are never fallback candidates.

Optional fixed inputs are `tokenizer_config.json`, `special_tokens_map.json`,
`generation_config.json`, and `chat_template.jinja`. Their presence is recorded and digested when
consumed. The loader does not infer semantics from directory/model names.

### 9.2 InferX integrity manifest schema v1

`inferx.manifest.json` is optional for developer fixtures and required by the production deployment
profile. Its canonical logical schema is:

```json
{
  "schema_version": 1,
  "model_revision": "deployment-owned immutable revision",
  "weights_entry": "model.safetensors.index.json",
  "files": [
    {
      "path": "config.json",
      "size": 1234,
      "blake3": "64 lowercase hex characters"
    }
  ]
}
```

Rules:

- root object and every child reject duplicate keys and wrong types;
- `schema_version` is exactly integer `1`; unknown versions are `Unimplemented`;
- `model_revision` is nonempty, valid UTF-8, at most 256 bytes, and treated as opaque display data;
- `weights_entry` is a safe relative path and exactly the discovered selected weight entry;
- `files` has unique sorted-or-unsorted paths but the parser canonicalizes by path for identity;
- each size is a nonnegative 64-bit integer and each digest is lowercase BLAKE3-256 hex;
- every consumed artifact is declared exactly once and every declared file is consumed; and
- size and digest are verified from the opened fd. Mismatch is `DataLoss`, never a warning.

When the manifest is absent, M3 still hashes every consumed artifact and uses the computed file
digests in the model fingerprint. It reports `integrity_manifest=false` in inspection/readiness so a
deployment policy can reject it. The manifest is not self-listed; its normalized semantic fields are
included directly in the fingerprint preimage.

### 9.3 Parser discipline

Each reader follows M1's two-stage pattern: bounded bytes -> schema-specific parsed value -> immutable
validated value. simdjson padded buffers are local to the parse call. No returned string view, array
view, DOM element, or error object may refer into them.

Common rules:

- check file size before allocation and allocate `size + SIMDJSON_PADDING` with overflow checks;
- require valid UTF-8 JSON and one root value with only JSON whitespace after it;
- reject duplicate keys even if the dependency's normal DOM lookup would select one;
- integers needed as integers may not arrive as floating-point or numeric strings;
- reject NaN/infinity (including values produced by conversion) and negative counts;
- enforce depth, object-member, array-element, string-byte, tensor, and shard limits before reserve;
- attach a JSON pointer/field path to every schema error; and
- canonical output is written by an InferX schema writer with fixed key order and number spelling, not
  by preserving input whitespace/member order.

Hugging Face config is extensible, so “strict” does not mean rejecting harmless generic metadata.
The Llama reader has three explicit sets: consumed semantic fields, allowed inert metadata fields,
and recognized feature fields whose unsupported value returns `Unimplemented`. An unknown field is
`Unimplemented` until classified; silently ignoring an unfamiliar architecture-affecting field is
forbidden. The classification table lives in `docs/model-loading.md` and unit tests.

## 10. Safetensors and shard-index reader

### 10.1 Public values and API

```cpp
enum class ArtifactDType {
  kBool, kF4, kF6E2M3, kF6E3M2, kU8, kI8,
  kF8E5M2, kF8E4M3, kF8E8M0, kF8E4M3Fnuz, kF8E5M2Fnuz,
  kI16, kU16, kF16, kBf16, kI32, kU32, kF32, kC64, kF64, kI64, kU64,
};

struct ArtifactTensor {
  std::string name;
  ArtifactDType dtype;
  std::vector<uint64_t> shape;
  ArtifactByteRange data;       // Relative to the data buffer, not file offset.
  uint64_t absolute_file_offset;
  uint64_t packed_size_bytes;
};

class SafeTensorReader {
 public:
  absl::StatusOr<SafeTensorsMetadata> ReadHeader(
      const ArtifactFile& file, const ArtifactLimits& limits) const;
};
```

`ArtifactDType` is the wire vocabulary, not M2's execution `DType`. Keep sub-byte formats so the
reader can validate their bit-packed byte lengths and reject them later as unsupported model weights
with a precise error.

### 10.2 Validation order

For every `.safetensors` file, perform these steps in order and stop at the first deterministic error:

1. require file size at least 8; `pread` exactly the 8-byte little-endian unsigned header length;
2. require `1 <= N <= 100,000,000`, and checked `8 + N <= file_size`;
3. read exactly N header bytes; require first byte `{`, valid UTF-8, and only permitted trailing ASCII
   space padding after the JSON object;
4. parse one object and reject duplicate tensor names/keys; `__metadata__`, if present, must be a
   string-to-string object and is never a tensor;
5. for each tensor, require exactly `dtype`, `shape`, and `data_offsets`; reject extra keys, unknown
   dtype spelling, rank over limit, invalid dimensions, and offsets not exactly two integers;
6. compute element count and `ceil(element_count * dtype_bits / 8)` with checked multiplication/add;
   scalar shape `[]` has one element and a zero dimension produces a legal zero-byte tensor;
7. require `begin <= end`, `end - begin == packed_size_bytes`, and checked
   `data_start + end <= file_size`;
8. sort `(begin,end,name)` independently of JSON order; require nonempty ranges to be contiguous from
   zero without overlaps or holes, permit multiple zero-byte tensors at legal boundaries, and require
   final end equals the complete data-buffer length; and
9. repeat file identity check before returning owned metadata.

The format is little-endian and row-major. It does not require a tensor's absolute address to satisfy
InferX execution alignment, so the reader records alignment but does not reject an otherwise valid
file merely for being unaligned. M4 must stage/copy an unaligned source rather than reinterpret it.

M3's dense Llama capability accepts only `F16`, `BF16`, or `F32` parameter tensors, rank 1 or 2, and
no quantization metadata. Other valid wire dtypes parse successfully and then fail capability
validation with `Unimplemented`; malformed dtype/size pairs are `DataLoss`.

### 10.3 Shard index

`SafetensorsIndexReader` accepts a root object with required `weight_map` and optional `metadata`.
`weight_map` maps a nonempty UTF-8 tensor name to a safe relative `.safetensors` path. Duplicate names,
wrong values, an empty map, excessive names/shards, or non-safetensors suffix return an error.
`metadata.total_size`, when present, is a nonnegative integer and must equal the sum of tensor payload
bytes across selected shard headers; it is not the sum of file sizes.

Open each unique shard in lexicographic safe-path order, validate its header once, and build an
`ExternalTensorCatalog` keyed by name. Then prove:

- every `weight_map` name exists in the named shard;
- that shard contains no tensor absent from `weight_map`;
- one tensor name occurs in exactly one shard and one index entry;
- all referenced shard files pass manifest size/digest checks when a manifest exists; and
- every unique shard is referenced by at least one weight.

Index member order and shard filename numbering carry no semantics. The catalog and diagnostics use
sorted paths/names, giving identical output for equivalent JSON member orders.

### 10.4 Differential and fuzz oracle

The official Hugging Face Rust `safetensors` implementation is the conformance oracle, not another
C++ parser. Commit a corpus of valid headers (including scalar/empty tensors and every recognized
dtype), official malformed cases, and M3 security cases. For each case, record whether official Rust
accepts it and the normalized tensor metadata. InferX must agree on format validity; its stricter
rank/resource/model capability errors are recorded separately and must not be mislabeled format
corruption.

Fuzzers target raw header length/files, header JSON, index JSON, and metadata-to-catalog composition.
They enforce per-input allocation/operation limits and exercise duplicate-key and near-`UINT64_MAX`
cases. A fuzzer must never `mmap` a size derived from bytes before validation.

## 11. Model registry, Llama specification, and weight plan

### 11.1 Architecture registry and package construction

```cpp
class ModelFactory {
 public:

```

Registration happens once during engine construction, before model loading and concurrent access.
Duplicate architecture tags fail startup. The baseline registers exactly `model_type="llama"`; it
never switches on a repository/model name. `architectures`, when present, must contain exactly the
supported causal-LM architecture for this package (`LlamaForCausalLM`) or a documented compatible
alias. Unknown model types/architectures are `Unimplemented`.

`ModelPackageLoader::Load()` is transactional:

1. open session and discover inputs;
2. parse/validate manifest and config;
3. build `ModelSpec` and logical parameter catalog;
4. validate index/shard metadata and external tensor catalog;
5. construct and validate the complete `WeightPlan`;
6. load/validate tokenizer metadata and all tokenizer pool instances;
7. cross-check tokenizer/model vocabulary and special IDs;
8. hash all consumed file bytes and build the model fingerprint;
9. recheck file identities; and
10. publish the immutable `ValidatedModelPackage`.

Nothing is inserted into a model registry and no readiness bit changes before step 10.

### 11.2 `ModelSpec`

The initial immutable value is conceptually:

```cpp
struct LlamaSpec {
  uint64_t vocab_size;
  uint64_t hidden_size;
  uint64_t intermediate_size;
  uint32_t num_hidden_layers;
  uint32_t num_attention_heads;
  uint32_t num_key_value_heads;
  uint32_t head_dim;
  uint64_t max_position_embeddings;
  double rms_norm_eps;
  double rope_theta;
  bool tie_word_embeddings;
  std::optional<TokenId> bos_token_id;
  std::vector<TokenId> eos_token_ids;
  std::optional<TokenId> pad_token_id;
  SourceWeightType source_weight_type;
};
```

All counts use checked conversions to the narrower runtime types. Required/defaulted/validated fields
are:

| Config field | Rule in the initial capability |
|---|---|
| `model_type` | required, exactly `llama` |
| `vocab_size` | required, positive, <= `INT32_MAX`; all special IDs are in range |
| `hidden_size`, `intermediate_size`, `num_hidden_layers`, `num_attention_heads` | required positive integers within configured model limits |
| `num_key_value_heads` | optional; defaults to attention heads; positive and divides attention heads |
| `head_dim` | optional; defaults to `hidden_size / num_attention_heads`; exact divisibility and `heads * head_dim == hidden_size` required |
| `max_position_embeddings` | required positive and <= configured maximum model context |
| `rms_norm_eps` | required finite positive number |
| `rope_theta` | optional default 10000; finite positive number |
| `hidden_act` | optional default `silu`; any other value is `Unimplemented` |
| `tie_word_embeddings` | optional default `false`; controls the `lm_head` alias rule below |
| `attention_bias`, `mlp_bias` | optional default `false`; `true` is `Unimplemented` |
| `rope_scaling` | absent/null only in M3; any object is recognized but `Unimplemented` until an execution milestone supports it |
| `sliding_window`, `quantization_config` | absent/null only; otherwise `Unimplemented` |
| `pretraining_tp` | absent or integer 1; other values are training/conversion semantics and unsupported |
| `bos_token_id`, `pad_token_id` | optional integer, nonnegative and below vocabulary size |
| `eos_token_id` | optional integer or nonempty integer array; normalize to sorted unique IDs in range |
| `torch_dtype` | optional hint; accept recognized FP32/FP16/BF16 spellings, but external tensor headers remain authoritative |
| `attention_dropout` | optional finite `[0,1]`; recorded for provenance but execution is inference/eval and applies no dropout |

Generic inert fields such as `transformers_version`, `_name_or_path`, `initializer_range`,
`use_cache`, and token string metadata are included in the documented allowlist but never override
the fields above. The canonical semantic config contains only normalized values InferX consumes and
a `model_schema_version`; raw config bytes are separately digested, so changing even allowed metadata
still changes package identity while semantically equivalent default spelling produces the same
semantic digest.

Derived checks include:

- `num_attention_heads % num_key_value_heads == 0`;
- all shape products and expected parameter bytes fit `uint64_t` and host `size_t` where allocated;
- max context plus maximum output arithmetic can be represented by M1 token types;
- EOS list and tokenizer metadata agree under section 14.3; and
- all source weight tensors use one supported floating family unless an explicit per-parameter mixed
  policy is added through ADR 0022. The baseline allows FP32, FP16, or BF16 packages, not a mixture.

### 11.3 Parameter schema and exact Hugging Face mapping

`ParameterSpec` contains a strong `ParameterId`, canonical internal name, semantic role, expected
shape, allowed source dtype set, logical layer (if any), and an optional alias target. It contains no
storage pointer/device and is sorted by canonical name in durable output.

For layer index `i` in `[0, num_hidden_layers)`, required external names and shapes are:

| External tensor / canonical parameter | Shape |
|---|---|
| `model.embed_tokens.weight` | `[vocab_size, hidden_size]` |
| `model.layers.i.input_layernorm.weight` | `[hidden_size]` |
| `model.layers.i.self_attn.q_proj.weight` | `[num_attention_heads * head_dim, hidden_size]` |
| `model.layers.i.self_attn.k_proj.weight` | `[num_key_value_heads * head_dim, hidden_size]` |
| `model.layers.i.self_attn.v_proj.weight` | `[num_key_value_heads * head_dim, hidden_size]` |
| `model.layers.i.self_attn.o_proj.weight` | `[hidden_size, num_attention_heads * head_dim]` |
| `model.layers.i.post_attention_layernorm.weight` | `[hidden_size]` |
| `model.layers.i.mlp.gate_proj.weight` | `[intermediate_size, hidden_size]` |
| `model.layers.i.mlp.up_proj.weight` | `[intermediate_size, hidden_size]` |
| `model.layers.i.mlp.down_proj.weight` | `[hidden_size, intermediate_size]` |
| `model.norm.weight` | `[hidden_size]` |
| `lm_head.weight` | `[vocab_size, hidden_size]` unless tied/omitted as below |

The baseline external layout is already the logical row-major `[out,in]` linear layout, so every
item uses `TransformKind::kIdentity`. `TransformSpec` still has a closed versioned enum and checked
input/output shape fields for later transpose/concatenate/pack operations; unknown kinds cannot be
silently treated as identity.

If `tie_word_embeddings=false`, `lm_head.weight` is required and distinct. If it is true:

- an omitted `lm_head.weight` creates an alias parameter targeting `model.embed_tokens.weight`;
- a present `lm_head.weight` is accepted only when its bytes are digest-identical to the embedding
  tensor, then normalized to the same alias; and
- shape equality alone is insufficient to claim a tie.

Bias tensors, rotary `inv_freq`, training-only state, optimizer state, quantization scales, or any
other external tensor are unexpected and fail with a sorted list. Supporting a known non-parameter
buffer later requires an explicit `ExternalTensorDisposition` in ADR 0022 and tests; no name-prefix
ignore rules are allowed.

### 11.4 Weight plan and coverage proof

```cpp
struct TensorSource {
  SafeRelativePath shard;
  FileIdentity expected_file;
  ArtifactByteRange file_range;
  ArtifactDType dtype;
  ArtifactShape shape;
  Digest256 file_digest;
};

struct WeightPlanItem {
  ParameterId parameter;
  TensorSource source;
  TransformSpec transform;
  ShardSpec logical_shard;  // replicated/full in M3
};

struct WeightPlan {
  uint32_t schema_version;
  std::vector<WeightPlanItem> items;
  std::vector<ParameterAlias> aliases;
  WeightCoverageSummary coverage;
};
```

M3's `ShardSpec` is exactly `kReplicatedFullTensor`; it reserves typed room for later TP/PP/EP but
does not contain a rank count or guess a split axis. Distributed planners derive new rank-local plans
from this logical plan later and include them in a different fingerprint layer.

Construction uses independent sets/maps and commits only after proof:

1. build the complete expected parameter catalog from `ModelSpec`;
2. match external names with exact string equality—no regex that can accept a malformed layer number;
3. parse layer indices with checked decimal conversion and range checks;
4. validate dtype, rank, each dimension, packed bytes, and transform output;
5. insert exactly one plan item per non-alias expected parameter, rejecting a second assignment;
6. account for tied aliases under the exact rule above;
7. compute `missing = expected - assigned`, `unexpected = external - consumed`, and duplicates; and
8. fail if any set is nonempty, otherwise sort items by `ParameterId`/canonical name and publish a
   summary whose expected/assigned/aliased/external counts reconcile exactly.

Diagnostics report at most the configured number of individual names plus omitted count, but the
returned status payload carries machine-readable reason/counts. There is no “strict=false” production
path for weight coverage.

## 12. Integrity and `ModelFingerprint`

### 12.1 Digest types and streaming

`Digest256` owns exactly 32 bytes, has constant-time equality, lowercase-hex parse/format, and no
implicit conversion to a string or generic hash. `Hasher` wraps one BLAKE3 state and has
`Update(span<const byte>)`, typed length-delimited record helpers, and one-shot `Finalize()`; calling
after finalization is a debug error and returns `FailedPrecondition` in checked paths.

Hash every consumed file from its opened fd in fixed-size sequential chunks. Retry `EINTR`, reject
short unexpected reads, and repeat file identity checks. Do not hash mmap padding, canonicalized JSON
instead of file bytes, a path string in place of file bytes, or only safetensors headers. The optional
manifest compares each computed digest before package publication.

### 12.2 Versioned preimage

`ModelFingerprint` is BLAKE3-256 of a binary, unambiguous, domain-separated record stream. Version 1
is:

```text
utf8("inferx.model-fingerprint")
u32_le(1)
record("architecture", utf8("llama"))
record("semantic_config", canonical ModelSpec bytes)
record("model_schema", u32_le(model schema version))
record("weight_plan_schema", u32_le(weight plan schema version))
record("tokenizer_capability", canonical tokenizer metadata bytes)
record("artifact", safe path + u64 size + 32-byte content digest) repeated in path order
record("model_revision", manifest revision bytes or empty)
record("source_layout", utf8("hf-safetensors-row-major-v1"))
record("quantization", utf8("none"))
record("adapter", utf8("none"))
record("rope", normalized rope type/theta/scaling values)
```

Every `record` encodes tag byte length, tag bytes, value byte length, and value bytes with fixed-width
little-endian lengths. Lists encode element count and length-delimited elements. Booleans and enums
have fixed numeric encodings. Floating-point semantic fields encode their finite IEEE-754 binary64
bits after `-0` normalization; JSON decimal spelling cannot affect them.

Root path, inode, mtime, CLI flags unrelated to semantics, log settings, and JSON member order are
excluded. File content bytes, even inert config metadata, enter through artifact digests. Equivalent
defaulted semantic config can share its semantic record but cannot collide when raw artifacts differ.

### 12.3 Namespace composition

M3 defines only the base package fingerprint. Later layers derive, rather than overwrite, it:

```text
ReplicaFingerprint = H(base model fingerprint, execution layout version,
                       TP/PP/EP plan, rank-local shard, kernel/quantization layout)
CacheFingerprint   = H(replica fingerprint, KV layout, RoPE policy, adapter,
                       tenant-sharing namespace)
```

The inspector prints algorithm, schema version, and lowercase digest. Replay/readiness protocols must
carry both schema and bytes; a bare hex string without algorithm/schema is invalid. Any change to
config, tokenizer, weights, tie disposition, RoPE, source layout, or schema version changes the M3
fingerprint. Copying the same package to a different directory does not.

## 13. Tokenizer interface and adapter

### 13.1 Public contract

```cpp
struct EncodeOptions {
  bool add_special_tokens = true;
  std::optional<TokenCount> max_tokens;
  TruncationSide truncation_side = TruncationSide::kRight;
};

struct DecodeOptions {
  bool skip_special_tokens = false;
  bool clean_up_tokenization_spaces = false;
};

class IncrementalDecoder {
 public:
  virtual absl::StatusOr<std::optional<std::string>> Push(TokenId id) = 0;
  virtual absl::StatusOr<std::string> Finish() = 0;
};

class Tokenizer {
 public:
  virtual absl::StatusOr<std::vector<TokenId>> Encode(
      std::string_view utf8, const EncodeOptions&) const = 0;
  virtual absl::StatusOr<std::string> Decode(
      std::span<const TokenId> ids, const DecodeOptions&) const = 0;
  virtual absl::StatusOr<std::unique_ptr<IncrementalDecoder>>
      NewIncrementalDecoder(const DecodeOptions&) const = 0;
  virtual const TokenizerMetadata& metadata() const = 0;
  virtual ~Tokenizer() = default;
};
```

Logical constness means encode/decode do not change tokenizer semantics. The facade may acquire a
mutable, exclusive dependency instance internally. Public spans/views are consumed during the call;
results own their memory. The destructor is virtual, nonthrowing, and does not wait for active work;
the owning engine shuts down the pool first.

`TokenId` is M1's signed 32-bit strong/value type. Before crossing a C ABI, reject negative IDs and
checked-convert to `uint32_t`. After encode, reject any backend ID greater than `INT32_MAX` or outside
the model vocabulary. Empty text is a valid tokenizer operation but `InputProcessor` applies the
product rule on whether an empty resulting prompt is admissible (baseline: reject).

### 13.2 Metadata

`TokenizerMetadata` owns:

- tokenizer schema/backend name and exact engine version;
- base and total vocabulary sizes, maximum token ID, and contiguous/noncontiguous ID property;
- optional BOS, EOS list, PAD, and UNK IDs plus all special IDs;
- default add-BOS/add-EOS behavior as actually implemented by the serialized post-processor;
- model max length as advisory metadata;
- supported normalizer/pre-tokenizer/model/post-processor/decoder type names;
- byte-fallback and cleanup behavior;
- available chat-template names and a selected default only when explicitly declared; and
- digests of every tokenizer artifact consumed.

Metadata is derived from the same qualified engine/config resolution that encode uses, not a second
home-grown parser that might disagree. It is immutable, sorted for canonical output, and fingerprinted.

### 13.3 Adapter seam and exception/panic safety

`DivedbTokenizerAdapter` is the only translation unit that includes dependency headers. It maps
dependency statuses/exceptions to InferX statuses, copies aliased return bytes immediately, adds
artifact/operation context, and redacts prompt/token content. It never exposes the dependency's
status, JSON, chat-message, `AddedToken`, or span type.

Malformed `tokenizer.json` must not be able to call a Rust `unwrap`, panic across FFI, abort, or
unwind into C++. The qualified construction ABI returns an owned error buffer/code. Run tokenizer
parser fuzzing in a subprocess too, so an accidental dependency abort is observed as a failed test
until removed. Catching C++ exceptions cannot recover a Rust abort and is not an acceptable adapter.

Backend/cache/environment behavior is fixed:

- pass the canonical local model directory; force local-only/no-hub mode;
- ignore `HF_ENDPOINT`, proxy, token, cache, and offline environment variables because the target has
  no network implementation;
- no credentials are read and no path outside the rooted package is consulted;
- engine-internal parallelism is set explicitly to avoid `worker_count * CPU_count` oversubscription;
  the baseline disables internal Rayon parallelism per single-string call and benchmarks batch mode
  separately; and
- record exact backend/Rust engine versions in capabilities and differential fixtures.

### 13.4 Incremental decode

The implementation must expose the upstream Rust `step_decode_stream` state machine used by the
selected engine. Each InferX decoder owns the equivalent of token ID buffer, emitted prefix, and
prefix index; a `Push` may return no bytes while a split UTF-8/byte-fallback sequence is incomplete.
It may return an owned valid UTF-8 chunk only when the upstream algorithm commits it. Do not decode
each token independently, repeatedly decode the full prefix and guess a suffix, emit replacement
characters for incomplete bytes, or retract prior output.

Rules:

- the concatenation of all returned chunks plus `Finish()` is byte-exactly equal to one-shot decode
  of the same IDs with the same `skip_special_tokens` and cleanup disabled;
- every nonempty chunk is valid UTF-8 and previously returned bytes never change;
- special tokens are either consistently retained or skipped for the decoder lifetime;
- invalid/out-of-vocabulary IDs fail before mutating stream state;
- after failure or `Finish`, another `Push` is `FailedPrecondition`;
- `Finish` flushes any valid remaining bytes, returns `DataLoss` for an irrecoverably incomplete
  decoder state, and is idempotent only as a zero-byte observation through a separate `finished()`;
  and
- stream state memory is bounded by generated tokens plus a small prefix; M7's maximum output tokens
  is enforced by the owner.

Differential tests cover upstream's byte-fallback split example, metaspace/leading-space behavior,
special tokens, emoji/CJK/combining characters, and every prefix of selected reference sequences.

## 14. Prompt processing and bounded tokenization

### 14.1 Input values

```cpp
using PromptInput = std::variant<RawTextPrompt, ChatPrompt, TokenIdPrompt>;

struct InputProcessingRequest {
  RequestId request_id;
  RequestEpoch epoch;
  ModelId model_id;
  PromptInput prompt;
  GenerateOptions generation;
  Deadline deadline;
};
```

The variant enforces exactly one representation. `RawTextPrompt` owns validatable bytes. `ChatPrompt`
owns ordered messages with a closed role enum plus UTF-8 content and an optional explicitly selected
template name. The M3 baseline supports text-only system/user/assistant messages; tools, images,
audio, reasoning channels, and checkpoint custom objects are `Unimplemented`. `TokenIdPrompt` owns
M1 token IDs and bypasses rendering/encoding but not vocabulary/context/request validation.

### 14.2 `PromptProcessor`

For raw text, call encode once with the request's explicit `add_special_tokens` policy (default true).
For chat:

1. validate message count, roles, ordering policy, per-message and aggregate input bytes;
2. select only the explicitly named template or checkpoint-declared default;
3. require the qualified template engine/capability to support every construct before rendering;
4. render with bounded output and deterministic options such as `add_generation_prompt`;
5. encode the rendered prompt exactly once with `add_special_tokens=false`, because templates own
   their emitted special tokens; and
6. discard rendered text after the owned token vector is constructed unless debug capture is
   explicitly enabled in a non-production test.

There is no fallback template, string concatenation approximation, double BOS insertion, or
model-name special case. Template syntax/render errors are `InvalidArgument` for invalid messages or
`Unimplemented`/`FailedPrecondition` for package capability, with no partial token result.

For all variants, validate nonempty result, every ID within tokenizer/model vocabulary, prompt token
limit, checked `prompt + max_output <= model/server context`, M1 request fields, deadline, and model
ID. Return M1's existing `GenerateRequest` so scheduling never receives text or dependency objects.

### 14.3 Model/tokenizer cross-check

Before readiness:

- tokenizer maximum emitted ID is less than `ModelSpec.vocab_size`;
- tokenizer total vocabulary is compatible with embedding rows; a sparse ID map is allowed only when
  maximum ID fits and the capability matrix covers it;
- config/tokenizer BOS, PAD, and EOS declarations must agree when both are present; an EOS config
  list may contain additional valid stop IDs explicitly represented in metadata;
- every declared special ID resolves in the tokenizer backend and lies in the model vocabulary;
- tokenizer/model maximum lengths do not silently reduce/raise each other—the effective request cap
  is the minimum of validated server and model execution limits, while tokenizer max length is
  advisory unless explicitly configured; and
- runtime vocabulary additions are disabled.

Disagreement is `FailedPrecondition` (`kTokenizerModelMismatch`), not a warning. The inspector prints
both values without dumping vocabulary content.

### 14.4 Queue and byte accounting

`TokenizerPool::Submit` validates fixed metadata and reserves prompt-owned bytes before moving the job
into the bounded channel. Return mappings:

| Condition | Status/reason |
|---|---|
| input or rendered per-request byte limit | `ResourceExhausted` / `kTokenizationInputLimit` |
| queued-job capacity full | `ResourceExhausted` / `kTokenizationQueueFull` |
| queued-byte budget full | `ResourceExhausted` / `kTokenizationByteBudget` |
| deadline already expired or wait expires | `DeadlineExceeded` / `kTokenizationDeadline` |
| caller/engine stop | `Cancelled` / `kTokenizationCancelled` |
| pool closed | `FailedPrecondition` / `kTokenizationPoolClosed` |

Queue time, render time, encode time, input/rendered bytes, output token count, worker saturation, and
status/reason are recorded as values/counters in M3; exporter integration waits for M10. No prompt
text, token string, chat message, path credential, or full absolute deployment path enters ordinary
logs/metrics.

Accepted jobs have exactly one completion even on cancellation/shutdown. The worker checks deadline
before render and encode and after dependency return; a dependency call itself is not forcibly
interrupted. M3 measures worst-case overshoot and bounds input size. If a tokenizer call can hang on
bounded valid input, the dependency fails qualification; detaching/leaking a worker is forbidden.
