# M4 implementation specification: reference operators and production CUDA backend adapters

- Status: proposed implementation contract
- Roadmap milestone: M4 in [`docs/plan.md`](../plan.md)
- Prerequisites: completed [M2](m2.md) and [M3](m3.md) contracts
- Immediate consumer: M5 single-request Llama execution
- Later consumers: M6 paged KV, M7 continuous batching, M12 graphs/fusion, M13 quantization, and
  M14-M16 distributed and expert execution

This document turns M4 into an executable engineering plan. It defines the independent FP32 CPU
reference, the hardware-neutral operator contracts, deterministic kernel selection, cuBLASLt GEMM,
CUDA glue kernels, contiguous causal MHA/GQA, the FlashInfer decision gate, warm-up, numerical
evidence, failure containment, and the exact handoff to M5. M4 implements and validates operations;
it does not implement a complete model executor or serving engine.

## 1. Outcome

At the end of M4, a supported InferX build can:

1. execute embedding, GEMM, RMSNorm, Llama RoPE, causal MHA/GQA, SiLU/SwiGLU, residual addition, and
   logits through a deterministic FP32 CPU reference;
2. describe every operation with checked shapes, dtypes, layouts, alias rules, workspace, phase, and
   asynchronous lifetime requirements without exposing a CUDA type to the control plane;
3. select a backend through a frozen `KernelRegistry`, including an explicit forced-backend mode for
   correctness and failure tests;
4. prepare and launch FP16, BF16, and FP32 dense GEMMs through cuBLASLt with FP32 accumulation,
   bounded workspace, a bounded algorithm cache, and no online benchmark search;
5. execute the small CUDA glue operations required by one dense Llama decoder layer;
6. append/read a correctness-oriented contiguous KV layout and execute causal prefill or decode for
   MHA and GQA;
7. use a qualified ahead-of-time native FlashInfer attention adapter when ADR 0029 accepts it, or a
   simple owned CUDA attention fallback for the complete M5 capability envelope when it does not;
8. warm and validate all required operation/backend capability classes before a model becomes ready;
9. compose one decoder layer on CPU and CUDA and compare every named intermediate against the
   independent reference; and
10. report stable capability, selection, workspace, numeric, dependency, sanitizer, and benchmark
    evidence sufficient for M5 to choose its initial supported model envelope.

The principal dependency and dispatch flow is:

```text
M3 ModelSpec + ParameterCatalog + mapped tensor leases
  -> private artifact/tensor adapter
  -> M2 TensorView / Buffer / device resources
  -> typed M4 operation request
  -> validate contract and derive KernelKey
  -> frozen KernelRegistry capability lookup
  -> prepared backend plan + bounded WorkspaceLease
  -> CPU call, or asynchronous CUDA launch on the caller's stream
  -> caller-owned CompletionFence and resource bundle
  -> comparison evidence or M5 semantic composition
```

The semantic composition boundary remains:

```text
Llama model semantics (M5)
  -> operation contracts (M4)
  -> selected prepared kernels (M4)
  -> tensor/runtime ownership and fences (M2)
  -> CUDA runtime/cuBLASLt/qualified attention implementation
```

M4 is complete only when every shape/dtype/layout class admitted by the declared M5 envelope has a
warm-up-validated backend. A backend that works for one benchmark shape, falls back after mutating an
output, allocates on first live use, or compares only against itself is not complete.

### Implementation status (2026-09-01)

The worktree now implements the hardware-neutral contracts, bounded FP32 CPU reference executor,
stable kernel key/capability registry, transactional finite warm-up, private M3-to-M2 tensor
adapter, prepared cuBLASLt GEMM/logits adapter, owned CUDA glue kernels, and bounded contiguous-KV
causal MHA/GQA fallback. ADRs 0026-0030 are closed; ADR 0029 rejects the unavailable recorded
FlashInfer pin, and CUTLASS remains unregistered.

The CPU-only GCC C++23 build, M4 unit tests, install, and public-header probes pass. CUDA host sources
also pass strict syntax checking and the owned kernel translation unit compiles in a diagnostic SM
89 pass. This host has NVCC 12.0.140, so the supported CUDA-enabled build correctly stops at the
repository's CUDA 13 floor. Real-GPU numeric, sanitizer, stress, and performance evidence remains a
required CUDA 13 CI gate and is not represented as complete by the local results. See
[`cuda-kernel-qualification.md`](../cuda-kernel-qualification.md).

## 2. Scope boundaries

### 2.1 In scope

- Hardware-neutral, typed operation contracts and layout vocabulary for the initial dense Llama.
- A deterministic, allocation-bounded FP32 CPU reference implementation independent of CUDA,
  cuBLASLt, CUTLASS, FlashInfer, PyTorch, and model execution code.
- Exact formulas and shape rules for embedding, row-major linear/GEMM, RMSNorm, Llama rotary
  embedding, contiguous causal MHA/GQA, SiLU/SwiGLU, residual, and logits.
- A private M3 artifact-to-M2 tensor adapter with explicit lease ownership and alignment staging.
- An immutable backend-capability representation, deterministic `KernelKey`, frozen registry,
  prepared-kernel lifetime, forced backend choice, and bounded dispatch cache.
- One worker-owned cuBLASLt handle and descriptor/algorithm plan cache per CUDA device context.
- FP16/BF16/FP32 cuBLASLt inputs and outputs needed by M5, with explicit FP32 compute/scale policy.
- Small owned CUDA kernels for embedding, RMSNorm, RoPE, elementwise SiLU/multiply, residual, KV
  append, reference attention fallback, and conversions proven necessary by the accepted layout.
- Contiguous KV metadata and attention execution for prefill and decode, including GQA head mapping.
- A native, ahead-of-time-only FlashInfer qualification spike and a closed accept/reject ADR.
- CUTLASS toolchain/build audit at its recorded pin; use is optional and requires a measured gap.
- Startup/model warm-up validation, capability diagnostics, error mapping, poisoning rules, and
  shutdown/resource behavior inherited from M2.
- Unit, integration, correctness, stress, failure, Compute Sanitizer, and performance evidence.

### 2.2 Explicitly out of scope

- A complete `LlamaForCausalLM`, weight upload/memory planner, token loop, CLI generation, or greedy
  decoding. Those are M5.
- Production paged KV allocation, block tables, prefix sharing, page-size selection, or paged
  attention. Those are M6 even if an accepted attention library also offers paged kernels.
- Continuous batching, chunked prefill, mixed prefill/decode scheduling, preemption, or request
  fairness. M7/M8 own those policies.
- Sampling, top-k/top-p, RNG, penalties, stop criteria, or device-side sampling. M9/M12 own them.
- CUDA graph capture, graph cache keys, stable graph buffers, or graph replay. Those are M12.
- Quantized weights/activations, FP8, INT8, INT4, packed layouts, LoRA, sparse GEMM, MoE, sliding
  window, rope scaling, attention bias, ALiBi, or multimodal operators.
- Tensor/pipeline/expert parallel collectives or NCCL. M14-M16 add collective operations and
  rank-local layouts without changing M4's single-device mathematical reference.
- Runtime JIT compilation, NVRTC, PyTorch/Triton/Python runtime dependencies, downloading kernels,
  or checkpoint-provided code.
- General tensor expression graphs, automatic differentiation, training, arbitrary broadcasting,
  implicit dtype promotion, or a public third-party kernel plugin ABI.
- Optimized/fused kernels without an independent reference, complete capability declaration,
  workspace accounting, and benchmark evidence.

M4 preserves all accepted M0-M3 behavior:

- C++23 host targets, target-scoped warnings, format/tidy/IWYU/header/install checks, offline builds,
  reproducible dependency pins, and no locally modified submodule contents;
- Abseil `Status`/`StatusOr`, structured reason payloads, checked integer/byte arithmetic, strong IDs,

- M2 rank-eight shapes, element strides, immutable-by-default views, non-overlapping mutable views,
  move-only buffers, allocation domains, memory categories, and explicit release;
- M2 worker-owned CUDA context, nonblocking streams, typed CUDA errors, sticky-fault poisoning,
  pooled events, metadata, staging, workspace, and `CompletionFence` acknowledgement;
- no raw address as identity, no raw CUDA type outside `platform/cuda`/CUDA kernels, and no host wait

- M3's `ArtifactDType`/execution `DType` separation, exact dense Llama parameter shapes, source
  `[out,in]` weight layout, rooted mapping leases, file identity, and complete weight coverage; and
- policy/mechanism separation: model code names operations, the registry selects implementations,
  and the CUDA context owns handles/resources.

Before M4 implementation merges:

1. M2 tensor/runtime/CUDA targets and required real-GPU lane must be implemented and green;

4. ADRs 0026-0030 below must be accepted before their dependent production targets merge;
5. the FlashInfer and CUTLASS exact gitlinks must be initialized only through the `kernels`

6. the CPU-only build/test/install path must continue to configure without discovering or loading

M4 may develop CPU contracts/reference work after M2 tensor values are fixed. CUDA adapter work must
wait for M2 context, stream, workspace, and fence ownership. Artifact adaptation must wait for M3
mapping lifetime. Parallel branches use those exact public contracts rather than temporary copies.

### 5.2 FlashInfer mandatory native-C++ spike

The spike is a disposable/isolated target, not production approval. It must prove all of the
following at the exact proposed revision:

1. configuration and compilation are offline and ahead of time with the accepted CUDA toolkit,
   host compiler, and explicit SM list;
2. the production link closure contains no Python, PyTorch, TVM, Triton, JIT compiler, package
   resolver, network client, generated-at-runtime source, or writable kernel cache;
3. only a reviewed native C++/CUDA subset is built; upstream tests/examples/tools remain disabled;
4. all device buffers, workspace, metadata, stream, and launch parameters are caller-provided or
   created once during backend construction—no launch-time CUDA or unbounded host allocation;
5. the adapter accepts an explicit non-default CUDA stream and makes no device/stream synchronize;
6. every supported dtype, head dimension, GQA ratio, phase, sequence range, alignment, and SM is
   expressible as a capability predicate before launch;
7. unsupported input returns a typed status without launch or output/KV mutation;
8. native exceptions/asserts/fatal macros cannot cross the adapter; asynchronous CUDA errors use
   M2's health classifier and poison rules;
9. prefill and decode outputs match section 17's independent reference matrix, including non-power-
   of-two lengths, empty-padding boundaries, GQA, high positions, and adversarial finite values;
10. memcheck, racecheck, initcheck, and synccheck pass for the complete accepted subset;
11. repeated mixed-shape, multi-stream invocation has no global mutable race or cross-stream scratch
    reuse; and
12. binary size, clean build time, adapter overhead, and kernel performance are recorded against the
    owned fallback and an equivalent direct upstream/native call.

If the pin fails, first determine whether an unmodified later upstream revision meets the contract.
If no reviewable pin does, reject it. Do not carry an undocumented local patch or retain Python/JIT
only for attention. The `inferx::ops` contract and correctness corpus remain unchanged either way.

### 5.3 CUTLASS audit

Initialize the recorded pin in the same isolated profile and record:

- accepted NVCC/host-language mode and SM compilation matrix;
- exact headers/components and whether nested dependencies are needed;
- clean and incremental build time plus object/binary size for the smallest useful instantiation;
- diagnostics, exception/assert behavior, stream/workspace ownership, and sanitizer results; and
- correctness/performance against cuBLASLt for any shape proposed for registration.

The valid baseline outcome is “qualified but unused.” Adding a CUTLASS backend requires a specific
missing capability or at least a 5% end-to-end-relevant improvement, not a favorable isolated shape.
Its public types remain confined to CUDA adapter translation units.

## 7. Common operator contract

### 7.1 Tensor and layout conventions

All public contracts use M2 `TensorView`/`MutableTensorView`. M4 does not add another tensor owner.
The baseline conventions are:

- logical activations are row-major `[tokens, hidden]`;
- dense weights are row-major `[out_features, in_features]`, matching M3 safetensors;
- a linear operation computes `Y = X * W^T`, not `X * W`;
- Q/K/V use logical row-major `[tokens, heads, head_dim]`;
- contiguous KV uses `[batch, max_context, kv_heads, head_dim]` for K and V separately;
- token IDs and positions are signed 32-bit execution metadata after checked conversion from strong
  host values; negative values are invalid;
- strides are in elements and must satisfy M2 reachability/non-overlap analysis;
- the initial CUDA production path accepts contiguous dense tensors only unless a capability
  explicitly advertises a tested padded leading dimension; and
- rank-zero and zero-sized generic tensors remain valid M2 values, but each operation below states
  whether an empty semantic invocation is legal.

An operation never guesses a transpose from dimensions. Layout, transpose, dtype, and phase are
explicit fields included in validation and the kernel key. Unsupported non-contiguous input returns
`Unimplemented`; invalid reachability/overlap returns `InvalidArgument`.

### 7.2 Execution and asynchronous semantics

Each typed request contains only non-owning views and value metadata. It has a `Validate()` path that
performs all shape, dtype, device, stride, alias, range, and checked-arithmetic validation before
backend selection. Validation must make no CUDA call and must leave outputs unchanged.

A prepared backend launch receives an operation request, a caller-owned operation context, and an
already acquired workspace slice. CPU success means complete. CUDA success means queued on the
explicit compute stream; it does not mean complete. The caller records a `CompletionFence` after the
last dependent launch and retains:

- every input/output/weight/KV buffer owner;
- the prepared-kernel/descriptor plan if the backend requires it;
- metadata and workspace leases; and
- any library-specific scratch lease

until the fence is observed and acknowledged. No operation creates, synchronizes, or destroys a
stream. No operation returns a fence that covers only part of a composed layer.

### 7.3 Aliasing rules

Default: output byte ranges may not overlap any input or weight range. Exact in-place aliasing is
permitted only where the operation contract says so:

| Operation | Allowed alias |
|---|---|
| residual add | output may exactly equal left or right input, never a partial overlap |
| elementwise SiLU | output may exactly equal input |
| elementwise multiply | output may exactly equal one input if it does not overlap the other |
| RMSNorm | baseline is out-of-place; an optimized in-place variant needs a separate capability |
| RoPE | Q output may exactly equal Q input and K output may exactly equal K input; Q/K may not overlap |
| GEMM/logits | no input/weight/output overlap |
| embedding | IDs/weight/output may not overlap |
| attention | output may not overlap Q/K/V/KV; KV append writes only validated destination slots |

Alias validation uses allocation identity plus checked byte intervals, never raw-pointer equality
alone. A backend advertises only alias modes it implements. Auto selection may not choose a backend
whose alias capability is weaker than the request.

### 7.4 Dtype and accumulation policy

The CPU reference accepts FP32 operation tensors. Test-only materialization converts FP16/BF16
inputs to FP32 before reference execution with exact IEEE storage conversion.

The initial CUDA capability accepts FP32, FP16, and BF16 storage where specified. Reductions,
RMSNorm statistics, attention scores/softmax accumulation, and FP16/BF16 GEMM accumulation use FP32.
Output storage is explicit per operation. There is no implicit mixed input family, integer-to-float
promotion, stochastic rounding, flush-to-zero promise, or TF32 in the baseline key.

`ops.math_mode=fp32_accumulate` fixes the semantic compute class, but different qualified kernels may
round at different intermediate points. Section 17 compares them by documented error metrics. Fast
math, TF32, reduced-precision reduction, or fused variants require distinct capability/key values and
an ADR-supported error study; they cannot impersonate the baseline.

### 7.5 Empty values and validation order

Validation order is deterministic:

1. validate enum/version fields and device equality;
2. validate dtype support;
3. validate rank and dimensions;
4. validate strides, reachability, alignment, and mutability/non-overlap;
5. validate operation-specific metadata, IDs, positions, sequence offsets, and ranges;
6. calculate all element/byte/workspace sizes with checked arithmetic;
7. validate alias policy; and
8. derive the normalized kernel key.

Embedding/GEMM/RMSNorm/RoPE/SwiGLU/residual/logits with zero tokens are successful no-ops after full
metadata validation and make no backend call. Hidden/head/vocabulary dimensions themselves must be
positive. Attention permits zero total query tokens as a no-op, but every nonempty query sequence
must have at least one causally visible key. A zero batch is rejected because it usually indicates
bad metadata rather than useful work.

## 8. Exact CPU FP32 reference operators

The reference library uses direct, readable loops with fixed traversal order. It does not call a
vendor BLAS, Eigen, oneDNN, a CUDA library, or an optimized M4 kernel. It is built without fast-math;
tests record compiler/version. It may be slow and is limited by configurable reference element/ops
caps so malformed or accidental production-sized inputs cannot consume unbounded CPU time.

Reference functions allocate no hidden output. The caller supplies validated output storage and any
explicit scratch buffer. Tests may use an owning fixture helper outside the operator library.

### 8.1 Embedding

Inputs:

- `token_ids`: contiguous rank-1 `[T]`, signed 32-bit;
- `weight`: contiguous FP32 `[V,H]`; and
- `output`: mutable contiguous FP32 `[T,H]`.

For every `t`, require `0 <= token_ids[t] < V`, then copy row `weight[token_ids[t], :]` to output.
Validate all IDs before the first output write so an invalid late ID cannot leave a partial result.
Repeated IDs are legal. `T=0` is a no-op; `V` and `H` are positive. CUDA uses a separate device-side
validation strategy or relies on already validated immutable token metadata, but failure tests still
prove out-of-range IDs cannot cause an out-of-bounds read.

### 8.2 GEMM and dense linear

The canonical operation is:

```text
A: [M,K]
B: [N,K]  (logical weight layout [out,in])
C: optional [M,N]
D: [M,N]
D[m,n] = alpha * sum(k=0..K-1, A[m,k] * B[n,k]) + beta * C[m,n]
```

Baseline Llama uses `alpha=1`, `beta=0`, and no C. The contract retains finite FP32 `alpha/beta` and
explicit transpose/layout fields needed by a general cuBLASLt adapter, but unsupported combinations
fail capability selection. `M=0` is a no-op; `K` and `N` are positive. The reference accumulates in
FP32 in increasing `k` order. A test-only FP64 oracle estimates conditioning; it is not the runtime
reference and is never used to make an optimized backend look artificially close.

Dense projections map directly:

| Projection | A | B | D |
|---|---|---|---|
| Q | `[T,H]` | `[Nq*D,H]` | `[T,Nq*D]` |
| K/V | `[T,H]` | `[Nkv*D,H]` | `[T,Nkv*D]` |
| attention output | `[T,Nq*D]` | `[H,Nq*D]` | `[T,H]` |
| MLP gate/up | `[T,H]` | `[I,H]` | `[T,I]` |
| MLP down | `[T,I]` | `[H,I]` | `[T,H]` |
| logits | `[T,H]` | `[V,H]` | `[T,V]` |

No projection silently reshapes or transposes its weight.

### 8.3 RMSNorm

Inputs are FP32 `x[T,H]`, `weight[H]`, finite positive `epsilon`, and `y[T,H]`. For each token:

```text
mean_square = (sum(i=0..H-1, x[i] * x[i])) / H
inverse_rms = 1 / sqrt(mean_square + epsilon)
y[i] = x[i] * inverse_rms * weight[i]
```

Sum, division, square root, and multiplication are FP32 operations in fixed order. Weight and input
must be finite for the normal correctness corpus; section 17 separately exercises NaN/Inf behavior.
`epsilon` comes from normalized M3 `ModelSpec` and is revalidated finite/positive at preparation.
Baseline is out-of-place because overwriting input during a parallel reduction is unsafe.

### 8.4 Llama rotary position embedding

The baseline supports unscaled Llama RoPE over the complete even `head_dim=D`; partial rotary
dimensions and rope-scaling objects remain unsupported. Logical Q is `[T,Nq,D]`, K is `[T,Nkv,D]`,
and positions are `[T]` nonnegative values below `max_position_embeddings`.

For `i` in `[0,D/2)`:

```text
frequency(i) = rope_theta ^ (-2*i/D)
angle(t,i) = position[t] * frequency(i)
pair = (i, i + D/2)
out_first  = x_first * cos(angle) - x_second * sin(angle)
out_second = x_second * cos(angle) + x_first  * sin(angle)
```

This half-split pairing matches the supported Hugging Face Llama semantics; it is not adjacent
even/odd pairing. Apply the same positions/frequencies to every Q and K head. V is not rotated.
Reference sin/cos are computed in FP32 from the normalized `rope_theta`. A CUDA backend may use a
precomputed table owned by the eventual model instance, but table dtype, maximum position, and
generation formula are part of its capability and correctness evidence. M4 itself does not decide
model weight/cache allocation.

### 8.5 SiLU, gated product, SwiGLU, and residual

Elementwise SiLU is:

```text
silu(x) = x / (1 + exp(-x))
```

The Llama MLP reference composes:

```text
gate = Gemm(x, gate_weight)
up   = Gemm(x, up_weight)
activated[t,i] = silu(gate[t,i]) * up[t,i]
output = Gemm(activated, down_weight)
```

`gate` and `up` are `[T,I]`; output is `[T,H]`. A fused CUDA SiLU-multiply kernel is allowed because
it is a bounded elementwise glue operation, but fused gate/up GEMM or down-projection fusion is not a
baseline requirement. It needs its own key/capability and comparison against the unfused path.

Residual addition requires equal shape/dtype/device and computes `out = left + right` elementwise.
Only the exact aliases in section 7.3 are valid. Partial overlap fails before writing.

### 8.6 Contiguous causal MHA/GQA and KV append

The flattened ragged request has:

- Q `[Tq,Nq,D]` after RoPE;
- newly projected/rotated K and projected V `[Tnew,Nkv,D]`;
- `query_indptr[B+1]` and `new_kv_indptr[B+1]`, starting at zero, nondecreasing, and ending at
  `Tq`/`Tnew`;
- `query_positions[Tq]`, strictly increasing within each sequence for the initial capability;
- `kv_lengths_before[B]` and `max_context`;
- separate mutable contiguous K/V buffers `[B,max_context,Nkv,D]`; and
- output `[Tq,Nq,D]`.

Initial prefill requires each sequence's query and new-KV counts to be equal and positions to be the
contiguous range beginning at `kv_lengths_before[b]`. Initial decode requires zero or one new token
per sequence and one query when present. Mixed prefill/decode batches are outside M4 even though the
metadata representation does not preclude them.

Validate the complete append plan before writing. Then append K/V at their absolute positions. For
query head `hq`, define `group_size=Nq/Nkv` and `hkv=floor(hq/group_size)`. Require positive heads and
`Nq % Nkv == 0`. For a query at absolute position `p`, visible keys are exactly positions `[0,p]`:

```text
score[j] = dot(Q[p,hq,:], K[b,j,hkv,:]) / sqrt(D), 0 <= j <= p
m = max(score)
prob[j] = exp(score[j] - m) / sum(k=0..p, exp(score[k] - m))
output[p,hq,d] = sum(j=0..p, prob[j] * V[b,j,hkv,d])
```

Dot products, maximum, exponentials, sum, probabilities, and V accumulation use FP32 in the
reference. The stable max-subtraction is mandatory. There is no dropout, bias, sliding window,
prefix mask, arbitrary attention mask, or cross attention. Every query has at least itself/new or a
prior key, so the all-masked case is rejected rather than assigned an arbitrary value.

KV append and attention form one semantic submission for tests: if a synchronous validation/launch
failure occurs before append launch, nothing is queued. Once writes are queued, an asynchronous
fault makes the result and affected context unusable under M2's poison policy; M4 never retries on a
second backend over potentially modified KV.

### 8.7 Logits

Logits is a named operation even though its mathematical core is GEMM. It validates hidden
`[T,H]`, LM-head weight `[V,H]`, and output `[T,V]`. The M5 baseline requests FP32 output so greedy
selection can consume a stable representation later; a lower-precision logits output requires a
separate capability. Tied embeddings use the same underlying weight owner but do not change the
operation contract.

`LogitsOp` may select the cuBLASLt GEMM backend internally, but keeps a distinct `OpKind`/key because
vocabulary size, output dtype, downstream lifetime, and benchmark envelope differ from internal
projections. It performs no softmax or sampling.

## 9. Artifact-to-execution tensor adapter

M3 mapping exposes validated bytes plus `ArtifactDType`, shape, range, and a lease. M2 tensor views
require execution `DType`, checked shape/strides, alignment, and an owner that outlives the view. The
private adapter performs exactly this translation; neither subsystem depends on the other.

For each mapped parameter:

1. require the `WeightPlanItem` identity/shape to match the requested `ParameterSpec`;
2. map only through M3 `ValidatedModelPackage::MapTensor` and retain its lease;
3. translate only F32/F16/BF16 to M2 dtype; valid but unsupported artifact dtypes return
   `Unimplemented`;
4. build a checked M2 shape and contiguous element strides;
5. verify mapped bytes equal the execution tensor's exact byte count;
6. if base address/offset meets dtype and selected backend alignment, expose a host immutable view
   retaining the mapping lease;
7. otherwise allocate a bounded aligned host staging buffer, copy the exact validated range, and
   retain that owner instead; and
8. publish a move-only adapted tensor whose view cannot outlive either mapping or staging storage.

No adapter casts unaligned bytes, changes endianness, transposes `[out,in]`, converts dtype, or uploads
to CUDA. Test-only `ReferenceTensorMaterializer` may convert F16/BF16 to FP32 under an explicit
element cap for CPU comparison. M5 owns model-wide device allocation and H2D upload planning.

Mapping and staging failures are transactional. Diagnostics identify canonical parameter ID/name,
artifact dtype/shape, required execution dtype/alignment, shard path, and reason without logging raw
addresses or model bytes.

## 10. Backend capability and `KernelRegistry`

### 10.1 Stable vocabulary and key

Use closed, versioned enums for at least:

```text
OpKind: embedding, gemm, rms_norm, rope, silu_multiply, residual, attention, logits
ExecutionPhase: generic, prefill, decode
BackendId: reference, cublaslt, inferx_cuda, flashinfer, optional cutlass
MathMode: fp32_accumulate (baseline), explicitly approved future modes
LayoutId: row_major_dense, qkv_token_head_dim, contiguous_kv_bshd
AliasMode: disjoint, exact_left, exact_right, exact_in_place
```

`KernelKey` contains only durable values:

- schema version and operation kind;
- phase;
- device kind and CUDA compute capability when applicable;
- input/weight/output dtypes and compute/math mode;
- rank, normalized logical dimensions, layout IDs, and supported leading dimensions;
- transpose/epilogue/alias modes;
- attention head counts, head dimension, causal flag, KV layout, and bounded sequence bucket;
- workspace limit/alignment class; and
- graph compatibility field reserved as `kNotGraphCaptured` in M4.

It contains no pointer, allocation ID, stream/event handle, request/model ID, opaque library object,
wall time, randomized hash seed, or artifact filename. Durable serialization uses fixed-width
little-endian/length-delimited records and a stable hash, not `std::hash`/`absl::Hash`.

### 10.2 Capabilities

A backend capability is an immutable declaration of exact or checked ranges for:

- operation/phase/device/SM;
- dtypes and accumulation/output policy;
- ranks, dimensions, head geometry, sequence/context limits;
- required contiguous/padded layouts and minimum alignment for each operand;
- legal alias modes;
- workspace-size/alignment function;
- deterministic/reproducibility classification;
- whether preparation may call library heuristics;
- whether launch performs any host or device allocation (production requires no); and
- backend/contract/dependency version strings used in diagnostics.

Capability matching is pure and returns either a normalized match plus exact workspace request, or a
typed rejection reason. It does not attempt a launch. Predicates must be testable at boundary-1,
boundary, and boundary+1. A broad “supports FP16 attention” flag is insufficient.

### 10.3 Registration, freeze, and deterministic selection

Registration occurs on the owning worker during context/model initialization. Duplicate
`(BackendId, capability_id)` or ambiguous exact-priority entries fail startup. `Freeze()` validates
the registry, sorts entries by stable backend priority then capability ID, builds bounded lookup
tables, and forbids further mutation. Concurrent lookup after freeze is read-only.

Selection order is:

1. validate the operation and derive its normalized key;
2. if a backend is forced, inspect only that backend and return its precise rejection;
3. otherwise enumerate registered entries in configured stable priority;
4. discard nonmatching capabilities and workspace requests above the caller cap;
5. select lowest configured priority, then stable capability ID as tie-break; and
6. return one `KernelSelection`, including rejected-candidate summaries for diagnostics.

Selection never depends on registration order, pointer order, unordered-container iteration, or
current load. Performance-derived priority changes only through committed benchmark evidence and
configuration/ADR, not an online race.

There is no fallback after launch begins. A preparation failure may try the next candidate only in
`auto` mode, before any output mutation and during preparation/warm-up. Forced mode returns the
failure. Synchronous launch error returns failure and preserves M2 health classification; uncertain
asynchronous errors poison the context. Retrying another kernel is forbidden.

### 10.4 Prepared kernels and bounded cache

Library descriptor creation, heuristic queries, candidate timing, and host allocation happen only in
an explicit `Prepare(key)` phase. The result is an immutable/move-only `PreparedKernel` owned by a
bounded per-context cache or model warm-up bundle. Launch uses already prepared descriptors and an
existing workspace lease.

Cache identity includes the complete normalized key plus backend and dependency/runtime versions.
Capacity is fixed at startup. Warm-up may fill it transactionally; capacity exhaustion is a startup
`ResourceExhausted` error with required/available counts. Serving does not evict a live prepared
kernel or grow the cache. Later milestones may introduce offline-generated buckets, but cannot hide
an unbounded shape-key cache.

Opaque vendor algorithm structs are never serialized as a durable cross-version cache. A local
diagnostic record may serialize documented algorithm attributes alongside exact toolkit/driver/SM,
but process startup revalidates/reselects the vendor object.

## 11. CPU reference executor

`CpuReferenceExecutor` is a thin dispatcher over the typed reference functions. It:

- accepts host-addressable FP32 tensors only;
- validates with the same operation contract used before CUDA dispatch;
- enforces configurable `max_reference_elements` and `max_reference_flops` using checked arithmetic;
- uses caller-provided output/scratch storage;
- performs no hidden thread-pool creation and defaults to a single deterministic thread;
- returns only after completion; and
- emits no backend selection based on CPU ISA.

The reference is correctness infrastructure, not a production CPU inference backend. Optional SIMD
or parallel CPU kernels must register as separate optimized backends and compare against it. Compiler
autovectorization is acceptable only if it preserves the declared FP32 semantics; build flags never
enable unsafe math reassociation.

A debug `ReferenceTrace` can record operation kind, normalized shapes, and per-output summary
(finite/NaN/Inf counts, min/max, L1/L2 norms, checksum). It never records full model values by
default. M5 may use this trace for intermediate diagnostics without embedding reference logic in its
model semantics.

## 12. cuBLASLt GEMM adapter

### 12.1 Ownership and API boundary

Create one `CublasLtContext` per M2 `CudaDeviceContext`/device worker. It owns a `cublasLtHandle_t`,
prepared descriptors/algorithm plans, and bounded diagnostics. It is constructed after the CUDA
device is pinned and destroyed before the underlying context/streams. It is worker-thread-affine;
M4 does not assume vendor-handle concurrent thread safety.

cuBLASLt types and calls remain in `platform/cuda/src/ops`. Generic headers see only backend IDs,
capabilities, and prepared-plan handles hidden behind an internal implementation. Every create/set/
heuristic/check/matmul/destroy status is translated with operation and scope.

### 12.2 Descriptor mapping

For canonical `D = A * B^T`:

- A is row-major `[M,K]`;
- B is row-major `[N,K]` and uses an explicit transpose in the operation descriptor;
- D is row-major `[M,N]`;
- C is omitted/aliased to D only under the exact vendor-valid beta-zero convention selected by the
  adapter; and
- leading dimensions and batch strides are derived from validated element strides with checked
  narrowing to vendor integer types.

Set every relevant descriptor attribute explicitly: compute type, scale type, transpose modes,
matrix order, rows/columns/leading dimensions, batch count/stride, epilogue, pointer mode, and math
mode. Do not rely on a column-major default. Baseline alpha/beta live in stable host storage for the
duration of the launch call. Unsupported row-major epilogues are not requested; SiLU/SwiGLU remain
separate unless a later qualified backend supplies the exact semantic fusion.

FP16 and BF16 inputs use FP32 compute and FP32 scale. FP32 uses the accepted pedantic/default FP32
compute chosen by ADR 0028, with TF32 disabled for the baseline. Output dtype follows the operation
contract; logits baseline is FP32.

### 12.3 Algorithm selection and cache key

The cuBLASLt plan key includes:

- CUDA runtime and cuBLASLt versions plus SM;
- M/N/K, batch count, all dtype/compute/scale/transposition/layout fields;
- leading/batch strides and epilogue;
- minimum actual alignment class of A/B/C/D;
- workspace cap and alignment; and
- deterministic/math-mode requirements.

Preparation creates descriptors, queries a bounded number of heuristic candidates, discards any
non-success result or workspace overflow, calls `cublasLtMatmulAlgoCheck`, and validates returned
workspace. Because an algorithm check cannot prove actual pointer alignment/launch success, warm-up
executes candidates on representative real-alignment buffers and checks completion/output.

`ops.warmup_mode=validate` chooses the first valid candidate in stable heuristic order after
correctness. Explicit offline `benchmark` mode times a bounded candidate set with M2 timing events,
discards warm-up iterations, uses median of at least 30 measured iterations, and chooses the faster
candidate only when the confidence/noise rule in ADR 0028 distinguishes it; otherwise stable order
wins. No live request performs this search.

### 12.4 Workspace and launch

Heuristic-reported workspace must fit the operation's M2 `WorkspaceLease` and satisfy at least the
vendor-required 256-byte alignment. Preparation stores the exact byte/alignment requirement. Launch
rechecks the supplied slice, operand device/shape/alignment class, current healthy context, and
explicit compute stream before calling `cublasLtMatmul`.

Launch performs zero CUDA allocation, descriptor creation, heuristic query, timing, synchronization,
or host heap allocation. It checks immediate status and `cudaPeekAtLastError` through M2's API seam.
Completion/sticky errors are observed through the caller's later fence. The adapter does not own or
release caller buffers/workspace.

### 12.5 Direct-call overhead gate

Benchmark the prepared adapter against a direct `cublasLtMatmul` call using the same handle,
descriptors, algorithm, workspace, stream, operands, iteration protocol, and clocks. Separate host
submission overhead from kernel elapsed time. Median adapter overhead must be <=3%; a near-zero direct
host time also reports absolute nanoseconds and confidence interval so a ratio is not misleading.

## 13. Owned CUDA glue kernels

The baseline may own only kernels whose semantics are small, stable, and not adequately served by
cuBLASLt/accepted attention backends:

- embedding gather;
- RMSNorm;
- Llama RoPE;
- SiLU plus elementwise gate/up multiply;
- residual addition;
- validated contiguous KV append; and
- bounded correctness attention fallback.

Every kernel has a host launcher isolated in `platform/cuda`, an explicit stream, checked launch
geometry, immediate launch check, capability declaration, and no device-side dynamic allocation,
cooperative global synchronization, printf, assert, or unchecked index arithmetic. Kernels use
64-bit checked host calculations and narrow only after grid/device-limit validation.

Kernel inputs are immutable except declared outputs/KV destinations. Tail elements are bounds
checked. Reductions initialize all shared/register lanes, use barriers only under uniform control,
and have dedicated racecheck/initcheck/synccheck fixtures. FP16/BF16 values convert to FP32 for
reduction/math and cast once at output unless ADR 0026 specifies otherwise.

Custom tuning follows a fixed process:

1. land/reference-test the simplest correct kernel;
2. enumerate capability boundaries and failure cases;
3. run all Compute Sanitizer tools;
4. benchmark representative and adversarial shapes against the same semantic baseline;
5. register only shapes where it is correct and justified; and
6. retain a forced reference/fallback route for diagnosis.

No “temporary” broad capability predicate is permitted. An optimized variant that covers fewer
shapes has a narrower capability ID and deterministic priority. Removing a slow simple kernel is
allowed only after another owned/qualified backend covers its complete required envelope.

## 14. CUDA attention backends

### 14.1 Common attention adapter contract

Both FlashInfer and the owned fallback consume the normalized section 8.6 request. The adapter
validates host metadata before upload, uses M2's generation-checked metadata ring, and supplies device
views plus the caller's stream/workspace. It never parses model config or allocates KV.

The baseline capability distinguishes:

- phase `prefill` versus `decode`;
- storage dtype FP32/FP16/BF16 and FP32 accumulation;
- `Nq`, `Nkv`, group size, and even `D`;
- total query/new-KV tokens, per-sequence lengths, batch, maximum context, and position range;
- contiguous separate K/V layout only;
- causal mask only;
- no dropout/bias/window/rope inside attention; and
- output storage dtype.

RoPE is applied before KV append. K cache therefore stores rotated K; V stores projected V. Decode
must not rotate cached K again. This convention is documented and tested at the boundary because a
different cache convention can produce plausible but wrong outputs.

### 14.2 Owned fallback envelope

If FlashInfer is rejected, the owned fallback must cover the entire M5 envelope. At minimum its
declared capability is:

- contiguous K/V and causal self-attention;
- FP32, FP16, and BF16 storage with FP32 score/softmax/value accumulation;
- `1 <= B <= 8`;
- positive `Nkv <= Nq <= 64` with `Nq % Nkv == 0`;
- even `2 <= D <= 256`;
- `max_context <= 4096`;
- prefill total query tokens `<=512`, decode at most one query per sequence; and
- all positions/lengths satisfying section 8.6.

These are capability maxima, not a claim of production performance. M5 may choose a narrower
envelope but not a wider one without expanding M4 tests/backends. The simple kernel may use multiple
passes/workspace for scores and softmax; it must remain bounded by the workspace function and cannot
allocate based on live lengths.

The fallback is a correctness/survival backend, not permission to advertise production long-context
throughput. It still must be race-free, support multi-stream instances with disjoint resources, and
meet the numeric suite. Performance is reported without a minimum speed gate except that pathological
host synchronization or per-launch allocation is forbidden.

### 14.3 FlashInfer adapter

If ADR 0029 accepts FlashInfer, map normalized metadata/layout into its reviewed native API without
semantic changes. The adapter owns any persistent plan/handler during device/model warm-up, while the
submission owns per-call workspace/metadata until its fence. Upstream global/JIT caches are disabled,
not wrapped with a mutex.

Register only the subset proven by the spike. If FlashInfer supports paged but not M4's contiguous
contract without a copy/repack, it may remain unregistered until M6; M4 must not manufacture fake
pages or hidden per-call conversion merely to claim integration. The owned fallback remains compiled
in correctness/failure builds even after acceptance.

### 14.4 Multi-stream behavior

M4 tests two nonblocking compute streams with disjoint inputs, outputs, KV buffers, workspace, and
metadata. A prepared immutable backend plan may be shared only if its library contract permits
concurrent launch; otherwise the context owns one prepared instance per stream/slot. No mutable
scratch, descriptor field, or host staging is shared without explicit ownership.

Cross-stream dependencies are expressed by M2 events. Attention does not use the default stream or
assume ordering with model upload/KV transfer. The multi-stream test checks both output isolation and
API counters for zero hidden synchronization.

## 15. Warm-up and readiness

### 15.1 Required capability set

`BuildRequiredKernelSet(ModelSpec, OperatorEnvelope)` produces a sorted finite set of normalized
operation requirements. The envelope includes:

- supported storage dtype and math mode;
- maximum batch, prompt/query tokens, context, and workspace;
- the finite token/sequence buckets M5 will submit;
- model H/I/V, layer count, Nq/Nkv/D, epsilon, theta, and maximum position; and
- prefill/decode phases and exact layouts/alias modes.

Checked derivation enumerates every Llama projection, normalization, RoPE, activation/residual,
attention class, and logits class. Equivalent layer requirements deduplicate by stable key. The
result contains no pointer or weight value. M5 may not submit outside the accepted envelope; later
milestones extend it through new warm-up evidence.

### 15.2 Warm-up transaction

Warm-up occurs after device context/pools exist and before model readiness:

1. build and validate the finite required set;
2. freeze the fully registered kernel registry;
3. select and prepare one backend for every key under the actual workspace/alignment caps;
4. allocate bounded test buffers from startup/test pools, never serving leases;
5. fill deterministic nontrivial inputs, including zero/negative/fractional values;
6. launch representative minimum, boundary, and bucket shapes on the real compute stream;
7. record/poll/acknowledge fences through the named startup wait path;
8. compare outputs and required KV mutations with CPU reference fixtures;
9. verify canary regions and M2 accounting/API counters;
10. commit the complete immutable `PreparedOperatorSet`; and
11. publish capability/readiness diagnostics atomically.

Any failure destroys the constructed prefix in reverse after safe fence handling and leaves the model
unready. No partial prepared set is published. Warm-up failures include missing backend, unsupported
SM/dtype/layout, insufficient workspace/cache/event capacity, vendor descriptor/launch error,
numeric mismatch, canary corruption, and asynchronous context poison.

### 15.3 Capability versus exact shape preparation

Capability predicates prove the complete admitted range structurally. Vendor algorithms that require
exact M/N/K descriptors are prepared for the finite shape buckets emitted by the envelope. An
unbucketed shape is rejected during plan preparation before execution, not used to trigger online
autotuning. Future schedulers may add buckets only by rebuilding/warming a new immutable prepared set
while the old set remains live for existing work.

`auto` selection may choose different backends for different keys, but the result is logged as a
sorted stable table. Readiness does not require one backend to cover every operation.

## 16. Ownership, concurrency, errors, and shutdown

### 16.1 Ownership table

| Object | Owner | Lifetime rule |
|---|---|---|
| CPU reference functions | `inferx_ops` | stateless; caller owns all views/storage |
| `KernelRegistry` | device/backend construction | mutable only before `Freeze`; then immutable until context teardown |
| cuBLASLt handle | CUDA device context/worker | created once; used on owning worker; destroyed before CUDA context |
| prepared kernel/descriptor | prepared-set cache | retained through every launch fence that may reference it |
| algorithm cache | CUDA context | fixed capacity; no serving growth/eviction |
| workspace/metadata | M2 lease in execution submission | retained through completion acknowledgement |
| artifact-adapted tensor | move-only adapter result | owns mapping or staging for full view lifetime |
| K/V buffers | future model instance/submission | M4 receives views; never owns/frees them |
| FlashInfer persistent state | CUDA attention backend | one per documented context/stream scope; closed after fences |

### 16.2 Error taxonomy

M4 extends structured `ErrorReason` without renumbering earlier values. Required semantic categories
include invalid op shape/layout/alias, unsupported operator capability, registry frozen/duplicate/
miss, preparation cache exhausted, insufficient workspace, vendor algorithm unavailable, synchronous
launch rejected, numeric warm-up mismatch, and attention metadata/KV range invalid.

Map scope consistently:

| Failure | Abseil code | Scope/action |
|---|---|---|
| malformed shape/metadata/alias/range | `InvalidArgument` | reject before backend/output mutation |
| valid but unsupported dtype/layout/phase/SM | `Unimplemented` | fail warm-up/readiness or forced request |
| workspace/cache/pool capacity | `ResourceExhausted` | fail preparation; accounting unchanged |
| registry not frozen/missing invariant | `FailedPrecondition`/`Internal` | startup programming error; no launch |
| cuBLASLt/adapter unsupported algorithm | `Unimplemented` | try next only during auto preparation |
| immediate invalid launch/resource limit | `InvalidArgument`/`ResourceExhausted` | no retry after any possible mutation |
| asynchronous illegal access/assert/device loss | `Unavailable` | first cause poisons context; drain/terminate worker per M2 |
| warm-up numeric/canary mismatch | `DataLoss`/`Internal` | backend is not registered ready; retain evidence |

Status payloads contain operation kind, backend/capability ID, normalized non-sensitive shape/dtype/
layout, phase, device/SM, workspace required/available, dependency version, and fault scope. They do
not contain tensor values, prompts, raw addresses, or unbounded lists.

### 16.3 Shutdown

M4 adds no independent shutdown thread. Device-context shutdown:

```text
reject new preparation/launch
-> drain or abandon complete execution resource bundles under M2 rules
-> release prepared operator set and vendor descriptors
-> close FlashInfer/backend persistent state
-> destroy cuBLASLt handle
-> continue M2 workspace/event/stream/context shutdown
```

If fences remain pending at deadline, retain prepared descriptors/handles and all referenced buffers
for retry; never destroy a vendor handle or unload kernel state that pending work may use. Destructors
are no-throw and nonblocking. Explicit `Close()` returns the first error plus cleanup diagnostics.

## 17. Correctness and numerical policy

### 17.1 Comparison method

For finite values, element comparison uses:

```text
abs(actual - reference) <= atol + rtol * abs(reference)
```

Also report maximum/mean absolute error, maximum/mean relative error for non-near-zero references,
L2 relative error, finite/NaN/Inf counts, and failing element count. GEMM/attention tests retain a
test-only FP64 result or forward-error estimate to distinguish conditioning from implementation
error. Passing a global norm cannot hide a catastrophic individual value unless the operation's ADR
explicitly uses a distribution metric as an additional, never sole, criterion.

Initial maximum tolerances, subject only to tightening by evidence, are:

| Operation/storage | `atol` | `rtol` | Additional gate |
|---|---:|---:|---|
| FP32 elementwise/embedding/residual/RoPE | `2e-6` | `2e-5` | embedding IDs/copies exact |
| FP32 RMSNorm/SiLU | `2e-5` | `2e-4` | finite-class agreement |
| FP32 GEMM/logits | `2e-4` | `2e-4` | scale-aware forward-error ratio recorded |
| FP32 attention | `3e-4` | `3e-4` | probability rows sum within `2e-5` in reference diagnostics |
| FP16 storage, FP32 accumulation | `2e-2` | `2e-2` | compare after output conversion to FP32 |
| BF16 storage, FP32 accumulation | `8e-2` | `5e-2` | compare after output conversion to FP32 |

M4's error-study report may define operation/shape-specific tighter thresholds for M5 logits. It may
not silently increase these maxima. If a required qualified vendor kernel exceeds a maximum for a
well-conditioned corpus, either choose another math mode/backend or accept an ADR with independent
model-level evidence before changing the gate.

### 17.2 Independent oracles and fixture provenance

The runtime CPU reference is the primary independent oracle. Committed fixtures additionally use a
hash-locked Python tool environment with straightforward PyTorch/Transformers expressions for Llama
semantics. Fixture manifests record:

- generator revision and dependency lock digest;
- seed and PRNG algorithm;
- exact shapes/dtypes/model constants;
- input/output binary digest and little-endian encoding;
- formula/layout version; and
- whether the value came from FP64, CPU FP32, or framework execution.

Ordinary runtime and CPU CTest do not require Python. Regeneration must be explicit and reviewed;
tests consume committed values. CUDA cannot be its own oracle, and comparing FlashInfer only with the
owned CUDA fallback is insufficient without CPU agreement.

### 17.3 NaN, infinity, and extreme finite values

Production operators do not scan entire tensors for finiteness. Contract tests deliberately include
NaN, positive/negative infinity, signed zero, denormals where supported, maximum finite values that
avoid intentional overflow, and softmax scores with large dynamic range.

The gate is safety and declared classification behavior:

- no out-of-bounds access, hang, illegal launch, or uninitialized output;
- embedding copies bit patterns exactly;
- elementwise operations follow IEEE classification where the formula is defined;
- reductions/softmax propagate NaN rather than fabricating an apparently valid unrelated result;
- positive-infinity attention-score combinations are handled according to ADR 0026's explicit
  reference rule or rejected from the supported finite-input capability; and
- signed-zero/denormal differences are recorded by math mode and never used as an excuse for broad
  tolerance changes.

The normal production capability promises correctness for finite model weights/activations. M4
warm-up uses finite values; adversarial classification is a separate required test lane.

### 17.4 Determinism

CPU reference traversal is deterministic for one compiler/build. Backend selection and prepared-set
serialization are deterministic for identical effective configuration, dependency/runtime versions,
SM, and benchmark-evidence mode. CUDA floating results need not be bit-identical across toolkit/SM,
but must satisfy the same committed thresholds.

Offline benchmark tuning records its evidence and selected algorithm. It is disabled in ordinary
replay/correctness tests unless the selection record is part of the test fixture. No request timing,
thread race, unordered iteration, or ambient cache contents influence selection.

## 18. Test matrix and evidence

### 18.1 Unit tests (`m4-unit`, CPU presubmit)

- Every request validation branch: rank, dtype, dimension, stride, alignment, range, zero-size, and
  exact/partial alias rules.
- Checked shape/workspace/FLOP arithmetic near integer limits.
- Exact small hand-calculated embedding, GEMM, RMSNorm, half-split RoPE, SiLU/SwiGLU, residual,
  MHA/GQA, KV append, and logits cases.
- GQA head mapping for ratios 1, 2, 4, and 8.
- Causal masking at position zero, pre-existing KV, multi-token prefill, and decode.
- Kernel-key canonical serialization, equality/hash vectors, and exclusion of pointer/registration
  order.
- Capability boundary-1/boundary/boundary+1 cases and deterministic selection tie-breaks.
- Duplicate registration, freeze, lookup-after-freeze, mutation-after-freeze, forced miss, and
  bounded prepared-cache exhaustion.
- Artifact dtype/shape/alignment adaptation and move/lifetime behavior using fake mapping owners.
- Vendor-independent fake backend preparation/launch failure injection with no mutation.

### 18.2 CUDA unit/integration tests (`m4-gpu`, required GPU presubmit)

- Each CUDA glue kernel for FP32/FP16/BF16 at tails, minimum, odd, and boundary sizes.
- cuBLASLt descriptor/key construction, heuristic filtering, workspace/alignment rejection, and one
  real prepared launch per supported dtype.
- Two nonblocking streams with disjoint resources and no default-stream/host synchronization.
- Metadata/workspace/event lease retention until final fence acknowledgement.
- Contiguous KV append/read across positions and sequence boundaries.
- Compose one complete decoder layer in this exact order:

```text
RMSNorm
-> Q/K/V GEMMs
-> RoPE(Q,K)
-> KV append + causal attention
-> output GEMM
-> residual
-> RMSNorm
-> gate/up GEMMs
-> SiLU * up
-> down GEMM
-> residual
```

Compare every named intermediate, output, and written KV region to CPU. Surround allocations with
canaries and verify untouched padding/unused KV positions. The integration harness returns before
completion, then test code polls/acknowledges through M2; it contains no hidden device synchronize.

### 18.3 Correctness sweeps (`m4-correctness`)

At minimum cover:

- dtypes: FP32, FP16, BF16 where capability exists;
- token/GEMM M: `0,1,2,7,16,31,64,127,256,512` within the backend envelope;
- representative K/N: tiny fixture dimensions plus `64,128,256,512,1024,4096` where supported;
- hidden/intermediate/vocabulary shapes from every committed M3/M5 fixture;
- RMSNorm epsilon: fixture values plus `1e-6,1e-5,1e-4`;
- RoPE positions: `0,1,2,31,127,max_position-1`, theta `10000`, head dims
  `2,8,32,64,128,256` within capability;
- attention batch: `1,2,4,8`; context: `1,2,3,31,32,127,128,511,512,1024,4096`; query counts
  across decode and non-power-of-two prefill;
- head tuples `(Nq,Nkv)` including `(1,1),(8,8),(8,4),(8,2),(32,8),(64,8)`; and
- aligned and every explicitly supported padded-leading-dimension/alignment class.

Use deterministic random inputs across at least 1,000 seeds per operation family in nightly CI,
with smaller fixed seed sets in presubmit. Record worst cases rather than only pass/fail. FlashInfer,
owned CUDA, and cuBLASLt each compare to CPU; optimized-vs-fallback comparison is supplementary.

### 18.4 Stress and concurrency (`m4-stress`)

- At least 100,000 mixed operation dispatches over a prewarmed finite key set.
- At least 100,000 workspace acquire/launch/fence/acknowledge/release cycles with accounting returning
  exactly to baseline.
- Concurrent launches on two streams for every backend declared multi-stream-safe.
- Repeated registry construction/freeze/destruction and prepared-set rollback under injected
  failures.
- Cache capacity and generation-near-wrap fake tests.
- Alternating prefill/decode and attention shapes for at least one hour nightly.
- Repeated context create/warm/close cycles; no leaked handle, event, workspace, metadata, or buffer.

Steady-state launches perform zero CUDA allocations, zero descriptor creation, zero heuristic query,
zero host heap allocations, and zero host synchronization. M2 API counters enforce this.

### 18.5 Failure tests (`m4-failure`)

- Unsupported SM/dtype/layout/math mode/head dimension/GQA ratio/phase.
- Invalid token ID, position, indptr, sequence length, KV capacity, shape, stride, alias, alignment,
  and integer overflow.
- Registry duplicate/frozen/miss and unavailable forced backend.
- Prepared-cache/workspace/event/metadata exhaustion with transactional rollback.
- Every cuBLASLt descriptor, heuristic, algorithm-check, matmul, and destruction error through fake
  seams where possible.
- Immediate CUDA launch rejection before fence and delayed illegal access/device-lost in isolated
  subprocesses.
- Numeric/canary warm-up mismatch prevents readiness.
- FlashInfer adapter reports unsupported/failure without fallback after mutation.
- Shutdown before warm-up, during preparation, with queued work, after poison, and at drain deadline.

Every failure asserts status code/reason/scope, first-poison preservation, unchanged accounting, and
whether outputs/resources are safe to reuse. Process-inconsistent CUDA faults run in subprocesses.

### 18.6 Compute Sanitizer (`m4-compute-sanitizer`)

Required owned-GPU jobs run:

- memcheck over every glue kernel, fallback attention, cuBLASLt integration, and accepted FlashInfer
  subset;
- racecheck over shared-memory reductions and concurrent-stream stress;
- initcheck over tail/partial tile, KV unwritten regions, and workspace reuse; and
- synccheck over RMSNorm/attention reductions and all kernels containing barriers.

No skipped test counts as success. Expected tool/runtime suppressions are minimal, versioned, scoped
to a dependency/toolkit pin, and linked to an upstream issue. InferX-owned findings have no
suppression path.

### 18.7 Performance evidence (`m4-performance`)

Record for every result: repository/dependency revisions, dirty state, compiler/NVCC, build type,
CUDA/driver/cuBLASLt, GPU/SM/memory/clocks/power mode, effective config, backend/capability/key,
workspace, input distribution, warm-up/iteration counts, timing method, and raw summary JSON.

Benchmarks include:

- CPU reference throughput only as a regression baseline, not a serving claim;
- frozen-registry lookup and launch-wrapper host overhead;
- each glue kernel by dtype/shape;
- prepared cuBLASLt adapter versus identical direct vendor call;
- attention backend versus direct accepted-library call where possible and owned fallback;
- one-layer CPU/CUDA breakdown; and
- representative M5 prefill/decode shapes plus boundary/outlier profiles.

Gates:

- adapter overhead <=3% versus the same underlying direct call;
- no InferX custom kernel is registered as preferred without independent correctness and a benchmark;
- a proposed optimized dependency/custom variant needs a capability or >=5% improvement on an
  end-to-end-relevant operation workload;
- no median target-shape regression >3% without accepted evidence; and
- performance claims exclude warm-up, allocation, and offline tuning unless explicitly labeled.

## 19. Diagnostics and evidence artifacts

Provide stable JSON schemas for:

### 19.1 Capability report

- schema version;
- sanitized device capability and toolkit/runtime/cuBLASLt versions;
- compiled backend IDs/dependency revisions;
- each capability ID and exact dtype/layout/shape/phase/workspace ranges;
- selected math modes and determinism classification; and
- rejected/deferred dependencies with reason.

### 19.2 Warm-up report

- model/operator-envelope fingerprint;
- sorted required keys;
- selected backend/capability per key;
- prepared workspace/cache use;
- representative validation cases and numeric summaries;
- preparation/warm-up elapsed time; and
- readiness/failure with stable reason.

### 19.3 Benchmark/correctness report

- environment/evidence metadata from section 18.7;
- per-case latency/throughput/error statistics;
- worst numeric cases with seed and fixture digest;
- direct-call comparisons; and
- sanitizer/test command plus exit status.

Reports omit pointers, hostnames, raw tensor/model values, prompts, request IDs, UUIDs in committed
goldens, and unbounded vendor logs. Local diagnostic mode may include a redacted device name and
hashed UUID under M2 policy.

Backend selection/tuning is not part of M3's content `ModelFingerprint`: two machines may select
different correct kernels for the same model. M4 creates a separate local
`OperatorCompatibilityFingerprint` over operator contract version, effective capability envelope,
math mode, layout versions, toolkit/backend versions, and prepared-key schema. It excludes opaque
algorithm bytes and timing results. M5 records both identities in diagnostic manifests.

## 20. Implementation sequence and independently verifiable gates

Each slice is independently reviewable and keeps earlier CPU tests green.

### M4.0 — Dependency spikes and decisions

- Initialize FlashInfer/CUTLASS through the explicit kernels profile.
- Run native build/toolchain/closure spikes and archive evidence.
- Accept ADRs 0026-0030; close FlashInfer as accepted or rejected.
- Do not merge a production dependency target in this slice.

Gate: reproducible offline spike commands, recursive closure/license report, exact CUDA/SM matrix,
and a closed attention fallback decision.

### M4.1 — Common contracts and CPU reference

- Add hardware-neutral operation values/validation.
- Implement all section 8 FP32 references and hand-calculated tests.
- Add fixture generator/lock and committed independent values.

Gate: CPU-only build/install/header tests; ASan/UBSan; exact small cases; randomized reference checks;
no CUDA dependency discovery.

### M4.2 — Registry, capabilities, and fake backends

- Add stable key serialization, capability predicates, registry freeze/selection, prepared-cache
  contract, and forced backend configuration.
- Exercise all deterministic/failure behavior with fake CPU backends.

Gate: boundary matrix, insertion-order/property tests, preparation rollback, zero allocations after
prewarmed lookup benchmark.

### M4.3 — Artifact/tensor adaptation

- Add the private M3-to-M2 adapter and aligned staging behavior.
- Prove mapping/staging ownership with fake and tiny M3 artifacts.

Gate: no view outlives owner, no unaligned cast, supported dtype/shape exactness, resource caps and
failure rollback.

### M4.4 — cuBLASLt GEMM

- Add worker-owned handle, descriptor wrappers, heuristic/check preparation, bounded plan cache,
  workspace use, and forced adapter.
- Qualify FP32/FP16/BF16 GEMM/logits shapes.

Gate: CPU correctness sweep, fake failure coverage, direct-call <=3% overhead, no steady-state
allocation/sync, Compute Sanitizer clean.

### M4.5 — CUDA glue kernels

- Add embedding, RMSNorm, RoPE, SiLU-multiply, residual, and KV append in the simplest correct form.
- Register exact capabilities only after per-kernel evidence.

Gate: dtype/shape/tail/adversarial corpus, sanitizer suite, launch counters, and microbenchmarks.

### M4.6 — Attention backend

- Implement the common adapter and owned bounded fallback.
- Integrate FlashInfer only if ADR 0029 accepted its exact native subset.
- Validate prefill/decode, MHA/GQA, KV convention, and multi-stream behavior.

Gate: full attention sweep, no hidden JIT/Python/allocation/sync, sanitizer clean, dependency/direct
benchmark evidence, forced fallback retained in tests.

### M4.7 — Warm-up and one-layer integration

- Derive the finite required set from `ModelSpec` plus M5 envelope.
- Build transactional prepared set/readiness diagnostics.
- Compose one decoder layer with intermediate comparison and fence/resource lifetime.

Gate: every M5 key prepared, every intermediate within tolerance, rollback tests, counters at
baseline, no first-use preparation in the integration execution path.

### M4.8 — Evidence, documentation, and handoff

- Run nightly stress/Compute Sanitizer/performance matrix.
- Commit capability, numeric, and benchmark reports.
- Finalize operator/registry/kernel qualification docs and M5 supported envelope.

Gate: definition of done checked with exact artifact links and no open blocker disguised as a TODO.

## 21. Exact developer and CI acceptance flow

Command names may be wired into the existing presets/targets, but M4 must provide equivalent
documented commands:

```bash
# CPU-only contract/reference lane
cmake --preset dev-gcc -DINFERX_BUILD_M4_REFERENCE_TESTS=ON
cmake --build --preset dev-gcc --parallel
ctest --preset dev-gcc --output-on-failure -L 'm4-unit|m4-integration'

# Independent compiler and sanitizers
cmake --preset dev-clang -DINFERX_BUILD_M4_REFERENCE_TESTS=ON
cmake --build --preset dev-clang --parallel
ctest --preset dev-clang --output-on-failure -L m4
cmake --preset asan-ubsan -DINFERX_BUILD_M4_REFERENCE_TESTS=ON
cmake --build --preset asan-ubsan --parallel
ctest --preset asan-ubsan --output-on-failure -L m4

# Required supported-GPU lane
cmake --preset cuda-release \
  -DINFERX_BUILD_M4_GPU_TESTS=ON \
  -DINFERX_ENABLE_FLASHINFER=<accepted decision>
cmake --build --preset cuda-release --parallel
ctest --preset cuda-release --output-on-failure -L 'm4-gpu|m4-correctness|m4-failure'

# Compute Sanitizer and retained evidence
cmake --build --preset cuda-release --target inferx_m4_compute_sanitizer
cmake --build --preset cuda-release --target inferx_m4_benchmarks
```

Also run repository format, clang-tidy, IWYU, public-header self-containment, dependency-manifest,
license/SBOM, install-consumer, and no-CUDA-include policy checks. GPU CI fails if no supported device
is visible, any required test is skipped, capability evidence is absent, or Compute Sanitizer reports
an error.

The release/evidence job uses immutable inputs and stores raw JSON plus a concise Markdown summary.
Performance regression comparison uses the same GPU class/toolkit/power policy; results from unlike
machines are informative but not a pass/fail comparison.

## 22. Risks and required experiments

| Risk/question | Required evidence | Decision/fallback |
|---|---|---|
| FlashInfer pin is Python/JIT-centric or native surface unstable | section 5.2 closure/build/correctness/sanitizer spike | reject; use owned bounded attention fallback |
| CUTLASS pin/toolchain causes build cost or incompatibility | section 5.3 compile/binary/perf audit | keep qualified-deferred and use cuBLASLt |
| cuBLASLt row-major/transposed mapping is wrong but shape-compatible | hand cases plus randomized direct CPU comparisons | explicit descriptors; no implicit column-major trick |
| heuristic algorithm later fails due pointer alignment | key actual alignment class; real-buffer warm-up launch | reject candidate/select next during preparation |
| opaque algorithm is invalid after toolkit/driver change | include versions and never persist opaque blob | re-prepare on every process start/change |
| finite dynamic shape space causes cache growth | declared buckets and fixed prepared-cache capacity | reject unprepared shape; rebuild immutable set offline |
| fallback attention is too slow for real M5 checkpoint | representative profile and FlashInfer spike | narrow M5 envelope or qualify stable native backend; do not weaken correctness |
| KV layout convention differs between adapter and model | named pre/post-RoPE KV fixtures and high-position decode | fix one rotated-K convention in contract |
| multi-stream vendor state races | disjoint two-stream stress under racecheck/TSan host tests | per-stream state or declare single-stream capability |
| FP16/BF16 errors compound at layer level | per-op plus full-layer worst-case error study | select stricter math/backend; M5 thresholds derive from evidence |
| custom reduction deadlocks or reads uninitialized tails | odd/tail shapes under synccheck/initcheck | simpler kernel/extra pass; never suppress owned finding |
| vendor launch fails after prior KV write | composed launch ordering/failure injection | poison/abort submission; never fallback or reuse uncertain KV |
| warm-up consumes too much startup time/memory | report prepared key count/cache/workspace/time | narrow finite M5 envelope; optimize preparation without moving it live |

## 23. Primary references and applicability notes

- [M2 tensor/CUDA runtime specification](m2.md) owns tensor views, streams, workspace, fences, error
  poisoning, and safe shutdown; M4 does not redefine them.
- [M3 artifact/model specification](m3.md) owns Llama configuration, exact parameter shapes, mapped
  tensor leases, and model identity; M4 adapts but does not parse artifacts.
- [NVIDIA cuBLAS 12.8 documentation](https://docs.nvidia.com/cuda/archive/12.8.0/cublas/index.html)
  defines cuBLASLt matrix layouts, descriptors, heuristic results, algorithm checks, workspace, and
  asynchronous matmul submission used by section 12.
- [CUDA Runtime API synchronization behavior](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-runtime-api/api-sync-behavior.html)
  supports the inherited rule that pageable copies/allocation/free cannot be assumed asynchronous.
- [NVIDIA Compute Sanitizer](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html)
  defines the scope and limitations of memcheck, racecheck, initcheck, and synccheck.
- [FlashInfer exact candidate revision](https://github.com/flashinfer-ai/flashinfer/tree/44428003ba219c14b5473fefec8f7bfd4b72178e)
  is audit input, not an approved runtime dependency.
- [CUTLASS exact deferred revision](https://github.com/NVIDIA/cutlass/tree/dc45f979ae336a235da1676b311f35efeb30149a)
  is audit input and optional implementation material.

Documentation describes observed APIs at the accepted pins/toolkit floor. Upgrading CUDA,
FlashInfer, or CUTLASS reruns their complete qualification, correctness, sanitizer, and performance
gates; a newer version number alone is not evidence.

## 24. Definition of done

### Contracts and CPU reference

- [ ] Every M4 operation has one documented shape/layout/dtype/alias/workspace/empty-input contract.
- [ ] FP32 CPU references implement the exact formulas in section 8 without an optimized dependency.
- [ ] Hand, randomized, and committed independent fixtures pass under GCC/Clang and ASan/UBSan.
- [ ] CPU-only configure/build/install does not discover or load CUDA/kernel dependencies.
- [ ] Artifact-to-tensor adaptation retains ownership and never performs an unaligned reinterpret cast.

### Registry and preparation

- [ ] Stable kernel keys/capabilities cover every required dimension and exclude pointer/runtime noise.
- [ ] Registry freeze and selection are deterministic across insertion order and repeated runs.
- [ ] Forced backend selection never falls back; auto fallback occurs only before mutation in prepare.
- [ ] Prepared caches/workspace are fixed and all required M5 keys fit before readiness.
- [ ] Serving launch does no heuristic search, descriptor creation, allocation, tuning, or host wait.

### CUDA backends

- [ ] cuBLASLt FP32/FP16/BF16 required GEMMs match reference and use bounded aligned workspace.
- [ ] Every owned glue kernel has exact capability, reference, failure, sanitizer, and benchmark evidence.
- [ ] Attention prefill/decode covers MHA/GQA and the full declared M5 contiguous-KV envelope.
- [ ] FlashInfer ADR is closed at an exact pin or rejection; the owned fallback covers every required key.
- [ ] CUTLASS audit is recorded; any registered use has a measured justified shape/capability.
- [ ] Immediate/asynchronous CUDA errors obey M2 scope/poison rules with no unsafe retry.

### Verification and evidence

- [ ] One decoder layer matches CPU at every named intermediate and leaves unused/canary bytes intact.
- [ ] Correctness sweeps meet section 17 tolerances; worst cases and M5-derived thresholds are retained.
- [ ] Stress returns all workspace/event/metadata/handle/accounting state to baseline.
- [ ] memcheck/racecheck/initcheck/synccheck are clean on a required supported GPU with no skipped success.
- [ ] Adapter overhead is <=3% versus identical direct calls and performance evidence is reproducible.
- [ ] Capability, warm-up, numeric, sanitizer, dependency, and benchmark reports are committed/reviewed.
- [ ] ADRs 0026-0030 and operator/registry/kernel docs match the implemented behavior.

## 25. Handoff to M5

M4 hands M5:

- immutable operator contracts and the FP32 CPU reference executor;
- the exact initial Llama execution layout, RoPE pairing, rotated-K cache convention, and numeric
  thresholds;
- a frozen prepared operator set covering a documented finite single-request prefill/decode envelope;
- cuBLASLt GEMM plus qualified CUDA glue/attention backends;
- a closed FlashInfer/CUTLASS disposition with exact dependency evidence;
- workspace/alignment requirements and ownership rules compatible with M2 fences;
- one-layer intermediate fixtures and a diagnostic summary format; and
- retained capability, warm-up, correctness, sanitizer, and performance evidence.

M5 owns semantic layer/model composition, model-wide device weight allocation/upload, contiguous KV
allocation, execution tickets, prompt-to-prefill/decode sequencing, logits consumption, and the
single-request CLI. It may not bypass the registry, reinterpret M3 bytes directly as device tensors,
change RoPE/KV conventions, submit an unprepared shape, or loosen M4 tolerances. If M5 requires a new
operator/dtype/layout/shape, that capability returns to M4's reference, qualification, warm-up, and
evidence gates before the M5 envelope expands.
