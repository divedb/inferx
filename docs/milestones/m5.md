# M5 implementation specification: minimal single-request Llama end-to-end path

- Status: proposed implementation contract
- Roadmap milestone: M5 in [`docs/plan.md`](../plan.md)
- Prerequisites: completed [M3](m3.md) and [M4](m4.md) contracts, including M2 transitively
- Immediate consumer: M6 production paged KV cache
- Later consumers: M7 asynchronous batching, M8 chunked prefill, M9 serving/sampling, and M12 graphs

This document turns M5 into an executable engineering plan. It defines transactional GPU model
loading, deterministic model memory planning, dense Llama semantic composition, a batch-one eager
CUDA executor, a simple contiguous KV cache, host greedy selection, incremental text output, the
reference/diagnostic path, failure containment, tests, evidence, and the exact handoff to M6.

M5 is the first complete token-to-token model execution slice. It intentionally favors explicit
ownership and diagnostic clarity over batching or peak throughput.

## 1. Outcome

At the end of M5, a supported InferX build can:

1. load one M3-validated dense, unquantized `LlamaForCausalLM` package into one qualified CUDA device;
2. calculate and validate all persistent weight, constant, activation, logits, contiguous-KV,
   staging, metadata, workspace, and reserve bytes before the first model allocation;
3. upload FP32, FP16, or BF16 weights without changing M3's `[out,in]` layout or duplicating tied
   parameters;
4. create a ready `CudaModelInstance` only after weight upload, M4 kernel preparation, and numeric
   warm-up complete transactionally;
5. execute one full-prompt prefill and one-token-at-a-time eager decode for batch size one;
6. preserve M1 request/epoch/step/ticket/completion identities and M2 stream/fence/resource lifetime;
7. store per-layer K/V in a simple fixed-capacity contiguous cache with transactional committed
   length and generation checks;
8. copy the final FP32 logits row asynchronously to pinned host storage, select greedy argmax with a
   fixed tie rule, and return one output token per completed step;
9. accept either validated token IDs or M3 text/chat processing, and incrementally decode emitted
   tokens through the qualified tokenizer;
10. run `inferx-generate` as local-only `load -> warm up -> prefill -> greedy decode -> stream ->
    unload`, without Python, network access, pickle, runtime JIT, or checkpoint code; and
11. compare named CPU/CUDA intermediates, logits, and generated tokens with committed independent
    fixtures and an opt-in local public checkpoint.

The end-to-end flow is:

```text
explicit local model directory
  -> M3 ValidatedModelPackage + ModelFingerprint
  -> M5 ModelMemoryPlanner
  -> transactional CudaModelInstance load
       map -> pinned staging -> async H2D -> prepare/warm M4 operators
  -> M3 PromptProcessor or validated token IDs
  -> M1 request lifecycle and one-item StepPlan
  -> M5 eager prefill ticket
       embedding -> decoder layers -> final norm -> last-row logits -> async D2H
  -> completed fence -> host greedy argmax -> token/text delta
  -> zero or more eager decode tickets using contiguous KV
  -> EOS or length terminal response
  -> drain tickets -> release request resources -> unload model -> close CUDA context
```

M5 is complete only when the same committed tiny artifacts pass artifact loading, CPU reference,
CUDA execution, greedy token generation, cancellation/drain, unload, sanitizers, and repeated-run
resource checks. A CLI that calls kernels directly, waits with `cudaDeviceSynchronize`, or bypasses
M1/M2 ownership is not an acceptable vertical slice.

### Implementation status (2026-08-31)

This file is a documentation specification only. No M5 source implementation is authorized by this
change. The present worktree does not yet contain M1/M2 implementations, M3's tokenizer/package gate
is open, and M4 is currently a proposed specification. M5 implementation must wait for those exact
interfaces rather than adding temporary duplicate request, tensor, CUDA, tokenizer, or operator
types.

## 2. Scope boundaries

### 2.1 In scope

- One process, one CUDA device context, one loaded model, one active request, and batch size one.
- Dense unquantized Hugging Face-compatible Llama from M3: FP32, FP16, or BF16 uniform weights.
- Immutable `LlamaForCausalLM` semantic composition over M4 operation contracts.
- Deterministic device memory planning with checked offsets/alignment and typed memory categories.
- One persistent model-weight arena, optional persistent constant arena, one activation slot, one
  final-logits device buffer, and fixed contiguous per-layer K/V storage.
- Bounded pinned staging and chunked asynchronous H2D weight upload using M2 streams/events/fences.
- Tied embedding/LM-head device aliasing according to M3's validated `WeightPlan`.
- Full-prompt prefill followed by eager one-token decode; no prompt chunking.
- Final-row logits only for ordinary generation; bounded full/intermediate capture in diagnostic tests.
- Deterministic host greedy argmax and EOS/length termination.
- Token-ID, raw-text, and supported chat-template inputs through M3's input contract.
- Incremental text decode and a local command-line executable.
- CPU reference model composition, independent fixture generation, intermediate diagnostics, and
  model-level numeric/token agreement evidence.
- Cancellation/deadline checks before submission and safe drain when work is already in flight.
- Explicit model unload and repeatable context shutdown.

### 2.2 Explicitly out of scope

- Multiple simultaneous requests, continuous/dynamic batching, scheduler fairness, preemption,
  prompt chunking, or mixed prefill/decode batches. M7/M8 implement them.
- Production paged KV, prefix sharing, copy-on-write, block tables, fragmentation control, or KV
  eviction. M6 replaces the M5 contiguous implementation behind an explicit interface.
- Beam search, stochastic sampling, penalties, top-k/top-p/min-p, logprobs, grammar constraints, or
  device-side sampling. M9/M12 own those features.
- CUDA graphs, graph caches, stable graph slots, speculative decoding, or multi-stream layer overlap.
- Quantization, dtype conversion during production weight load, FP8/INT8/INT4, packed weights, LoRA,
  sparse/MoE models, adapters, or arbitrary architecture plugins.
- Tensor, pipeline, expert, or data parallelism; NCCL; peer access; remote workers; remote KV.
- Sliding-window attention, rope scaling, attention/MLP bias, multimodal inputs, cross attention, or
  any model capability rejected by M3/M4.
- Model download, Hub resolution, authentication, remote code, Python/PyTorch runtime, pickle, or
  runtime compilation.
- A production HTTP server, public compatibility API, multi-tenant admission, or production telemetry.
- Treating the CLI's polling loop as the M7 serving engine architecture.

## 3. Inherited contracts and merge prerequisites

M5 preserves all accepted contracts from M0-M4:

- C++23 host code, scoped warnings, format/tidy/IWYU/header/install checks, offline reproducibility,
  pinned dependencies, and no exception crossing InferX boundaries;
- M1 immutable requests, request FSM, strong request/sequence/epoch/step/ticket IDs, one controller
  mutator, token-range definitions, plan-buffer leases, stale completion rejection, and exactly one
  terminal response;
- M2 tensor shapes/strides/views, move-only buffers, typed memory categories/accounting, healthy/
  poisoned CUDA context, nonblocking streams, pooled events, pinned staging, workspace leases,
  completion acknowledgement, and nonblocking destructors;
- M3 rooted immutable model artifacts, complete weight coverage, normalized `ModelSpec`, exact
  parameter shapes/dtypes/aliases, `ModelFingerprint`, tokenizer metadata, prompt processing, and
  incremental decoding; and
- M4 row-major layouts, `[out,in]` weights, half-split Llama RoPE, rotated-K cache convention,
  prepared operator set, forced backend, numeric policy, and no post-launch fallback.

Before M5 implementation merges:

1. M1's lifecycle, `StepPlan`, `ExecutionCompletion`, and response contracts must be implemented and
   versioned for a real output token/EOS reason;
2. M2's device context, allocators, streams, copies, metadata/workspace pools, and fences must pass
   their required real-GPU and Compute Sanitizer gates;
3. M3 must publish a complete `ValidatedModelPackage`, qualified tokenizer, prompt processor, and
   mapping lease—artifact-only inspection is insufficient for the text CLI;
4. M4 must publish a frozen prepared operator set covering M5's exact envelope and close its
   attention-backend decision;
5. the supported CUDA/driver/SM and GPU CI ownership from ADRs 0005/0019 must be current; and
6. the deterministic tiny model/tokenizer/reference artifacts required below must be generated by a
   hash-locked tool environment and reviewed before GPU results are accepted.

M5 may not weaken a prerequisite to make the demo run. If its desired checkpoint exceeds M4's
attention/workspace envelope or M2's budgets, narrow the declared M5 capability or return to the
owning milestone with new evidence.

## 5. Initial supported capability envelope

The M5 capability is the intersection of M3's dense Llama and M4's prepared operator envelope:

| Property | Initial rule |
|---|---|
| architecture | exactly normalized dense `LlamaForCausalLM` / `model_type=llama` |
| batch/active requests | exactly one |
| source/execution weights | one uniform FP32, FP16, or BF16 family; no conversion/mixture |
| activations/KV | same storage family selected for the model; reductions/logits follow M4 policy |
| prompt | nonempty, at most `execution.max_prefill_tokens` and full-prefill in one step |
| output | positive `max_output_tokens`, bounded by config and checked context sum |
| context | `prompt_tokens + max_output_tokens <= execution.max_context_tokens <= model maximum` |
| heads | M3-valid MHA/GQA and within M4 attention capability |
| head dimension | even and within M4 RoPE/attention capability |
| RoPE | unscaled full-head Llama RoPE with M4 half-split pairing |
| KV | contiguous, separate K/V, batch one, rotated K, fixed capacity |
| logits | final hidden row only, FP32 device/host output for ordinary generation |
| generation | greedy only; EOS set from validated model/tokenizer metadata; length fallback |
| input | token IDs, raw text, or supported M3 chat messages; exactly one variant |

The fallback M4 envelope currently caps batch at 1 for M5, prefill tokens at 512, total context at
4096, query heads at 64, and head dimension at 256. A qualified attention backend may support more,
but M5 does not expand until fixtures, memory plans, warm-up, and stress evidence cover the new
effective limits.

An opt-in public checkpoint must fit this same capability. Its popularity or repository label never
overrides config/operator validation.

## 7. Configuration and validation

M5 adds a versioned `execution` configuration section to the immutable effective configuration:

| Field | Range/default | Rule |
|---|---|---|
| `execution.max_prefill_tokens` | `1..512`, default `512` | cannot exceed M4 prepared attention/activation envelope |
| `execution.max_context_tokens` | `2..4096`, default `4096` | resolved minimum with model maximum and M4/KV capability |
| `execution.max_output_tokens` | `1..4096`, default `256` | request value may be lower, never higher |
| `execution.model_device_budget_bytes` | positive or null | null uses remaining M2 device budget after reserve/pools |
| `execution.model_host_budget_bytes` | positive, default `2 GiB` | mapped/reference/staging ownership cap, checked with M3 limits |
| `execution.weight_alignment_bytes` | fixed `256` in schema v1 | must cover every selected M4 weight alignment requirement |
| `execution.activation_slots` | exactly `1` | M7 expands for in-flight batching; M5 rejects other values |
| `execution.logits_output_dtype` | exactly `float32` | required for host greedy baseline |
| `execution.enable_intermediate_diagnostics` | false | explicit startup-only memory-plan change, never live toggle |
| `execution.max_diagnostic_bytes` | `0..1 GiB`, default `64 MiB` | total retained/copied diagnostic payload cap |
| `execution.poll_backoff_us` | `10..1000`, default `50` | CLI/test polling only; no device synchronize |

GiB/MiB use powers of 1024 and JSON stores integer bytes. Defaults and resolved model-dependent
values retain provenance. Unknown fields fail. Model configuration never raises server/device limits.

Validation order before model allocation is:

1. validate generic configuration and selected CUDA device capability;
2. validate complete M3 package and tokenizer/model cross-check;
3. intersect model shape/dtype/context with M4 registered capability envelope;
4. validate prompt/output/context configuration with checked addition;
5. calculate persistent and transient memory plans with checked arithmetic;
6. compare every category and total against M2 trackers, device reserve, host/pinned budgets, pool
   geometry, prepared-kernel cache, workspace, event, metadata, and staging capacities; and
7. build a finite M4 warm-up requirement set.

Failure returns the first deterministic error plus a bounded machine-readable summary. No CUDA model
allocation, mapping flood, tokenizer worker, or readiness state is created before this validation
finishes.

## 8. Model semantic contract

### 8.1 `LlamaForCausalLM` boundary

`LlamaForCausalLM` is immutable semantic composition over an M3 `ModelSpec`/parameter catalog. It
does not own device memory, choose kernels, allocate KV, load files, tokenize, select CUDA streams,
or sample. It receives:

- a validated `ForwardBatch` with batch size one, work kind, token/position views, and logical KV
  transaction;
- immutable `ModelWeights` views keyed by M3 `ParameterId`;
- an activation-plan lease and typed contiguous KV views;
- an `OpExecutor` backed by M4 CPU reference or prepared CUDA operators; and
- an optional bounded `IntermediateTraceSink`.

The same semantic order drives CPU and CUDA, while independent framework fixtures detect shared
orchestration mistakes. Parameter lookup is resolved into a fixed layer/role table at model-instance
construction; no string-map lookup occurs per layer/token.

### 8.2 Exact forward order

For token IDs `tokens[T]`, positions `positions[T]`, and hidden width H:

```text
hidden = Embedding(tokens, model.embed_tokens.weight)

for layer i in [0,L):
  residual = hidden
  norm = RMSNorm(hidden, layer.i.input_layernorm.weight, epsilon)
  q = Gemm(norm, layer.i.self_attn.q_proj.weight)
  k = Gemm(norm, layer.i.self_attn.k_proj.weight)
  v = Gemm(norm, layer.i.self_attn.v_proj.weight)
  q, k = Rope(q, k, positions, rope_theta)
  attention = CausalAttentionAndKvAppend(q, k, v, layer i KV transaction)
  projected = Gemm(attention, layer.i.self_attn.o_proj.weight)
  hidden = Residual(residual, projected)

  residual = hidden
  norm = RMSNorm(hidden, layer.i.post_attention_layernorm.weight, epsilon)
  gate = Gemm(norm, layer.i.mlp.gate_proj.weight)
  up = Gemm(norm, layer.i.mlp.up_proj.weight)
  activated = SiluMultiply(gate, up)
  down = Gemm(activated, layer.i.mlp.down_proj.weight)
  hidden = Residual(residual, down)

final_hidden = RMSNorm(hidden, model.norm.weight, epsilon)
selected_hidden = final_hidden[last logical token, :]
logits = Logits(selected_hidden, lm_head.weight or embedding alias)
```

Inference applies no dropout. Q/K/V are reshaped as views into M4's `[T,heads,head_dim]` layout; no
copy/transpose is implied. RoPE runs before KV append, so cached K is rotated exactly once. Every
layer sees the same input token positions and its own KV storage.

Ordinary generation computes only the final logical row through the LM head. Diagnostic full logits
requires an explicit preplanned output shape/budget and does not alter production defaults.

### 8.3 Prefill and decode positions

For prompt length `P` and `O` already committed output tokens:

| Work | input token values | positions | KV before | append range | output position |
|---|---|---|---|---|---|
| prefill (`O=0`) | complete prompt `[0,P)` | `0..P-1` | length 0 | `[0,P)` | 0 |
| decode (`O>=1`) | previously emitted token `O-1` | `P+O-1` | `P+O-1` | `[P+O-1,P+O)` | O |

The first generated token comes from prefill logits and is not KV state until it is consumed by the
first decode. The last emitted token need not enter KV if EOS/length ends generation. These rules
must match M1's logical read/write ranges exactly.

Position/range/count calculations use checked strong values. Prompt plus requested maximum output is
validated conservatively against context capacity even though EOS may end early.

### 8.4 Stable intermediate names

Diagnostic names are schema-versioned and independent of backend:

```text

layers.{i}.input_norm
layers.{i}.q_proj
layers.{i}.k_proj
layers.{i}.v_proj
layers.{i}.q_rope
layers.{i}.k_rope
layers.{i}.attention
layers.{i}.o_proj
layers.{i}.post_attention_residual
layers.{i}.post_attention_norm
layers.{i}.mlp_gate
layers.{i}.mlp_up
layers.{i}.mlp_activated

```

Names are generated from checked layer IDs, never arbitrary model strings. Adding/removing/renaming a
point increments the trace schema. Production execution has a null sink compiled to a predictable
branch and performs no diagnostic allocation/copy.

## 9. Deterministic model device memory plan

### 9.1 Categories and complete plan

`ModelMemoryPlanner` constructs an immutable plan before allocation. It covers:

- device weight arena and alignment padding;
- persistent model constants required by selected M4 kernels, such as an optional bounded RoPE table;
- one activation arena for maximum prefill shape;
- final FP32 device logits row `[V]`;
- contiguous K and V for every layer at configured context capacity;
- persistent device token/position/attention metadata slots not already supplied by M2;
- M2 workspace/event/metadata/staging capacities consumed by an execution ticket;
- optional preplanned diagnostic capture storage; and
- device reserve/unavailable bytes.

Each plan entry has a closed memory category, stable name/parameter ID, byte count, power-of-two
alignment, offset, lifetime interval, alias target if any, and owning arena. All align-up/add/multiply
operations are checked in 64 bits and for device `size_t`/vendor narrowing.

The acceptance equation is:

```text
existing M2 persistent allocations
+ weight arena
+ constant arena
+ activation arena
+ logits buffer
+ contiguous KV
+ M5 metadata
+ optional diagnostic storage
+ configured device reserve
<= physical device memory and M2 device budget
```

Workspace is not double-counted if already allocated by M2's fixed pool, but the plan proves one slot
can satisfy the maximum prepared M4 requirement. Host/pinned mapping/staging budgets are reported
separately.

### 9.2 Weight arena layout

Iterate non-alias `WeightPlanItem`s in canonical `ParameterId` order:

1. translate M3 artifact dtype to the identical M2 execution dtype;
2. require exact expected shape and checked bytes;
3. derive required alignment as the maximum of schema-v1 256 bytes, dtype alignment, CUDA copy
   requirements, and all prepared backend operand requirements;
4. align the current arena offset and assign the complete tensor range;
5. advance with checked addition; and
6. record padding separately for diagnostics.

Alias parameters allocate no bytes and refer to the complete target slice. An alias cannot point to
another alias, change dtype/shape, or select a subrange. Tied LM head and embedding therefore share
one device range and one owner.

The arena is one explicit device allocation in M5. Zero-fill padding is optional diagnostics; no
kernel reads padding. Weight contents remain byte-identical to the M3 source, little-endian, row-major
`[out,in]`, and immutable after upload. Production loading performs no transpose, repack, cast, or
quantization.

### 9.3 Contiguous KV formula and layout

For L layers, capacity C, `Nkv` KV heads, head dimension D, and dtype bytes S:

```text
elements_per_kind = L * C * Nkv * D
kv_bytes = 2 * elements_per_kind * S
```

Every product is checked. One backing allocation is divided into separately aligned K and V arenas;
each per-layer view has logical shape `[1,C,Nkv,D]` and matches M4. The physical canonical layout is:

```text
K[layer, position, kv_head, dim]
V[layer, position, kv_head, dim]
```

No layer/head interleaving or page padding is hidden. M6 may replace the implementation, not reinterpret
this layout as paged storage.

### 9.4 Activation liveness and reuse

The maximum prefill token count determines arena sizes. Named logical buffers include hidden,
residual/norm, Q/K/V, attention output, projected output, gate/up/activated, down output, token/
position metadata, and logits source row. The planner builds an ordered operation DAG and assigns
non-overlapping byte slices by lifetime.

Reuse is legal only when the last reader is ordered before the next writer on the same stream. It
does not require a host fence between sequential operations, but the complete arena remains owned by
the execution ticket until its final fence. Exact M4 in-place aliases may shorten liveness; partial
aliasing is never introduced by the planner.

The initial simple plan may use more memory than an optimal coloring, but it must:

- publish every slice and lifetime;
- prove no overlapping live mutable tensors;
- fit the configured device budget;
- use the same precomputed offsets for every prefill/decode within the envelope; and
- perform no per-step allocation.

Diagnostic capture extends lifetimes only through a separately generated `DiagnosticCapturePlan` at
model load. Enabling diagnostics after readiness is rejected.

### 9.5 Plan identity

`ModelInstanceFingerprint` is separate from M3's content identity. It is a domain-separated digest of:

- M3 `ModelFingerprint`;
- M5 memory/forward schema versions;
- execution dtype/layout and configured capability envelope;
- M4 `OperatorCompatibilityFingerprint`; and
- persistent weight/constant/KV/activation plan records.

It excludes device pointers, allocation IDs, timing, opaque cuBLAS algorithms, current KV contents,
request tokens, and host/device UUID. Equivalent content may have different instance fingerprints on
different execution layouts without changing the model content fingerprint.

## 10. Transactional GPU model loading

### 10.1 Load state machine

The model instance has explicit states:

```text
Empty -> Planning -> Allocating -> Uploading -> Warming -> Ready
  \          \             \           \          \
   +----------+-------------+-----------+-----------> Failed -> Closing -> Closed
Ready -> Draining -> Closing -> Closed
```

Only `Ready` accepts requests. State is worker-owned. A model handle contains strong slot/generation;
unload increments generation so stale tickets/handles cannot name a later model.

`CudaModelLoader::Load` is transactional:

1. retain immutable validated package/model identities;
2. validate capability and build complete memory/warm-up plans;
3. reserve all memory categories transactionally;
4. allocate model arenas in deterministic order;
5. materialize views and alias table;
6. upload every non-alias weight through section 10.2;
7. initialize persistent constants and metadata;
8. construct contiguous KV/cache generation state;
9. freeze/prepare the M4 operator set for the exact model envelope;
10. run warm-up with dedicated/resettable KV state and deterministic inputs;
11. verify fences, numeric summaries, canaries, accounting, and package/file identities; and
12. atomically publish `CudaModelInstance`/`ModelHandle` as ready.

Nothing enters the live model registry before step 12. Failure drains submitted work, releases the
constructed prefix in reverse, rolls back trackers, preserves the first error plus cleanup details,
and publishes no handle.

### 10.2 Bounded weight upload

M3 mapped file memory is not assumed pinned. For each planned weight in canonical order:

1. obtain an M3 mapping/window lease for a bounded source range;
2. acquire one fixed M2 pinned staging slot;
3. copy at most `staging_slot_bytes` from mapped host bytes to the pinned slot;
4. queue H2D into the exact weight-arena offset on the transfer stream (or explicitly aliased compute
   stream when transfer is disabled);
5. record a generation-checked event/fence covering that chunk;
6. retain mapping, staging, destination owner, and fence together until completion;
7. rotate through a fixed double-buffered staging set, polling/waiting only under the named model-load
   startup reason before reusing a slot; and
8. repeat until exact tensor bytes are uploaded.

Chunk/range math is checked; zero-byte tensors make no CUDA call. No pageable async H2D, direct file
GPU mapping, unbounded host copy, or tensor-sized pinned allocation is used. A source mapping is
released only after its bytes have been copied into pinned storage; the pinned slot is released only
after H2D completion.

M3 already verifies file digests/identity. Load tests may perform full/sampled D2H verification into
bounded pinned memory, but production does not reread every device byte. Warm-up and fixture checks
provide semantic transfer evidence.

### 10.3 Warm-up isolation

Warm-up uses the final weight/activation/operator plans but cannot contaminate request state. It uses
a dedicated cache transaction or resets the M5 cache generation/committed length only after the
warm-up fence. Written KV bytes need not be memset because committed length controls visibility.

Warm-up covers prefill and decode boundary keys, final logits D2H, argmax, and tied/untied LM-head
access. It verifies selected intermediate summaries against M4/M5 fixtures. Readiness remains false
until the final fence is acknowledged and cache/accounting state returns to the defined warm baseline.

## 11. Contiguous KV cache transaction

### 11.1 State and ownership

`ContiguousKvCache` owns no CUDA allocation directly; `CudaModelInstance` owns backing storage and the
cache owns checked views/state:

- model handle/generation;
- sequence ID and `KvSequenceGeneration`;
- capacity C and committed length;
- at most one pending append transaction;
- per-layer K/V views; and
- pending ticket/fence identity.

States are empty, active, append-pending, poisoned, and closing. M5 has one sequence. Acquire from
empty assigns sequence/generation with committed length zero. Reset is legal only with no pending
ticket, increments generation with overflow protection, drops logical visibility to zero, and does
not need to erase bytes.

### 11.2 Append transaction

`PrepareAppend(expected_begin, count, ticket)` validates:

- active matching model/sequence/generation;
- no pending append;
- `expected_begin == committed_length`;
- checked `expected_begin + count <= capacity`;
- matching M1 KV logical range and M5 token positions; and
- all layer views/capabilities.

It returns a move-only transaction containing the old/new length and per-layer destinations. Launch
may write those destinations, but committed length does not change. On successful matching execution
completion, `Commit()` advances length in a no-fail mutation. Cancellation after successful GPU work
may discard request output and reset after drain; it must not expose partially transitioned KV to
another request.

If synchronous failure occurs before any launch, rollback leaves length unchanged. If any related
work may have launched and completion fails asynchronously, mark cache/context poisoned and never
reuse its contents. A stale ticket/generation cannot commit or roll back a newer transaction.

### 11.3 Visibility and layer consistency

All layers commit one common logical length. A step cannot make layer 0 visible while a later layer
failed. Visibility advances only after the final model ticket succeeds, not per kernel/layer.

M4 attention sees prior committed `[0,begin)` plus the current appended range for that layer. It
cannot read positions `>= new_length`. Debug tests fill unused KV with poison/canaries and prove
length metadata prevents access. M6 retains the transactional visibility rule while replacing
physical ranges with page reservations.

## 12. Eager CUDA execution backend

### 12.1 Interface and one-item restriction

`CudaExecutionBackend` implements the hardware-neutral execution contract using M1 plans and M2
resources. M5 accepts one `ScheduledSequence` per `StepPlan`, one model, and one in-flight ticket.
Batch/mixed plans return `Unimplemented` before mutation.

Submission receives a move-only M1 `StepPlanLease`, validates IDs/epoch/ranges against model/cache,
acquires all preallocated slot leases, prepares a KV append transaction, writes bounded token/
position metadata, and launches the semantic forward path on the explicit compute stream. It never
reads request-owned vectors after submission; needed token values are copied into ticket-owned
pinned/device metadata before the M1 submit transition commits.

### 12.2 Final logits and completion fence

After final FP32 logits `[V]` are produced:

```text
compute records logits-ready event
-> transfer stream waits (or same compute stream is used explicitly)
-> async D2H logits into ticket-owned pinned buffer
-> transfer records final completion event/fence
```

That final fence covers every prior model kernel, all KV writes, logits, and host-visible logits.
There is no intermediate host wait. `Poll()` uses M2 fence query. Once complete, the backend runs
bounded host argmax, constructs one `ExecutionCompletion`, and moves the ticket to delivered state.

The completion echoes ticket/step/request/sequence/epoch/work/range. Success has exactly one output
token and a commit-ready KV transaction; failure has no token and no reusable uncertain output.
`Acknowledge` occurs only after M1 lifecycle completion is applied, then releases plan, activation,
metadata, logits, workspace, event, and KV transaction ownership.

### 12.3 Partial submission failure

Validation/resource acquisition/preparation happens before the first launch. Still, a later launch in
the layer sequence can fail after earlier work was queued. The backend must not return a bare status
and lose ownership:

- before any queued operation: rollback resources and return submission error;
- after work queued but context healthy enough to record completion: return a failed/draining ticket
  whose fence and resource bundle are polled/acknowledged without output/KV commit;
- if fence recording/query cannot establish safety: poison context, transfer the complete bundle to
  M2 deferred shutdown ownership, and return scoped `Unavailable`; and
- never try another kernel/backend over possibly mutated activations or KV.

Fake launch seams count whether work was queued so every boundary is testable.

### 12.4 Polling and waits

Normal backend APIs are nonblocking. The M5 CLI uses bounded fence polling with configured monotonic
backoff because the next greedy token depends on completed logits. It may call M2's named
`WaitUntil(..., kCliSingleRequest)` helper, which queries events and honors cancellation/deadline; it
must not call stream/device synchronize.

This serialized token dependency is expected in M5 and is not evidence of a hidden synchronization
inside operators. Benchmarks report host polling/wait separately. M7 replaces the CLI loop with
asynchronous coordinator completion processing.

## 13. Single-request lifecycle and generation algorithm

### 13.1 Runner ownership

`SingleRequestRunner` is an integration adapter, not a second request state machine. It owns/uses:

- M1 `LifecycleCoordinator`, one-request registry, response sink, and plan pool;
- M3 input processor/tokenizer lease/incremental decoder;
- one ready model handle and M5 contiguous-KV sequence lease;
- one in-flight CUDA execution ticket at most; and
- bounded CLI response/output storage.

It drives the existing M1 states and applies all completions through the controller. Direct mutation
of prompt/output counters, reservation, or terminal response is forbidden.

### 13.2 Admission and input processing

Exactly one input variant is accepted. Token IDs are copied/validated against vocabulary. Text/chat
uses M3 template/tokenization rules and returns an owned token vector. Then validate:

- prompt nonempty and within prefill limit;
- request output limit positive and within configured limit;
- checked prompt plus maximum output within model/context/KV capacity;
- special token/model metadata consistency already established by package load;
- request/model IDs and default priority/tenant capability; and
- deadline not expired.

Only after input success does the runner acquire a fresh KV sequence generation and reservation.
Input/tokenization failure allocates no GPU request state.

### 13.3 Prefill/decode loop

The exact loop is:

```text
admit/input ready/reserve
-> build one-item full-prompt StepPlan
-> backend accepts plan; commit SubmitPrefill
-> poll/drain matching completion
-> prepare incremental decode/response and KV commit
-> commit PrefillCompleted and emit output token/text
-> if EOS or output limit: finish

while output remains:
  build one-item decode plan for the most recently emitted token
  -> backend accepts; commit SubmitDecode
  -> poll/drain matching completion
  -> prepare incremental decode/response and KV commit
  -> commit DecodeCompleted and emit output token/text
  -> if EOS or output limit: finish

flush incremental decoder
-> emit exactly one terminal response
-> acknowledge/release sequence/request resources
```

The tokenizer incremental-decode step and response reservation occur before the no-fail lifecycle
commit. If they fail, no token delta is committed; the request becomes failed after safe execution
acknowledgement. Bytes already emitted by earlier tokens are not rolled back, and the terminal error
is authoritative.

### 13.4 EOS and length

Add a real `FinishReason::kEos` through the next versioned M1 response schema; do not reuse
`kSimulatedEos`. A generated token matching any normalized EOS ID is emitted as the final token delta,
passed through incremental decode, then followed by the EOS terminal response. If the output count
reaches the requested maximum first, finish with `kLength`.

If an EOS token is also at the length boundary, EOS wins because token classification occurs before
the post-commit length guard. The fixture oracle uses the same rule. Prompt tokens equal to EOS do
not terminate generation.

## 14. Greedy selection and incremental text

### 14.1 Host argmax

Ordinary generation receives exactly V FP32 logits in a ticket-owned pinned host buffer. Validate V
against model vocabulary and the planned byte count. Greedy selection scans token IDs in increasing
order and replaces the winner only for a strictly greater logit, so exact ties select the lowest ID.

NaN logits return `DataLoss` with no output token. Positive/negative infinity follow numeric order;
all negative infinity selects ID zero by the tie rule but records a diagnostic counter. The normal
finite fixture corpus must not produce nonfinite logits. Argmax performs no softmax and allocates no
memory.

The argmax reference has hand tests for ties, signed zero, infinities, NaN at every position, V=1,
and maximum accepted vocabulary. CPU framework reference generation is configured greedy with the
same tie/EOS/length rules.

### 14.2 Incremental decode

Create one M3 `IncrementalDecoder` per request with cleanup disabled as required by M3. For every
committed token, call `Push(token)` exactly once in output order. Emit only newly stable bytes. On
successful EOS/length, call `Finish()` and emit its final bytes before the terminal response.

Token-ID mode can request `--output=tokens` and avoid text rendering, but model/tokenizer package
validation still ensures IDs are in range. Text output never repeatedly decodes the complete prefix
and never guesses UTF-8 suffix boundaries.

## 15. `inferx-generate` CLI contract

### 15.1 Inputs and local-only behavior

The executable is intentionally narrow:

```text
inferx-generate
  --model-dir PATH
  exactly one of:
    --prompt TEXT
    --prompt-file PATH
    --chat-file PATH
    --tokens-file PATH
  --max-output-tokens N
  [--device N]
  [--output text|tokens|jsonl]
  [--deadline-ms N]
  [--diagnostic-intermediates FILTER]
```

`--tokens-file` is a bounded UTF-8 JSON array of nonnegative integer token IDs parsed through the M1
strict JSON policy. `--chat-file` uses M3's supported chat schema/template. `--prompt-file=-` may read
bounded stdin. Supplying zero or multiple input variants is an error.

The model path is explicit/local. The CLI never treats it as a Hub name, follows descendant symlinks,
loads shared objects, invokes Python, fetches missing files/kernels, or enables trust-remote-code.
Prompt text on the command line may be visible in process listings; documentation recommends stdin/
file for sensitive input.

### 15.2 Output modes

- `text`: stdout contains incremental decoded bytes only; diagnostics/progress go to stderr.
- `tokens`: stdout contains one decimal token ID per line.
- `jsonl`: stdout contains versioned `ready`, `token`, and `terminal` records with output position,
  token ID, optional text delta, finish reason, counts, and stable status fields.

JSONL does not include prompt/model bytes, logits, pointers, device UUID, wall-clock-dependent fields
in golden mode, or unbounded diagnostics. stdout write failure triggers cancellation/drain and a
nonzero exit. Human diagnostics include model content/instance fingerprints, resolved capability,
memory summary, and timings without printing secrets.

Exit zero means a normal EOS/length terminal response and successful cleanup. Validation, model-load,
unsupported capability, resource exhaustion, execution failure/context poison, cancellation/deadline,
and output I/O failure map to documented stable nonzero categories while retaining the underlying
status in stderr/JSONL.

### 15.3 Reproducible example

The completed milestone documents one command runnable from a fresh supported environment, for
example:

```bash
./build/apps/inferx_generate/inferx-generate \
  --model-dir tests/fixtures/m5/tiny_llama \
  --prompt-file tests/fixtures/m5/prompts/basic.txt \
  --max-output-tokens 32 \
  --device 0 \
  --output jsonl
```

The fixture and expected JSONL/token output are committed. The command performs no network access and
returns nonzero instead of skipping when CUDA/model capability is unavailable.

## 16. CPU reference model and intermediate diagnostics

### 16.1 CPU reference composition

Materialize tiny-model FP16/BF16 source weights as FP32 through M4's bounded test/reference adapter.
Run the exact section 8 semantic order with M4 CPU reference operators and a host contiguous KV
implementation. It supports the committed tiny fixtures only under explicit element/FLOP/host-byte
caps; it is not a production fallback.

The CPU path shares immutable `ModelSpec`/parameter identities and operation contracts, but no CUDA
kernel, cuBLASLt result, device KV bytes, or GPU execution code. Independent framework fixtures catch
mistakes shared by the CPU/GPU semantic driver.

### 16.2 Diagnostic records

For a selected stable intermediate, record:

- trace schema/name/layer/work kind/output position;
- dtype, shape, strides, and logical element count;
- finite/NaN/+Inf/-Inf counts;
- min/max, mean, L1/L2 norm computed in a documented precision;
- BLAKE3 digest of canonical little-endian logical FP32 values; and
- comparison metrics to reference where available.

Default diagnostic mode records summaries only. Full tensor dumps require an explicit safe output
directory, allowlisted name filter, total byte cap, no overwrite unless requested, and atomic file
publication. Dump files contain schema metadata and raw little-endian values; paths cannot escape the
chosen directory. Device capture uses preplanned pinned storage and named diagnostic waits, never a
live serving toggle.

Diagnostics are disabled in performance gates except the dedicated overhead measurement. A trace
failure does not leave a GPU ticket/resource unowned.

## 17. Independent fixtures and numerical acceptance

### 17.1 Deterministic tiny model matrix

Commit at least these tiny artifact variants, all passing M3 complete coverage:

- FP32 untied embedding/head;
- FP32 tied/omitted LM head;
- FP16 and BF16 variants of the supported execution shape;
- MHA (`Nq=Nkv`) and GQA (`Nq>Nkv`) variants; and
- tokenizer/special-token variants needed for EOS and incremental byte-boundary cases.

At least one diagnostic fixture has two or more decoder layers, nontrivial H/I/V, non-power-of-two
prompt lengths, and context enough for 32 outputs. Weights are deterministic finite values chosen to
exercise signs/scales without pathological logits. Fixtures include manifest/fingerprint and exact
generator lock digest.

The generation reference corpus contains at least 100 prompts spanning lengths 1, 2, boundaries,
multilingual text, whitespace, special tokens, repeated tokens, high token IDs, EOS-early, and
length-terminated cases. Each records up to 32 greedy output tokens unless EOS.

### 17.2 Framework oracle

A hash-locked Python test tool uses a pinned Transformers/PyTorch/safetensors/tokenizers environment
to load the same local artifact with eval mode, dropout disabled, cache behavior recorded, and greedy
generation. It emits:

- normalized prompt token IDs/positions;
- selected named intermediates for small cases;
- prefill and each decode final-row FP32 logits;
- KV shape/position summaries and optionally bounded values;
- greedy output tokens and EOS/length reason; and
- dependency versions, seed, input/output digests, and generator revision.

Generated data is committed; ordinary CTest/runtime does not invoke Python. Regeneration is a
reviewed explicit command and diffs fixture manifests.

### 17.3 Model-level threshold derivation

M4 provides per-operation ceilings and worst-case evidence. ADR 0036 chooses exact M5 logits/
intermediate thresholds before implementation acceptance using disjoint calibration and holdout
fixture sets:

1. run CPU FP32, framework, and every required CUDA dtype/backend on calibration cases;
2. calculate max/mean absolute, relative, L2, and top-k/margin statistics per named point;
3. propose thresholds no greater than M4's composed error ceiling and no smaller than a documented
   numerical floor;
4. freeze thresholds and seeds;
5. evaluate the untouched holdout set; and
6. reject/change backend or math mode if holdout fails—do not tune thresholds on holdout failures.

Every dtype must meet its accepted intermediate/logit thresholds. More importantly, final greedy
tokens must match exactly for every committed prompt and step. A close logit vector cannot excuse a
token divergence. Fixtures with near-zero top-1 margin remain in numeric reporting; the exact-token
corpus must still include realistic non-curated prompts.

### 17.4 Comparison points

The required per-step comparison is:

- embedding and every section 8.4 named intermediate for the full diagnostic tiny case;
- per-layer newly written K/V for prefill and at least positions 0, boundary, and decode tail;
- final norm and final-row logits for every reference prompt/step;
- greedy token, output position, EOS/length reason; and
- incremental decoded byte stream.

FP32 CPU/framework differences are reported separately from CUDA/reference differences so a fixture
adapter bug cannot be hidden by a wide combined tolerance.

## 18. Cancellation, deadlines, errors, and shutdown

### 18.1 Cancellation/deadline points

Check cancellation/deadline:

- before tokenization and after input ready;
- before model/KV reservation;
- before every prefill/decode submission;
- while polling an in-flight ticket; and
- after completion before response commit.

If no work is in flight, transition terminal and release immediately. If work is in flight, enter
M1 `Cancelling`, stop submitting new work, continue polling, do not commit token/KV/output, apply
`InFlightDrained`, acknowledge ticket/fence, reset cache generation, and then release. M5 does not
attempt kernel cancellation.

A completion that wins the deterministic M1 event order may commit; a cancellation that wins does
not. Late/stale completions cannot mutate a reused request/cache generation.

### 18.2 Error taxonomy and scope

M5 extends stable reasons for model plan overflow/too large, model allocation/upload/warm-up failure,
stale model handle, invalid forward/position/KV transaction, nonfinite logits, and model unload with
live ticket. It preserves earlier numeric values.

| Failure | Status/scope |
|---|---|
| malformed prompt/token/config/range | `InvalidArgument`, request rejected before GPU state |
| valid unsupported model/operator envelope | `Unimplemented`, model readiness fails |
| memory plan exceeds budget/allocation OOM | `ResourceExhausted`, transaction rolls back |
| artifact mutation/digest/weight mismatch | M3 `DataLoss`, model load fails |
| H2D immediate failure | scoped load failure; drain submitted transfers and roll back |
| M4 warm-up numeric/capability failure | model unready; no request accepted |
| stale handle/epoch/ticket/KV generation | `FailedPrecondition`; no newer state mutation |
| synchronous launch failure after queued work | failed draining ticket; no output/KV commit |
| asynchronous CUDA fault/device loss | `Unavailable`; poison context/model, drain safely, stop worker |
| NaN logits/incremental-decode failure | request `DataLoss`; acknowledge execution, no new token commit |
| CLI output failure | cancel/drain request, nonzero exit; model may remain healthy |

Statuses include bounded model/instance IDs, operation/layer, work kind, logical position/range,
required/available memory category, backend/device scope, and retryability. They exclude prompt/model
bytes, logits, raw pointers, or unbounded parameter lists.

### 18.3 Unload and shutdown

Model unload is explicit/idempotent:

```text
Ready -> Draining; reject new request/submission
-> cancel or finish the one request by deadline
-> poll/apply/acknowledge all tickets and reset KV generation
-> release prepared operator set/diagnostics
-> release KV, activations, logits, constants, weights explicitly
-> verify model memory categories returned to pre-load baseline
-> invalidate handle generation -> Closed
```

If deadline expires with uncertain GPU work, retain all referenced model memory and return
`DeadlineExceeded`; do not free and claim unload success. Context-level poison follows M2's safe
shutdown. The model instance is destroyed before cuBLASLt/operator/CUDA context owners it references.

Destructors do not synchronize. A destructor reached before explicit close records a leak/invariant
failure and transfers safe ownership to context teardown where possible.

### 19.4 Correctness (`m5-correctness`)

- Compare every named intermediate on diagnostic fixtures.

No expected-value regeneration occurs in the test. A mismatch prints bounded summaries and the exact
fixture/step/intermediate name, not whole tensors/prompts.

### 19.5 Stress and soak (`m5-stress`)

- At least 1,000 sequential generations with varied legal prompt/output lengths in one loaded model.
- Verify after every request that KV has no pending transaction, activation/workspace/metadata/logits
  leases are returned, plan slot is available, no ticket remains, and non-model categories equal
  their warm baseline.
- Nightly repeated load/generate/unload cycles across dtype/tie variants.
- Cancellation injected before/during/after every eager step over thousands of deterministic seeds.
- Near-context-capacity sequences and repeated KV generation reuse without memset dependence.
- Multi-hour one-model decode soak recording memory/counters and output checksums.

The required 1,000-request gate permits persistent model weights/KV backing/operator plans to remain
at the warm model baseline. After unload, all model categories also return to pre-load baseline.

### 19.6 Failure and sanitizer (`m5-failure`, `m5-compute-sanitizer`)

- Model-too-large plan, device OOM, staging exhaustion, malformed prompt, unsupported model/context,
  stale model/cache/ticket, and every injected CUDA submission/completion failure.
- Cancellation/shutdown with weight upload, warm-up, prefill, decode, or logits D2H in flight.
- ASan/UBSan for CPU planner/reference/lifecycle/CLI; TSan for tokenizer/runner/control paths.
- Compute Sanitizer memcheck over load/prefill/decode/unload; racecheck/initcheck/synccheck over the
  complete tiny-model path and M4 kernels.
- Canary/poison checks around weight, activation, logits, and KV ranges; unused KV never read.
- API counters fail on per-token `cudaMalloc`, `cudaFree`, descriptor preparation, default stream,
  stream/device synchronize, or pageable async transfer.

GPU tests cannot pass by skipping. Process-inconsistent device faults run in isolated subprocesses.

### 19.7 Performance (`m5-performance`)

Record without a pass threshold:

- artifact validation, memory planning, allocation, upload, operator preparation/warm-up, and total
  load-to-ready time;
- first and steady prefill tokens/s by prompt length;
- decode time per output token (TPOT), separating GPU, logits D2H, polling, argmax, and incremental
  decode;
- total generation time, peak device/pinned/host bytes by category, arena padding/high-water;
- per-operation/kernel breakdown using profiler/timing events; and
- unload/drain time.

Evidence records repository/dependency/fixture/model fingerprints, dirty state, compiler/NVCC,
CUDA/driver/SM/GPU clocks/power, backend selection, config, prompt/output lengths, iterations, and raw
JSON. Warm-up is excluded from steady execution metrics but reported separately. M5 makes no serving
throughput claim and sets no optimization gate; unexpected synchronization/allocation remains a
correctness failure.

## 23. Risks and required experiments

| Risk/question | Required evidence | Decision/fallback |
|---|---|---|
| full contiguous KV/model does not fit public checkpoint | pre-allocation memory report over candidate models | narrow context/model; do not overcommit; M6 changes KV, not weight reality |
| row-major source weight mapping produces plausible wrong GEMM | small hand weights plus every projection intermediate | retain identity layout; fix adapter/descriptors, never ad-hoc transpose |
| double-buffer upload reuses mapping/staging too early | delayed-copy fake and real event tests | retain mapping/staging/fence bundle until completion |
| tied LM head accidentally duplicates/diverges | plan/range identity and readback tests | one target allocation/view; no alias upload |
| activation reuse overwrites a still-live async input | liveness DAG, canaries, Compute Sanitizer | simpler larger arena or later reuse point |
| prefill/decode off-by-one corrupts RoPE/KV | P/O table property tests and high-position reference | preserve M1 ranges and rotated-K convention |
| synchronous launch fails mid-layer | queued-work seam at every op | return draining failed ticket or poison; never bare rollback/free |
| logits D2H introduces device-wide sync | API counters/profiler stream trace | event dependency + pinned copy + final transfer fence |
| host greedy differs on ties/NaN/EOS boundary | hand/golden tests and framework adapter rule | lowest ID; NaN error; EOS wins after emitted token |
| CPU/GPU semantic driver shares same orchestration bug | pinned independent framework intermediates/tokens | reject until both independent and CPU comparisons agree |
| numeric errors compound to token divergence | calibration/holdout logits/margin report across dtype | stricter M4 backend/math or narrower supported dtype; never excuse token mismatch |
| diagnostic mode changes production lifetime/performance | separate preplanned capture plan and overhead benchmark | keep off by default; bounded startup-only option |
| cancellation frees in-flight KV/weights | delay injection at every state and generation checks | enter cancelling/drain; retain complete resource bundle |
| 1,000 requests leak only small per-token objects | allocator/API counters and baseline check every request | preallocate/fix ownership; do not hide with periodic restart |

## 25. Definition of done

### Model semantics and memory

- [ ] Dense Llama forward order, positions, RoPE/KV convention, logits selection, and intermediate
      names are implemented once and match this document.
- [ ] CPU semantic/reference path matches independent fixtures within accepted thresholds.
- [ ] Complete deterministic memory plan succeeds or fails before model allocation with checked math.
- [ ] Weight bytes/layout/dtype are preserved, tied aliases share storage, and upload is bounded/pinned.
- [ ] Activation liveness has no live overlap and steady execution performs no allocation.

### Model instance and eager execution

- [ ] Model load/warm-up is transactional and no handle/readiness publishes on partial failure.
- [ ] Contiguous KV generation/append/commit/reset is transactional and stale-safe.
- [ ] Prefill/decode ranges and positions match M1 for every boundary test.
- [ ] Final fence covers all model kernels, KV writes, logits, and D2H host visibility.
- [ ] Partial submission/cancellation/failure retains resources until safe drain/acknowledgement.
- [ ] Unload returns model categories to pre-load baseline or retains uncertain resources with error.

### Output and CLI

- [ ] Greedy FP32 host argmax has exact lowest-ID tie/NaN policy and no softmax.
- [ ] EOS token is emitted and real EOS/length precedence matches fixtures.
- [ ] Token, text/chat, incremental decode, and text/tokens/JSONL modes pass ordered event tests.
- [ ] The documented local tiny-model command works from a fresh supported environment without network.
- [ ] CLI cancel/deadline/stdout failure drains safely and exits nonzero with one terminal outcome.

### Verification and evidence

- [ ] Every named diagnostic intermediate, required KV write, and logits step meets ADR 0036 thresholds.
- [ ] At least 100 prompts match reference token-for-token for up to 32 tokens unless EOS.
- [ ] After 1,000 sequential requests, every non-model category equals its warm baseline.
- [ ] Repeated load/unload returns all model categories and CUDA handles to pre-load baseline.
- [ ] ASan/UBSan/TSan and memcheck/racecheck/initcheck/synccheck required paths are clean with no skip.
- [ ] No per-token CUDA allocation/free, descriptor preparation, pageable async copy, default stream,
      or stream/device synchronize appears in API counters/profiler evidence.
- [ ] Load/prefill/decode/TPOT/memory/kernel evidence and worst numeric cases are retained.
- [ ] ADRs 0031-0036 and model/memory/numeric/CLI documentation match behavior.

## 26. Handoff to M6

M5 hands M6:

- a correct batch-one `LlamaForCausalLM` semantic path and ready CUDA model instance;
- immutable device weights, activation/workspace plans, and prepared M4 operators;
- exact prefill/decode token positions, logical KV read/write ranges, and rotated-K convention;
- a correctness-oriented contiguous KV implementation with generation and transactional visibility;
- real eager execution tickets/fences/completions integrated with M1 lifecycle;
- deterministic tiny-model intermediate/logit/token fixtures and numeric thresholds;
- a local generation CLI and repeatable load/generate/unload command; and
- memory, failure, sanitizer, profiler, and performance baselines.

M6 replaces only the physical KV implementation and extends its reservation/metadata. It keeps
M5's model weights, semantic operator order, token positions, transactional commit-after-completion,
ticket ownership, and contiguous KV as the correctness oracle. M6 must prove paged/contiguous
logits and tokens agree before the eager baseline can cease being the default. It cannot reuse pages
before the covering fence, expose partially committed layer KV, or change generation semantics to
fit a page allocator.
