# M12 implementation specification: single-GPU performance

- Status: proposed implementation contract
- Roadmap milestone: M12 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M11](m11.md), including M1-M10 transitively
- Immediate consumers: M13 quantization/model expansion and M14 worker isolation/tensor parallelism
- Later consumers: M15 pipeline parallelism, M16 expert parallelism, M17 speculative decoding, and
  M18 disaggregated prefill/decode

> **Re-planning note (2026-09-03, ADR 0042):** the M1 CPU
> scheduler simulator this specification assumed as its offline oracle was removed. Simulator-based
> gates, tools, stages, and imported-workload plans below are void until re-planned against real
> execution (serving benchmarks, recorded traces, and soak suites).


This document turns M12 into an executable engineering plan. It defines a qualified GPU sampling
path, compact device-to-host results, asynchronous bounded output preparation, double/triple-buffered
step metadata, CPU preparation of plan N+1 while GPU step N runs, measured decode buckets, stable CUDA
graph arenas, graph capture/replay/cache lifecycle, deterministic padding, profile-guided backend and
fusion selection, a versioned autotune cache, failure/fallback containment, telemetry, correctness,
performance evidence, the single-GPU v0.1 release, and the handoff to M13/M14.

M12 optimizes execution routes. It does not change model, sampling, scheduling, KV, prefix-cache,
protocol, or output semantics. The accepted M9 CPU sampler and M11 eager engine remain the reference
paths. An optimization is enabled only for a capability tuple that passes its independent equivalence,
resource, failure, and performance gates.

## 1. Outcome

At the end of M12, InferX can:

1. select CPU or GPU sampling per accepted step from a frozen capability table while preserving M9's
   transform order, counter RNG, token choice, logprob ordering, and failure semantics;
2. keep full vocabulary logits on device for qualified GPU sampling and copy only a fixed-size sampled
   decision and requested bounded alternatives to host;
3. transfer CPU sampling and token/output preparation through bounded generation-checked jobs so the
   coordinator and device worker do not perform tokenizer, stop-matching, or formatting work inline;
4. prepare a pure plan draft and host metadata for step N+1 while GPU step N runs, then revalidate and
   transactionally accept or discard the draft after all causally earlier events are applied;
5. use double- or triple-buffered metadata/result slots without overwriting a slot until its upload,
   execution, D2H, output-job, and acknowledgement ownership has drained;
6. replay measured decode shapes through stable-address CUDA graphs whose backends, workspaces,
   sampling route, table/cache generations, and arena leases are validated for every launch;
7. pad only into explicit inactive lanes that cannot write request KV, consume RNG, produce output, or
   alter active-lane numerics and choose the smallest eligible measured bucket deterministically;
8. capture, validate, cache, touch, evict, quarantine, and destroy graph entries within a fixed host/
   device budget while always retaining a correct eager route;
9. load or produce a checksummed autotune decision only for an exact device/software/model/operator/
   shape identity and freeze the selected backend before readiness;
10. attribute launch gaps, graph eligibility/hits/padding, sampling/D2H/output/overlap cost, arena
    memory, and backend decisions through M10's bounded privacy-safe telemetry; and
11. prove at least 90% graph hit rate on the selected workload, at least 99% reduction in logits D2H
    traffic, no slower qualified sampling at target concurrency, and at least 15% SLO-goodput gain over
    the exact M11 baseline without a correctness or reliability regression.

```text
coordinator turn                         device worker / GPU                 output pool
----------------                         -------------------                 -----------
apply completion/output events
build M8/M11 transaction
reserve metadata/result/output slots
accept immutable step N  -------------> resolve eager/graph + CPU/GPU route
commit scheduler/KV ownership           upload sealed metadata
capture pure snapshot for N+1            execute eager or graph
prepare N+1 draft in parallel            sample on GPU or stage CPU logits
                                         compact D2H + final fence
                         <-------------  completion transfers owned values
commit valid KV completion
dispatch bounded output job ----------------------------------------------> sample if CPU route
prepare other requests / N+1 draft                                         decode/stop/render
                         <------------------------------------------------ prepared output result
apply cancel/deadline precedence
commit token/history/output once
revalidate N+1 draft; accept or discard
```

M12 is complete only if disabling every M12 optimization returns to the same M11 feature set, an
unsupported or cold route falls back before the first CUDA operation without changing the accepted
logical plan, and an error after launch is never hidden by replaying work on a second path.

### Implementation status (2026-08-31)

This file is a documentation specification only. This change does not add or authorize M12 source,

## 2. Scope boundaries

### 2.1 In scope

- Qualified GPU implementations of every advertised M9 sampling parameter and logprob combination.
- One fixed compact device result record per active sequence plus bounded requested alternatives.
- CPU sampling fallback for unsupported hardware/configurations and the unchanged CPU oracle.
- Bounded asynchronous CPU sampling fallback, token rendering, incremental decode, stop matching, and
  output-record preparation using immutable snapshots and coordinator commit.
- Pure CPU plan-draft preparation during an in-flight GPU step, with exact generation revalidation.
- Double/triple-buffered pinned/device metadata and compact result rings with explicit slot states.
- CUDA graphs for evidence-selected single-token decode batch buckets; prefill/mixed graphs only after
  a separate M12 ADR amendment and the same gates.
- Stable graph input, metadata, workspace, logits/sampling, output, and inactive-lane arena slices.
- Capture-safe backend qualification, deterministic bucket selection/padding, eager fallback, graph
  cache budget/LRU/eviction/quarantine, and replay leases.
- Startup/offline autotuning and profile-guided backend/fusion selection under a frozen registry.
- Exact memory-accounting integration with M2/M5/M6/M11 and fixed telemetry/fault/replay extensions.
- Paired micro/model/embedded/HTTP performance evidence and the single-GPU v0.1 release bundle.

### 2.2 Explicitly out of scope

- More than one accepted GPU model step executing concurrently. M12 overlaps CPU preparation/output
  with the one worker-owned GPU step; it does not introduce concurrent model tickets on multiple
  compute streams.
- Changing M8 ranking, fairness, deadline, chunk, cache-aware, or preemption policy to manufacture
  larger graph batches. The selected plan is bucketed after scheduling.
- Multi-step decoding inside one graph, speculative decoding, draft tokens, KV rollback, beam search,
  or grammar-constrained sampling; M17 owns speculative execution.
- Graphing arbitrary prefill/mixed shapes by default, dynamic-shape graph mutation, request-specific
  graph construction, or waiting for a larger bucket solely to improve graph hit rate.
- Using CUDA graph replay as a correctness fallback, retrying after an uncertain launch, or silently
  switching sampling algorithms after a ticket starts.
- JIT compilation, downloading kernels/tuning data, loading executable code from an autotune cache,
  or benchmarking untrusted candidates in a serving process.
- Quantization, a second model family, tensor/pipeline/data/expert parallelism, distributed sampling,
  KV transfer/offload, or multiple worker processes; M13-M18 own those features.
- Moving stop/usage/protocol semantics into CUDA, emitting directly from a device callback, or letting
  output workers mutate `RequestContext`, penalty history, KV tables, response mailboxes, or sockets.
- Replacing M10 health/diagnostics with profiler hooks, exposing prompts/tokens/seeds in metrics, or
  leaving Nsight/NCU collection enabled in production.
- Claiming graph-cache memory is free/evictable KV capacity or allocating graph arenas from space
  already promised to admitted requests.

## 6. Baseline, optimization axes, and comparison identity

### 6.1 Frozen M11 baseline

The M12 baseline is the exact successful M11 candidate image/configuration on the same reference
hardware, including model artifacts, eager backends, page size, prefix-cache default, waiting policy,
CPU sampler, synchronous-reference output path, telemetry policy, workload schedule, SLO, driver,
CUDA/dependency pins, power/clocks, container, and successful request set.

The baseline manifest contains source/image/config/model/system/workload fingerprints and raw M10/M11
evidence. A comparison with any differing semantic, workload, SLO, cache, or success-set fingerprint
is invalid rather than normalized after the run.

### 6.2 Orthogonal switches and required ablations

M12 exposes four semantic-preserving optimization axes:

1. CPU versus qualified GPU sampling;
2. reference-inline versus asynchronous output preparation;
3. plan-overlap off versus pure N+1 draft preparation; and
4. eager versus eligible CUDA graph execution.

Profile-guided backend/fusion selection is a fifth frozen model-startup choice. Evidence runs the
M11 baseline, each axis individually, cumulative combinations in the implementation order, and the
final selected configuration. This separates interaction gains from one favorable aggregate number.

### 6.3 Route invariants

- A logical `StepPlan` has one request set, token ranges, positions, tables, sampling snapshots,
  output slots, and completion semantics independent of physical route.
- Pre-accept proposal may choose the qualified CPU/GPU sampling location. The worker's later route
  selection may change only graph versus eager launch, stable arena, and metadata/result slot within
  that fixed sampler/backend semantics; neither boundary can change scheduler selection, token budget,
  KV mutations, RNG index, output ordering, or response capacity.
- Every possible route in an accepted route set has already passed capability and capacity checks.
- The device worker selects exactly one route before the ticket's first CUDA operation and records it.
- Once any operation for the ticket is issued, no alternate eager/graph/sampler route may rerun it.
- Route off/miss/fallback is a bounded reason, not an internal error and not a model-health change.

## 7. Execution capability and route selection

### 7.1 Published capability snapshot

The device worker publishes an immutable bounded generation-checked snapshot containing:

- model/device/backend-registry generations and health;
- supported eager phase/shape/workspace routes;
- GPU sampler parameter/logprob/vocabulary/batch capability and health generation;
- Ready graph keys, bucket shapes, graph-entry/arena generations, free replay instances, and padding
  limits;
- metadata/result/output/sampling/workspace/event capacity by closed class;
- graph-cache/device/host budget, capture state, and retired/quarantined counts; and
- frozen autotune/backend/fusion decision fingerprint.

The coordinator reads the publication only. It does not traverse the worker's graph cache or CUDA
objects. Snapshot staleness is expected and is handled by route-set validation, never by dereferencing
an old entry.

### 7.2 Deterministic route order

Route selection has two ordered stages. First, proposal fixes exactly one sampling location:

1. select GPU when the normalized tuple has a qualified retained capability; otherwise
2. select the CPU reference and reserve its full-logits host result/output-job capacity.

That CPU/GPU choice is part of the accepted logical/physical plan and cannot change afterward. Within
the fixed sampling location, the route set prefers a matching Ready graph and always contains its
qualified eager form. A graph with CPU sampling exists only when its captured variant produces full
logits and the CPU host result capacity is already reserved.

Configuration may force CPU or require a qualified GPU tuple, but it may not omit the eager form for
a supported M11 request. A graph miss/stale/busy offer falls to eager with the same sampler, RNG,
result schema, workspace bound, and logical plan. A GPU sampler capability miss is known during
proposal and selects CPU; it is not discovered after logits exist.

The route-set tuple and stable preference reason are included in the plan digest. Before worker-
channel acceptance, ordinary capability/capacity failure rejects the proposal and lets M8 roll back.
After acceptance, graph unavailability is a guaranteed eager execution, not a rejected submission.

### 7.3 Physical acceptance boundary

Backend/channel acceptance reserves a conservative resource envelope covering the eager route and
the preferred graph route for the fixed sampler. It durably transfers an immutable route-set identity
to the ticket before the coordinator's no-fail M8/M11 commit. From that point the worker must return a
matching completion/drain record and can always execute the prepared eager form while the context is
healthy.

The route-set identity includes strong model/backend/sampler generations, optional graph offer,
metadata/result/output slots, maximum workspace/padding class, table/cache namespace and epoch bundle,
policy generation, and ticket generation. When dequeuing the accepted command, the worker acquires a
graph replay lease or records eager fallback before the first CUDA operation; the final route is added
to the completion identity. Neither value contains raw pointers outside the device worker.

## 8. GPU sampling contract

### 8.1 Qualification and per-step selection

GPU sampling implements M9 sampling version 1; it does not define version 2. Qualification is by the
exact tuple of SM/toolchain, vocabulary bound, dtype of the FP32 logits input, batch bucket, normalized
parameter feature mask, maximum sparse bias/history entries, EOS count, requested top-logprobs bucket,
workspace class, and eager/graph mode.

Every public M9 parameter remains accepted independently of GPU support. Before plan acceptance:

- a qualified tuple selects GPU sampling;
- an unqualified tuple selects the CPU reference and full-logits D2H capacity;
- a forced GPU route on an unqualified tuple is rejected as configuration/capability error; and
- automatic mode never changes normalized sampling parameters to fit a GPU kernel.

Qualification requires all conformance, failure, sanitizer, and target-concurrency benchmarks for the
tuple. A model cannot advertise GPU sampling merely because one greedy kernel ran successfully.

### 8.2 Immutable device inputs

The M9 sampling snapshot is packed into a versioned device view containing:

- sampling version, normalized seed, zero-based committed output position, and fixed Philox substream;
- temperature/top-k/top-p/min-p and repetition/frequency/presence penalties in canonical types;
- ordered bounded logit-bias `(token_id, value)` pairs;
- ordered unique history `(token_id, count)` pairs whose counts match committed history;
- normalized EOS token IDs and `min_output_tokens` state;
- requested top-logprobs bound and compact-result destination identity;
- active-lane bit, request/sequence/epoch/ticket/snapshot generations; and
- vocabulary length, logits stride, scratch offsets, and integrity checksum.

The coordinator owns the logical snapshot; the device worker copies a sealed value through the M12
metadata lease. Device kernels never read `RequestContext`, tokenizer state, prefix-tree metadata,
host vectors, or another lane's variable-length arrays. Sparse offset/count ranges are checked,
nonoverlapping, and bounded by startup proof.

### 8.3 Normative transform pipeline

For every active row, the GPU route performs the exact M9 stage order:

1. validate identity/ranges and inspect FP32 logits for NaN and infinities;
2. apply ordered additive bias;
3. apply repetition, frequency, and presence penalties from committed history;
4. mask EOS while below the minimum output length;
5. run lowest-token-ID deterministic argmax for temperature zero; otherwise apply temperature;
6. compute the versioned stable normalization;
7. apply top-k, top-p, and min-p with M9's tie and always-retain rules;
8. renormalize and select using the M9 Philox variate/comparison rule;
9. select and order requested logprob alternatives; and
10. write one compact result record and completion status.

Parallelization and fusion may combine passes only if intermediate-conformance tests show the same
survivor set, tie order, selected token, status class, and accepted logprob thresholds. The reduction
tree, accumulator precision, comparison boundaries, and special-value behavior are part of ADR 0082
and sampling/backend identity. Fast-math or implementation-defined unordered atomics are forbidden on
the normative path.

Sampling version 1 retains M9's deterministic FP64 accumulation in token-ID order and its strictly-
greater cumulative selection comparison. If a parallel reduction/scan cannot reproduce the required
token/alternative identities and existing numeric threshold on adversarial boundaries, that kernel/
bucket is not qualified; M12 does not silently substitute a different association rule.

The GPU route must match the M9 CPU oracle's selected token and ordered alternative token IDs exactly
for every known-answer, randomized, adversarial-boundary, and model-produced fixture. Logprob values
must meet M9's already-declared thresholds; M12 cannot widen them. If this cannot be achieved for a
tuple, that tuple remains CPU-routed.

### 8.4 RNG indexing and batch independence

Philox key/counter construction is byte-identical to M9. It contains normalized request seed,
sampling version, zero-based committed output position, and fixed substream tag. It does not contain
batch lane, graph bucket, padded size, device clock, stream, ticket retry count, scheduler step,
worker thread, or graph replay ordinal.

Inactive padded lanes execute no RNG transition. A cancelled/uncommitted result does not consume a
mutable RNG state because the next variate is derived again from the committed output position.
Rebatching, cache hits, M8 preemption, graph/eager switching, and CPU/GPU switching therefore cannot
change the requested variate.

### 8.5 Compact result and D2H contract

One fixed-capacity `CompactSamplingResult` contains:

- result schema and integrity checksum;
- request/sequence/epoch/ticket/sampling-snapshot identities;
- sampling version, output position, and route/backend identity;
- selected token ID and selected finite logprob where requested;
- up to the configured maximum unique alternatives in probability-descending/token-ID-ascending
  order, each with token ID, value, and special-value class;
- survivor count, normalized status class, and diagnostic boundary flags; and
- no prompt, decoded text, raw logits, probability vector, seed, or device pointer.

The result row has a startup-proved fixed maximum and is copied through a stable pinned result slot.
The ticket's final fence covers model/KV writes, sampling kernels, compact D2H, and result checksum
publication. Host code cannot inspect the slot before fence completion and cannot release/overwrite it
until the completion value is copied or ownership transfers to an output job.

For the qualified target workload:

```text
cpu_sampling_logits_d2h_bytes = active_sequences * vocabulary_size * sizeof(float)
gpu_sampling_d2h_bytes        = active_sequences * compact_result_stride
d2h_reduction                 = 1 - gpu_sampling_d2h_bytes / cpu_sampling_logits_d2h_bytes
```

Report payload and transfer-protocol bytes separately. The roadmap gate requires at least 99%
reduction in logits/result D2H bytes for qualified steps; H2D metadata and unrelated telemetry are not
misclassified as logits traffic.

### 8.6 Sampling failures and fallback boundary

- Unsupported tuple, disabled route, unavailable capacity, or unhealthy-but-contained sampler selects
  CPU before acceptance.
- NaN, no selectable token, invalid normalization, or semantic result status produced by a successful
  kernel is the same request-scoped M9 result; it does not rerun on CPU.
- An identity/checksum mismatch detected before launch rejects the route without mutation.
- A CUDA launch, execution, D2H, or fence error after work begins has uncertain device state and
  follows M2/M10 poison/drain; it is never retried through CPU sampling.
- A GPU result that fails host identity/checksum validation is not committed and follows the
  ownership-integrity containment matrix.

Sampling can be disabled independently after a contained qualification/configuration issue only when
no accepted ticket uses it. Runtime circuit state is part of the capability generation; active
tickets finish under their retained route identity.

## 9. Asynchronous output preparation

### 9.1 Purpose and ownership

M12 removes CPU sampling fallback and token/output preparation from the device worker/coordinator hot
paths while retaining M9's prepare-before-commit rule. A bounded `OutputProcessorPool` consumes owned
immutable jobs and returns proposed results. It never commits request state or writes a response.

For a GPU-sampled step, the job contains the compact result. For a CPU-sampled step, it additionally
owns the completed pinned full-logits row lease and runs the unchanged M9 sampler before rendering.
In both cases it receives:

- strong request/sequence/epoch/ticket/output-job identity;
- immutable sampling snapshot and committed output position;
- immutable incremental-decoder/stop-matcher state snapshot;
- stable vocabulary render-table handle/generation;
- endpoint/output profile needed to prepare bounded protocol-neutral values;
- pre-reserved result/text/logprob storage; and
- cancellation-independent deadline only for watchdog classification, not semantic mutation.

Jobs contain no request pointer, mutable penalty state, KV/table handle, socket, mailbox, graph/stream,
or device memory. A full-logits host lease is read-only and released by the job result/drain path.

### 9.2 Output-pending lifecycle

After a valid device completion is applied, the coordinator may commit successful KV/computed-token
progress and transition each sampling item into `OutputPending`. It does not yet commit the sampled
token, penalty count, RNG/output position, decoder/stop state, usage, mailbox event, or finish reason.
An `OutputPending` request is not decode-eligible and has at most one live output job.

The output worker:

1. validates immutable identities and result capacity;
2. runs CPU sampling when selected;
3. resolves selected/alternative render entries;
4. applies incremental UTF-8 decode and stop matching to the copied state;
5. prepares the exact token delta/logprob/usage/finish proposal and next decoder/stop state;
6. seals a checksummed `PreparedOutput`; and
7. publishes it into the reserved result slot without touching coordinator state.

The coordinator applies cancellation/deadline/shutdown and stale-event precedence first. If the
request epoch/job/output position still match, one no-fail transaction commits token, penalty history,
output count, decoder/stop state, mailbox record or terminal, resource release, and next readiness.
Otherwise it drains the job/result/host-logits lease and commits no token.

### 9.3 Ordering and boundedness

Worker assignment is deterministic by job ordinal modulo fixed worker count. Each worker has a bounded
SPSC input/result path and precreated tokenizer/decoder scratch qualified under M3. Result capacity is
reserved during M8 prepare, so an accepted GPU completion can always enqueue or place the job in a
bounded coordinator-owned pending slot.

Results from one device completion batch are applied in canonical plan-item order. A bounded reorder
array may hold an early-finishing later item until preceding items are present or terminally drained.
Across batches, observed completion ordinals are recorded for replay; no request has two jobs, so its
output can never reorder.

Queue saturation prevents selecting additional sampling work before plan acceptance. It does not
block the coordinator, device worker, or output worker and does not discard an accepted result.

### 9.4 Output failure behavior

CPU semantic sampling failures preserve M9's request-scoped result. Renderer/decoder/stop/output
capacity failures commit no new token and terminally fail that request after ownership drains. A
stale job is discarded. A worker exception/crash is contained by M10: its owned jobs move to an
explicit failed-result/drain path or make the component unready; they are never silently lost.

Async output off uses the same immutable job and coordinator commit functions on the reference host
path, making the switch an execution-placement change rather than a second semantic implementation.

## 10. Plan N+1 overlap and metadata pipeline

### 10.1 Scope of overlap

M12 retains one accepted GPU model ticket at a time. While step N is in flight, CPU work may:

- capture a bounded immutable scheduling/resource/capability snapshot;
- rank candidates and calculate a pure M8/M11 proposal;
- choose provisional execution/sampling/graph buckets;
- materialize static host metadata fields into an unsealed slot; and
- compute validation digests and exact resource deltas.

It may not reserve/commit KV, cache, table, response, output, workspace, graph, metadata, event,
channel, request-state, or worker resources; upload metadata; submit CUDA work; touch cache LRU; alter
ready time; or consume a phase/bypass counter. A draft is advisory and disposable.

For the same request as step N, the sampled token and output commit are unknown, so the draft may
contain only a bounded dependency placeholder and static shape data. It cannot fabricate token,
position, stop, history, table epoch, or sampling state. Other already-ready requests can be drafted
fully from the snapshot.

### 10.2 Overlap snapshot and draft identity

The coordinator publishes one value-only `OverlapInputSnapshot` per accepted step when a fixed draft
slot is free. It includes every M8 read-phase field plus:

- request, output-pending, table/cache/reset, resource, and response generations;
- current in-flight ticket's conservative held-resource set and possible completion deltas;
- device capability/graph-cache/autotune generations;
- output/metadata/result ring capacity generations;
- stable policy clock value and deadline interpretation from the originating turn; and
- closed reason codes for fields intentionally deferred until step N completes.

A pure planner returns a `PreparedStepDraft` containing the source digest/generations, proposed
canonical request items, route/bucket preferences, static packed metadata, resource-delta bounds,
dependency placeholders, and explanation codes. It owns no live scheduler/device resource.

### 10.3 Revalidation and commit

After processing causally earlier cancellation, deadline, device completion, output, reset, policy,
and shutdown events, the coordinator revalidates the draft field by field against the current owner
state. Dynamic placeholders are resolved from committed values. Revalidation outcomes are:

- **exact reusable:** use the draft proposal and packed static fields;
- **patchable:** apply only the finite ADR-listed fields whose bounds/layout cannot change, then run
  the full ordinary M8/M11 validator;
- **stale:** discard without state mutation and plan normally; or
- **invalid invariant:** enter existing containment, not ordinary stale fallback.

The normal M8/M11 prepare, acceptance, no-fail commit, and rollback remain authoritative. Draft reuse
does not skip resource acquisition, generation checks, cache match pinning, table/mirror construction,
output reservation, or physical route acceptance.

### 10.4 Metadata/result slot state machine

Every pinned-host/device metadata or result slot has strong slot/generation and moves through a closed
state machine:

```text
Free -> HostPreparing -> Sealed -> Accepted -> Uploading -> InFlight
     -> D2H/Completed -> CopiedOrTransferred -> Acknowledged -> Free

HostPreparing/Sealed -> DraftDiscarded -> Free
any accepted state with uncertain CUDA work -> DeferredOrPoisonRetained
```

Only the current owner may write a HostPreparing slot. Sealing computes schema/range/checksum and
makes it immutable. A draft slot is not uploadable until the ordinary plan commits. Device metadata,
graph arena, and output result slots use distinct generations even when backed by one startup
allocation.

Double buffering is the minimum for one in-flight plus one preparing slot. Triple buffering is
selected only when evidence shows a third independently owned completed/output-transfer or capture
slot removes a real stall. Ring depth is fixed at startup and included in memory/capacity proof.

### 10.5 Planner worker and coordinator progress

If a dedicated planner thread is used, it consumes value snapshots through bounded SPSC queues and
runs only pure CPU functions with fixed scratch. It cannot call clock, CUDA, allocator, cache, request,
or telemetry-owner mutation APIs. The coordinator never waits for it: missing/late output triggers
ordinary planning and invalidates that draft generation.

Planner cost has a per-job operation bound and watchdog heartbeat. A planner failure degrades overlap,
not inference, only if all jobs/slots reconcile and the reference coordinator planner remains healthy.
Repeated stale/late drafts trip a circuit breaker that disables new drafts for a cooldown generation.

## 11. CUDA graph eligibility and bucket policy

### 11.1 Initial graph envelope

The initial production graph envelope is one-token decode for a batch of active sequences. A step is
graph-eligible only when:

- its work composition is exactly the qualified decode phase, with no prefill/recompute/mixed item;
- every operation/backend in the frozen forward and sampling route is graph-capture qualified;
- model, dtype/layout, attention/page geometry, vocabulary, sampling, workspace, and result shapes fit
  one Ready bucket exactly or through permitted inactive-lane padding;
- diagnostics/full-logits dumps, fault actions requiring eager boundaries, and unsupported telemetry
  capture are off for that ticket;
- all dynamic inputs are represented in stable graph metadata rather than host branches or changed
  kernel topology;
- a matching Ready graph entry and free stable replay instance exist in the advertised generation;
- every exact KV table/cache/page handle and epoch can be pinned for the ticket; and
- selected graph memory/workspace/result/output resources satisfy the M8/M11 capacity transaction.

An ineligible decode and every prefill/mixed step use eager execution. Graph eligibility never rejects
a request that the eager M11 capability supports.

### 11.2 Graph shape class

A `GraphShapeClass` contains only launch/topology-affecting values:

- graph schema; model-instance/operator-registry/backend-selection fingerprints;
- device compute capability and compiled kernel capability class;
- phase and one-token-per-active-sequence contract;
- active sequence batch bucket and maximum block-table/context metadata bucket;
- dtype/layout/head/vocabulary/page geometry already frozen by the model instance;
- exact selected backend/algorithm and workspace class for every graph-visible operation;
- sampling route, normalized feature-mask bucket, sparse-metadata bound, and top-logprobs result bucket;
- graph-visible telemetry/debug mode and completion-result schema; and
- stable arena layout/capture-policy generation.

Actual token IDs, positions, sequence lengths, table entries, prefix namespace IDs, block handles,
RNG seeds/output positions, sampling values, request IDs, and ticket generations are replay metadata,
not reusable graph-key dimensions. They are validated for every replay and copied into stable inputs.
Omitting them from the cache key does not omit them from ownership identity.

### 11.3 Deriving measured buckets

Bucket candidates come from the fixed M10/M11 reference workload trace plus declared capability
limits, never from ad hoc production growth. An offline deterministic selector evaluates:

- fraction of graph-eligible steps covered;
- active-lane utilization and padded FLOPs/tokens;
- graph entry, stable arena, workspace, metadata, and opaque-runtime memory;
- expected launch-gap reduction and measured per-bucket speedup;
- cold capture/warmup time and graph-cache churn; and
- worst-case pressure on KV/cache capacity and startup readiness.

The selector chooses a bounded ordered set under configured host/device/count budgets and emits its
input digest, objective weights, selected/rejected buckets, and predicted coverage. The selection is
reviewed in ADR 0085 and frozen in the model performance profile.

At runtime, choose the smallest Ready bucket that fits the accepted plan's actual active sequence,
table-metadata, sampling, and result bounds. Ties use canonical bucket ID. The scheduler neither waits
nor reorders requests to fill it. A larger Ready bucket may be used only when its configured maximum
padding ratio permits; otherwise the route is eager.

### 11.4 Eligibility and hit denominators

Telemetry distinguishes:

- all accepted GPU steps;
- decode steps inside the declared graph envelope;
- graph-eligible steps after semantic/capability checks;
- Ready-entry offers;
- successful replay hits; and
- misses by fixed reason: no bucket, padding cap, entry cold/capturing/quarantined, no arena instance,
  stale generation, debug/fault mode, memory/circuit state, or prelaunch validation.

The roadmap graph hit rate is successful graph replays divided by graph-eligible accepted steps after
warmup. Reports also publish coverage against all decode and all steps so a narrow denominator cannot
hide poor usefulness.

## 12. Stable graph arenas and address leases

### 12.1 Arena contents

Each graph entry owns one or more fixed-layout `GraphArenaInstance` values carved from the startup-
reserved graph super-arena. An instance provides stable aligned addresses for:

- paired pinned-host/device step metadata and active-lane masks;
- token IDs, positions, sequence lengths, table offsets/entries, and logical generation records;
- sampling parameters, sparse bias/history/EOS arrays, and compact result records;
- graph-specific activation and operation workspace slices not safely shared with eager execution;
- inactive-lane sink metadata/KV destinations and canaries;
- graph-visible status/error words and checksums; and
- optional stable graph memcpy source/destination buffers when ADR 0086 qualifies captured copies.

Weights, immutable constants, and the fixed M6 KV pool remain model-owned stable allocations. A graph
may reference their stable base addresses, but dynamic block-table values choose exact pages. It may
not capture a raw per-request table pointer, a movable metadata-ring address, a cache-index node, a
response buffer, or an output-job object.

The arena layout plan publishes every offset, size, alignment, lifetime, alias, initialization rule,
and maximum. Arithmetic is checked. No graph capture/replay path allocates device or pinned memory.

### 12.2 Replay instance lease

An instance has strong entry/slot/generation and states:

```text
Free -> HostWritable -> Sealed -> ReplayAccepted -> InFlight
     -> Completed -> Acknowledged -> Free
Free -> CaptureOwned -> Validating -> Free
any uncertain state -> Retired/PoisonRetained
```

A move-only replay lease owns the host/device arena slice, graph executable reference, workspace,
result slot, execution event, and exact dynamic identity bundle. It remains live through final fence
acknowledgement. Output work receives copied compact values or an explicitly transferred host lease;
it never holds the graph executable or device arena.

An entry cannot be evicted/destroyed and an arena cannot be reassigned while any capture, replay,
event, result-copy, or deferred fence names its generation. Reuse increments generation even if the
same virtual address is returned.

### 12.3 Stable versus ordinary metadata rings

Eager steps use the M2/M12 generational metadata ring. Graph replays use the graph instance's stable
paired metadata because captured memcpy/kernel nodes require invariant addresses. Both serialize the
same logical metadata schema and run the same validator.

A prepared eager slot cannot be reinterpreted as a graph slot, and graph memory is never lent to the
ordinary ring between replays. This deliberate separation trades fixed memory for address safety and
is included in graph usefulness/budget decisions.

## 13. Capture qualification and lifecycle

### 13.1 Backend capture-safety contract

Every graph-visible backend declares and is tested for:

- fixed launch topology for its shape class;
- stable pointer/workspace/handle requirements;
- no serving-time allocation/free, host synchronization, device query, lazy initialization, JIT,
  host callback into InferX, or data-dependent host branch during capture/replay;
- capture compatibility of external library handles/algorithms under the project's exact pins;
- explicit stream/event dependency behavior and error reporting;
- deterministic outputs inside existing numeric thresholds; and
- clean teardown after capture failure.

The registry defaults to `graph_unsafe`. Qualification is per exact backend/algorithm and toolchain,
not inherited by an operation name or library. Warm-up must execute every selected backend eagerly
before capture so lazy initialization cannot occur inside the capture boundary.

### 13.2 Graph entry state machine

```text
Missing -> CaptureQueued -> Capturing -> Validating -> Ready
   |             |              |            |
   +-------------+--------------+------------+-> Quarantined
Ready -> EvictPending -> Retired -> Missing
```

Transitions are device-worker-owned and generation checked. Ready is published only after capture,
instantiation, multiple replay validation, output comparison, canary validation, memory accounting,
and final context-health check all succeed.

The default release profile captures evidence-selected buckets during model warm-up from preallocated
arenas. Optional lazy capture is allowed only on a disposable capture stream/instance at a documented
device-idle boundary, under a per-turn/cooldown budget, and never ahead of queued request progress.
A miss serves eagerly while capture is absent.

### 13.3 Transactional capture

Capture uses synthetic bounded fixture inputs and dedicated scratch KV/table pages that cannot alias
live/admitted request pages. A capture transaction:

1. validates model/backend/key/policy and reserves a free cache entry/arena from existing budgets;
2. initializes all stable inputs, inactive sinks, status words, and canaries;
3. runs the qualified eager route to produce an expected result;
4. captures and instantiates on the disposable capture resources;
5. replays multiple active-count/length/sampling boundary cases;
6. compares intermediates where required, final logits/sampling result, scratch KV, and canaries to
   the eager route under existing thresholds;
7. measures arena and opaque graph-runtime memory deltas; and
8. atomically publishes Ready or destroys/quarantines the private entry.

No partially constructed graph is visible. Capture failure releases only provably safe resources. A
sticky/uncertain CUDA error poisons the context; a documented isolated capture incompatibility
quarantines that key and preserves eager readiness.

### 13.4 Warm-up and recapture

Model readiness requires eager warm-up. It requires graph warm-up only when configuration declares a
bucket mandatory. Optional graph capture failure leaves the model Ready/eager with Degraded graph
capability and a stable reason.

Any change to model generation, backend/autotune fingerprint, graph schema, arena layout, sampling
kernel identity, page/table layout, telemetry capture mode, or accepted software/device identity
invalidates the entry. M12 does not patch an old executable across incompatible generations; it
drains leases and recaptures or uses eager.

## 14. Graph replay transaction

### 14.1 Dynamic replay descriptor

For every replay, the physical route owns a checksummed descriptor containing:

- graph key/entry/arena generations and exact actual/padded shape;
- request/sequence/epoch/ticket and canonical lane mapping;
- token positions, sampling snapshot/output positions, and active mask;
- complete M6 table/mirror epochs and generational block handles;
- M11 cache namespace/reset generations and shared-page owner/pin identity bundle;
- workspace/result/output/event leases and graph-visible policy generation; and
- expected metadata/result schemas, byte ranges, and completion ordinal.

The reusable graph key proves compatible topology; this descriptor proves that the current logical
owners may use the stable instance. Every block the kernels can read or write is resolved from the
descriptor and pinned through final fence acknowledgement.

### 14.2 Prepare and prelaunch fallback

Before M8 acceptance, prepare:

1. graph offer/key/generation validation from the immutable worker snapshot;
2. exact table/cache/page/execution pins and mirror generation;
3. value-only metadata, inactive-padding plan, ranges, checksum inputs, and route-set seal;
4. conservative eager plus graph workspace/result/output/event/completion capacity for the fixed
   sampler; and
5. the ordinary M8/M11 KV/response/request transaction and worker-channel acceptance reservation.

After the accepted command reaches the device worker and before its first CUDA operation, the worker
tries to acquire the offered graph entry/arena replay lease and fills/seals that stable instance. A
cold/stale/busy offer selects the already guaranteed eager form and emits a prelaunch fallback reason.
The logical plan, sampling location, resource upper bound, and coordinator commit remain unchanged.

Normal graph unavailability cannot leave an accepted ticket without a route. If the promised eager
form itself is unexpectedly invalid after acceptance, the worker returns the required accepted-ticket
failure/drain record and enters capability/invariant containment; it cannot ask the coordinator to
roll back an already committed transaction. Graph replay is never launched speculatively and then
followed by eager execution for the same ticket.

### 14.3 Launch, completion, and acknowledgement

The selected replay performs the qualified metadata upload/captured memcpy, one graph launch, compact
result D2H where selected, and one final completion fence. Extra streams/events exist only when the
captured dependency graph proves them necessary; host code does not synchronize between nodes.

Completion validates final fence, device status/checksum, descriptor/ticket identity, and active-lane
results before publishing the atomic batch. The coordinator then follows ordinary M8/M11 completion
and M12 output-pending behavior. Acknowledgement releases execution/cache/table pins, graph replay
lease, arena/result/workspace/events, and retained policy/backend generations exactly once.

Any launch/replay/kernel/copy/fence error after the first CUDA operation is potentially partial. The
ticket returns failure/drain identity, its writable KV remains uncertain, graph entry is quarantined,
and M2/M10 decide context poison/controlled exit. It never retries eager.

## 15. Graph cache, memory budget, and eviction

### 15.1 Entry identity and contents

A graph cache key contains the complete section 11.2 shape class plus key schema. A Ready entry owns:

- graph definition/executable wrappers and backend-generation references;
- one or more stable arena instances and their layout/generations;
- conservative and measured host/device/opaque-runtime bytes;
- capture/validation evidence digest;
- insertion and last successful replay ordinals;
- replay/hit/failure counters with checked saturation policy; and
- state checksum, circuit/quarantine reason, and policy generation.

Two keys never share a mutable arena. Immutable weights/constants/KV base allocation may be common
because their model lifetime dominates every graph.

### 15.2 Capacity accounting

Startup reserves explicit upper bounds for:

- graph super-arena device bytes and alignment loss;
- stable pinned-host graph metadata/result bytes;
- graph entry/instance/event/lease/cache metadata;
- library/driver graph executable headroom measured on the reference stack;
- capture scratch and validation fixtures; and
- retired/quarantined resources awaiting safe destruction.

The reserved graph budget is removed from general device feasibility before M6 KV/cache geometry and
request admission limits are finalized. Lazy entries suballocate only from this reservation. They do
not consume `free_blocks`, `guaranteed_reclaimable_cache_blocks`, active-request workspace promises,
or untracked CUDA allocations.

Because opaque runtime allocation may not have an exact API-level size, ADR 0086 defines a
conservative per-entry charge plus before/after device-memory evidence and a global safety margin.
Post-capture growth beyond the charge aborts publication, quarantines/destroys the entry safely, and
can disable further capture. Reports distinguish exact InferX arena bytes from conservative opaque
charges.

### 15.3 Deterministic admission and LRU eviction

The cache has fixed maximum keys, entries, instances, and bytes. Entry admission is optional; failure
uses eager. To admit within budget, select only Ready entries with zero capture/replay/retired leases,
ordered by:

1. nonmandatory before mandatory release bucket;
2. last successful replay ordinal ascending;
3. insertion ordinal ascending; and
4. canonical graph key digest/entry strong ID.

Preview/eligibility does not touch LRU. After a successful graph completion, the entry commits the
ticket's coordinator-assigned accepted-plan ordinal as its access ordinal. Failed, stale, quarantined,
or eager-fallback routes do not make an entry look hot; wall clock and worker timing are not LRU order.

Eviction removes publication, marks EvictPending, waits for already-owned leases, destroys the graph
executable on the device worker at a safe nonblocking boundary, increments arena generations, returns
suballocations, and publishes final accounting. If destruction may synchronize or context health is
uncertain, defer it to drain/shutdown and keep memory charged.

### 15.4 Churn control

Per-key capture attempt limits, exponential ordinal-based cooldown, minimum observed eligible count,
per-interval capture/eviction budget, and a maximum Ready-set generation rate prevent oscillation.
These affect optimization only and are fixed in the runtime policy snapshot/replay.

A key that repeatedly captures and evicts without enough successful replays is suppressed. The model
continues eager; readiness is degraded only if a mandatory release bucket becomes unavailable.

## 16. Padding correctness and inactive lanes

### 16.1 Active-lane mapping

The accepted M8 plan's canonical item order maps active items to graph lanes `0..A-1`. Lanes
`A..B-1` are inactive. M12 does not reorder active requests by length, tenant, prefix, sampling
parameters, or cache state to improve packing.

Every kernel receives or derives the same active mask. Actual lengths/positions/table bounds remain
per active lane. Batch padding cannot turn a logical decode into extra token work for a request.

### 16.2 Inactive resources

Inactive lanes use dedicated graph-arena sink inputs and, where a backend requires an address, a
capture-owned sink KV/table region. They:

- never reference an active or cached request's writable page;
- never acquire a request table/cache owner or consume M6 quota;
- cannot increment computed/scheduled/output/token/usage counters;
- cannot update real penalty history, RNG state, cache LRU, telemetry request outcomes, or response;
- write only within canaried sink/result ranges reset before replay; and
- are omitted from completion items.

Backends that cannot prove masked inactive writes remain graph-unsafe. Pointing dummy lanes at lane 0
or a shared cached page is forbidden even if output is later ignored.

### 16.3 Padding policy and evidence

Configuration bounds padded lanes and padded-to-active ratio by bucket. Reports publish active and
padded sequences, estimated and measured padded FLOPs, per-bucket utilization, latency, energy/power
where available, and goodput. A graph route is not chosen when padding makes its measured cost exceed
the eager route under the frozen selector policy.

Correctness compares every active output/intermediate and verifies all sink canaries. Tests randomize
which active count fits each bucket and use adversarial table/position values next to inactive lanes.

## 17. Autotune cache and backend freeze

### 17.1 Tuning scope

Autotuning selects among already-qualified backends/algorithms for an exact operation shape. It does
not invent semantic variants, alter M4 numeric policy, change model/KV layout, compile code, or run on
live request data. Initial tuning occurs in the offline tool or model startup/warm-up before Ready.

Candidate lists are deterministic and bounded by the frozen registry. Each candidate declares
workspace, alignment, graph compatibility, supported shapes/dtypes, and semantic version. An
unqualified candidate is not timed.

### 17.2 Complete tune key

The canonical key includes:

- autotune schema and benchmark-method version;
- GPU architecture and every device attribute used by the backend;
- driver, CUDA runtime/toolkit, cuBLASLt and optional dependency versions/build fingerprints;
- InferX build/source and kernel-registry fingerprints;
- model-instance/operator/numeric/layout/page fingerprints;
- operation, phase, dtype/quantization placeholder, exact dimensions/strides/alignment;
- batch/token/context/table bucket and sampling/logprob feature bucket where applicable;
- workspace limit, graph/eager mode, deterministic/accuracy requirements; and
- relevant power/clock policy class when performance portability evidence requires it.

Device ordinal, filesystem path, wall clock, hostname, request/tenant/token data, and raw pointers are
not semantic key fields. A hardware UUID may scope a local measurement record but cannot substitute
for the capability fields.

### 17.3 Candidate qualification and selection

For each key, tuning:

1. validates candidate capability/workspace and prepares independent fixture inputs;
2. runs correctness against the accepted eager/reference backend before timing;
3. warms all candidates, randomizes trial order deterministically, and uses timing-event pools;
4. records p50/p95/dispersion across sufficient repetitions, not the single fastest observation;
5. rejects unstable, erroring, numerically failing, or >3% target-shape-regressing candidates;
6. selects by the ADR's robust statistic with canonical backend ID tie-break; and
7. records all candidates, raw summaries, environment/key digest, and selected reason.

The winning decision is installed only before registry/model readiness. Changing it invalidates
dependent graph keys and requires drain/recapture; a live request never changes backend mid-ticket.

### 17.4 Persistent cache format and corruption

The optional local cache is a versioned length-delimited checksummed data file with canonical
endianness, entry/count/byte limits, duplicate-key rejection, and atomic publication. It stores keys,
qualified backend IDs, measurements, thresholds, and evidence digests—never executable binaries,
device pointers, library handles, prompts, weights, or credentials.

Loading revalidates schema, checksum, exact key, current registry membership, backend capability, and
workspace. Unknown/stale entries are misses. Corruption quarantines/ignores the file and uses a
deterministic safe default or retunes according to startup policy; it does not make the model serve
with an unvalidated algorithm. Cache directories follow M10 filesystem ownership/permission and size/
retention rules.

## 18. Profile-guided backends and fusions

### 18.1 Bottleneck evidence

Optimization begins with a paired timeline and profile of the M11 baseline. Measure coordinator/
planner/output CPU, launch gaps, H2D/D2H, every operator/backend, sampling, graph replay, workspace,
memory traffic, occupancy, and idle intervals by prefill/decode/batch bucket.

Nsight Systems, Nsight Compute, CUDA event microbenchmarks, and bounded profile-build markers are
evidence tools. Their versions/commands and profiler overhead are recorded. Production binaries keep
profiling markers/tools disabled unless the reviewed low-overhead marker option is selected.

### 18.2 Candidate policy

A custom fusion/backend is proposed only for a measured top bottleneck and receives:

- a semantic operation composition and alias/lifetime contract;
- supported shape/dtype/device/workspace/graph matrix;
- independent reference and intermediate fixtures;
- special-value, boundary, odd-shape, alignment, and failure tests;
- eager and graph capture qualification;
- microbenchmark plus end-to-end ablation; and
- registry priority/fallback and removal criteria.

Likely candidates may include metadata transforms, sampling passes, logits-to-sampling handoff, or
adjacent elementwise operations, but M12 does not preapprove any kernel by name. Fusing across a KV
commit boundary, sampling version boundary, or diagnostic stable intermediate requires a new ADR.

### 18.3 Selection gates

The original qualified backend remains available. A candidate must meet existing numeric/output
correctness, improve its target suite by at least the roadmap's general 5% end-to-end significance or
enable the required graph/GPU-sampling capability, and avoid >3% median regression on protected
shapes. The final engine must meet the aggregate 15% goodput gate; favorable kernel-only speedup is
insufficient.

## 19. Memory planning and capacity accounting

### 19.1 Disjoint memory categories

M12 extends M2/M5/M6/M10 accounting with exact disjoint categories:

- ordinary eager model activation/workspace and metadata rings;
- GPU-sampling parameters, sparse metadata, candidate/reduction scratch, and compact results;
- CPU-sampling full-logits pinned result slots;
- async output job/result/text/logprob/reorder pools and per-worker scratch;
- overlap snapshot/draft/static-metadata pools;
- graph super-arena live/free/alignment loss by entry/instance;
- graph capture/validation scratch;
- graph executable conservative opaque-runtime charge;
- autotune fixture/workspace/timing/cache host storage; and
- retired/quarantined/deferred resources not yet safely reusable.

Bytes are current/peak/reserved by host, pinned host, and device kind. No category is counted as M6
physical KV, M11 evictable cache, general eager workspace, or operating-system free memory.

### 19.2 Startup formulas

For configured graph entries `E`, instances per entry `I_e`, arena layout bytes `A_e`, pinned stable
bytes `H_e`, conservative opaque charge `O_e`, capture scratch `C`, and safety margin `S`:

```text
graph_device_reserve = Sum_e(I_e * A_e + O_e) + C + S
graph_pinned_reserve = Sum_e(I_e * H_e) + capture_host_scratch
```

GPU-sampling scratch is the maximum qualified bucket's checked sum of transformed values, survivor/
selection metadata, deterministic reduction workspace, sparse inputs, and compact outputs multiplied
by the number of concurrently owned route slots. CPU fallback includes a full FP32 vocabulary row for
every permitted concurrent CPU-sampling item. Output capacity covers every accepted but uncommitted
sampling result plus worker/reorder slots.

Every multiplication/addition/alignment is checked and the memory plan lists logical versus rounded
bytes. The combined model weights/constants, M6 KV pool and low-water reserve, eager arenas, M12
reserves, M10 telemetry/diagnostics, allocator headroom, and driver/library safety margin must fit
before model loading. Startup fails or reduces only explicitly auto-sized optional graph buckets under
a deterministic recorded selector; it never silently shrinks request/context/KV guarantees.

### 19.3 Serving allocation rule

Steady serving performs no heap, pinned, device, graph-executable, or backend-workspace allocation.
All accepted work uses fixed pools/suballocations. Optional lazy capture uses only pre-reserved graph
and capture capacity and cannot run concurrently with a resource it might overwrite.

Pool exhaustion is handled before plan acceptance as temporary route unavailability/backpressure.
Unexpected CUDA OOM after acceptance is not recovered by evicting prefix/graph entries and retrying an
uncertain ticket; it follows device poison. Graph eviction is an optimization-management operation,
not an emergency allocator inside a launch path.

### 19.4 Capacity reconciliation

Owner snapshots prove:

- live + free + retired slots equal fixed capacity for every metadata/result/output/draft/graph pool;
- each accepted ticket owns exactly one physical route and all its leases;
- each OutputPending request owns exactly one job or reserved pending/result transition;
- graph entry charged bytes equal live arenas plus conservative executable/capture charges;
- M6/M11 page guarantees are unchanged by graph/cache accounting; and
- quiescence returns all ordinary resources to baseline, with poison-retained resources explicit.

The invariant checker uses owner-published immutable snapshots. Telemetry/debug threads never inspect
live CUDA allocators, graph caches, output queues, or request state.

## 20. Scheduler, KV, prefix-cache, and lifecycle integration

### 20.1 Scheduling semantics

M8/M11 select the logical plan before graph bucket selection. Scheduler token/sequence/workspace/KV/
response limits use actual work, while physical route validation additionally charges padding,
graph/sampler metadata, and the conservative route-set envelope. Before acceptance, an envelope that
cannot fit rejects the proposal. After acceptance, an unavailable graph uses the guaranteed eager form;
neither case removes a selected request to fit a smaller graph bucket after M8 commit.

Reference waiting order, cache-aware policy if enabled, priority aging, deadlines, chunking,
preemption, and arrival tie-breaks are unchanged. Plan-overlap drafts call the same pure policy code
with an immutable clock snapshot and never update policy counters until ordinary commit.

### 20.2 KV and prefix-cache ownership

Graph/eager and CPU/GPU sampling routes name the same logical table snapshot and write ranges. For
every accepted ticket:

- exclusive writable pages and immutable shared prefix pages are pinned through final device fence;
- graph metadata contains namespace/table/reset/page generations and device-mirror epoch;
- active lanes validate read/write bounds against actual lengths, not padded bucket maxima;
- inactive lanes cannot name request pages;
- M11 reset/eviction may tombstone cache records but cannot release active table/execution ownership;
  and
- acknowledgement releases exactly the pins owned by the ticket regardless of route.

A cache hit/miss or reset may invalidate an overlap draft or advertised graph descriptor but cannot
invalidate an already accepted replay lease. Graph reuse does not reuse KV content; it only reuses
the launch topology around dynamic table metadata.

M11's one-token first-logits ceiling is unchanged: a prefix-cache hit never supplies hidden state or
logits, and M12 GPU sampling consumes only logits produced by an actually executed accepted step.

### 20.3 Completion and cancellation

Device completion, KV commit, output-job dispatch, and token/output commit are separate ordered
boundaries. Cancellation/deadline observed with device completion wins under M7: CUDA ownership
drains, writable KV follows its valid/uncertain result rule, and no output job/token commit occurs.

Cancellation after OutputPending marks the request terminal-pending, drains the job/result, and
commits no sampled token. A prepared N+1 draft referencing that request becomes stale. Cancellation
never directly frees graph arena, metadata, logits, output, table, or cache pins from a nonowner
thread.

### 20.4 Deadline and estimator accounting

M8 deadline admission keeps its semantic estimator. M12 adds observed route-specific execution,
sampling, output, padding, and launch-gap components to future immutable estimator snapshots only
after sufficient samples. The currently measured ticket never changes its own estimate.

Graph cold capture is excluded from request execution and cannot delay a queued deadline. Async output
time is part of TPOT/end-to-end and OutputPending age is visible to watchdogs. A faster-route preview
that becomes stale before acceptance is re-evaluated; a deadline is not accepted using work that the
final route cannot meet.

### 22.2 Trace and replay events

Bounded events cover capability publication, draft offered/result/revalidation, metadata slot
transition, route candidate/selection/fallback, sampling begin/result/status, output job transition,

selection, memory delta, and fault/containment.

Events carry strong generations, closed bucket/route/backend IDs, active/padded counts, byte/resource
deltas, ordinals, durations, policy/key schema, and stable reasons. Ordinary traces omit logits,
probabilities beyond aggregate error, token IDs, seeds, prompts, outputs, namespace values, and raw
addresses. Protected fixture replay follows M10 capsule rules.

### 22.3 Health and watchdog

- Ordinary graph miss, inactive padding, stale draft, CPU sampler selection, capture skip, cache
  eviction, or autotune miss is healthy.
- Repeated overlap/output saturation or graph churn may degrade only that optimization while the
  bounded eager/reference route continues.
- A mandatory graph/sampler capability loss makes model readiness false according to config.
- Output worker loss is request-progress critical when accepted jobs cannot be recovered/drained and
  follows M10 unready/exit containment.
- Sampling identity mismatch, graph writing an inactive/shared wrong page, stale stable address,
  owner/pin corruption, or uncertain CUDA work poisons the replica.

Device worker, output workers, planner, graph capture/cache manager, and autotune startup publish
progress ordinals, current operation class, owned job/ticket/entry counts, and expected deadlines.
Thresholds use measured bucket/capture/tune bounds and avoid treating a long declared startup capture
as a serving hang.

### 22.4 Profiler isolation

Production request handlers cannot start/stop external profiling, dump kernels, or enable full tensor
capture. Profile builds use reviewed local control and M10 authorization, bounded marker strings from
closed enums, explicit duration/storage limits, and a nonproduction behavior fingerprint.

Profiler/tool failure must not be interpreted as inference evidence. Performance runs state whether
profiling was enabled; gate numbers come from unprofiled paired trials, with separate profiled runs
used only for attribution.

## 23. Failure and containment matrix

| Failure | Required result |
|---|---|
| GPU sampling tuple unsupported | select CPU before acceptance; same request semantics |
| GPU sampling metadata/snapshot invalid | prelaunch rejection/rollback; no kernel |
| GPU semantic NaN/no survivor | M9 request failure; no sampled-token commit |
| GPU sampler launch/execution/D2H error | uncertain ticket; poison/drain, never CPU retry |
| compact result checksum/identity mismatch | no token commit; ownership-integrity containment |
| CPU full-logits/output job pool unavailable | do not accept that step; bounded scheduler defer |
| output job stale after cancel/deadline | drain/discard; no token/history/output commit |
| output worker failure with recoverable owned input | explicit failed result and request failure; release once |
| output worker/job ownership uncertain | component unready/controlled exit; never lose job silently |
| overlap draft late/stale | discard and run ordinary planner; no state change |
| overlap planner crash/circuit open | disable drafts, reference planning if pools reconcile |
| metadata/result slot generation mismatch | prelaunch reject or poison if already in flight |
| graph key/offer/arena stale before launch | guaranteed eager route with same sampler; no graph launch |
| graph entry/arena capacity unavailable | eager miss; no request failure |
| capture/instantiate/validation incompatibility | quarantine key, eager route; poison only if CUDA uncertain |
| graph replay/launch/kernel/copy/fence error | quarantine plus device poison/drain; never eager retry |
| inactive lane touches request/shared KV or canary | isolation/ownership invariant; poison and controlled exit |
| graph cache full with no evictable entry | skip capture/use eager; keep budget honest |
| graph executable destruction not safely nonblocking | defer to drain; memory remains charged |
| graph/opaque memory exceeds reserved charge | do not publish entry; disable capture or fail mandatory warm-up |
| autotune key miss/stale entry | deterministic default or startup retune per config |
| autotune corrupt/oversized/duplicate cache | quarantine/ignore file; never load unvalidated choice |
| autotune candidate correctness failure | reject candidate; retain qualified baseline |
| autotune CUDA uncertainty | fail model warm-up/poison context; do not serve |
| route/config update races an active ticket | ticket retains old generation; new offers wait for safe boundary |
| shutdown with capture/replay/output/draft work | ordered stop, drain/ack, retain uncertain resources |

No after-launch error is converted into a graph miss, CPU fallback, empty output, or successful
request. Temporary optimization pressure is not mislabeled model/internal failure.

## 24. Reset, drain, shutdown, and model lifecycle

### 24.1 Prefix reset and policy changes

M11 prefix reset invalidates new cache lookup but does not invalidate table owners already pinned by
an accepted eager/graph ticket. It invalidates overlap drafts and replay offers whose descriptor has
not been accepted. Ready graph executables remain shape-compatible because they contain no prefix
content; only dynamic metadata generations change.

Disabling an M12 route stops publication/selection for new plans. Active tickets/jobs complete under
retained generations. Graph/backend/autotune/bucket geometry changes require model drain and rebuild,
not an in-place hot patch.

### 24.2 Ordered model drain

For model unload or process shutdown:

1. stop admission and new capture/autotune/draft creation;
2. stop accepting new physical routes while draining or cancelling queued logical work by M10 policy;
3. drain/ack accepted eager/graph GPU tickets and deferred fences;
4. drain output jobs/results/reorder slots and apply or discard them by cancellation order;
5. invalidate/free unowned overlap drafts and ordinary metadata/result slots;
6. remove graph Ready publication, drain replay/capture leases, and destroy executables safely;
7. release graph/capture/sampling/output/autotune arenas and verify accounting;
8. continue M11 prefix/KV, M10 telemetry, M9 network, and M2 CUDA teardown order; and
9. publish final immutable snapshot/evidence and require ordinary resources at baseline.

Shutdown never waits on a planner/output worker while holding mutable coordinator or device state.
Bounded channels close in producer-to-consumer order so every accepted ticket/job has one completion
or drain record. Deadline expiry abandons external delivery but does not free in-flight resources.

### 24.3 Poisoned device

On device poison, stop graph capture/replay/eager submission and GPU sampling, fail readiness, drain
host-only output jobs whose inputs are already safe if policy permits, and retain uncertain graph/KV/
workspace/metadata/event allocations until the named M2 shutdown synchronization/worker exit. A
poisoned process does not attempt graph eviction or autotune cleanup to reclaim device memory.

## 25. Structural replay and safe diagnostics

`inferx-m12-replay` composes production CPU route, overlap, output-job, bucket, graph-cache policy,
and memory-accounting without CUDA. Given M10 structural events it must
reproduce:

- capability generations and ordered route candidates/final prelaunch route;
- overlap snapshot/draft/revalidation/stale reasons;
- metadata/result/output/graph lease state and capacity;
- graph eligibility/bucket/padding/hit/miss/touch/eviction decisions;
- output pending/job ordering/cancel commit or discard;
- autotune key hit/miss/decision identity; and
- all resource and terminal invariants byte-identically.

CUDA numerical/capture replay uses committed protected fixture capsules with exact logits, metadata,
sampling inputs/results, graph keys, bucket shapes, and expected eager outputs. Production structural
traces do not contain those sensitive values.

Safe diagnostics report aggregate route counts, bucket coverage/utilization, graph entry states and
memory classes, sampling/result byte distributions, metadata/output/draft pool occupancy, stale/fallback
reasons, launch-gap buckets, autotune/backend fingerprints, health, and checksums. They never dump raw
logits, tokens, seeds, probabilities tied to requests, prompts/outputs, tenant/prefix identifiers,
device addresses, or executable graph internals.

The device/output/planner owners publish immutable bounded M10 snapshots. Admin, metrics, watchdog,
diagnostics, and profiler-control threads never traverse live graph caches, pools, queues, request
tables, or CUDA state.

## 27. Performance methodology and gates

### 27.1 Experimental controls

Use the exact section 6 baseline and M10 open-loop methodology. Pin hardware, power/clocks, driver,
CUDA/dependencies, CPU affinity/NUMA, model/cache/config, workload/arrival trace, request seeds, warmup,
measurement duration, telemetry setting, and trial success criteria. Randomize paired trial order and
run enough repetitions for confidence intervals.

Do not compare runs with different admitted/completed request sets without publishing both the SLO
goodput curve and failure/drop reasons. Exclude no cold captures or fallback from a claim unless the
release profile guarantees startup warm capture and the report labels steady-state separately.

### 27.2 GPU sampling and transfer

For greedy and representative sampled/logprob configurations across vocabulary and batch buckets,
measure:

- transform/filter/select/top-logprob kernel and end-to-end sampling latency p50/p95/p99;
- CPU sampler time, GPU sampler time, D2H copy/fence/host validation, and output-job time;
- full-logits versus compact payload/protocol bytes and achieved bandwidth;
- workspace/metadata/result/pinned memory and active-lane utilization;
- qualified/fallback rate and reasons; and
- token/alternative/logprob conformance.

On the target concurrency/workload, qualified GPU sampling must be no slower than CPU sampling and
must reduce logits/result D2H bytes by at least 99%. Averages cannot hide a slower important bucket;
the capability matrix disables buckets that miss their protected latency/goodput gate.

### 27.3 Overlap and output pipeline

Measure device completion-to-next-launch gap, coordinator turn/planner time, draft exact/patchable/
stale/late rate, metadata fill/upload, output-pending duration, job queue/worker utilization, response
event latency, CPU cores/context switches/cache misses, and ring occupancy for overlap/output off/on.

Overlap must reduce launch idle time or end-to-end goodput materially without increasing policy
starvation, request p99 beyond the general 5% bound, or CPU saturation. Triple buffering is retained
only if it improves the selected workload beyond noise relative to double buffering after its memory
cost.

### 27.4 Graph buckets and cache

For every selected bucket and actual active count, measure eager versus graph:

- launch count and CPU launch gap;
- graph replay, model, sampling, D2H, and complete step latency;
- active/padded work and useful/padded utilization;
- cache eligibility/hit/miss/fallback and churn;
- capture/instantiate/validation/warm-up time;
- exact arena/pinned and conservative opaque memory; and
- power/energy where the reference runner supports stable measurement.

After declared warmup, successful graph replays divided by graph-eligible accepted steps must be at
least 90% on the selected workload. The report also lists graph coverage of all decode/all steps,
memory per percentage point of coverage, and eager fallback latency. Graph arenas remain within the
configured/reserved budget with zero address/lease reuse races.

### 27.5 Autotune and fusion

Publish candidate correctness, workspace, trial distributions, selected decisions, cache cold/load
time, key hit/miss rate, and micro/end-to-end ablations. NCU/Nsight profiles before and after identify
the remaining top bottlenecks by phase/bucket. A tuning/fusion claim must survive fresh-process and
cache-loaded runs and cannot depend on an unrecorded clock/tool state.

### 27.6 End-to-end completion gate

Run embedded and HTTP open-loop SLO curves for no-reuse and M11 selected prefix-reuse workloads,
short/medium/long prompts and outputs, deterministic greedy and representative sampling/logprob modes,
streaming/nonstreaming, and dynamic concurrency/batch distributions.

Measure TTFT, TPOT/inter-token, end-to-end p50/p95/p99/max, prompt/output tokens/s, requests/s, SLO
goodput, GPU utilization, launch gaps, CPU utilization, memory high water, graph/sampler/output route
rates, cache behavior, errors/drops, and exact output equality.

The final selected M12 engine must improve SLO goodput by at least 15% over the exact M11 baseline,
meet the graph and sampling gates, preserve M10 telemetry overhead and M11 reuse gates, and show no
correctness/reliability/resource regression. Protected workload cells may not regress >5% goodput or
p99 without a reviewed ADR and capability/default restriction.

## 33. Definition of done

### Sampling and output

- [ ] Every advertised GPU sampling tuple preserves M9 transform/RNG/status semantics, selected token
      and ordered alternative IDs exactly, and logprobs within unchanged thresholds.
- [ ] Qualified GPU steps copy only bounded compact results, reduce logits/result D2H bytes >=99%,
      and are no slower than CPU sampling at target concurrency.
- [ ] In automatic mode, unsupported/disabled GPU sampling selects CPU before acceptance; required-
      GPU mode rejects capability explicitly, and after-launch errors never retry or consume a
      different RNG result.
- [ ] Async CPU sampling/render/decode/stop jobs are bounded and immutable; only the coordinator
      commits token/history/output/finish state once after epoch validation.
- [ ] Cancellation/deadline/output failure at every OutputPending boundary emits no uncommitted token
      and releases or explicitly retains every host/device/result lease.

### Overlap, graphs, and memory

- [ ] Plan N+1 preparation performs no owner mutation/GPU work, and exact/patchable/stale drafts all
      pass the ordinary M8/M11 validator/transaction before submission.
- [ ] Metadata/result/draft/graph slot generations prevent overwrite/reuse through final fence,
      output transfer, acknowledgement, and deferred poison ownership.
- [ ] Selected graph buckets are trace/evidence derived, deterministic, and use inactive sinks that
      cannot touch request/shared KV, RNG, counters, or output.
- [ ] Graph capture-safe backends, stable arenas, replay descriptors, table/cache/page pins, final
      fence, cache LRU/eviction/quarantine, and no-post-launch-fallback invariants pass all tests.
- [ ] Successful graph replay rate is >=90% of graph-eligible steps after warmup on the selected
      workload, all coverage denominators are published, and eager fallback is always correct.
- [ ] Graph/sampling/output/overlap/autotune memory is startup-reserved, remains within configured
      host/pinned/device/opaque budgets, and never weakens M6/M11 guarantees.

### Tuning, correctness, operations, and release

- [ ] Autotune keys include exact device/software/model/operator/shape identity; cache corruption/
      staleness cannot install an unqualified backend; registry decisions freeze before readiness.
- [ ] Every profile-guided backend/fusion has independent correctness, eager/graph, failure, micro,
      end-to-end, and protected-shape regression evidence.
- [ ] M11 reference and every M12 axis/combination produce identical tokens/text/usage/finish/terminal
      semantics, valid KV/logits, and accepted logprob equality across cache/phase/API matrices.
- [ ] M10 fixed telemetry/privacy/health/watchdog/fault/diagnostic/container rules remain satisfied;
      optimization off/on and profiler-off production behavior are explicit.
- [ ] Final selected configuration improves SLO goodput >=15% over exact M11, meets graph/sampling/
      reuse/telemetry gates, and has no unexplained p99, fairness, failure, or resource regression.
- [ ] Unit/integration/correctness/stress/failure/fuzz/ASan/UBSan/TSan/Compute Sanitizer suites,
      paired benchmarks, NCU/Nsight attribution, 24-hour soak, ADRs 0081-0089, documentation,
      capability matrix, and immutable single-GPU v0.1 bundle all pass without hidden skips.

## 34. Handoff to M13 and M14

M12 hands M13/M14 a correctness- and performance-gated single-GPU v0.1 baseline with independent
eager/graph routes, CPU/GPU sampling, bounded async output and plan overlap, stable arena and metadata
leases, exact autotune/backend identity, fixed telemetry/fault/replay schemas, and complete evidence.

M13 may add quantized descriptors/backends and a second dense model family. Every new dtype/format/
architecture invalidates or extends sampling/operator/autotune/graph keys explicitly, receives its own
capture/workspace/numeric qualification, and cannot reuse an M12 graph or tune decision by model name.

M14 may move the device worker into one process per GPU and add tensor-parallel collectives/sampling.
Graph executables, stable arenas, raw CUDA/backend handles, and local autotune files remain worker-
local; coordinator/worker protocols carry only versioned logical routes, plans, generations, compact
results, health, and evidence identities. Single-process single-GPU eager/CPU fallback remains
supported through the same logical contract.
