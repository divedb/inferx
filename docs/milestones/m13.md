# M13 implementation specification: quantization and a second dense model family

- Status: proposed implementation contract
- Roadmap milestone: M13 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M12](m12.md), including M1-M11 transitively
- Parallel sibling: M14 worker isolation and tensor parallelism depends on M12, not M13
- Later consumers: M14 may qualify quantized shard layouts independently; M16 owns quantized MoE

This document turns M13 into an executable engineering plan. It defines strict quantization metadata,
canonical scale/zero-point/group/packing contracts, portable quantized tensor bundles, an FP8 W8A8
linear profile on qualified hardware, a measured choice of exactly one AWQ-or-GPTQ INT4 family, a
canonical W4A16 runtime layout, secure inspection/conversion tools, transactional quantized model
loading and backend preparation, independent dequantized references, a dense Qwen2 semantic/weight
adapter built from shared modules, graph/autotune/cache identity extensions, fixed quality and
perplexity evidence, failure containment, tests, performance gates, and release handoff.

M13 adds new model bytes and numeric behavior; it does not reinterpret an old model identity. An
unquantized Llama/Qwen instance, an FP8 instance, and an INT4 instance always have different package,
model-instance, graph, autotune, and prefix-cache identities. Quantization is never inferred from a
filename, model name, tensor dtype alone, or the presence of a scale-like tensor.

## 1. Outcome

At the end of M13, InferX can:

1. parse and validate a versioned quantization declaration before weight planning, with exact format,
   bit width, storage dtype, scale convention/granularity, zero-point convention, group axis/size,
   packing order, tail padding, accumulator/output dtype, source algorithm, and provenance;
2. represent each quantized parameter as one complete logical bundle whose packed values, scales,
   zero points, optional auxiliary metadata, shapes, byte ranges, and coverage reconcile exactly;
3. reject missing, duplicate, unexpected, mixed, corrupted, or incompatible quantization components
   before device allocation or readiness;
4. dequantize canonical FP8 and selected INT4 bundles through an independent bounded FP32 reference
   with bit-exact unpack/scale semantics and compare every optimized backend against it;
5. load one closed FP8 linear profile on hardware/backend tuples that pass numeric, graph, memory,
   failure, and performance qualification, while leaving KV/residual/norm/output semantics explicit;
6. evaluate AWQ versus GPTQ using legal local artifacts and native C++/CUDA backend evidence, select
   exactly one family in an ADR, normalize it to one canonical W4A16 layout, and reject the other;
7. transform canonical portable weights into a backend-specific immutable packed layout during
   transactional model load without retaining an unexplained duplicate full-weight copy;
8. instantiate dense `Qwen2ForCausalLM` through the shared dense decoder, RMSNorm, RoPE, GQA attention,
   SwiGLU, paged KV, scheduler, sampler, output, HTTP, telemetry, and M12 execution routes;
9. isolate Qwen-specific behavior to strict config normalization, parameter mapping, Q/K/V projection
   biases, declared position policy, tokenizer/template provenance, and independent fixtures;
10. extend M12 backend/autotune/graph and M11 prefix namespaces with complete architecture and
    quantization identities so no stale unquantized or cross-format resource can be reused;
11. prove load/generate/unload for Llama and Qwen in FP16/BF16 plus every advertised quantized cross-
    product, with unsupported model/format/hardware tuples rejected at validation or warm-up; and
12. meet predeclared kernel/logit/top-k/quality/perplexity thresholds, expected weight-memory reduction
    within the roadmap's 5% overhead rule, and at least 10% improvement in a declared capacity or
    end-to-end performance metric for every enabled format.

```text
rooted local model package
  config + quantization declaration + safetensors/index + tokenizer/template + manifest
                                  |
                                  v

          |                                  |
          v                                  v
shared DenseDecoderSpec             QuantizedTensorBundle catalog
  + Llama or Qwen2 traits          packed values + scales + zeros
          |                                  |

                                  |

                                  |

```

M13 is complete only if the original M12 unquantized route remains supported, every enabled format is
identified and quality-gated independently, Qwen adds no duplicate scheduler/KV/sampling/server path,
and no production request performs format discovery, weight dequantization fallback, packing,
allocation, backend search, or quality calibration.

This file is a documentation specification only. This change does not add or authorize M13 source,

## 2. Scope boundaries

### 2.1 In scope

- A generic versioned quantization descriptor with closed, format-specific validation profiles.
- Exact packed-weight, scale, zero-point, grouping, tail, byte-order, alignment, and provenance rules.
- FP8 E4M3 linear weights plus dynamically quantized FP8 activations under one qualified scale profile;
  FP16/BF16 model-visible outputs and FP32 accumulation/reference policy.
- Exactly one selected INT4 family, AWQ or GPTQ, normalized to a portable grouped W4A16 layout.
- Quantized dense attention/MLP linear projections; embedding and LM-head quantization only if their
  separately named operation/backend tuples pass the same gates.
- CPU dequantization/reference utilities for bounded tests, inspection, conversion validation, and
  quality tooling; not production CPU inference.
- Local data-only quantization inspector and canonical conversion/repacking tool with secure parsing,
  deterministic output, provenance, manifest, and round-trip validation.
- Transactional model load, portable-to-backend packing, prepared operator selection, stable memory,
  eager/graph qualification, autotune invalidation, unload, and accounting.
- Dense `model_type=qwen2` / `Qwen2ForCausalLM` with full causal attention, default unscaled RoPE,
  GQA/MHA, Q/K/V biases, RMSNorm, SwiGLU, and existing supported tokenizer/chat-template subset.
- Llama and Qwen FP16/BF16 baselines and separately qualified FP8/INT4 model-format tuples.
- Independent kernel/intermediate/logit/top-k/greedy/quality/perplexity evaluation and performance
  evidence with thresholds frozen before backend optimization.

### 2.2 Explicitly out of scope

- KV-cache quantization, quantized K/V pages, compressed prefix-cache blocks, mixed KV dtypes within a
  pool, or cross-quantization prefix sharing. KV quantization requires a separate later experiment/ADR.
- INT8, FP4, NF4, GGUF, bitsandbytes runtime formats, mixed-bit layers, sparse weights, SmoothQuant,
  quantization-aware training, LoRA/adapters, or arbitrary user-defined quantization plugins.
- Supporting both AWQ and GPTQ in the initial release. The unselected family is a clear
  `Unimplemented` capability even if metadata appears superficially compatible.
- Guessing missing scales/zeros/group size/packing, accepting opaque pickled quantizer state, or
  silently treating packed bytes as an ordinary integer tensor.
- Runtime calibration, live-request tuning/repacking/dequantization, on-demand kernel compilation,
  network artifact/model downloads, or automatic quantization during server startup.
- Requiring a production dequantize-to-BF16 fallback when a quantized kernel is unavailable. A
  quantized package without a prepared backend fails before serving.
- Quantizing norms, biases, RoPE constants, residual streams, sampler inputs, response values, or
  M6/M11 KV unless a later format-specific ADR explicitly adds them.
- Qwen1, Qwen2-MoE, Qwen2-VL/audio/multimodal, Qwen3, hybrid/sliding-window layers, YaRN/dual-chunk or
  other scaled RoPE, speculative heads, tool-use protocol semantics, or remote code execution.
- Model-name heuristics, approximate Qwen tensor mapping, tolerating unexpected training tensors, or
  duplicating Llama's forward loop under a Qwen namespace.
- Distributed quantized sharding/collectives. M13 defines slice/packing metadata and tests boundaries;
  M14 must qualify actual rank-local packing and kernels separately.
- Claiming quantized output must be token-identical to BF16 for arbitrary real prompts. Quantized
  accuracy uses predeclared format-specific numeric/quality criteria; route equality within the same
  quantized artifact remains exact where M9/M12 require it.

## 6. One-format-at-a-time selection and capability policy

### 6.1 Delivery order

M13 progresses through closed capability increments:

1. format-neutral descriptor/bundle/reference/inspection foundations with quantized serving off;
2. one exact FP8 profile for eligible dense linear roles and hardware;
3. evidence-backed selection and implementation of exactly one INT4 family;
4. unquantized dense Qwen2 on the shared runtime; and
5. only the Llama/Qwen/format cross-products that independently pass all gates.

The INT4 implementation cannot begin by adding both parsers and waiting to see which works. ADR 0090
must select the family from evidence before public artifact compatibility or source-format enums are
frozen.

### 6.2 AWQ versus GPTQ selection experiment

Evaluate both candidates using the same declared Llama/Qwen model sizes and reference hardware:

- legally usable local prequantized artifact availability and reproducible provenance;
- exact metadata/packing variants encountered and ability to normalize without guessing;
- native C++/CUDA backend availability, license, dependency/toolchain/SM support, and maintenance;
- prefill/decode/batch/odd-dimension coverage and graph-capture compatibility;
- load/repack time, host/device memory, workspace, and stable-address requirements;
- dequantized kernel correctness, logit/top-k/greedy and fixed quality/perplexity results;
- prompt/output throughput, TTFT/TPOT/SLO goodput, and break-even concurrency;
- future M14 shard-alignment feasibility; and
- fuzz/failure behavior for malformed metadata and corrupt packed weights.

The scorecard, weights, raw evidence, disqualifiers, selected format/profile ID, and rejected family
remain in ADR 0090. Popularity alone is not a decision. If neither family passes quality plus >=10%
capacity/performance benefit, INT4 remains experimental/off and M13 does not claim it complete.

### 6.3 Capability tuple

Support is advertised only for an exact tuple:

```text
architecture schema
+ quantization format/profile and source algorithm
+ source/canonical/backend packed-layout schemas
+ model dimensions and eligible parameter-role set
+ activation/KV/output dtype and numeric policy
+ device SM/attributes + driver/CUDA/dependency/backend versions
+ phase/batch/token/context/page/workspace/graph class
+ M12 graph/autotune profile generation
```

Startup validates all model parameters/operations against this table. A partial model whose early
layers have kernels but later layers do not is rejected before allocation/readiness. Runtime never
falls back a single unsupported layer to host or an unplanned dequantized dense weight.

## 7. Quantization type model and descriptor

### 7.1 Separation from tensor dtype

`ArtifactDType` describes wire elements/carriers. Runtime `DType` describes ordinary logical tensor
elements. `QuantizationDescriptor` describes how one or more stored tensors reconstruct a logical
parameter and how an optimized operation consumes it.

The descriptor contains:

- descriptor schema and exact `QuantizationFormatId`/profile version;
- source algorithm/family and conversion-tool provenance ID;
- logical parameter dtype/shape/layout and semantic role;
- value bit width, signedness/encoding, storage carrier dtype, byte/bit order, pack axis, elements per
  storage unit, row/block stride, and alignment;
- scale presence, dtype, shape/layout, granularity, axis/block geometry, and multiply/divide
  convention;
- zero-point presence, logical dtype, stored packing/layout, signed/unsigned/bias convention, and
  whether absence means symmetric rather than zero;
- group axis/size/count/tail rule and logical-to-group mapping;
- optional permutation/group-index metadata with a closed disposition; initial profiles require
  canonical logical order and reject arbitrary runtime permutations;
- weight, activation, accumulator, intermediate, model-visible output, bias, and KV dtypes;
- finite/range/rounding/saturation/subnormal/special-value policy;
- canonical source layout and selected backend-derived layout IDs;
- eligible architecture/parameter roles and explicit unquantized exclusions; and
- content checksum/fingerprint inputs and all configured limits.

All enums are closed and versioned. Every optional field has format-specific presence rules; “absent”
never means “choose a common default.” Floating scale values are tensor contents and enter package
digests, not copied into unbounded config diagnostics.

### 7.2 Canonical serialization and equality

Serialization is length-delimited, canonical little-endian, fixed-enum-width, shape-count bounded,
and independent of JSON member order/path. Equality compares every semantic field. Hash acceleration
is collision-guarded by complete equality.

Descriptor schema, exact canonical bytes, component tensor digests, source algorithm, conversion
provenance, and logical parameter ID enter the model fingerprint. Backend-derived layout enters the
model-instance/operator/graph/autotune identities but does not rewrite the portable package content
identity.

### 7.3 Validation order

For every quantized parameter:

1. validate schema/format/profile and descriptor limits;
2. validate logical role/shape/dtype against the architecture parameter catalog;
3. derive group/scale/zero/packed shapes and bytes with checked arithmetic;
4. resolve every exact component tensor by name and prove dtype/shape/byte-range/alignment;
5. validate scale finite/positive rules, zero-point range, tail padding, canonical unused bits, and
   optional metadata disposition;
6. prove components are used once, do not overlap, and cover the logical parameter exactly;
7. validate format-specific eligible role and model-wide consistency policy;
8. validate portable-to-backend transform and hardware/backend capability; and
9. add exact bytes/descriptors/provenance to fingerprints and memory plan.

Malformed wire bytes are `DataLoss`; valid but unsupported profile/shape/hardware is `Unimplemented`;
inconsistent model metadata is `InvalidArgument`/model validation failure. Error precedence is fixed
and independent of shard/file order.

## 8. Quantized tensor bundle, grouping, and packing

### 8.1 Bundle ownership and coverage

One `QuantizedTensorBundle` represents one logical parameter and contains strong component handles:

- packed/FP8 value tensor;
- scale tensor;
- zero-point tensor only when required;
- optional closed auxiliary tensor admitted by the selected profile;
- immutable descriptor and source byte ranges/digests; and
- logical shape, reconstructed element count, packed payload bytes, metadata bytes, and padding bytes.

No component can belong to two parameters unless an exact M3 alias rule names the complete bundle.
Tied embedding/head aliases share all components and descriptor or are rejected; sharing only packed
values with different scales is not a tie.

Coverage proves every expected architecture parameter has exactly one ordinary tensor, quantized
bundle, or complete alias, and every external tensor has exactly one allowlisted disposition. Name
prefixes such as `scale`, `qweight`, or `zeros` are never globally ignored.

### 8.2 Matrix conventions

For a logical linear weight `W[O,I]` in existing canonical row-major `[out,in]` order:

- grouping, when present, is along input coordinate `i`;
- `G = CeilDiv(I, group_size)` with checked arithmetic;
- group index is `g(i) = Floor(i / group_size)` for canonical profiles;
- scales and zeros are logically `[O,G]` unless the profile specifies tensor/row granularity;
- pack order advances `i` within one output row before `o`;
- logical shape never includes alignment or tail padding; and
- backend-specific transpose/tile/swizzle is a derived transform, not portable artifact semantics.

For sub-byte values, the descriptor gives the exact bit offset and nibble order. `Int4GroupLinearV1`
packs the lower input index in the low nibble and the next index in the high nibble of an unsigned
byte. Odd `I` sets the unused high nibble to the canonical zero-dequantizing tail encoding and the
validator rejects noncanonical unused bits.

### 8.3 Tail groups, rows, and shard boundaries

The portable layout represents a final partial input group. Missing logical tail elements are padded
with the group's zero-dequantizing code and never contribute to a dot product. Scale/zero tensors have
the full checked `G`; no group reads past logical `I`.

A backend may require `I`, `O`, or `group_size` alignment. Such a tuple is rejected at warm-up unless
the prepared transform has an explicit canaried padded backend layout whose kernel masks logical
bounds. Padding cannot add a model parameter or alter bias/output shape.

`QuantizedSlicePlan` defines whether a future input/output shard boundary is:

- directly sliceable without splitting a packed unit/group;
- sliceable after a deterministic offline/backend repack with adjusted scale/zero rows; or
- unsupported because it would require ambiguous group/permutation semantics.

M13 remains replicated single-GPU, but unit/property tests cover every byte/nibble/group boundary and
odd dimension so M14 cannot infer a slicing rule later.

### 8.4 Dequantization formula and reference

The canonical grouped affine formula is:

```text
W_hat[o,i] = (Q[o,i] - Z[o,g(i)]) * S[o,g(i)]
```

For a symmetric profile, the descriptor defines `Q`'s signed decode and `Z` is structurally absent;
absence is not numeric zero unless that profile says so. Scale convention always reconstructs the
logical value by multiplication; importers using inverse scales convert explicitly.

The bounded CPU reference decodes carriers/bits with integer operations, converts scale/zero to FP32,
and reconstructs FP32 `W_hat`. For weight-only INT4 it converts the ordinary FP16/BF16 input to FP32;
for W8A8 FP8 it independently applies the profile's exact per-row activation quantize/dequantize rule
to produce `X_hat`. It then evaluates `X_hat * W_hat^T` with the declared FP32 accumulation and bias/
output conversion. It validates finite/range/tail invariants and can emit per-tensor error summaries/
digests, not full values by default. It is independent of CUDA/vendor pack and is never a production
request fallback.

## 9. FP8 linear profile

### 9.1 `Fp8LinearV1` envelope

The initial FP8 profile is deliberately closed:

- E4M3 finite FP8 stored weights for eligible dense linear matrices;
- dynamically quantized E4M3 activations per logical input row/token;
- one FP32 reconstruction scale per output row for weights and one per input row for activations;
- reconstruction is `stored_fp8_value * scale`;
- FP32 multiplication/accumulation semantics as qualified by the backend, with FP16 or BF16
  model-visible outputs matching the unquantized model's activation family;
- FP16/BF16 ordinary bias added under the existing linear semantic order;
- FP32 final logits as required by M9/M12; and
- unchanged FP16/BF16 KV, residual, norm, attention softmax, embedding, and sampler storage unless a
  separately named role is qualified.

This row/outer-vector scale profile is a semantic contract, not “whatever FP8 mode the library picks.”
If the accepted toolchain/device backend cannot express and qualify it, the tuple is unsupported; the
implementation does not silently switch to tensorwide/block scaling under the same profile ID.

### 9.2 Weight conversion

For each output row, deterministic offline conversion:

1. rejects nonfinite source weights;
2. computes the configured FP32 maximum-absolute statistic in canonical input order;
3. uses scale `1` for an all-zero row, otherwise `max_abs / max_finite(E4M3)`;
4. divides by scale, rounds with the profile's exact nearest/tie rule, and saturates to the declared
   finite E4M3 range;
5. stores the canonical FP8 byte and FP32 reconstruction scale;
6. reconstructs every value for error/checksum statistics; and
7. records converter/tool/source/profile/calibration-free provenance.

The exact E4M3 bit encoding, signed zero, subnormal, rounding, saturation, and NaN/Inf rejection have
known-answer vectors independent of compiler/vendor conversion intrinsics. Importing an existing FP8
checkpoint validates that its declared scale convention/bytes reproduce the same canonical formula.

### 9.3 Dynamic activation quantization

For every logical input row, a prepared GPU kernel computes the same finite max-absolute/zero-row rule,
writes a stable FP32 row scale, converts to canonical E4M3, and reports nonfinite input before the
matmul consumes it. Reduction order and conversion identity are backend/profile fields and tested
across eager/graph buckets.

Activation FP8 scratch/scales are M12 workspace/graph-arena slices owned through the final ticket
fence. There is no persistent activation calibration state, cross-request amax history, delayed scale,
or mutable global scale. Padding/inactive graph lanes write only canaried sink slices.

### 9.4 Backend and fallback rules

The qualified backend must express exact A-row/B-output-row scales, operand layouts, accumulator,
bias/output conversion, workspace, alignment, and graph-capture behavior under the pinned device/
software tuple. M4/M12 preparation validates algorithms with real buffers and independent reference
outputs before readiness.

An unavailable FP8 algorithm, dimension, scale mode, or graph route fails that model-format tuple at
warm-up or selects an already prepared eager FP8 route for graph-only misses. It never converts the
model to BF16 after allocation or runs a dequantize-plus-BF16 production layer as a hidden fallback.

## 10. Selected INT4 W4A16 profile

### 10.1 Source-family decision

`Int4GroupLinearV1` is enabled only after ADR 0090 names AWQ or GPTQ. The selected source family and
algorithm/provenance are part of artifact identity. The other family's config/tensors produce a clear
unsupported-format error before weight planning even if a conversion might theoretically exist.

The runtime consumes one canonical layout, not every ecosystem serialization. `inferx-quant-convert`
adapts allowlisted variants of the selected family after complete validation and records exact source
metadata/bytes/tool version. Nonidentity GPTQ activation-order/group-index permutations or AWQ packing
variants are accepted only if the selected ADR defines a deterministic semantics-preserving
canonicalization; otherwise they are rejected rather than guessed.

### 10.2 `Int4GroupLinearV1` canonical layout

The initial canonical runtime profile is:

- 4-bit weight-only affine quantization and FP16/BF16 activations/outputs (`W4A16`);
- unsigned `Q` values in `[0,15]` with an explicit unsigned zero point in `[0,15]`;
- groups contiguous along input axis, with the release-selected group size (initial candidate 128)
  encoded in every descriptor and no implicit default;
- FP16 positive finite reconstruction scales logically `[O,G]`;
- packed zero points logically `[O,G]` using the descriptor's low-first nibble order;
- packed values row-major, lower input index in the low nibble;
- final partial group/byte padded with its exact zero point so padding reconstructs zero;
- an unused high nibble in a packed zero-point row is the canonical unsigned zero bit pattern and is
  never read as a logical group;
- FP32 accumulation with FP16/BF16 model-visible output and ordinary bias semantics; and
- no activation reordering, arbitrary `g_idx`, mixed group sizes, or per-layer bit widths.

For logical `W[O,I]` and `G=CeilDiv(I,group_size)`, portable payload planning is:

```text
qweight_bytes = O * CeilDiv(I, 2)
scale_bytes   = O * G * sizeof(FP16)
zero_bytes    = O * CeilDiv(G, 2)
```

Each row may receive explicit portable alignment padding only when the descriptor records its stride;
canonical packages otherwise use tight rows. Descriptor, index, manifest, and file alignment bytes
are reported separately from numeric payload.

### 10.3 Reference and import validation

For every imported bundle, validation reconstructs `W_hat` with section 8.4, proves scale/zero ranges,
canonical unused nibbles, logical group coverage, and absence/identity of forbidden permutations. The
converter compares reconstructed values before and after canonical repacking exactly in FP32 and
records maximum/mean source-baseline quantization error.

The selected AWQ/GPTQ algorithm determines how `Q/S/Z` were calibrated, but no opaque calibration
state participates in runtime math. Required calibration provenance/dataset digest/tool parameters are
retained in the manifest. Untrusted Python/pickle quantizer objects are not server inputs.

### 10.4 Eligible parameters and exclusions

Initial quantized roles are attention Q/K/V/output and MLP gate/up/down linear weights. Norms and Qwen
Q/K/V biases remain ordinary FP16/BF16. Embedding and LM head remain ordinary unless a separately
qualified quantized embedding/logits operation meets quality, memory, and performance gates; an alias
cannot be half quantized.

The capability report lists eligible, quantized, excluded, aliased, and padding/metadata bytes by
semantic role. Memory claims use the actual eligible subset rather than dividing total model bytes by
four.

## 11. Quantized artifact, weight plan, and identity

### 11.1 Package declaration

A quantized package has one required top-level manifest declaration containing:

- quantization manifest schema;
- exact model-wide format/profile and selected source-family ID;
- default component naming/layout schema plus explicit per-parameter overrides, if allowed;
- activation, accumulator, output, bias, and KV dtype policy;
- eligible and intentionally excluded parameter-role sets;
- canonical converter/algorithm/calibration provenance;
- expected source and portable packed-layout schemas;
- complete component file/size/digest manifest; and
- compatibility requirements and declared quality-evidence identity.

`config.json` quantization metadata is parsed through a selected-family adapter and must agree exactly
with the manifest. It cannot override the manifest or fill missing security/shape information. A
package with quantized-looking tensors but no supported declaration is rejected. An unquantized
package must not contain quantization components/declaration.

The manifest is bounded JSON or the project's versioned data-only manifest format under M3's rooted
session. Duplicate/unknown fields, conflicting aliases, path traversal, special files, unbounded
strings/lists, nonfinite numbers, and unsupported versions fail before mapping weight payloads.

### 11.2 Canonical component names and mapping

For canonical parameter name `P`, the portable package uses exact suffixes such as:

```text
P.qweight
P.scales
P.qzeros       # present only for the affine INT4 profile
```

FP8 value tensors may retain `P.weight` only when the manifest and wire dtype make the bundle
unambiguous; otherwise canonical conversion uses the explicit component schema. Source AWQ/GPTQ
names are accepted only inside that selected source adapter and normalize into strong component roles.

The weight planner builds one `QuantizedWeightPlanItem` per logical parameter containing exact source
ranges, component IDs, descriptor, portable-to-backend transform, logical shard, final allocation,
and alias. Sorted coverage diagnostics list missing/duplicate/unexpected components by logical
parameter and role, never by loose suffix matching.

### 11.3 Model-wide consistency

The initial profiles require:

- one architecture, source activation family, quantization format/profile, group policy, and portable
  layout schema across the package;
- every eligible linear role quantized unless the manifest's closed exclusion rule permits it;
- every excluded/norm/bias/embedding/head tensor in the declared ordinary FP16/BF16 family;
- no FP32/FP16/BF16 mix among ordinary model weights except exact FP32 scales/constants authorized by
  profile;
- alias targets have identical bundle/ordinary representation; and
- tokenizer/vocabulary/special IDs agree with embedding/head logical shapes independently of packing.

A per-layer exception list is not accepted initially because it turns one format into an unbounded
mixed-policy matrix. A future mixed policy needs a new profile, memory/quality identity, and tests.

### 11.4 Fingerprints and namespaces

M13 versions M3's fingerprint preimage and records:

- architecture/model schema and normalized Llama/Qwen semantic config;
- quantization manifest/descriptor/weight-plan schemas;
- format/profile/source algorithm and calibration/conversion provenance;
- every packed value/scale/zero/ordinary tensor file digest;
- eligible/excluded/alias role policy and portable layout;
- tokenizer/template/artifact/revision/adapter/RoPE identities; and
- ordinary/activation/accumulator/output/KV dtype policy.

`ModelInstanceFingerprint` additionally contains selected backend-derived packed layout, kernel/
algorithm/autotune profile, device capability, workspace/memory plan, and graph schema. M11 prefix
namespace and M12 graph/autotune keys consume these exact versioned fingerprints.

Consequences:

- BF16, FP8, and INT4 never share prefix-cache pages or graph/tune entries;
- two differently calibrated/packed quantized artifacts do not share merely because decoded model
  name/format match;
- backend repacking changes instance identity but not portable content identity; and
- copying identical canonical package bytes to another safe directory preserves content fingerprint.

## 12. Inspection, conversion, and provenance tools

### 12.1 `inferx-quant-inspect`

The read-only inspector uses the production rooted parsers/validators and emits bounded human or
canonical JSON output containing:

- architecture/model/quantization/profile/provenance fingerprints;
- logical parameters and exact bundle components/dtypes/shapes/ranges/digests;
- group/scale/zero/pack/tail/alignment policy and validation status;
- eligible/quantized/excluded/aliased role coverage;
- theoretical payload, required metadata, file padding, source/portable/backend planned bytes;
- candidate hardware/backend compatibility and reason codes; and
- optional bounded dequantized summary/error statistics against a supplied local baseline.

Default output never prints full weights/scales/zeros, tokenizer vocabulary, prompts, calibration
examples, or unrestricted paths. Explicit tensor dumps require M10 protected diagnostic policy,
allowlisted parameters, byte caps, no overwrite, and a nonproduction build/runtime gate.

### 12.2 `inferx-quant-convert`

The converter is offline, local-only, and transactional:

1. open source/baseline package through rooted M3 sessions and validate complete identity;
2. recognize exactly one supported input adapter and reject opaque code/pickle/custom Python modules;
3. construct the target architecture parameter catalog and complete quantized plan;
4. convert or losslessly normalize one tensor bundle at a time under fixed staging limits;
5. validate canonical bytes, unpack/dequant formula, tail/canaries, and source-to-output statistics;
6. write new safetensors shards/manifest into a fresh sibling temporary directory;
7. reread the entire output with production readers, recompute coverage/fingerprints, and run selected
   bounded model/quality smoke fixtures;
8. fsync/atomically publish according to M10 tool filesystem policy; and
9. leave a complete failure report and remove/recover the unpublished temporary output safely.

It never edits a source package in place, follows symlinks outside roots, overwrites by default,
downloads data, imports model remote code, or trusts source offsets/names without independent checks.

### 12.3 Conversion versus calibration

Two modes are distinct:

- **canonicalize:** normalize an already quantized checkpoint from the selected allowlisted family
  without changing reconstructed logical values; and
- **quantize:** derive FP8 or selected INT4 components from an unquantized baseline using the exact ADR
  algorithm and local calibration corpus where required.

Canonicalize proves FP32 reconstructed equality before/after. Quantize records algorithm parameters,
seed, calibration example/token ordering and digest, clipping/search settings, tool/dependency/build
fingerprints, source baseline fingerprint, per-tensor errors, and final quality-evidence identity.

If M13 does not implement the selected AWQ/GPTQ calibration algorithm in a reviewed tool environment,
it supports canonicalization of prequantized legal artifacts only and says so explicitly. It may not
label a simple min/max quantizer as AWQ or GPTQ.

### 12.4 Reproducibility and trust

Two conversions from identical bytes/config/tool/environment must produce byte-identical canonical
manifest/tensors/shard order/fingerprint. Parallel processing may change runtime only, not reduction,
packing, file ordering, or output bytes.

Tool dependencies have exact pins, licenses, hashes, SBOM/provenance, and are isolated from the
serving runtime dependency graph. Evaluation/calibration dataset licenses and redistribution rules are
recorded. Secrets/credentials and local absolute paths do not enter public manifests.

## 13. Transactional quantized model loading

### 13.1 Extended load states

The M5/M12 model load transaction adds explicit quantized phases:

```text
ValidatedPackage -> QuantPlan -> MemoryPlan -> Allocate -> Map/Stage
                 -> PortableValidate -> BackendPack -> Upload/Prepare
                 -> EagerWarmup -> GraphWarmup -> QualitySmoke -> Ready
```

No registry/readiness publication occurs before every required phase succeeds. Failure closes the
constructed prefix in reverse, retains uncertain CUDA resources under M2, and restores host/device/
pinned/file/descriptor/graph/autotune counters exactly.

### 13.2 Complete memory plan

Before allocation, plan disjoint bytes for:

- mapped source packed/ordinary components and bounded open-file leases;
- host decode/validation and transform scratch by maximum tensor/chunk;
- pinned upload staging and transform result slots;
- canonical device values/scales/zeros only if the backend consumes them directly;
- final backend-derived packed values/metadata/alignment;
- ordinary excluded weights, biases, norms, embedding/head and aliases;
- FP8 activation-quant/scale or INT4 dequant-GEMM workspace per eager/graph bucket;
- prepared descriptors/algorithms, graph stable arenas/executable charge, autotune/warm-up scratch;
- model/KV/activation/telemetry/diagnostic safety margins from prior milestones; and
- temporary overlap only for the exact chunked pack/upload pipeline.

The plan proves peak, Ready, and unload bytes independently. It does not assume source mappings are
device memory or subtract theoretical compression twice. If both canonical and backend-packed device
copies are necessary, the capability report names/charges both; the preferred design streams into
one final backend layout and retains only portable host artifact bytes.

### 13.3 Portable-to-backend transform

Each prepared transform has exact input descriptor/layout/digests, output layout/schema/shape/strides/
alignment/bytes, backend/device/software identity, workspace, chunk order, canaries, and independent
unpack validation. It may transpose/tile/swizzle/repack but cannot recalibrate or change reconstructed
quantized values.

For each chunk:

1. reserve output range/staging/workspace/event and validate nonoverlap;
2. map/copy exact source component ranges;
3. validate source checksum/descriptor/tail bits;
4. run CPU or qualified GPU pack into transaction-private output;
5. fence and validate output canaries plus sampled/full reference unpack according to fixture policy;
6. commit the immutable final range and release staging; and
7. record bytes/time/checksum without exposing contents.

No final weight view becomes reachable until all parameters, aliases, operators, and warm-ups validate.
Backend-packed bytes enter the instance fingerprint and cannot be reused across a different key.

### 13.4 Preparation and warm-up

After upload, construct the complete quantized operator set for every model phase/bucket and role.
Warm-up executes representative min/odd/max shapes, biases, tails, paged attention integration,
GPU sampling/logits, eager and every mandatory graph bucket. It compares against dequantized reference
and model fixtures, validates workspace/canaries/fences, and freezes the registry/autotune decisions.

Optional graph capture failure follows M12 eager fallback only if eager quantized backends are fully
ready. Missing/invalid quantized eager backend fails the model; warm-up never dequantizes the whole
weight as a serving substitute.

### 13.5 Unload and repeated startup

Drain requests/tickets/output jobs/graphs under M12, destroy graph entries and prepared quantized
operators, release derived packed/scales/ordinary weights, transform/upload staging, mappings/files,
and package metadata, then prove model categories equal their pre-load baseline. Pending/uncertain
device work retains every referenced weight/backend/descriptor until safe M2 teardown.

Repeated mixed startup tests load/unload Llama/Qwen and BF16/FP8/INT4 packages in every order, including
one failed transaction between successes. A failure cannot poison future model slots unless CUDA
ownership is uncertain.

## 14. Quantized operator and backend contract

### 14.1 Logical operation

The hardware-neutral quantized linear operation is:

```text
W_hat = DequantizeWeight(W_quantized)
X_hat = X                                      # W4A16
X_hat = DequantizeActivation(Quantize(X))      # W8A8
Y[M,O] = X_hat[M,I] * W_hat[O,I]^T + optional_bias[O]
```

Its contract contains ordinary input/output/bias views, immutable quantized weight bundle handle,
logical dimensions/strides, descriptor/profile, phase/bucket, accumulator/output policy, workspace,
aliases, and asynchronous completion. It does not expose packed bytes as an ordinary matrix or let
the model perform dequantization.

Bias is added exactly once after the dot product under the model's existing semantic order. FP8
activation quantization is an explicit prepared suboperation/fusion inside the backend contract; INT4
keeps FP16/BF16 activation. Output layouts match shared dense modules so RMSNorm/RoPE/attention/MLP
code does not know the weight representation.

### 14.2 Backend key and capability

The M4/M12 prepared key adds:

- quantization descriptor/profile and selected source-family provenance class;
- portable and backend packed-layout schemas;
- component/scale/zero dtypes/granularity/group/tail/packing;
- activation/accumulator/output/bias dtype and numeric policy;
- logical and padded M/N/K, strides/alignment, phase/batch/token/context bucket;
- parameter semantic role and fused epilogue identity;
- device SM/attributes, driver/CUDA/vendor/dependency/kernel versions;
- workspace limit, eager/graph mode and stable-arena layout; and
- deterministic/autotune/correctness evidence generations.

Keys exclude raw pointers, request/model display name, wall time, and source path. Complete equality
guards hashes. A format, group size, scale convention, Qwen bias, output dtype, backend pack, or
software change cannot hit an old prepared plan/graph/tune entry.

### 14.3 Backend preparation

Preparation:

1. validates exact descriptor/role/shape/device capability;
2. resolves final packed views/scales/zeros and actual alignment;
3. enumerates a bounded qualified candidate set;
4. validates workspace and graph-capture requirements;
5. executes each allowed candidate on independent fixture data;
6. checks dequantized reference and format-specific numeric gates/canaries;
7. optionally benchmarks under M12 autotune methodology; and
8. freezes one eager plan plus separately qualified graph plans before readiness.

No live request queries heuristics, builds descriptors, allocates, packs, compiles, or changes
algorithm. A forced backend is test/config only and fails warm-up when incompatible.

### 14.4 Launch and failure boundary

Launch validates model/backend/weight-bundle/packed-layout/workspace/graph/ticket generations and
operand ranges before issuing work. It owns no weights and holds all views through the ticket final
fence. It performs zero allocation, repacking, dequantization fallback, descriptor creation, timing,
synchronization, or host data-dependent dispatch.

An immediate prelaunch validation failure rejects before mutation where the M8/M12 acceptance
boundary permits. Any possible asynchronous mutation/error follows existing ticket poison rules; it
is not retried with another quantized or BF16 backend.

### 14.5 Independent reference and intermediate checks

Operator tests compare optimized output with the section 8.4 reconstructed FP32 weight/reference
linear, report M4 error metrics, and preserve format/profile-specific thresholds from ADR 0097.
Fixtures include raw packed/scale/zero bytes and expected reconstructed weights so the CUDA packer and
kernel cannot share the same bug unnoticed.

Model diagnostic checkpoints compare layernorm output, biased Q/K/V before RoPE, rotated Q/K, KV
writes, attention output, MLP gate/up/down, layer output, final norm, logits, and top-k. Diagnostics
remain bounded/off in performance runs.

### 15.1 Exact architecture envelope

| Field | Initial M13 rule |

### 15.3 Derived semantic values

Derive with checked arithmetic:

- `q_out = num_attention_heads * head_dim`;
- `kv_out = num_key_value_heads * head_dim`;

- full-attention layer type for every layer; and
- embedding/head/position/KV sizes within M3/M5/M6/M12 capacity.

Q/K projection biases are applied before reshape/RoPE; V bias before reshape/KV write. Q and K receive
the existing half-split full-head RoPE convention; V does not. The rest of layer order matches the
shared pre-norm dense decoder.

## 18. Runtime integration and namespace effects

### 18.1 KV, scheduler, and prefix cache

M13 leaves KV storage FP16/BF16 and uses the existing rotated-K paged layout. Quantized Q/K/V
projection outputs are converted to the model activation/KV dtype before RoPE/KV write. M6 table,
quota, low-water, preemption, and completion rules are unchanged.

M11 namespace includes architecture, exact quantized model/instance fingerprints, numeric/output/KV
policy, position/RoPE, tokenizer/template, layout/page/device, adapter, and tenant. Therefore:

- an ordinary and quantized instance never share cached pages;
- FP8 and INT4 never share even if they originated from the same baseline;
- two separately calibrated or backend-packed instances do not share unless the complete declared
  namespace identity matches; and
- Qwen/Llama never share under equal token IDs.

Cache hit/miss/reset/eviction and M8 scheduling cost work unchanged. Quantization quality/performance
tests run with cache off/miss/hit so reuse cannot hide numeric or backend defects.

### 18.2 M12 graph and autotune

Every quantized backend is eager-qualified first, then each selected decode graph bucket is captured
and compared against its quantized eager route. Graph keys/descriptors add format/profile, packed
layout, scale/group/tail, architecture/bias, workspace, and backend/autotune fingerprints. Old M12
unquantized graphs are unmatchable.

FP8 dynamic activation scale buffers and INT4 backend workspace use stable graph-arena slices. Inactive
lanes cannot write real scale/KV/result memory. Graph misses use the prepared eager backend of the
same quantized format; they do not switch to unquantized weights.

Autotuning operates only on already-correct quantized candidates before readiness. Tune-cache keys
include every M13 identity. Format/profile/backend changes are misses, not compatible aliases.

### 18.3 Sampling, output, and protocol

The final logits operation produces one contiguous FP32 row per active sequence exactly as M9/M12
require, even when the LM head is eventually quantized. CPU/GPU sampling, RNG, logprobs, stop matching,
output jobs, usage, HTTP/SSE, cancellation, and response values are format/model-family independent.

Qwen vocabulary sizes and quantized logit distributions require separate GPU-sampler and graph bucket
qualification, but sampling version/algorithm is unchanged. For the same quantized artifact and seed,
eager/graph and CPU/GPU sampling routes must select identical tokens under M9/M12 gates.

### 18.4 Failure and health boundaries

Malformed/unsupported package/model/format/backend tuples fail before serving and do not degrade an
already Ready independent model slot. Once a quantized ticket launches, CUDA/weight/scale/workspace
uncertainty follows M2/M10 poison; it is never retried through another format.

Metric/export/quality-tool failure cannot change inference. Production readiness does not run a full
quality corpus, but it requires the exact signed/manifested evidence identity and bounded warm-up
fixtures configured for that capability.

## 19. Numerical correctness hierarchy

### 19.1 Four distinct comparisons

Do not collapse these gates:

1. **packing correctness:** portable/backend pack reconstructs the exact intended quantized values;
2. **kernel correctness:** optimized operation matches the dequantized quantized-weight reference;
3. **route correctness:** eager/graph and CPU/GPU sampler routes for one quantized artifact agree; and
4. **quantization accuracy:** quantized model differs from its FP16/BF16 source only within predeclared
   logit/top-k/greedy/quality/perplexity thresholds.

The first and route identity gates require exact bytes/IDs where specified. Kernel numeric thresholds
measure implementation error. Quantization accuracy thresholds measure deliberate representation loss
and cannot excuse a pack/kernel bug.

### 19.2 Packing and operation gates

- INT4 unpacked `Q/Z`, group mapping, tail codes, and reconstructed FP32 weights match independent
  known-answer fixtures exactly.
- FP8 stored bytes/scales and reconstructed FP32 values match the canonical conversion fixtures;
  activation conversion matches profile bit/range rules.
- Backend pack/unpack reconstructs the portable quantized logical values exactly or within only the
  explicit lossless representation conversion rule; it may not requantize.
- Optimized GEMM/linear output compares with FP32 dequantized reference using format/shape-specific
  ADR 0097 tolerances plus max/mean/L2/finite-class/error-location reports.
- Bias, Q/K/V unequal GQA dimensions, odd M/N/K, partial groups, graph padding, and maximum workspace
  all receive separate thresholds/evidence.

Thresholds are calibrated on representative well-conditioned and adversarial fixtures, frozen before
candidate timing, and may tighten but not widen to admit a backend.

### 19.3 Model intermediate and logit gates

For Llama and Qwen, compare quantized execution with:

- the same canonical quantized values dequantized into the M4/M5 FP32 reference path; and
- the original FP16/BF16 source model for quantization-accuracy evidence.

Record per stable intermediate maximum/mean/L2 error and finite classes, final logit maximum/mean/L2,
top-1/top-k set/order agreement, selected greedy token agreement on the committed fixture corpus, and
worst prompts/layers/tokens. Dequantized-reference mismatch fails implementation correctness even if
source-baseline quality looks acceptable.

Tiny crafted fixtures require exact expected greedy tokens for each committed quantized package.
Real-model quantized-versus-source greedy agreement is a predeclared metric/threshold, not universal
token identity. Within one quantized package, all scheduler/cache/eager/graph/sampler/API routes retain
the exact deterministic token/output behavior required by prior milestones.

### 19.4 Special values and overflow

Source weights/scales/biases required finite by profile. Zero/negative/nonfinite scales, out-of-range
zero points, noncanonical FP8 NaN/Inf encodings, invalid unused nibbles, or accumulator/output overflow
fixtures fail with stable classification. Runtime nonfinite activation/output follows M4/M9 behavior;
an optimized kernel cannot clamp silently unless the profile formula explicitly says so.

## 20. Fixed quality and perplexity evaluation

### 20.1 Corpus and split

Before optimized kernels are measured, ADR 0097 commits:

- a legal immutable calibration corpus where the selected quantizer requires one;
- a disjoint fixed holdout quality/perplexity subset not used to choose per-tensor quantization values;
- tokenizer/template/model baseline fingerprints and exact preprocessing/token-window/stride rules;
- example/document/token counts, inclusion/exclusion, ordering, seed, and content digests;
- reference evaluator/dependency/tool/container fingerprints; and
- per-format metrics, thresholds, statistical method, and failure policy.

Corpora are local inputs with documented licenses/provenance. Runtime/server tests do not fetch them.
Sensitive/private evaluation data uses access-controlled evidence digests rather than committed text.

### 20.2 Metrics

At minimum report for each architecture/model/format:

- token-weighted negative log likelihood and perplexity, with baseline and absolute/relative delta;
- final-logit/top-1/top-k agreement on a fixed prompt/token corpus;
- greedy token/prefix/full-generation agreement and first-divergence positions;
- one fixed task/quality score when the selected release claim depends on it;
- finite/error/failure counts and excluded examples with stable reasons; and
- bootstrap or declared confidence interval where the metric is sampled.

Scores are computed from the complete advertised model output, not only dequantized weights or a
handpicked layer. Failed/nonfinite examples count as failures, not exclusions.

### 20.3 Threshold freeze and acceptance

FP8 and selected INT4 have separate exact thresholds set from baseline, calibration candidates, and
product tolerance before optimized backend selection. Llama and Qwen may have separate declared
limits when evidence justifies them, yielding separate capability tuples.

Changing corpus, preprocessing, baseline, metric, threshold, or evaluator after seeing an optimized
kernel result creates a new evidence version and repeats selection. A format failing quality remains
off/experimental even if memory/performance is excellent. A format passing quality but missing the
10% capacity/performance benefit also remains unadvertised under the roadmap gate.

### 20.4 Evaluation reproducibility

`inferx-quality-eval` reads local model packages and a canonical workload manifest, uses deterministic
batching/seeds, records every successful/failed token count, and emits a checksummed result bundle.
It can compare source baseline, dequantized reference on bounded fixtures, portable quantized eager,
and final graph route without changing prompts or output set.

Reruns use the same M10 hardware/software/evidence controls. Results include raw aggregate sufficient
statistics and worst-case identifiers hashed/redacted under dataset policy, never unbounded text.

## 21. Configuration, capability matrix, and startup proof

### 21.1 Configuration fields

M13 extends the immutable model configuration with:

| Field | Initial rule |
|---|---|
| `models[].architecture_profile` | exact `llama_dense_v1` or `qwen2_dense_v1`; normally artifact-derived/agreed |
| `models[].quantization.mode` | `artifact`, `none_required`, or exact required profile; no `auto_guess` |
| `models[].quantization.allowed_profiles` | closed deployment allowlist; empty means unquantized only |
| `models[].quantization.required_source_family` | exact selected INT4 family where applicable |
| `models[].quantization.max_transform_staging_bytes` | positive bounded within host/pinned plan |
| `models[].quantization.backend_pack` | exact `auto_qualified` or forced test backend/layout |
| `models[].quantization.quality_evidence_manifest` | required signed/digested local evidence for advertised format |
| `models[].qwen2.allow_full_attention_only` | true in M13; no sliding fallback |
| `models[].qwen2.template_profile` | exact supported prompt-template profile/digest |
| `performance.autotune` / graph profile | M12 settings extended by exact M13 identities |
| `diagnostics.quantization` | safe aggregate summaries; sensitive tensor inspection off |

Artifacts remain authoritative for semantic bytes. Configuration may narrow support or require an
exact profile; it cannot reinterpret the artifact descriptor, choose a missing group size, change
scales/zeros, enable a rejected Qwen feature, or bypass quality evidence.

### 21.2 Capability matrix

The generated matrix has one row per exact:

```text
architecture + model fixture/size class
+ ordinary/FP8/selected-INT4 profile
+ eligible/excluded parameter roles
+ activation/KV/output dtype
+ device/SM + software/backend/packed layout
+ prefill/decode/mixed batch/token/context/page bucket
+ eager/graph + sampling route
```

Each row records `supported`, `experimental`, or `rejected` plus stable reason; numeric/quality,
memory, performance, graph, and soak evidence IDs; and limits. An umbrella “Qwen supported” or “INT4
supported” flag is insufficient.

Ordinary Llama/Qwen FP16/BF16 rows remain independent from quantized rows. A tuple can pass Llama and
fail Qwen due dimensions/biases/vocabulary/quality/backend and is advertised accordingly.

### 21.3 Startup proof

Before readiness, prove:

- package/architecture/quantization/config/evidence fingerprints and schema compatibility;
- complete ordinary/bundle/alias coverage and safe source ranges/digests;
- all descriptor group/scale/zero/pack/tail/shape arithmetic and component limits;
- exact final device/pinned/host/graph/workspace/KV/telemetry memory plan including peak transform;
- every model operation/phase/bucket has a prepared eager backend and required graph variants;
- quantized pack/kernel warm-up and bounded model fixtures pass their frozen thresholds;
- M11 namespace and M12 graph/autotune/sampling schemas include M13 identity;
- Qwen tokenizer/template/vocabulary/special IDs and GPU-sampling capacity reconcile;
- required quality-evidence bundle matches exact package/baseline/evaluator/corpus and passed; and
- all strong counts/IDs/pools can represent the configured maximum without overflow.

Startup does not reduce context, graph buckets, KV blocks, batch, or quality thresholds silently to
make a model fit. Explicit auto-sizing from prior milestones reruns with the quantized memory plan and
records its result before admission limits freeze.

### 21.4 Runtime updates

Model architecture, quantization profile, packed layout, backend set, quality evidence, memory/KV
geometry, graph set, and tokenizer/template are immutable for one loaded instance. Changing any of
them drains/unloads and creates a new generation. Runtime policy may route traffic among already Ready
model slots but cannot convert or retune a live model.

Safe snapshots report:

- architecture/format/profile and public capability fingerprint;
- parameter-role counts and ordinary/packed/scale/zero/padding/derived/alias byte totals;
- load/pack/warm-up phase/status/timing and pool high water;
- prepared eager/graph/autotune backend counts and rejected reason classes;
- aggregate quantized operation, nonfinite/failure, graph hit, prefix-cache, and performance counters;
- quality evidence identity/status and aggregate metric thresholds/results where licensing permits; and
- health, owner generations, checksums, and resource reconciliation.

Full component values or reconstructed weights require the protected fixture-only tool path. M10
diagnostic/admin workers read immutable owner snapshots and never map model files, traverse live

### 22.4 Health and containment

- Invalid/unsupported model-format packages fail their load slot without degrading an independent
  already Ready model/device when no CUDA work occurred.
- Optional format capability unavailable is healthy when config did not require it; a requested model
  remains unready with a stable explanation.
- Quality-evidence mismatch/failure prevents publication but is not device poison.
- Backend pack/warm-up numeric mismatch quarantines that prepared model transaction and records
  `DataLoss`; no request sees it.
- Any uncertainty about live device weights/scales, asynchronous pack/kernel writes, graph pointers,
  or ticket ownership poisons the device/model component under M2/M10.

Load/pack/warm-up and serving workers publish progress/current tensor role or operation class, owned
resource counts, and measured deadlines without sensitive names/values. Watchdogs distinguish large
declared model load from a stall using manifest-derived work bounds.

| Failure | Required result |
|---|---|

## 25. Performance and memory methodology

### 25.1 Baselines and controls

For each architecture, compare a quantized artifact with its exact FP16 or BF16 source baseline on the
same M12 candidate image, hardware/software/power/clocks, tokenizer/template, context/page/cache/graph/
sampling/telemetry config, workload/arrival trace, request seeds, warmup, successful set, and trial
method. Llama uses the published M12 baseline; Qwen first establishes an equivalent unquantized M13
baseline before any quantized claim.

Report quantization conversion separately from server load. Randomize paired trial order, retain raw
samples/confidence, and do not compare different prompts/success sets or graph coverage silently.

### 25.2 Weight-memory formulas and 5% rule

For eligible parameter set `E`:

```text
ideal_value_bytes = Sum_p(Ceil(logical_elements_p * value_bits / 8))
required_metadata_bytes = scales + zeros + descriptors + per-row/group indexes required by profile
planned_ready_bytes = ideal_value_bytes + required_metadata_bytes
                    + explicit alignment/padding + required derived-layout bytes
```

Ordinary excluded weights/biases/norms/embedding/head and graph/workspace/KV bytes are reported
separately. Aliases count physical bytes once. Source mappings and load-time staging appear in peak/RSS,
not Ready device-weight bytes.

For the target real checkpoint:

- measured Ready quantized weight-category bytes must be within 5% of the checked planned value;
- required quantization metadata plus unavoidable alignment/padding must be no more than 5% above the
  ideal eligible packed-value payload unless the roadmap criterion is revised by accepted evidence;
- total model-memory reduction versus baseline is computed from actual mixed eligible/excluded roles;
  and
- theoretical W8/W4 ratios are never applied to the whole model when roles remain ordinary.

Tiny/odd stress fixtures may exceed a percentage due fixed descriptors; they validate correctness and
report absolute bytes, while release memory claims use the declared target checkpoint.

### 25.3 Load and operation benchmarks

Measure source validation/map, portable validation, CPU/GPU pack, H2D, backend prepare/autotune,
eager/graph warm-up/capture, total time-to-ready, peak host/pinned/device/RSS, Ready bytes, and unload.

For every eligible linear role/shape/bucket measure pack throughput and GEMM/linear p50/p95/p99,
workspace, bandwidth, utilization, launch gaps, graph hit/padding, dynamic FP8 quantization overhead,
and INT4 dequant-GEMM behavior. Compare optimized backend to dequantized reference only for correctness;
performance compares final quantized route with the source baseline route.

### 25.4 End-to-end serving and quality tradeoff

Run prefill-heavy, decode-heavy, mixed continuous-batch, short/medium/long context, cache no-reuse/
reuse, greedy/sampled/logprob, and embedded/HTTP open-loop workloads. Report:

- prompt/output tokens/s, requests/s, TTFT, TPOT, end-to-end p50/p95/p99/max and SLO goodput;
- batch/bucket/graph/cache/sampler route distributions and GPU/CPU utilization;
- Ready/peak model/KV/graph/workspace/pinned/RSS memory and maximum feasible concurrency/model size;
- load/time-to-ready and restart cost;
- errors/drops/fallback/rejection and exact capability row; and
- paired logit/top-k/greedy/NLL/perplexity/quality metrics.

Before trials, each format declares one primary capacity/performance metric. It must improve that metric
by at least 10% versus its architecture's source baseline while passing quality and protected SLO
cells. Weight-memory reduction can be the capacity metric only when measured Ready bytes and usable
model/concurrency capacity reflect it; a theoretical packed ratio alone is insufficient.

No advertised tuple may regress a protected target workload beyond the project-wide 5% end-to-end
bound without an ADR restricting its use. A format can be valuable for capacity and slower at low
batch, but the capability matrix/default must state that crossover explicitly.

### 25.5 Format acceptance

An FP8 or selected INT4 tuple is enabled only when it simultaneously:

- passes artifact/packing/kernel/route/model correctness and all failure/sanitizer gates;
- passes its frozen logit/top-k/greedy/quality/perplexity limits;
- meets the memory-plan/5% overhead rule;
- improves its predeclared capacity/performance metric by at least 10%;
- retains a correct eager quantized path and any advertised graph route;
- survives repeated load/unload and 24-hour soak without resource growth; and
- publishes exact supported/rejected matrix and evidence.

Failure of one architecture/format/hardware row disables only that row if isolation is proven. The
format milestone is not reported complete until the roadmap-required FP8 and one selected INT4 release
rows pass.

## 28. Risks and required experiments

| Risk | Required evidence | Decision/fallback |
|---|---|---|
| ecosystem metadata variants are ambiguous | candidate artifact census and strict adapter corpus | canonicalize exact allowlist or reject; never guess |
| supporting both INT4 families multiplies scope | ADR 0090 weighted comparison | select exactly one; other remains unsupported |
| FP8 scale mode unavailable on target pin/SM | native backend spike and capability matrix | unsupported tuple; do not change profile meaning |
| FP8 activation quantization erases GEMM gain | quantize+GEMM model ablation by phase/batch | restrict tuple or keep off if <10% benefit |
| INT4 kernel helps decode but hurts prefill | shape/SLO crossover curves | advertise restricted workload/default honestly |
| group/tail packing corrupts odd dimensions | independent bit oracle/property/sanitizer suite | reject unsupported alignment or explicit padded layout |
| backend repack changes quantized values | portable/backend round-trip reconstruction | pack must be lossless; no hidden requantization |
| load peak holds source and derived full copies | phase memory timeline/near-capacity load | chunked transform, exact peak plan, fail before allocate |
| metadata/alignment erodes theoretical memory | per-role byte reconciliation | enforce target 5% rule and report exclusions |

## 30. Definition of done

### Artifact, format, and loading

- [ ] Quantization descriptors/bundles encode and validate every scale/zero/group/pack/tail/dtype/
      provenance field explicitly; missing/ambiguous metadata never receives a guessed default.
- [ ] FP8 bytes/scales and selected INT4 Q/S/Z/tails match independent known answers; complete
      component/ordinary/alias coverage and fingerprints are deterministic and collision guarded.
- [ ] AWQ versus GPTQ is selected once through retained evidence; only the chosen exact family/profile
      is parsed/converted/served initially.
- [ ] Inspection/conversion tools are local, data-only, bounded, reproducible, transactional, fuzzed,
      provenance-complete, and absent from the serving trust path where configured.
- [ ] Quantized memory planning/load/backend pack/warm-up/publication/unload is transactional, performs
      no serving-time pack/allocation, and returns all safe resources to baseline.

### Operators, Qwen, and integration

- [ ] Every advertised FP8/INT4 op/backend matches dequantized reference, has eager plus declared graph
      qualification, exact key/autotune identity, bounded workspace, and no production dequant fallback.
- [ ] `DenseQwen2V1` accepts only exact full-attention/default-RoPE dense semantics, maps required Q/K/V
      biases and all weights one-to-one, and matches independent config/intermediate/logit fixtures.
- [ ] Llama and Qwen share dense model modules, KV/scheduler/cache/sampling/output/server/operations;
      an architecture-diff review finds no duplicated runtime logic beyond documented traits/maps.
- [ ] Ordinary and quantized model/instance/graph/autotune/prefix namespaces are pairwise distinct and
      no cross-format/architecture page, graph, packed weight, or tune result is reused.
- [ ] Every advertised Llama/Qwen × FP16/BF16/FP8/selected-INT4 tuple passes load/generate/API/cache/
      graph/cancel/drain/unload tests; every other tuple rejects before serving.

### Accuracy, performance, operations, and evidence

- [ ] Packing, kernel implementation, route equivalence, and quantization-accuracy comparisons remain
      separate and all pass their frozen criteria.
- [ ] Each enabled format/model row passes predeclared intermediate/logit/top-k/greedy and fixed
      holdout quality/perplexity thresholds whose corpus/evaluator version predates optimization.
- [ ] Measured Ready weight bytes match the checked plan within 5%, target metadata/alignment overhead
      satisfies the roadmap 5% rule, and ordinary/excluded/alias/peak bytes are reported honestly.
- [ ] Every enabled format improves its declared capacity or end-to-end performance metric >=10% over
      its exact architecture baseline and publishes workload crossover/quality tradeoffs.
- [ ] M10 telemetry/privacy/health/fault/container rules, M11 cache isolation, and M12 graph/sampling/
      autotune/SLO gates remain valid for M13 routes.
- [ ] Unit/integration/correctness/quality/stress/failure/fuzz/ASan/UBSan/TSan/Compute Sanitizer,
      repeated mixed load/unload, 24-hour soak, ADRs 0090-0099, docs, capability matrix, tools, fixtures,
      and immutable evidence pass without hidden skips.

## 31. Handoff to distributed and MoE milestones

M13 publishes an optional extension to the M12 single-GPU baseline: strict portable quantized bundles,
derived backend layouts, exact format/architecture identities, qualified dense Llama/Qwen operators,
Qwen semantic traits, slice-plan validation, quality thresholds, tools, and complete capability/
performance evidence. M14 remains independently implementable from M12 and must not be blocked by
M13.

If M14 consumes M13, it must define rank-local quantized bundle slicing/repacking, group/scale/zero
ownership, per-rank derived-layout fingerprints, collective/logit behavior, graph/autotune keys, and
quality/performance evidence for each topology. It cannot split a nibble/group or reuse a single-GPU
packed layout by assumption.

M16 may reuse the descriptor/reference/tool foundations for quantized MoE only after its own expert-
weight, grouped-GEMM, routing/placement, quality, topology, and performance ADR. Dense M13 success does
not qualify expert weights, mixed formats, or distributed quantized collectives automatically.
