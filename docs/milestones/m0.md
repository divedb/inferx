# M0 implementation specification: reproducible repository, unified CLI, and dependency qualification

- Status: proposed implementation contract
- Roadmap milestone: M0 in [`docs/plan.md`](../plan.md)
- Prerequisites: none
- Immediate successor: M1

This document turns M0 from an acceptance summary into an executable implementation plan. It defines
the files, CMake targets, dependency rules, CI jobs, tests, evidence, and merge order needed to finish
M0. An implementation may change a named tool or version only through an ADR that preserves the
interfaces and completion gates below.

## 1. Outcome

At the end of M0, a developer can take a fresh checkout and, without network access during CMake
configure or build:

1. initialize the small core dependency profile;
2. configure, compile, test, analyze, install, and consume a C++23 `inferx::base` library;
3. build and run an optional CUDA smoke target on a supported NVIDIA GPU;
4. reproduce the same operations in GitHub Actions;
5. identify every source/system dependency, exact revision, license, feature owner, and enablement
   status;
6. build and install exactly one user-facing executable, `inferx`, whose capabilities are exposed as
   discoverable CLI11 subcommands; and
7. inspect build/toolchain metadata and benchmark evidence from machine-readable artifacts.

M0 establishes engineering mechanics and the permanent command-line architecture, not the internal
implementation of every later inference feature. It must be intentionally small enough that M1 can
change core value types without preserving a premature ABI. Later milestones add implementations
behind the command contracts in section 7; they do not add executables.

## 2. Repository baseline

The original M0 implementer started from these historical facts rather than assuming infrastructure:

- only `.clang-format`, `.clang-tidy`, `.gitignore`, `.gitmodules`, gitlinks, and documentation exist;
- no CMake, source, test, benchmark, container, or installed-package files exist;
- no root project license or internal-use notice exists; the repository owner must decide the
  distribution terms rather than a coding agent selecting a license;
- `.clang-format` currently declares C++20 and must be updated to C++23;
- all seven declared submodule worktrees are uninitialized;
- the previous `.github/workflows/phase0.yml` was deleted in the current `HEAD`; it is useful history,
  not code to restore verbatim; and
- `docs/` is currently untracked and must be committed as part of the first M0 change.

The unified-CLI amendment starts from a later repository state. The top-level build currently creates
five application executables under `apps/`: `inferx-info`, `inferx-model-inspect`, `inferx-generate`,
`inferx-sim`, and `inferx_fsm_schema`. These are migration inputs, not interfaces to preserve. Their
useful behavior must move behind reusable library APIs and be reached through `inferx` subcommands;
their executable targets, directories, install rules, names, and aliases must be removed. No wrapper,
symlink, or compatibility executable may keep a legacy application name alive.

## 3. Scope boundaries

### 3.1 In scope

- C++23 project and target conventions.
- CPU build, tests, sanitizers, format, static analysis, include hygiene, install/export, and consumer
  validation.
- One unified CLI target named `inferx`, with CLI11 parsing, reusable configuration values, and thin
  dispatch adapters.
- Migration of useful behavior from all existing `apps/` executables into reusable library APIs and
  `inferx` subcommands.
- Optional CUDA language/toolkit detection and a single device/kernel smoke test.
- Source dependency initialization that is explicit, pinned, profile-based, and offline after
  bootstrap.
- CI, developer containers, dependency/license inventory, SBOM procedure, ADRs, and build metrics.
- Failure tests for missing dependencies, unsupported toolchains, and requested-but-missing CUDA.

### 3.2 Explicitly out of scope

- Status/ID/FSM/scheduler implementations from M1.
- Tensor, allocator, or CUDA runtime abstractions from M2.
- Model artifacts/tokenization from M3.
- Production kernels, cuBLASLt, FlashInfer, CUTLASS integration, NCCL, networking, or server code.
- A stable shared-library ABI, plugin ABI, package-manager release, or public semantic-version promise.
- Downloading dependencies from CMake with `FetchContent` or `ExternalProject`.
- Building every declared optional submodule in default CI.
- Running CUDA tests on CPU-only GitHub-hosted runners and calling a skipped test a pass.
- Additional user-facing executables, including one executable per server, benchmark,
  inspection, download, or client mode.
- Business logic, model loading, inference execution, HTTP serving, or benchmark measurement inside
  argument callbacks or CLI command handlers.

default implementation; a change requires evidence in the corresponding ADR.

## 6. Build-system contract

### 6.1 Toolchain floor

The qualification ADR records exact versions and container digests. Use this candidate floor while
implementing:

| Tool | Candidate baseline | Reason |
|---|---|---|
| CMake | 3.28 | Mature presets/install/CUDA behavior while available on Ubuntu 24.04 |
| Ninja | 1.11 | Fast deterministic dependency scheduling and consistent CI/developer behavior |
| GCC | 13 | First supported GNU C++23 compiler lane |
| Clang | 18 | Primary warnings/tidy/sanitizer lane on Ubuntu 24.04 |
| Python | 3.12 | Developer scripts only; never a runtime dependency |
| CUDA toolkit | 12.8 candidate | Qualify against current gitlinks and target GPUs before accepting ADR 0005 |

The supported-platform document distinguishes:

- **required:** built in every pull request;
- **supported:** regularly tested on an owned runner;
- **experimental:** may build but does not block a release; and
- **unsupported:** rejected at configure time when detection is reliable.

Do not claim support for a compiler, CUDA version, driver, GPU architecture, or distribution merely
because CMake configured once.

### 6.2 Top-level CMake behavior

`CMakeLists.txt` must:

1. call `cmake_minimum_required(VERSION 3.28)` before `project()`;
2. declare `project(InferX VERSION 0.0.0 LANGUAGES CXX)`; CUDA is enabled only by the CUDA module;
3. set `CMAKE_CXX_STANDARD 23`, `CMAKE_CXX_STANDARD_REQUIRED ON`, and `CMAKE_CXX_EXTENSIONS OFF`;
   also publish `target_compile_features(inferx_base PUBLIC cxx_std_23)` so installed consumers get
   the language requirement;
4. set `CMAKE_EXPORT_COMPILE_COMMANDS ON` for top-level developer builds;
5. include `GNUInstallDirs`, `CTest`, project options, dependencies, and install rules;
6. add only M0-owned subdirectories;
7. avoid global include directories, compile definitions, warning flags, and linker flags; and
8. behave correctly as both the top-level project and an `add_subdirectory` dependency.

No CMake code may perform a network download. If a required submodule is absent, configuration fails
with its path and the exact `tools/deps/bootstrap.py --profile core` remediation. Optional dependency
directories are never inspected unless their feature is enabled.

### 6.3 Cache options

Use namespaced options and document each in `cmake -LH` output.

| Option | Top-level default | Subproject default | Constraint |
|---|---:|---:|---|
| `BUILD_TESTING` | `ON` | `OFF` | Standard CTest switch; default is set from `PROJECT_IS_TOP_LEVEL` before including CTest |
| `INFERX_BUILD_BENCHMARKS` | `ON` | `OFF` | Builds non-installed developer microbenchmarks; does not control the user-facing `inferx bench` command |
| `INFERX_BUILD_CLI` | `ON` | `OFF` | Builds the single `inferx` user-facing executable |
| `INFERX_ENABLE_CUDA` | `OFF` | `OFF` | Explicit opt-in; toolkit absence is fatal when `ON` |
| `INFERX_WARNINGS_AS_ERRORS` | `ON` | `OFF` | Applies only to InferX-owned targets |
| `INFERX_ENABLE_CLANG_TIDY` | `OFF` | `OFF` | Enabled by analysis preset/target, not every edit build |
| `INFERX_ENABLE_IWYU` | `OFF` | `OFF` | Fails clearly if requested tool is absent |
| `INFERX_ENABLE_ASAN` | `OFF` | `OFF` | CPU-only in M0; mutually exclusive with TSan |
| `INFERX_ENABLE_UBSAN` | `OFF` | `OFF` | Combined with ASan in the standard preset |
| `INFERX_ENABLE_TSAN` | `OFF` | `OFF` | CPU-only and mutually exclusive with ASan |
| `INFERX_DEPENDENCY_PROVIDER` | `submodule` | `system` | Allowed values: `submodule`, `system` |

`BUILD_TESTING` is the single source of truth for test targets. Do not add a parallel namespaced test
switch that can disagree with CTest.

Sanitizer configuration rejects invalid combinations at configure time. CUDA plus a CPU sanitizer
preset is rejected in M0 rather than producing a partially sanitized binary.

### 6.4 Target graph

Create target-scoped policy libraries:

```text
inferx_project_options   INTERFACE  C++ features, platform-independent definitions
inferx_project_warnings  INTERFACE  compiler warnings for InferX-owned targets
inferx_sanitizers        INTERFACE  selected sanitizer compile/link flags

inferx_base              STATIC     minimal installed base library
  public alias: inferx::base
  private/build-only: project_options, project_warnings, sanitizers

inferx_cli               STATIC     CLI11 registration, validation, config construction, dispatch
inferx                    EXECUTABLE the only user-facing/runtime executable and installed binary
inferx_base_test         EXECUTABLE GoogleTest unit test
inferx_absl_qualification_test EXECUTABLE adapter/dependency smoke; not installed
inferx_cxx23_smoke       EXECUTABLE compile/runtime C++23 feature sentinel
inferx_base_benchmark    EXECUTABLE Google Benchmark smoke

inferx_cuda_smoke        STATIC/OBJECT, only when INFERX_ENABLE_CUDA=ON
inferx_cuda_smoke_test   EXECUTABLE, CTest label gpu
```

`inferx_cli` is an internal, non-installed target so its parser and dispatcher can be tested without
spawning a process. It may depend on CLI11 and application-facing library interfaces; reusable
InferX libraries must not depend on `inferx_cli` or CLI11. The `inferx` executable contains only the
process entry point and links `inferx_cli`. Test, qualification, CUDA smoke, and Google Benchmark
executables are non-installed implementation artifacts and are not part of the user-facing binary
contract.

The build must contain no application executable targets named `inferx-info`,
`inferx-model-inspect`, `inferx-generate`, `inferx-sim`, `inferx_fsm_schema`, `inferx-serve`,
`inferx-loadgen`, or similar. A source file moved out of a legacy application may be retained only
after its `main()` and argument parsing are removed and it has a reusable library owner.
Set `inferx`'s build-tree runtime output to `${CMAKE_BINARY_DIR}/inferx` so documented invocations do
not depend on a generator-specific application subdirectory.

Set `EXPORT_NAME base` on `inferx_base` so the installed export is `inferx::base`. Link policy and
sanitizer targets through `BUILD_INTERFACE` generator expressions (or apply their properties directly)
so a static-library export does not retain unresolved build-only target names.

Use one CMake helper such as `inferx_apply_project_options(<target>)` for every InferX-owned library,
executable, test, benchmark, and CUDA host source. The helper attaches warnings and the selected
sanitizer to final executables as well as libraries, ensuring sanitizer runtime link flags are not
lost when an instrumented static library is consumed.

The public version API should be no larger than necessary:

```cpp
namespace inferx {

struct Version {
  int major;
  int minor;
  int patch;
};

[[nodiscard]] Version GetVersion() noexcept;
[[nodiscard]] std::string_view GetVersionString() noexcept;

}  // namespace inferx
```

Use generated headers only for controlled build metadata that cannot be expressed by the fixed
version header. Do not embed absolute source/build paths, timestamps, usernames, or a dirty working
tree into release objects: they break reproducibility and may disclose local information.

### 6.5 Compiler warnings

Start with the following InferX-owned host flags and adjust only for a documented compiler false
positive:

```text
GCC/Clang:
  -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion
  -Wshadow -Wcast-qual -Wformat=2 -Wundef -Wnon-virtual-dtor
  -Woverloaded-virtual -Werror (when enabled)
```

Do not pass project `-Werror` or sanitizer flags into Abseil, GoogleTest, Google Benchmark, CUDA, or
any optional dependency. Treat deprecation warnings in InferX adapters as project warnings. CUDA
warning flags are selected separately because blindly forwarding all host flags through NVCC is
fragile.

### 6.6 Presets

`CMakePresets.json` is checked in; `CMakeUserPresets.json` is ignored and reserved for local paths or
GPU architecture overrides. Use Ninja single-config builds under `out/build/<preset>`.

Required configure/build/test preset names:

| Preset | Compiler/build | Important cache values |
|---|---|---|
| `dev-gcc` | GCC, Debug | tests/tools on, Werror on |
| `dev-clang` | Clang, Debug | tests/tools on, Werror on |
| `asan-ubsan` | Clang, Debug | ASan+UBSan on, frame pointers on |
| `tsan` | Clang, Debug | TSan on, ASan/CUDA off |
| `cpu-release` | primary compiler, Release | tests/benchmarks/tools on |
| `analysis` | Clang, Debug | clang-tidy and IWYU on |
| `cuda-release` | qualified host compiler, Release | CUDA on, explicit architecture list |

All build and test presets use the same name as their configure preset, so the normal flow is:

```bash
cmake --preset dev-clang
cmake --build --preset dev-clang --parallel
ctest --preset dev-clang
```

The CUDA preset must never rely on CMake's `native` architecture in release/CI. Set the architecture
list from the accepted support matrix, and let a developer override it in `CMakeUserPresets.json`.
The GPU test prints the actual device/compute capability and fails when that device is outside the
declared matrix.

### 6.7 Installation and downstream consumption

Use standard GNU install directories and install:

- public headers under `${CMAKE_INSTALL_INCLUDEDIR}/inferx`;
- the static base library under the appropriate library directory;
- exactly one runtime program, `inferx`, under `${CMAKE_INSTALL_BINDIR}`;
- `InferXTargets.cmake` with namespace `inferx::`;
- `InferXConfig.cmake` and `InferXConfigVersion.cmake`; and
- the repository-owner-approved license/internal-use notice and minimal package metadata.

`tests/consumer` is a separate CMake project. It must not use `add_subdirectory`, source-tree paths,
or build-tree targets. The integration test performs:

```text
build InferX -> install to a temporary prefix
-> configure consumer with only CMAKE_PREFIX_PATH=<prefix>
-> find_package(InferX CONFIG REQUIRED)
-> link inferx::base
-> compile and run version assertion
```

If a public exported target depends on Abseil, the same prefix must contain the pinned Abseil package
and `InferXConfig.cmake` must use `find_dependency(absl CONFIG)`. Do not accidentally succeed because
the source checkout is on an include path. M0 may keep Abseil private until M1 exposes Status, but it
must prove the future installed-dependency strategy in a dedicated consumer fixture.

The install test enumerates `${CMAKE_INSTALL_BINDIR}` and fails if any project-owned executable other
than `inferx` is present. No legacy executable is installed as an alias, symlink, or forwarding stub.

## 7. Unified `inferx` command-line contract

### 7.1 One-binary rule

The only user-facing invocation is:

```text
inferx <subcommand> [options]
```

This rule applies to every milestone and supersedes executable names in older milestone examples.
New user capabilities are subcommands or, when one capability has several coherent modes, nested
subcommands. A separate executable requires an accepted ADR demonstrating a process-level isolation,
security, packaging, or operational requirement that cannot be met by `inferx`; naming convenience is
not sufficient.

The initial command tree is:

```text
inferx
├── serve
├── bench
│   ├── latency
│   ├── throughput
│   └── serve
├── run
├── chat
├── complete
├── inspect
├── download
├── version
└── env
```

`bench` may gain nested modes without adding binaries. Other coherent capabilities may gain new
top-level or nested subcommands, but must preserve the one-binary rule. Commands advertised by a
production build must dispatch to a real implementation or return a specific feature-or-backend
unavailable failure; a successful no-op placeholder is forbidden.

Representative invocations are:

```bash
./inferx serve --model meta-llama/Llama-3.1-8B-Instruct
./inferx bench latency --model meta-llama/Llama-3.1-8B-Instruct --output-format json
./inferx run --model meta-llama/Llama-3.1-8B-Instruct --prompt "Hello"
./inferx chat --model meta-llama/Llama-3.1-8B-Instruct
./inferx complete --prompt "Hello"
./inferx inspect --model meta-llama/Llama-3.1-8B-Instruct
./inferx download --model meta-llama/Llama-3.1-8B-Instruct
./inferx version
./inferx env
```

### 7.2 Command responsibilities

| Command | User-visible responsibility | Reusable implementation boundary |
|---|---|---|
| `serve` | Start an inference server for a validated model/runtime configuration | server facade plus engine/model/runtime APIs |
| `bench latency` | Measure warm and cold latency distributions, including TTFT and TPOT where applicable | benchmark runner and inference/client APIs |
| `bench throughput` | Measure request, generated-token, prompt-token, and total-token throughput where applicable | benchmark runner and inference APIs |
| `bench serve` | Exercise a running server with a reproducible workload and report client-observed latency/throughput | bounded load-generator library and protocol client |
| `run` | Execute one or more local requests without starting a persistent server | model loader and local inference API |
| `chat` | Run an interactive session or one-shot chat request against `inferx serve` | reusable OpenAI-compatible client API |
| `complete` | Send one text-completion request to a running server | reusable OpenAI-compatible client API |
| `inspect` | Report architecture, tokenizer, context length, tensor shapes, dtype, quantization, runtime configuration, and estimated memory | artifact/model inspection API; no inference side effects |
| `download` | Resolve, download, verify, and prepare a Hugging Face model in the configured local cache | model-resolution/cache API |
| `version` | Print InferX version, Git revision, build type, compiler, and compiled backend features | base build-information API |
| `env` | Print compiled and detected backend support, CUDA/ROCm and driver versions, GPU/device inventory, and relevant runtime environment | platform/runtime diagnostics API |

`serve` is the process entry for the eventual OpenAI-compatible HTTP API. Protocol parsing and server
lifecycle remain in the server library; the CLI handler only creates its configuration and calls the
facade. Likewise, `bench` does not embed benchmark loops in its CLI callback, and `download` does not
implement HTTP or Hugging Face cache rules in the CLI layer.

### 7.3 Legacy executable migration

The current applications are consolidated as follows:

| Removed executable | Replacement | Required code movement |
|---|---|---|
| `inferx-info` | `inferx version` and `inferx env` | build and environment inspection become reusable diagnostic APIs |
| `inferx-model-inspect` | `inferx inspect` | artifact/model reporting becomes a reusable inspection API |
| `inferx-generate` | `inferx run` | model loading, prompt preparation, and generation remain in their owning libraries |
| `inferx-sim` | removed with the simulator (ADR 0042) | simulator library and command deleted |
| `inferx_fsm_schema` | a library API called by tests/docs tooling, or an `inferx` nested diagnostic command if users need it | schema generation moves to the lifecycle/engine owner |
| future `inferx-serve` | `inferx serve` | server implementation remains reusable |
| future `inferx-loadgen` | `inferx bench serve` | load generation and statistics remain reusable |

Do not preserve the old binaries as deprecated shims. Tests and documentation must invoke the new
command or the reusable API. Any scripts that truly require an independent helper process are
developer tooling, are not installed, and require an explicit build-system exception; they must not
duplicate product CLI functionality.

### 7.4 CLI11 integration

CLI11 is the only command-line parsing framework for InferX-owned user interfaces. Add upstream CLI11
from `https://github.com/CLIUtils/CLI11.git` as a pinned Git submodule at `third_party/CLI11`; record
its exact URL, revision, release tag, license, owner, qualification report, and upgrade/rollback
procedure in `third_party/manifest.json`, and add it to the `core` bootstrap profile. CMake
configure/build remains offline. In submodule mode, consume the upstream `CLI11::CLI11` target without
modifying vendored sources; in system-provider mode, use `find_package(CLI11 CONFIG REQUIRED)` with
the qualified minimum version.

CLI11 owns:

- subcommand and nested-subcommand registration;
- required and optional arguments, defaults, and repeatability;
- mutually exclusive and dependent options;
- range, path, and custom semantic validation;
- case-normalized enum parsing;
- top-level and per-command help;
- `--version`; and
- parse-error formatting and usage output.

No user-facing path may use Abseil flags, `getopt`, a hand-written `argv` loop, or a second parser.
GoogleTest/Google Benchmark's own test-runner switches are outside the installed CLI contract.

Construct the CLI in testable registration functions. Parse once, normalize CLI11 failures into the
exit-code contract below, construct typed configuration values, and dispatch through injected command
interfaces. Callbacks must not load a model, initialize a device, start a network listener, download
content, or run a benchmark. CLI11 and `argc`/`argv` types must not appear in public model, server,
runtime, benchmark, artifact, or inference headers.

### 7.5 Shared configuration and option semantics

Define reusable typed configuration structures for shared model, runtime, generation, client,
benchmark, logging, and diagnostic settings. Existing configuration types should be extended rather
than shadowed by CLI-only copies. Registration helpers bind the same structures into each applicable
subcommand so spelling, defaults, enum values, validation, and help text cannot drift.

The shared vocabulary includes:

| Option | Type and baseline semantics |
|---|---|
| `--model` | required model ID or local path for model-owning commands |
| `--tokenizer` | optional tokenizer ID/path; defaults to the model's tokenizer |
| `--device` | validated enum or device selector such as `auto`, `cpu`, `cuda`, `cuda:N`, or a qualified future backend |
| `--dtype` | case-normalized supported enum such as `auto`, `float32`, `float16`, or `bfloat16`; unsupported build/backend combinations fail validation |
| `--tensor-parallel-size` | positive integer; must fit available/selected devices |
| `--max-model-len` | positive token count bounded by the model and runtime |
| `--max-batch-size` | positive bounded request count |
| `--temperature` | finite non-negative value; zero selects deterministic greedy behavior |
| `--top-p` | finite value in `(0, 1]` |
| `--top-k` | non-negative integer; zero means disabled |
| `--seed` | unsigned 64-bit deterministic seed, shared globally and by execution/benchmark commands |

Keep names and meanings compatible with vLLM and SGLang where that does not violate InferX's typed
configuration or safety contracts. A familiar spelling must not be retained with different units or
semantics. Help text states units, defaults, bounds, and whether a value is model-, build-, or
backend-dependent.

At minimum `serve` supports:

```text
--model
--host
--port
--dtype
--device
--tensor-parallel-size
--max-model-len
--max-running-requests
--gpu-memory-utilization
--temperature
--seed
```

`--model` is required. Ports are in `[1, 65535]`; request and parallel counts are positive;
`--gpu-memory-utilization` is finite and in `(0, 1]`; and host/bind policy is validated before
dispatch. The parser expresses structural exclusions such as `--prompt` versus `--prompt-file` and
interactive versus one-shot chat. Cross-field and hardware/model-dependent checks live in shared
configuration validators called before the implementation facade, not duplicated in handlers.

Top-level options are registered consistently for every command; logging applies to all commands and
the seed is propagated to commands that execute deterministic workloads:

```text
--log-level trace|debug|info|warning|error
--log-file <path>
--seed <unsigned-64-bit-integer>
```

They may appear in the documented top-level position and are inherited by subcommands through one
configuration object. A repeated option with conflicting values is rejected. Logs go to stderr or
the selected file; command data intended for piping remains on stdout. Secrets, prompts, tokens, and
credentials are never printed by default.

### 7.6 Benchmark contract

All benchmark modes accept `--output-format text|json`; the default is `text`. JSON output is a
versioned object written to stdout or an explicit output path and is not mixed with logs. It includes
the effective model/runtime configuration, seed, workload parameters, warm-up policy, request counts,
success/failure counts, InferX/build revision, backend/device identity, and metric units.

Where applicable, benchmark results include:

- end-to-end latency and percentile distribution;
- time to first token (TTFT);
- time per output token (TPOT), with the exact denominator documented;
- requests per second;
- prompt, generated, and total tokens per second; and
- failures, timeouts, and incomplete requests so throughput cannot hide errors.

Workload generation and measurement use reusable APIs and deterministic seeds. The text and JSON
renderers consume the same result object. Adding a benchmark mode extends `inferx bench`; it never adds
an installed executable.

### 7.7 Help, discovery, version, and environment output

These commands form a tested discovery contract:

```text
inferx --help
inferx serve --help
inferx bench --help
inferx bench latency --help
inferx --version
inferx version
inferx env
```

Top-level help lists every available subcommand with a one-line purpose and the global options.
Subcommand help lists required inputs, defaults, enum choices, constraints, and examples. Help and
version succeed without model, network, CUDA/ROCm runtime, or GPU initialization. With no subcommand,
`inferx` prints concise help and returns the documented usage-error code; `inferx --help` returns zero.

`inferx --version` is a stable concise alias for `inferx version`. `inferx version` reports the InferX
version, Git revision (or an explicit reproducible `unknown` value), build type, compiler ID/version,
C++ standard, and compiled backend features. `inferx env` reports those compiled features separately
from detected runtime state, including CUDA/ROCm runtime and driver versions, GPU/device identity and
memory, and relevant visibility settings. Missing optional runtimes/devices are valid diagnostic
results, not crashes. A later `--output-format json` must preserve stable field names and schema
versioning.

### 7.8 Exit codes and errors

The process returns stable, meaningful non-negative exit codes:

| Code | Meaning |
|---:|---|
| `0` | success, including help and version |
| `2` | CLI syntax, unknown command/option, missing required argument, or invalid configuration |
| `3` | model/tokenizer resolution, download, validation, or loading failure |
| `4` | runtime, backend, device, inference, client, or server failure |
| `5` | benchmark setup, execution, validation, or output failure |
| `6` | requested feature is not compiled or supported in this build/environment |

CLI11 parse errors use one consistent `error:` prefix, identify the offending command/option, and
show the nearest relevant usage hint. Runtime errors do not masquerade as parse errors. Handlers map
typed library failures at the process boundary; libraries never call `std::exit`.

### 7.9 CLI tests

Test parser construction and configuration mapping in-process, dispatch through fakes, and add a
small process-level integration suite. The suite covers:

- top-level help and every subcommand/nested-subcommand help;
- `--version`, `version`, and `env` without model or accelerator initialization;
- invalid commands and options, including consistent suggestions/error text;
- every missing required argument case;
- invalid range, path, enum, mutually exclusive, dependent, and cross-field values;
- defaults and explicit values for every shared configuration field;
- identical names and semantics for shared options across `serve`, `run`, and relevant `bench` modes;
- top-level logging and seed propagation;
- dispatch to exactly the correct implementation with the expected typed configuration;
- text and JSON benchmark output separation from logs;
- success, parse/configuration, model-loading, runtime, unavailable-feature, and benchmark exit codes;
- proof that help/parse failures have no model, device, network, or filesystem side effects; and
- install-tree enumeration proving that `inferx` is the only installed project executable.

Golden help tests normalize only unstable wrapping/absolute paths; option names, defaults, required
markers, enum values, and subcommand descriptions remain asserted. CLI tests have bounded timeouts and
work from any current working directory.

### 7.10 C++23 sentinel

`tests/compile/cxx23_smoke.cc` must use selected library/language features rather than only inspect a
compiler macro. At minimum cover:

- `std::expected` or another accepted C++23 library facility;
- `std::span` and `std::string_view` non-owning views;
- `std::jthread`/`std::stop_token`; and
- a `constexpr`/concept constraint used by future code.

Add feature-test assertions with diagnostics. The sentinel verifies the supported standard library,
not just the front-end compiler. If the candidate GCC/Clang lane lacks a required C++23 library
facility, either raise the toolchain floor or document the facility as unavailable; do not silently
compile that lane as C++20.

### 7.11 Unit and benchmark seed

The unit test checks the compile-time and runtime version values plus installed header behavior. The
benchmark invokes the version/base call enough times to prove Google Benchmark registration and JSON
output. It does not claim a meaningful runtime performance number.

An Abseil qualification test constructs and inspects `absl::Status`/`StatusOr` entirely inside the
test target. It proves the chosen pin and CMake targets work without prematurely exposing the M1
error API from `inferx::base`.

Register CTest labels:

| Label | Contents |
|---|---|
| `unit` | Base/version unit test |
| `compile` | C++23 sentinel/header self-containment probes |
| `dependency` | Abseil and build-only dependency qualification smoke |
| `integration` | Install/consumer and CLI tests |
| `failure` | Expected configure failures |
| `gpu` | CUDA device/kernel smoke |

Every test has a bounded timeout and works from any current working directory.

## 8. Dependency management and qualification

### 8.1 Provider rules

Use git submodules as the canonical source-provider mode because the repository already uses
gitlinks. The `system` provider exists for packaging/downstream users and must enforce minimum
versions. The rules are:

- CMake never runs Git or downloads content.
- `tools/deps/bootstrap.py` is the only documented initializer.
- `core` initializes Abseil, CLI11, GoogleTest, and Google Benchmark only.
- future profiles initialize only the direct dependencies required by that feature.
- nested submodules are initialized only when a qualification report proves they are required.
- optional missing dependencies do not affect a default configure.
- an enabled feature with a missing dependency fails immediately and names its bootstrap profile.

CLI11, GoogleTest, and Google Benchmark are added as pinned gitlinks during M0. Select maintained
tagged revisions compatible with the accepted compiler floor, record them in `manifest.json`, and run
their own tests only during upgrade qualification, not every InferX build.

In submodule mode, add dependency directories as `SYSTEM` and `EXCLUDE_FROM_ALL` where supported.
Set dependency options before `add_subdirectory` and restore/contain cache effects. The baseline is:

| Dependency | Required CMake behavior |
|---|---|
| Abseil | `ABSL_PROPAGATE_CXX_STD=ON`, dependency tests off; enable its install rules only in the dedicated installed-dependency fixture |
| CLI11 | use upstream `CLI11::CLI11`; examples, tests, and docs off; private to `inferx_cli` and never exposed by an installed library |
| GoogleTest | upstream tests/install off for the ordinary build; build GoogleMock only because M0 declares it as a test dependency |
| Google Benchmark | upstream tests, GoogleTest tests, and install off; only InferX benchmark target is registered |

Never use `set(... CACHE ... FORCE)` without a helper that limits the effect to dependency setup and
documents why. A parent project embedding InferX must not have its dependency options unexpectedly
overwritten.

### 8.2 Manifest schema

`third_party/manifest.json` is checked in and validated against gitlinks. Its schema version starts at
1. Each source dependency entry includes:

```json
{
  "name": "abseil-cpp",
  "source_kind": "git-submodule",
  "path": "third_party/abseil-cpp",
  "url": "https://github.com/abseil/abseil-cpp.git",
  "revision": "2c004366e983c5be8334ac1ea3d4420e8fbcbea7",
  "license": "Apache-2.0",
  "license_file": "third_party/abseil-cpp/LICENSE",
  "owner": "base",
  "features": ["core"],
  "default_enabled": true,
  "status": "candidate",
  "qualification": "docs/dependencies/abseil-cpp.md"
}
```

Allowed status values are `candidate`, `approved`, `qualified-deferred`, `experimental`, and
`rejected`. `check_manifest.py` verifies required fields, unique name/path/URL, 40-hex revisions,
gitlink equality, `.gitmodules` equality, license file existence for initialized dependencies, and
feature/profile consistency. It exits nonzero on drift.

Do not treat the duplicated revision field as the lock: the gitlink is authoritative. The manifest
exists to make intent, license, ownership, and automation explicit, and the drift checker prevents
the two from diverging.

### 8.3 Per-dependency qualification report

Create `docs/dependencies/<name>.md` for all existing and newly added dependencies. Each report must
answer:

1. Which exact InferX contract would use it?
2. Is that use required now, deferred, experimental, or rejected?
3. What source and transitive dependencies are pulled in?
4. Does it configure/compile with accepted compilers, standard library, CUDA pin, and C++23 host mode?
5. Does it throw exceptions, require RTTI, spawn threads, use global state, JIT, Python, or PyTorch?
6. What is its public/native C++ API stability and namespace behavior?
7. What license/notice obligations and known security issues apply?
8. What binary/build/startup cost does a minimal adapter add?
9. How will upgrades be tested and rolled back?
10. What is the final disposition and approving ADR/PR?

Required M0-specific outcomes:

- **Abseil:** approve for base error/logging utilities if CPU build/install integration passes; do
  not use Abseil flags in the product CLI.
- **CLI11:** approve as the sole product command-line parser after help/error/validator behavior and
  GCC/Clang integration pass; keep it private to `inferx_cli`.
- **Beast:** mark deferred; document required Boost.Asio/System closure before M9.
- **CUTLASS:** mark deferred; record header-only/toolkit/SM compatibility for the selected pin.
- **FlashInfer:** mark deferred/candidate; do not approve production use without M4's native C++ spike.
- **Folly:** reject/remove unless a concrete C++23/Asio gap and dependency-cost comparison is accepted.
- **HPC-Ops:** mark experimental and disabled; record hardware/Python/toolkit constraints.
- **Tokenizer:** mark deferred candidate; M3 owns correctness/thread-safety approval.
- **GoogleTest/Google Benchmark:** approve as build/test-only dependencies.

Removing a rejected submodule means updating `.gitmodules`, the gitlink, manifest, and documentation
in the same commit. It does not mean deleting files from an initialized user checkout with an
unscoped filesystem command.

### 8.4 License and SBOM procedure

`third_party/README.md` lists source dependencies and points to generated evidence. CI validates that
each initialized approved/candidate dependency exposes the manifest's license file. Do not copy
license text into a second location unless required for binary redistribution.

`tools/deps/generate_sbom.sh` invokes a pinned Syft release/container to produce SPDX JSON from the
installed prefix and source dependency manifest. The script:

- writes only below the selected build/artifact directory;
- records the Syft version/digest;
- includes system CUDA/NCCL components when present;
- never uploads the SBOM; and
- validates JSON before returning success.

M0 CI runs an SBOM smoke on the CPU install and uploads it as a workflow artifact. Release signing and
vulnerability policy are later release work, but the generation procedure must already be
reproducible.

## 9. Formatting, analysis, and include hygiene

### 9.1 Formatting

Update `.clang-format` to `Standard: c++23` while preserving Google base style and the 100-column
limit. `tools/check_format.sh` obtains its file list from `git ls-files` limited to InferX-owned
`.h`, `.cc`, `.cu`, and `.cuh` files. It excludes `third_party` and generated/build directories by
construction, not a broad `find` filter.

Provide separate targets:

- `format`: mutates tracked InferX source files;
- `format-check`: runs `clang-format --dry-run --Werror` and never mutates; and
- CI invokes only `format-check`.

Pin/record the clang-format major version because formatting output can change between releases.

### 9.2 clang-tidy

Retain the current checks as the starting set, update header matching for absolute build paths if
needed, and run only over InferX compile commands. `run_clang_tidy.sh`:

- requires an existing `analysis` configure directory;
- selects project files from `compile_commands.json`;
- excludes dependency/generated files;
- uses the qualified clang-tidy binary/version; and
- emits fixes only in an explicitly requested developer mode, never in CI.

Warnings remain errors. A suppression must be local, name the exact check, state why it is a false
positive or required boundary, and have a tracking issue when temporary.

### 9.3 IWYU and public headers

The `analysis` preset runs IWYU on InferX-owned targets. In addition, `check_headers.py` generates one
temporary translation unit per installed public header containing only that include and compiles it
with the supported compiler. This catches transitive-include reliance independently of IWYU.

Generated probes live under `out/`, are never added to Git, and use the same target compile features
and public include paths as a consumer. `version.h` must pass this check in M0.

### 9.4 Aggregate targets

Provide convenience targets without hiding individual results:

```text
check-fast      format-check + unit/compile tests
check-analysis  clang-tidy + IWYU + header self-containment
check           check-fast + check-analysis + integration/failure tests
```

Sanitizer and CUDA presets remain separate invocations; an aggregate target must not recursively
configure other build trees.

## 10. CUDA smoke design

CUDA is optional in the default CPU project but strict when requested.

### 10.1 Configure behavior

When `INFERX_ENABLE_CUDA=ON`:

1. use `check_language(CUDA)` and fail with the supported-toolkit/bootstrap guidance if absent;
2. call `enable_language(CUDA)` and `find_package(CUDAToolkit REQUIRED)`;
3. validate host compiler/toolkit compatibility and explicit `CMAKE_CUDA_ARCHITECTURES`;
4. set a required CUDA language standard accepted by ADR 0005; and
5. add only `platform/cuda/smoke` in M0.

Do not let optional CUDA detection alter CPU-only exported target interfaces. No CUDA header appears
under `include/inferx/base`.

### 10.2 Runtime behavior

The smoke test:

- queries device count and properties;
- selects device 0 only within the test process;
- allocates a tiny device buffer;
- launches a kernel that writes a known pattern;
- copies it back and validates every element;
- checks every CUDA return and the post-launch error; and
- releases all resources on every exit path.

The smoke code is intentionally not the M2 RAII/runtime design. Keep its C++ interface private to the
test subtree so it can be replaced wholesale.

On a developer machine with a toolkit but no GPU, the test may use CTest skip code 77 and prints the
reason. The owned GPU CI job treats “no visible device,” unsupported compute capability, or a skipped
test as job failure. This distinction prevents false-green GPU coverage.

## 11. CI implementation

The repository is hosted on GitHub, so M0 uses GitHub Actions. Pin third-party actions to immutable
commit SHAs with a comment containing the human-readable release. Set minimal workflow permissions and
cancel superseded pull-request runs.

### 11.1 CPU workflow

`.github/workflows/ci-cpu.yml` runs on pull requests and pushes to `main` with these jobs:

| Job | Preset/action | Required evidence |
|---|---|---|
| `policy` | manifest, format, ADR/dependency links, no generated/tracked build outputs | Individual logs plus manifest result |
| `gcc` | `dev-gcc` | configure, build, all non-analysis CPU tests |
| `clang` | `dev-clang` | configure, build, all CPU tests |
| `asan-ubsan` | matching preset | zero sanitizer findings/leaks |
| `tsan` | matching preset | zero race findings |
| `analysis` | analysis preset | zero tidy/IWYU/header failures |
| `install-consumer` | `cpu-release` plus temporary install | independent `find_package` consumer succeeds |
| `build-metrics` | `cpu-release` | configure/clean/no-op times and sizes uploaded |
| `sbom` | installed CPU prefix | valid SPDX JSON artifact |

Checkout does not use `submodules: recursive`. It checks out source, then runs the core bootstrap
profile so optional dependencies cannot make CPU CI slow or fragile. Cache dependencies/build output
only after one uncached lane proves clean reproducibility. Cache keys include OS image, compiler,
CMake, preset, and all core gitlink revisions.

### 11.2 GPU workflow

`.github/workflows/ci-gpu.yml` uses an explicitly managed/self-hosted GPU runner or an approved GPU
runner service. It runs on manual dispatch and protected/main changes initially, then becomes a
required pull-request check before M2 merges.

The job records:

- GPU name, UUID-redacted topology summary, compute capability, and memory;
- driver, CUDA compiler/runtime, host compiler, CMake, and Ninja versions;
- configured architecture list;
- configure/build output and the non-skipped `gpu` CTest label; and
- `compute-sanitizer` smoke if supported by the qualified toolkit.

The runner is cleaned through runner-level isolation/container lifecycle, not repository scripts that
delete broad directories. Do not expose host `/dev` devices to untrusted pull-request code without an
approved security model.

### 11.3 Workflow hygiene

- Use concurrency groups to cancel older runs on the same PR.
- Set job and test timeouts.
- Upload only logs, benchmark/build metrics, test XML, and SBOM; never upload the whole build tree.
- Keep secrets unavailable to pull-request jobs and unnecessary to ordinary builds.
- A flaky retry does not turn red into green. Record and fix the failure; only infrastructure-owned
  setup steps may have a bounded documented retry.

## 12. Developer containers and local setup

Provide two pinned Dockerfiles or equivalent devcontainer layers:

- `cpu-dev.Dockerfile`: accepted Ubuntu/compiler/CMake/Ninja/Python/clang tools/IWYU/Syft versions;

## 13. Tests and evidence in detail

### 13.1 Unit

- Version values and string are internally consistent.
- Public header can be included alone and from multiple translation units.
- CLI11 parser registration accepts only documented options, constructs the expected typed
  configurations, dispatches through fakes, and returns the stable exit codes in section 7.8.
- Dependency manifest schema/drift checker has fixtures for valid and invalid entries.

### 13.2 Integration

- Fresh checkout with only the core submodule profile configures/builds/tests offline.
- Install/consumer test locates only the installed package.
- Both GCC and Clang lanes produce and run the CLI/tests.
- The build and install trees expose `inferx` as the only project-owned user-facing executable.
- Top-level and nested help work without initializing a model, accelerator, or network service.
- CPU-only configuration does not load/require CUDA or optional dependency paths.
- CUDA configuration builds and runs the device pattern check on a GPU runner.

### 13.3 Correctness

- C++23 feature sentinel compiles/runs on every advertised host lane.
- `inferx --version` and `inferx version` equal the CMake project version and agree on build metadata.
- Manifest revisions match the exact gitlinks and `.gitmodules` URLs.
- Installed headers/library are the ones used by the consumer test, verified through verbose build
  output or a source-tree-poison fixture.

### 13.4 Stress

`tools/ci/repeat_build.py` creates distinct, validated paths below `out/stress/` and repeats at least
three times:

```text
fresh configure -> parallel build -> test -> install -> consumer test
```

Run with different parallelism values (1 and the CI allocation), and once with tests discovered in a
different order. It must not depend on a previous generated file or write to the source tree. The
script never accepts `/`, a home directory, or the repository root as an output path.

### 13.5 Failure

Use small CTest-driven fixture projects to verify these configure failures and message fragments:

| Scenario | Required result |
|---|---|
| Missing core submodule | Fail and print the exact core bootstrap command |
| Missing CLI11 submodule | Fail and name `third_party/CLI11` plus the exact core bootstrap command |
| Unknown dependency provider | Fail and list valid values |
| Unsupported/too-old CMake or compiler | Fail before compiling project sources with minimum version |
| C++23 library facility missing | Compile test fails with named missing facility/toolchain guidance |
| ASan and TSan both enabled | Configure failure identifying incompatible options |
| CUDA enabled, toolkit/compiler missing | Configure failure; never silently disable CUDA |
| CUDA architecture unset/unsupported | Configure failure with accepted list |
| Analysis enabled, tool absent | Configure failure naming required tool/version |
| Consumer without required installed dependency | `find_package` failure naming that dependency |
| Manifest/gitlink drift | Policy check failure naming path and both revisions |

Expected-failure tests pass only when the command fails for the expected reason; an unrelated failure
does not satisfy the test.

### 13.6 Performance/build metrics

`measure_build.py` captures, in JSON:

- machine/OS/container and compiler/CMake/Ninja identifiers;
- core dependency revisions;
- configure wall/user/system time and peak RSS;
- clean parallel build time and peak RSS;
- no-op build time;
- unit-test time;
- install and consumer-build time;
- `inferx_base`, `inferx_cli`, and `inferx` file sizes; and
- CUDA smoke compile time when applicable.

M0 establishes the baseline and has no absolute time gate. A missing/invalid metrics artifact fails
the metrics job. M1 and later can add regression thresholds after representative CI variance is
known. Never compare numbers from different runner/toolchain manifests as if they were equivalent.

The install/consumer orchestration may be a CTest fixture or script, but its logs must display the
temporary install prefix and independent consumer configure command. All generated output stays below
`out/` or a validated temporary directory.

## 16. Definition of done

M0 is complete only when all boxes are true.

### Build and package

- [ ] Fresh CPU checkout plus core bootstrap configures/builds/tests offline with GCC and Clang.
- [ ] All InferX host targets require C++23 with extensions off.
- [ ] Public headers compile independently.
- [ ] `inferx::base` installs and an independent consumer finds/links/runs it.
- [ ] The build and install trees contain exactly one user-facing executable, named `inferx`; all
      legacy `apps/` executable targets, install rules, wrappers, and aliases are removed.
- [ ] Missing required dependencies and requested CUDA fail with actionable messages.
- [ ] No configure/build/test writes an untracked/generated file outside `out/` or its temp directory.

### Quality

- [ ] Format check passes with the pinned clang-format version and `.clang-format` says C++23.
- [ ] clang-tidy, IWYU, warnings-as-errors, ASan, UBSan, and TSan pass for InferX-owned CPU code.
- [ ] Tests are labeled, bounded by timeouts, and produce useful failure output.
- [ ] Three repeated fresh builds pass with no hidden generated dependency.
- [ ] Build metrics JSON is valid and retained as CI evidence.

### Unified CLI

- [ ] CLI11 is the only product command-line parser and remains private to `inferx_cli`.
- [ ] `inferx --help` and help for every top-level and nested command are complete and return zero.
- [ ] `serve`, `bench`, `run`, `chat`, `complete`, `inspect`, `download`, `version`, and
      `env` follow `inferx <subcommand> [options]`; benchmark modes are nested below `bench`.
- [ ] `serve`, `run`, and applicable benchmark modes use the same typed model/runtime/generation
      configuration structures and option semantics.
- [ ] Top-level log level, log file, and deterministic seed options propagate consistently.
- [ ] CLI handlers only validate, construct configuration, and dispatch to reusable APIs; no server,
      benchmark, model-loading, download, or inference implementation remains under `apps/`.
- [ ] Help, invalid-command, missing-argument, invalid-value, mutually-exclusive-option,
      configuration-mapping, dispatch, output-format, and exit-code tests pass.
- [ ] `inferx version` reports version/revision/build/compiler/backend features, and `inferx env`
      distinguishes compiled support from detected drivers/devices.

### CUDA

- [ ] CPU presets do not detect, include, link, or require CUDA.
- [ ] CUDA preset uses the accepted toolkit/host compiler and explicit architecture list.
- [ ] GPU smoke runs rather than skips on the owned runner and validates device-written data.
- [ ] Compute-sanitizer smoke is clean or an ADR documents why the selected runner/toolkit cannot run
      it and supplies an equivalent required check.

### Dependencies and governance

- [ ] `.gitmodules`, gitlinks, `manifest.json`, bootstrap profiles, and reports agree.
- [ ] Every dependency has exact source/revision, license, owner, feature, status, transitive closure,
      qualification evidence, and upgrade/rollback procedure.

- [ ] CLI11 is pinned, manifest-qualified, in the core bootstrap profile, and private to the CLI.
- [ ] GoogleTest and Google Benchmark are pinned and build/test-only.
- [ ] License validation and CPU SPDX SBOM smoke pass.
- [ ] ADRs 0001 through 0007 are accepted and cross-linked from implementation/docs.

### CI and documentation

- [ ] CPU policy/GCC/Clang/sanitizer/analysis/install jobs pass on a fresh checkout.
- [ ] GPU workflow records non-skipped device/toolchain evidence.
- [ ] Actions and container bases are immutable-pinned; workflows have minimal permissions/timeouts.
- [ ] `docs/development.md` commands match the actual presets and CI.
- [ ] `docs/supported-platforms.md` distinguishes required, supported, experimental, and unsupported.

## 17. Handoff to M1

The M0 handoff is a tagged or otherwise immutable green commit with these artifacts attached or
linked:

- CPU CI test/analysis results;
- GPU smoke environment and result;
- M0 build metrics JSON;
- dependency manifest and qualification reports;
- SPDX JSON smoke artifact;
- accepted ADRs and supported-platform matrix; and
- known limitations with owners/milestones.

M1 may add Status, IDs, and configuration to `inferx::base` or new libraries, but it may not weaken
M0's offline build, install/consumer test, target-scoped warnings, or dependency manifest gates. M2 owns replacement of the private CUDA smoke code with production RAII/runtime
abstractions. Every later milestone preserves section 7's single-binary and thin-dispatch contracts.
