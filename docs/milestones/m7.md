# M7 implementation specification: asynchronous engine and continuous batching

- Status: proposed implementation contract
- Roadmap milestone: M7 in [`docs/plan.md`](../plan.md)
- Prerequisite: completed [M6](m6.md), including M1-M5 transitively
- Immediate consumer: M8 chunked prefill, fairness, and preemption
- Later consumers: M9 HTTP serving, M10 operations, M12 graphs, and M14 worker processes

This document turns M7 into an executable engineering plan. It defines the embeddable asynchronous
API, bounded request/response ownership, coordinator and device-worker loops, tokenizer integration,
phase-homogeneous FCFS continuous batching, paged-KV transactions, execution tickets, event ordering,
cancellation/deadlines, graceful shutdown, deterministic plan replay, tests, performance gates, and
the exact handoff to M8.

M7 introduces concurrency and batching, not new model math or scheduling sophistication.

## 1. Outcome

At the end of M7, a supported InferX process can:

1. accept concurrent token, text, or supported chat requests through an embeddable `AsyncEngine`;
2. return a move-only `RequestHandle` whose bounded stream yields ordered token/text deltas followed
   by exactly one terminal event;
3. apply explicit backpressure when ingress, tokenizer, active-request, response-storage, plan,
   workspace, metadata, sequence, or KV quota capacity is unavailable;
4. keep all request/FSM/scheduler/KV/accounting mutation on one `EngineCoordinator` thread;
5. run tokenization in M3's bounded exclusive-instance pool and return owned results by value;
6. submit immutable, value-only batch plans to one device-worker thread over a bounded SPSC channel;
7. execute one GPU step at a time while the coordinator continues input, cancellation, deadline,
   response, and tokenization work;
8. continuously form full-prompt prefill or one-token decode batches in deterministic FCFS order;
9. reserve M6 KV append transactions and every per-step resource before an accepted submission;
10. validate and commit per-item completions/tokens/KV only after the matching final fence;
11. cancel, time out, abandon, drain, or shut down at every request state without stale mutation,
    duplicate terminal output, leaked quota/pages/tickets, or unsafe GPU resource reuse; and
12. reproduce scheduler decisions from a versioned event/plan trace and meet the roadmap throughput,
    TPOT, and coordinator-overhead gates.

```text
application threads
  -> bounded MPSC command channel
       submit / cancel / abandon / shutdown
  -> EngineCoordinator (sole mutable owner)
       registry + FSM + scheduler + quotas + M6 tables + response mailboxes
       |                         ^
       v                         |
     bounded tokenizer jobs -> tokenizer workers -> bounded result channel
       |
       v
     one immutable StepSubmission -> bounded SPSC -> DeviceWorker
                                                   M5/M6 batched CUDA execution
                                                   -> final fences/argmax
     completion batch <- bounded SPSC <------------+
       |
       v
     validate/commit KV + lifecycle + ordered response
       |
       v
  RequestHandle bounded consumer stream
```

M7 is complete only if batch composition cannot change greedy results, every admitted request has one
terminal outcome, and all bounded resources return to baseline after normal, cancellation, failure,
abandonment, and shutdown scenarios.

### Implementation status (2026-08-31)

This file is a documentation specification only. No M7 source implementation is authorized by this
change. M7 implementation waits for M1's real lifecycle/channel contracts and M6's value-only paged
plans; it must not replace them with a second state machine, unbounded futures, or pointer-bearing
worker messages.

## 2. Scope boundaries

### 2.1 In scope

- One process, one loaded model, one CUDA device worker, one coordinator, and configured tokenizer
  workers.
- Thread-safe embeddable submit/cancel/response-handle API; no HTTP.
- Bounded command, tokenizer-job/result, device-plan/completion, and response-storage paths.
- M1 request registry/FSM/resource lifecycle used by real requests.
- Multiple active/tokenizing/queued/ready requests and one in-flight GPU batch.
- Iteration-level FCFS over eligible requests with finite sequence/token/KV/workspace budgets.
- Phase-homogeneous full-prompt prefill batches and phase-homogeneous one-token decode batches.
- Flattened ragged batch execution and one final logits row/greedy token per sequence.
- M6 quota, block table, append transaction, table epoch, mirror, and paged attention integration.
- Ordered response streaming, dropped-handle cancellation, basic explicit cancellation/deadlines.
- Cancel and drain shutdown modes with bounded deadlines and memory-safe device teardown.
- Deterministic coordinator/plan trace and CPU replay.
- Correctness versus serial M5/M6, stress/failure/sanitizer/performance evidence.

### 2.2 Explicitly out of scope

- HTTP/SSE/OpenAI protocol, authentication, tenant policy, rate limiting, or network backpressure.
- Chunked prefill, mixed prefill/decode batches, decode priority, aging, preemption, or deadline-aware
  scheduling optimization. M8 owns these.
- Prefix caching, shared pages, speculative decoding, CUDA graphs, GPU sampling, quantization, or
  distributed workers.
- More than one GPU step in flight, compute/collective overlap, multiple models, hot reload, or
  cross-device routing.
- Blocking the coordinator on tokenization, GPU completion, application response consumption, file
  I/O, logging/export, or device synchronization.
- Detaching threads/resources at shutdown or treating process exit as cleanup.
- Unbounded per-request queues, `std::async`, one thread per request, callback invocation on the
  coordinator thread, or caller-owned pointers in engine state.

## 6. Immutable configuration and capacity proof

M7 adds an `engine` section:

| Field | Default/range | Rule |
|---|---|---|
| `engine.max_active_requests` | 1024 | registry/mailbox/table upper bound |
| `engine.command_queue_capacity` | 2048 | bounded MPSC submit/cancel/abandon/shutdown commands |
| `engine.max_sequences_per_step` | 128 | <= M4/M6/operator/metadata/activation capability |
| `engine.max_scheduled_tokens_per_step` | 2048 | full-prefill aggregate or decode sequence count |
| `engine.max_prefill_sequences_per_step` | 16 | limits ragged prompt batch and activation high-water |
| `engine.max_decode_sequences_per_step` | 128 | <= general sequence limit |
| `engine.max_inflight_steps` | exactly 1 | M7 invariant; later milestone may expand |
| `engine.response_event_capacity` | derived | at least sum of admitted request output limits + terminals |
| `engine.response_byte_capacity` | explicit bounded budget | reserves incremental decoded bytes before admission |
| `engine.device_plan_channel_capacity` | exactly 1 | one worker/one step; no hidden queueing |
| `engine.device_completion_capacity` | exactly 1 | completion batch cannot be dropped |
| `engine.poll_backoff_us` | 10..1000, default 50 | device-worker fence polling, no busy spin/device sync |
| `engine.shutdown_timeout_ms` | positive, default 30000 | policy deadline; memory safety still governs teardown |

M3 tokenizer queue/worker limits and M6 KV/page limits remain their owning configuration fields.

Startup proves, with checked arithmetic:

- registry/request/context/table/mailbox pool slots cover `max_active_requests`;
- response record/byte budgets can reserve each accepted request's `max_output_tokens + 1` events
  and tokenizer-derived maximum decoded bytes;
- plan/completion scratch covers `max_sequences_per_step` atomically;
- activation/logits/workspace/metadata/event capacities cover the maximum phase batch;
- full prompt limits fit per-step tokens and prefill sequence caps;
- M6 quota/table capacity and low-water reserve are compatible; and
- every channel capacity and shutdown ownership graph is nonzero/acyclic.

Impossible combinations fail before threads start. Configuration does not silently reduce limits.

## 7. Public asynchronous API and response ownership

### 7.1 Submission

`AsyncEngine` is application-owned, thread-safe at its public boundary, and move-disabled. `Start()`
completes model readiness and threads before accepting work. `Submit(request, deadline, stop)` uses a
fixed submission-receipt pool:

1. perform cheap immutable size/enum/deadline checks;
2. acquire a receipt slot without moving the request on failure;
3. push a move-only submit command to the bounded MPSC channel;
4. wait only for coordinator admission/rejection, not tokenization/model execution;
5. on acceptance return a move-only `RequestHandle` bound to a mailbox generation; and
6. on timeout/stop, post withdrawal if the coordinator already observed the command, avoiding an
   orphan admitted request.

Only the coordinator checks duplicate request ID, registry/response capacity, model capability, and
creates context/mailbox. Thus public concurrency does not add a second registry lock. Queue full is
`ResourceExhausted`; stopped/closed is `Unavailable`/shutdown status.

### 7.2 Request handle

The handle contains strong request/subscription/mailbox-generation values and a shared subscription
domain, never a `RequestContext*`. It supports blocking/try-next with deadline/stop and idempotent
`Cancel()`. One handle has one consumer; concurrent `Next()` calls are invalid.

Destroying an undrained handle posts a bounded `Abandon` command. Abandon detaches external delivery,
requests cancellation if nonterminal, and retains an internal terminal audit record. It never directly
erases context, quota, KV, ticket, or mailbox from the application thread.

Engine shutdown wakes all handle waits. After queued events drain, `Next` returns closed. A moved-from
or stale-generation handle fails without touching a newer request/mailbox.

### 7.3 Response event schema

Version 2 extends M1 token output without changing identity:

```text
OutputDelta:
  request, TokenId, zero-based output position, owned stable text-delta bytes
TerminalResponse:
  request, finish reason/status, prompt/output counts, owned final text-flush bytes,
  terminal monotonic time
```

Each token appears exactly once and output positions are contiguous from zero. EOS token delta
precedes EOS terminal. Any bytes returned by `IncrementalDecoder::Finish` are stored in the terminal
record, so no unreserved text-only event is needed. Exactly one terminal is last. No event follows it.

### 7.4 Mailbox and slow consumers

At coordinator admission, reserve from fixed global pools:

- exactly `max_output_tokens + 1` response record slots; and
- bounded text bytes derived from tokenizer maximum token bytes/configured per-request cap.

The per-request SPSC mailbox therefore cannot become full for a valid request even if the consumer
does not read during generation. Coordinator publication is no-fail after `ResponseSink::Prepare`.
GPU progress never blocks on a slow consumer.

After terminal, GPU/KV/request execution resources release immediately; mailbox reservation remains
until the handle drains or abandons. Slow consumers consume bounded response capacity and can cause
new submissions to receive backpressure, never unbounded memory. M9 may add network-specific policy;
M7 does not discard accepted response events.

## 8. Thread topology, channels, and wakeups

| Channel | Producers -> consumer | Payload/ownership |
|---|---|---|
| command | application/handle threads -> coordinator | move-only submit or value cancel/abandon/shutdown |
| tokenizer jobs | coordinator -> tokenizer workers | owned bounded prompt/job and request epoch |
| tokenizer results | tokenizer workers -> coordinator | owned token vector/status and echoed identity |
| device control | coordinator -> device worker | move-only submission, ticket acknowledgement, or stop command |
| completions | device worker -> coordinator | complete atomic ticket batch with echoed identities/tokens/status |
| response mailbox | coordinator -> one request consumer | pre-reserved response record/text slices |

All use M1 bounded-channel/ring semantics and explicit Close. The coordinator never performs a
blocking push. Tokenizer/device result capacity is sized so an accepted job/ticket always has one
result slot reserved; workers cannot deadlock trying to report completion.

The coordinator waits on a doorbell/condition plus the earliest monotonic deadline when no immediate
work exists. Producers publish then notify. Predicates/queue state, not notification counts, decide
work. Device worker polls its one final fence with bounded backoff while also observing stop/poison;
it never calls device/stream synchronize.

Thread affinity is checked in debug: coordinator mutations on its thread, tokenizer instance on its
own worker, CUDA context/handles on device worker. No CUDA host callback enters engine code.

## 9. Coordinator event loop and total order

### 9.1 Coordinator-owned state

The coordinator solely owns request registry/FSM, arrival order, scheduler snapshots/scratch,
resource accountant, M6 quota/allocator/tables/transactions/pins, response reservations, plan pool,
in-flight ticket registry, deadline index, shutdown state, and trace ordinal.

It never owns CUDA buffers/handles and never waits for GPU/tokenizer/application I/O.

### 9.2 Turn order

One turn drains bounded batches in this order:

1. shutdown, abandon, explicit cancel, and expired deadline events;
2. device completion/failure batches;
3. tokenizer results;
4. accepted submit commands;
5. response/mailbox reclamation acknowledgements;
6. invariant checks and at most one planning/submission attempt if device idle.

Within a class, use coordinator-observed channel ordinal, with request `ArrivalKey` as documented
tie-break where applicable. Cancel/deadline observed in the same turn as completion wins: completion
drains ownership but commits no token/KV. This matches M1 replay semantics.

Drain counts per turn are configured/fixed scratch bounds so a producer flood cannot prevent later
classes forever. If a queue remains nonempty, immediately schedule another turn before sleeping.

### 9.3 Main loop

```text
start with validated pools/model/threads
while not Closed:
  wait until command/result/completion/deadline/planning work
  drain priority classes
  validate/apply completions and acknowledge tickets
  build immutable scheduling/resource/KV snapshot
  if worker idle, build/reserve/submit at most one batch
  publish prepared responses
  validate invariants and record bounded trace
  advance shutdown phase when conditions are met
```

Observer/log/export failure never rolls back committed state. It disables that sink, records first
error, and enters controlled cleanup if required.

## 10. Input/tokenizer integration

Accepted token-ID input is validated/copied and transitions directly to Queued. Text/chat transitions
to Tokenizing after a job slot and exact queued-byte reservation are secured. Tokenizer workers own
exclusive backend instances, copy all backend-owned bytes, and emit one success/failure result.

Coordinator accepts a tokenizer result only when request ID/sequence/request epoch/state/job ID match.
Stale results are acknowledged/discarded without mutating a reused request. Success revalidates prompt,
context, response-byte bound, and model vocabulary before Queued. Failure creates one terminal.

Cancellation during tokenization marks cancellation and retains the job/result capacity until the
worker result drains; it cannot forcibly destroy a thread-affine tokenizer instance. New jobs stop
during shutdown; accepted jobs either drain or their results are safely discarded by identity.

## 11. FCFS admission and continuous batch planning

### 11.1 Admission

Eligible Queued requests are scanned in M1 `ArrivalKey`. For each, calculate sequence slot, M6
promised-block quota, response reservation (already held), and conservative execution capability.

- Never fits: fail request, continue scan.
- Temporarily unavailable or M6 low water: stop scan (head-of-line blocking).
- Reservable: prepare M1 reservation + M6 quota/table acquisition, commit both in one no-fail turn,
  enter PrefillReady, continue while capacity permits.

M7 does not preempt or bypass the head request. For a finite workload and successful finite GPU
steps, resource release eventually makes the head admissible or proves it never fits; this is its
no-starvation argument.

### 11.2 Phase selection and fill

When worker is idle, find the earliest `PrefillReady` or `DecodeReady` request. Its work kind selects
the phase. Scan later ready requests in FCFS order and add only the same phase while all exact budgets
fit. A nonmatching phase is skipped for this batch but retains order within its own phase; a matching
request that exceeds remaining budget stops same-phase fill rather than allowing later bypass.

Prefill schedules the complete prompt and must fit per-request/per-step limits. Decode schedules
exactly one token/sequence. No mixed-phase batch or chunking is allowed.

Budget checks include total flattened tokens, phase sequence cap, activation/logits bucket, M4
prepared key, workspace, metadata/event slots, M6 append/page/quota/table state, plan/completion scratch,
and deadline/context. All arithmetic is checked.

### 11.3 Batched forward representation

Phase-homogeneous `ForwardBatch` contains flattened owned token/position metadata, query/new-KV
indptr, ordered sequence entries, and one M6 physical plan per sequence. Dense GEMMs operate over
total tokens. Paged attention uses ragged metadata. Final-row gather produces `[B,H]`, logits `[B,V]`,
and one host greedy token per sequence in plan order.

Prefill selects each sequence's final prompt row; decode selects its sole row. Padding never becomes
a logical token or KV entry. Batch item ordinal is stable FCFS order and echoed by completion.

### 11.4 Transactional submission

For selected items:

1. acquire/reset a fixed plan buffer and batch execution slot;
2. prepare every M1 Submit transition;
3. begin/pin every M6 append transaction and create physical plans;
4. validate complete plan, prepared M4 key, scratch/output capacity, and identities;
5. assign step/ticket IDs and construct a move-only `DeviceSubmission`;
6. `TryPush` to the capacity-one worker channel—the acceptance boundary;
7. no-fail mark M6 blocks Writing and commit every M1 Submit transition; and
8. register the one in-flight ticket/resource ownership.

Failure before step 6 rolls back all items/resources. Queue full leaves states ready. Once pushed,
the worker must return an atomic completion batch even for later validation/launch failure; it cannot
silently reject. Partial CUDA submission follows M5 draining-ticket/poison rules.

## 12. Device worker and completion protocol

The device worker owns CUDA context/model/device KV arenas, prepared M4 kernels, activation/logits/
workspace/metadata slots, and current submission. It accepts exactly one plan while idle.

Execution:

1. validate schema/model/slot IDs and resolve M6 handles/mirrors;
2. upload flattened token/position/block metadata;
3. execute the M5 semantic model over the phase batch;
4. async D2H B FP32 logits rows under the final fence;
5. poll fence, classify health, run allocation-free host argmax per item;
6. produce exactly B ordered `ExecutionCompletion`s atomically; and
7. push the reserved completion slot, then wait for coordinator acknowledgement before reusing plan/
   metadata/workspace/activation/logits resources.

GPU/context failure after launch fails every item sharing uncertain work and poisons the replica.
Per-item post-fence errors such as NaN logits may fail that item while peers succeed. Completion
storage is preallocated and cannot partially publish. Worker never commits tokens/KV/request states.

Coordinator validates ticket/step/item_count/ordinal/request/sequence/request epoch/work/range/M6
table generation+epoch. It prepares all per-item M1 response and M6 commit/abort decisions before a
no-fail apply. Batch peers may independently finish, decode-ready, cancel, or fail. Then coordinator
acknowledges the ticket and enqueues an `AcknowledgeTicket` value into the now-empty capacity-one
device-control channel; only that acknowledgement lets worker and M6 release resources/pins. Failure
to publish this reserved acknowledgement is an engine invariant/shutdown failure, never permission
to reuse the slot. Planning resumes only after the worker reports/enters idle for that ticket.

Unknown, duplicate, partial, malformed, or stale completion is an invariant failure. It cannot be
used to free current resources.

## 13. Cancellation, deadlines, abandonment, and response ordering

Cancellation is an idempotent coordinator command. Non-in-flight requests terminalize/release in the
same prepared transaction. In-flight requests enter Cancelling; their matching completion drains
without token/KV commit, then quota/pages/reservation release after acknowledgement.

Deadlines use monotonic time and the same path/reason. Coordinator maintains a fixed-capacity deadline
heap/index and wakes at the earliest. Expiration is `now >= deadline` and wins over same-turn
completion. Removing a terminal/cancelled deadline is generation-checked.

Abandon additionally marks external subscription detached. The engine still creates its internal
terminal audit record and releases execution resources. It may reclaim/drop undelivered mailbox data
only after the handle generation is invalidated; no other handle can observe that mailbox.

Response preparation (including incremental decoder step and owned text slice) precedes lifecycle/KV
commit. Mailbox reservation guarantees no-fail publication. Per-request order is token position,
then terminal. Batch order never changes per-request output order.

## 14. Graceful shutdown

States:

```text
Running -> StopAdmission -> Draining or Cancelling -> StopTokenizers
-> StopDeviceWorker -> CloseResponses -> Joined -> Closed
```

`Shutdown(kDrain)` rejects new submit, lets admitted/tokenizing/queued/ready/in-flight requests finish
until deadline. `Shutdown(kCancel)` cancels all requests immediately in ArrivalKey order and drains
in-flight work without token commit. A second call is idempotent; cancel may escalate drain.

Order:

1. publish StopAdmission and close submit acquisition;
2. process cancel/drain policy while coordinator remains alive;
3. stop new tokenizer jobs, drain accepted jobs/results, join tokenizer workers;
4. stop planning after no runnable request, drain/ack final device ticket;
5. close worker plan channel; device worker closes CUDA model/pools/context safely and joins;
6. emit/commit all terminal responses, close mailboxes/command result waits;
7. verify registry, channels, plan/ticket, M6 quota/pages/tables/pins, workspace/metadata, and response
   ownership; and
8. join coordinator and mark Closed.

Deadline expiry marks unfinished requests shutdown/Unavailable but does not authorize freeing uncertain
GPU resources. M2/M5/M6 may retain context/model/pool and return `DeadlineExceeded`; no detached worker
or destructor synchronization hides the failure.

## 15. Deterministic trace and plan replay

Trace schema records coordinator-observed monotonic time/ordinal and value events: submit decision,
input ready/failure, cancel/deadline/abandon/shutdown, resource snapshots, eligible order, admission
decision, batch plan, M6 physical-plan digest, worker acceptance, completion, lifecycle/KV commit,
response, idle reason, and invariant result.

Production trace uses counts/digests and redacts prompt/token/text/request-sensitive values. Test
fixture mode may contain explicit token values under committed non-sensitive fixtures. Neither mode
contains pointers, CUDA handles, unordered object serialization, or wall time.

`inferx-engine-replay` uses ManualClock, recorded input-ready/completion values, fake device latency,
M1 scheduler/FSM, and M6 CPU manager. It must reproduce admission decisions, StepPlan bytes, batch
item order, idle reasons, lifecycle outcomes, and final resource summary. Real concurrent producer
arrival is not inherently deterministic; the recorded coordinator ordinal is the replay input.

Replay bounds file bytes/events/requests/tokens/depth and fails on missing/duplicate/out-of-order
identities. Failure seeds/traces are minimized while preserving the first divergence.

## 16. Error containment

M7 adds stable reasons for engine not running/stopping, command/tokenizer/device/response capacity,
submission withdrawn, stale tokenizer result, malformed completion batch, response subscription
stale/detached, and shutdown deadline.

| Failure | Scope/action |
|---|---|
| invalid/duplicate request or impossible context | reject submit/request; no GPU reservation |
| command/response/active capacity | `ResourceExhausted`; explicit caller backpressure |
| tokenizer queue full after admission | remain Received until slot or cancel; bounded, no silent drop |
| tokenization failure | one request terminal failure |
| M6 quota temporary/low water | queued head remains; no busy loop |
| plan/resource/channel unavailable | ready state retained; retry after resource event |
| worker prelaunch failure after accepted plan | completion failure for all items; drain/rollback |
| per-item post-fence failure | fail item; valid peers may commit |
| CUDA async/context failure | fail all batch items, poison worker/replica, stop planning/drain |
| stale/duplicate completion/result/handle | side-effect-free reject; invariant failure if ownership uncertain |
| response consumer/output failure | abandon/cancel request; peers/engine remain healthy |
| observer/replay sink failure | retain committed truth; disable sink and controlled cleanup |

No queue overflow drops an accepted command/result/completion/response. Capacity is reserved before
the producer action that guarantees a future message.

## 17. Tests and evidence

### 17.1 Unit/CPU (`m7-unit`)

- Submit receipt races: full/closed/timeout/stop/withdrawal and move-only request preservation.
- Handle move/stale/drop/cancel/Next races and mailbox exact ordering/capacity/reclamation.
- Capacity proof and every boundary-1/boundary/boundary+1 configuration.
- Coordinator turn priority, drain limits, deadlines, ingress ordinals, idle/wakeup behavior.
- Tokenizer job/result stale/cancel/shutdown and queued-byte accounting.
- FCFS phase selection/fill, budgets, head-of-line block, never-fits, no eligible starvation.
- Batch flatten/indptr/position/final-row/item ordinal properties.
- Multi-item reservation rollback and accepted-channel submission commit.
- Completion atomicity, peer success/failure, stale/duplicate/malformed batches.
- Shutdown transition at every request/engine state using fake tokenizer/worker/clock.
- Replay golden and randomized trace round-trip/plan-byte equality.

### 17.2 Integration (`m7-integration`, required GPU)

- Concurrent token/text/chat submissions enter tokenization/admission at different times.
- Prefill batches with different prompt lengths and decode batches with sequences finishing at
  different EOS/length iterations.
- Requests join/leave later iterations while one batch is in flight.
- M6 page boundaries/low-water/temporary blocking and subsequent admission.
- Cancellation/deadline/drop before tokenization, queued, ready, in-flight, and after terminal.
- Slow consumers never block GPU; response capacity backpressures later submission.
- Drain/cancel shutdown with tokenization and GPU work concurrently active.
- Embedded API event order and exact cleanup; no HTTP involved.

### 17.3 Correctness (`m7-correctness`)

Run each request serially through forced M5/M6 baseline, then through M7 schedules varying:

- arrival order/timing, prompt/output lengths, text/token inputs;
- prefill/decode batch sizes 1 through supported maxima;
- ragged prompt composition and physical page order;
- EOS/length and cancellation peers; and
- FP32/FP16/BF16, MHA/GQA, page sizes/backends in supported matrix.

Require per-request final-row logits within M5 thresholds and exact token positions, token IDs,
decoded bytes, finish reason, counts, and terminal status. Batch peers cannot affect output. At least
100 committed prompts and randomized batch decompositions run in required GPU CI/nightly.

### 17.4 Stress/TSan/soak (`m7-stress`)

- Thousands of concurrent submitters with unique/duplicate IDs and bounded receipt waits.
- Queue saturation, tokenizer backlog, response-budget exhaustion, plan/completion capacity.
- Cancellation/deadline/abandon storms and slow/non-consuming handles.
- At least 1,024 active requests for coordinator allocation/latency/invariant tests.
- Two-hour nightly GPU soak with varied finite arrivals/lengths and periodic snapshots.
- TSan over application producers, coordinator, tokenizer workers, fake device worker, handles, and
  shutdown; core coordinator state remains single-writer.

At end: `completed + cancelled + failed == admitted`; one terminal per admitted request; every queue,
receipt, mailbox, registry, plan/ticket, tokenizer byte/job, M6 quota/page/table/pin, workspace/event/
metadata, and non-model memory counter returns to baseline.

### 17.5 Failure/sanitizer (`m7-failure`)

- Dropped handle and output consumer failure at every response position.
- Timeout/cancel/shutdown at every M1 state and same-turn completion precedence.
- Tokenizer failure/stale result/worker stop; device acceptance/prelaunch/mid-launch/completion failure.
- Stale request epoch/table epoch/block generation/ticket/item, duplicate/partial completion.
- CUDA poison/device lost in subprocess; coordinator fails/drains all affected work exactly once.
- ASan/UBSan/TSan plus M6/M5 Compute Sanitizer on representative batches.
- API counters reject per-step allocation, default stream, pageable async copy, or device/stream sync.

### 17.6 Performance (`m7-performance`)

Record concurrency sweeps (1,2,4,... through saturation), prompt/output distributions, batch sizes,
prefill/decode tokens/s, request throughput, TTFT, TPOT/inter-token p50/p90/p95/p99, end-to-end
latency, coordinator turn/planning time, queue/tokenizer/response wait, CPU utilization, GPU
utilization, metadata H2D, kernel breakdown, memory/KV high-water, and idle reasons.

Gates on recorded reference hardware:

- suitable continuous-batch concurrency achieves >=2x output-token throughput versus serial M5;
- decode-only p99 TPOT regresses no more than 10% versus serial M5;
- coordinator loop work excluding waits has p99 <=1 ms at 1,024 active synthetic requests;
- steady coordinator planning and device submission make zero heap/CUDA allocations after warm-up;
  and
- no eligible request starves in finite-load FCFS stress.

Methods use open/closed loop labels, 30+ steady samples, exact hardware/software/model/config/fixture
identity, raw JSON, and confidence/noise reporting. M7 makes no HTTP goodput claim.

## 18. Diagnostics and metrics

by FSM state; tokenizer jobs/bytes; admission/plan idle reasons; batch phase/sequence/token histograms;

## 21. Risks and experiments

| Risk | Evidence | Decision/fallback |
|---|---|---|
| response reservation is too memory-heavy | event/text budget sweep and slow-consumer stress | reduce accepted output/active limits; never unbounded or drop accepted output |
| submit receipt blocks caller/coordinator deadlock | close/timeout/withdrawal model + TSan | coordinator never waits on caller; result slot reserved before enqueue |
| tokenizer results reorder FCFS | recorded arrival/eligibility traces | FCFS among eligible ready requests; M8 changes policy only with evidence |
| phase-homogeneous batching starves one phase | finite-load adversarial proof/soak | earliest eligible phase; M8 adds progress protection/chunking |
| plan channel acceptance precedes worker error | fault at every worker stage | every post-accept failure returns atomic completion/drain |
| batch item failure corrupts peers | per-item argmax and batch-wide CUDA fault tests | logical post-fence failures scoped; uncertain GPU fault fails whole batch |
| coordinator event flood delays deadlines/completion | bounded drain/priority latency benchmarks | tune fixed drain quotas/doorbell; preserve total-order rules |
| slow consumer holds admission forever | response/active-slot pressure tests | explicit bounded backpressure; drop/cancel handle; M9 adds network policy |
| one in-flight batch limits overlap | profiler CPU/GPU timeline | retain correctness-simple M7; increase only with later ownership ADR/evidence |
| 2x throughput gate misses due tiny model/host logits | concurrency/kernel/transfer profile | optimize batching/metadata first; report honest blocker, do not weaken correctness |
| shutdown deadline meets hung GPU | subprocess/fault drain tests | retain context/resources and return error; never detach/free uncertain work |

## 23. Definition of done

### API, ownership, and concurrency

- [ ] Submit/handle/cancel/abandon/response contracts are bounded, generation-safe, and TSan-clean.
- [ ] One coordinator is the sole mutator; worker/tokenizer/application messages are value-only.
- [ ] Every accepted future result/completion/response has capacity reserved before producer action.
- [ ] Slow/dropped consumers cannot block GPU or lose accepted responses; they cause bounded backpressure.
- [ ] Coordinator/device worker perform no steady heap/CUDA allocation or hidden synchronization.

### Scheduling and execution

- [ ] FCFS admission/phase selection/batch fill and all exact budgets match replay/goldens.
- [ ] Full-prompt prefill and one-token decode batches use M6 transactions atomically.
- [ ] Post-accept worker failure always returns drainable ownership; no silent plan rejection.
- [ ] Completion validation/commit/acknowledgement rejects every stale/duplicate/partial identity.
- [ ] Batched logits/tokens/text/reasons match serial M5/M6 for every committed fixture.

### Lifecycle and shutdown

- [ ] Cancel/deadline/abandon at every state yields exactly one terminal and safe resource release.
- [ ] Same-turn event precedence is documented, executable, and replayed identically.
- [ ] Drain/cancel shutdown closes channels and joins owners in dependency order.
- [ ] Completed + cancelled + failed equals admitted; every queue/mailbox/request/ticket/KV/resource
      counter returns to baseline after tests/soak.

### Evidence

- [ ] Thousands-submission/cancellation/slow-consumer stress and two-hour soak pass.
- [ ] ASan/UBSan/TSan and required Compute Sanitizer paths are clean without skip.
- [ ] Throughput >=2x serial M5, decode p99 TPOT <=10% regression, coordinator p99 <=1 ms at 1,024.
- [ ] Correctness/stress/failure/performance/replay evidence and minimized seeds are retained.
- [ ] ADRs 0043-0048 and async-engine/batching/replay docs match implementation.

## 24. Handoff to M8

M7 hands M8 a bounded embeddable API, one-writer coordinator, tokenizer/device workers, ordered
responses, exact lifecycle/cleanup, phase-homogeneous continuous batching, M6 transactional paged KV,
deterministic plan replay, serial/batched correctness corpus, and concurrency/performance baselines.

M8 may add page-aligned chunked prefill, decode progress reservation, mixed/alternating phase policy,
priority aging, deadline-aware decisions, low-water preemption, and recomputation. It may not bypass
M7's command/response backpressure, mutate request/KV state from workers, submit before resource
transactions prepare, free in-flight ownership, weaken completion identities, or change output order.
Every new policy must remain deterministic for a fixed snapshot/trace and token-identical to the M7
uninterrupted baseline.
